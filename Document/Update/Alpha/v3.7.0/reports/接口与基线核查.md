# v3.7.0 D0 报告：接口与基线核查

- 日期：2026-10-25
- 任务：开发计划 D0 / 阶段 R1（接口与基线冻结）
- 结论类型：**事实核查与冻结**，不是功能验收。所有 A/B 门仍未开始（`not_started`）。
- 方法：读源码与既有产物 + 只读扫描 12000 条已录 trace + 运行离线工具。**本轮未打开游戏、未采集、未训练、未修改旧控制代码。**
- 配套：[设计文档](<../设计文档.md>)、[冻结 schema](<../contract/escape-schema.json>)、[基线 fixture](<../fixtures/baseline-golden.json>)、[代码快照](<../data/manifest.json>)、[trace 审计数据](<../data/trace-audit.json>)。

> 本轮最重要的三个结论：
> 1. 旧链路的“完整（complete）”**不等于**“弹池与状态来自同一帧”：12000 条决策里弹池数量与引擎计数器只有 26.8% 完全相等，差值最大 ±416。
> 2. 旧 pilot 的“20 帧视界 / 320 颗上限 / 240 px 近邻”会在真实布局上退化成“什么都没看见”：`far-static-wall` fixture 输入 24 颗，实际使用 0 颗。
> 3. 以上都不是靠改阈值能修的，必须在适配层把“同帧、可审计、显式未知”做成契约。

## 3. 既有数据审计（12000 条决策）

对象：v3.6.1 T2 两个臂各 2 局（`t2-power` / `t2-enemy` 的 `collect-ep39/40.jsonl`），只读扫描。完整数据：[data/trace-audit.json](<../data/trace-audit.json>)。

| 指标 | 结果 | 说明 |
|---|---|---|
| 决策数 | 12,000 | 4 局 × 3,000 |
| `complete` 比例 | **0.999917**（11999/12000） | 唯一原因是 1 条 `frame_mismatch` |
| 帧推进分布 | 2 帧：11999；7 帧：1 | frameskip=2 在正常情况下成立 |
| 速度类别（按分量） | axis 3361、diagonal 1880、focus_axis 1065、focus_diagonal 669、idle 5025 | 四类全部出现，合计 12000 |
| 速度偏离模型 | **0**（0.0%） | 所有决策帧都落在实测四值上 |
| 弹池最大/均值 | 单局最大 434；均值 115.8–150.3 | 远未到 601 上限，但已超过旧 320 上限 |
| 弹池计数 vs 引擎计数 | 完全相等 **26.8%**；±2 内 34.5%；范围 −410 … +416 | 逐局中位数 0 … +49.5（四局为 0 / +49.5 / +40 / +30.5） |
| 首步快照 | 4/4 有 `player`、`clock`；`bullets.count = 0`；`items`/`boss` 为 `empty`（非 `error`） | 首步不缺字段 |

**解读（保守）**：

- 帧对齐与速度模型在既有数据上**成立**，可以据此冻结运动学与 `frameskip=2`。
- 但“弹池计数 vs 计数器”不是同帧一致性的证明，且差异幅度远超一个更新窗口。**我们未能确定原因**（见 §6 U-01），因此既不把它当作 bug 也不当作证据，只把它列为“不能用”。
- `complete=true` 的含义是“字段组可读”，不是“同一时刻”。任何“路线在这里是否安全”的结论都必须是新适配层用自己的同步证明得到的。

## 4. 发现清单

严重度：**阻断** = 不修就不能开工；**高** = 会直接污染效果结论；**中** = 会造成局部错误或统计偏差；**低** = 一致性/可读性。

| ID | 严重度 | 发现 | 影响 | 要求 / 去处 |
|---|---|---|---|---|
| D-01 | 高 | 弹池与状态不是同帧（26.8% 相等，±416） | 任何“当前弹幕”判断都可能基于错帧 | 适配层用“两次读取同一 `frame_id`”证明同步；否则 `hazards=null` + `missing_reasons`（F-09） |
| D-02 | 阻断 | 空池与读失败不可区分（旧 pilot 回退 obs 近邻） | 会把“读失败”当成“没有子弹”，产生假安全 | `hazards: null` vs `()` 契约 + 校验器（已落地） |
| D-03 | 中 | 采样超时会静默接受 1 帧推进 | 决策间隔与假设不符，扫掠复核会错位 | 记录 `observed_frame_age`；正式评估按 B-05 剔除并公开 |
| D-04 | 高 | 旧 pilot 有效视界可退化为 8 帧 | 支持 H1，但旧 baseline 的“20 帧”说法不准确 | 报告与配对分析统一称“≤20 帧，可提前到 8 帧” |
| D-05 | 高 | 320 颗 + 240 px 近邻截断会整体丢弃远处弹墙 | 直接对应 FR-05；旧 baseline 在 SC-09 类场景“看不见封路” | 新层按扫掠包络裁剪并显式记录丢弃量与理由 |
| D-06 | 中 | 圆近似在 45° 偏乐观：盒接触时仍报 +0.67 px（几何差 1.17，pad 只抵 0.5） | 旧 baseline 在斜向偏乐观；换口径后 bomb 阈值含义变化 | 新层用 AABB；bomb/min_clearance 阈值需按新口径重新校准（D-15） |
| D-07 | 低 | 规划夹取比真实夹取内缩 0.825 px | 旧 baseline 在墙边略保守，不会非法越界 | 新层用真实夹取 `[8,376]×[16,432]`；与旧臂比较时注明 |
| D-08 | 低 | obs 路径与 raw 路径半径下限不同（1.0 vs 0.5 px） | 离线回放与真机小弹半径不一致 | 新层只用 raw 口径；离线回放如需解码必须注明 |
| D-09 | 高 | ECL 子弹时间会改写在飞速度 | 线性预测在变速帧失效，可能给出高置信错误 | `unsupported_hazards` 显式标记；变速帧不做高置信预测 |
| D-10 | 中 | 输入 1 帧沉降未写入旧 trace | 实际执行的动作可能比记录晚 1 帧 | 契约 `action_latency_frames=1` 默认值；评估时按实际值 |
| D-11 | 高 | `complete=true` 被当作“同一时刻”使用 | 方法学错误：旧 trace 的完整性不能当同步性 | 报告与新契约区分“可读完整”与“同帧一致” |
| D-12 | — | 首步快照 4/4 完整 | 通过（与 v3.6.0 T0 结论一致） | 继续沿用首步门 |
| D-13 | — | 帧推进 11999/12000 恰为 2 | 通过 | 但必须记录异常那 1 条 |
| D-14 | — | 速度分量 12000/12000 命中模型 | 通过 | 运动学可冻结 |
| D-15 | 中 | `bomb_min_clearance=-1.5` 是圆口径下的经验阈值 | 换 AABB 后同一数值含义不同，不能直接搬 | 新层阈值只在开发集重新标定，并在预注册里写清口径 |

> D-15 单列：它不是“发现旧代码错误”，而是提醒**阈值与口径绑定**。把旧的 −1.5 直接搬到新碰撞口径，会让“该不该 bomb”悄悄改变。
