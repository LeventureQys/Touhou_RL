# S3-5 单元测试与一键验证任务书

- 所属 Stage：Stage 3（开发）
- SubStage：S3-5
- 依赖前置：S3-1..S3-4 的模块函数全部实现（可先写测试再补实现，但本 SubStage 的"完成"以全部用例通过为准）
- 并行状态：可与 S3-4 的脚本编写并行；执行必须在前序完成后串行
- 所属阶段：Stage 3 开发

---

## 1. 背景与目标

新功能必须有单元测试（正常路径 + 至少一个边界/异常），且测试要实际执行并留下证据。本 SubStage 提供：

1. 自包含单元测试运行器（不依赖 Pester，零第三方依赖）；
2. 一键端到端验证脚本 `Verify.ps1`，把"环境 → 构建体检 → 装配 → 两次运行 → 仓库卫生"串起来并产出汇总 JSON。

## 2. 需要新建的文件

| 文件 | 内容要求 |
| --- | --- |
| `tools/th08/tests/Invoke-UnitTests.ps1` | 自包含断言器；逐条打印 `PASS <id> <desc>` / `FAIL <id> <desc> :: <detail>`；汇总 `TOTAL/PASSED/FAILED`；全绿 `exit 0`，否则 `exit 6` |
| `tools/th08/Verify.ps1` | 端到端：`param([switch]$SkipBuild, [switch]$SkipRun)`；产出 `build/reports/verify-report.json`；`exit 0/4/5/6` |

## 3. 单元测试用例清单（最低要求，不得删减）

| ID | 目的 | 输入 | 期望 | 类型 |
| --- | --- | --- | --- | --- |
| T-01 | 目标哈希校验通过 | `resources/th08.exe`（若不存在则用 `build/play/th08.exe` + 尺寸/哈希参数注入） | `Verified=$true`，`Size=840704` | 正常 |
| T-02 | 篡改文件被拒 | 复制目标到临时文件并翻转 1 字节 | 抛 `TH08-E02` | 异常 |
| T-03 | PE 解析正确 | canonical 目标 | `IsPe32=$true`、`Machine=0x014C`、`Subsystem=2`、`ImageBase=0x00400000` | 正常 |
| T-04 | 非 PE 被拒 | 任意文本文件 | 抛 `TH08-E05` | 异常 |
| T-05 | cfg 写入字段正确 | 零售 `th08.cfg` 副本 | 长度 60、`Windowed=1`、`Version="0x00080001"` | 正常 |
| T-06 | cfg 写入幂等 | 连续两次 T-05 | 两次 SHA-256 相同 | 正常（边界） |
| T-07 | 非法 cfg 源被拒 | 59 字节文件 | 抛 `TH08-E06` | 异常 |
| T-08 | 清单校验：齐备通过 | 已装配的 `build/play` | `Assert-Th08Runtime.Ok=$true` | 正常 |
| T-09 | 清单校验：缺文件失败 | 临时目录缺 `thbgm.dat` | 抛 `TH08-E06` | 异常 |
| T-10 | 键脚本解析通过 | `profiles/l2-gameplay.json` | 步骤数 >0，字段规范化 | 正常 |
| T-11 | 键脚本非法 action | `{"steps":[{"action":"jump"}]}` | 抛 `TH08-E12` | 异常 |
| T-12 | 键脚本越界 | `key.vk=300` | 抛 `TH08-E12` | 边界 |
| T-13 | 日志审计通过 | 正常 run 的 `*_log.txt` | `Pass=$true`，`RequiredMissing=@()` | 正常 |
| T-14 | 日志审计拦截致命 | 注入 `Fatal error` 的临时日志 | `Pass=$false` 且 `ForbiddenFound` 含 `Fatal` | 异常 |
| T-15 | 空白截图判定 | 生成 640x480 纯黑 PNG，按运行器算法算 `distinctColors/meanLuma` | 触发空白规则（`distinctColors<64` 或 `meanLuma<2`） | 边界 |

| T-18 | 构建报告与产物代码哈希一致 | 读取 `build/reports/build-{normal,bugfix}.json` 中与当前 `build/th08.exe` 整文件哈希匹配的那一份 | `Get-Th08CodeHash` 输出的 64 位哈希等于报告 `artifact.codeSha256` | 正常 |

> 若某条因环境原因无法构造（如 T-17 的桩文件不存在），用"等价构造"替代并在完成报告注明替代方式；不允许删减用例。

## 4. `Verify.ps1` 步骤契约

| 步骤 | 名称 | 动作 | 通过判定 |
| --- | --- | --- | --- |
| 1 | `env` | `Assert-Th08Target` + 前缀四项检查 | 返回 `Verified=$true` |
| 2 | `build` | 若未 `-SkipBuild`：`Invoke-Th08Build normal -Fresh` → `Invoke-Th08Build bugfix -Fresh`；否则读取既有 `build/reports/build-*.json` | 两报告 `exitCode=0` 且 PE 字段正确 |
| 3 | `runtime` | `Initialize-Th08Runtime` + `Assert-Th08Runtime` | `Ok=$true` |
| 4 | `unit-tests` | 调 `tests/Invoke-UnitTests.ps1` | `exit 0` |
| 5 | `run-gameplay` | 若未 `-SkipRun`：`Invoke-Th08Run -ProfilePath profiles/l2-gameplay.json -Tag verify` | 报告 `exit.code=0`、审计通过、必需截图齐全 |
| 6 | `run-menuexit` | 若未 `-SkipRun`：同上用 `l2-menuexit.json` | 报告 `exit.code=0`、自然退出 |
| 7 | `repo-hygiene` | `git -C third_party/th08 status --short`；根仓库 `git status --short` | 子模块输出为空；根仓库不出现私有二进制/数据（`*.dat`/`*.exe`/`prefix/`） |
| 8 | `claims-untouched` | 读取 `third_party/th08/config/claims.csv` 行数 | 等于 1（仅表头） |

`verify-report.json` 记录每步 `{name, ok, exitCode, detail}` 与总 `pass`；任一步失败 `pass=false` 且脚本退出码对应失败类型（构建 4 / 运行 5 / 单测 6）。

## 5. 可观察验收标准

| 编号 | 检查 | 通过标准 |
| --- | --- | --- |
| S3-5-a | 单测全绿 | `Invoke-UnitTests.ps1` 输出 `FAILED 0`，`exit 0`；用例数 ≥17 |
| S3-5-b | 单测覆盖异常路径 | 至少 6 条用例属异常/边界（T-02/04/07/09/11/12/14/15/17 中任 6 条） |
| S3-5-c | 单测可重复 | 连续两次执行结果一致（全绿） |
| S3-5-d | 一键验证 | `Verify.ps1`（不带 `-Skip*`）→ `exit 0`，`verify-report.json` 中 8 个步骤全 `ok=true`，总 `pass=true` |
| S3-5-e | 测试不污染仓库 | 执行后 `git -C third_party/th08 status --short` 为空；临时文件全部位于 `build/` 或 `$env:TEMP` |
| S3-5-f | 失败可诊断 | 人为破坏一步（如临时改 `play/th08.cfg` 的 `0x22`）→ `Verify.ps1` 返回非 0，报告定位到 `runtime` 步骤且 `detail` 含 `TH08-E06`；随后恢复 |

## 6. 禁止事项

- 禁止引入 Pester 或任何需联网安装的依赖。
- 禁止在测试中使用真实零售目录的写操作；禁止对 `D:\Games\...` 的 DAT 做哈希以外的读取（复制它们作为测试夹具）。
- 禁止让测试互相依赖执行顺序（每条用例自带 set-up/tear-down，临时目录用 `Join-Path $env:TEMP ("th08-test-" + [guid]::NewGuid())`）。
- 禁止把测试产生的临时文件留在仓库内。

## 7. 自测要求

1. 单测：连续两次执行，记录 `TOTAL/PASSED/FAILED` 与耗时。
2. `Verify.ps1` 全量执行一次（含两次构建与两次运行），记录总耗时与各步骤结果。
3. 失败诊断演练（S3-5-f）一次，记录输出片段。
4. 以上证据写入 `Stage3/完成报告.md` 的 S3-5 小节。
