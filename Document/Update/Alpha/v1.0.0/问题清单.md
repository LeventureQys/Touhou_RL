### Q-01 运行载体路线：是否以 VC7 原生重建版作为本项目正式"跑通"目标？

- 问题描述：F-07 已证明本机可运行 VC7 原生重建的 bugfix 版（与零售 1.00d 同 ABI、同地址布局、同数据格式）。但上游同时存在三条其它运行路线：①现代 Linux 移植（`docs/PLAY_LINUX.md`，上游标注 Done、经 WSLg 与 Kali 虚拟机验证，但需要安装 WSL 与 32 位依赖，且是本机不可分发的移植体）；②现代 Windows 移植（`docs/PORTING.md:26` 标注 In progress，且 `PORTING.md:62-73` 明确 MinGW 版仍有未解决的启动失败、依赖 DX8 SDK 的 `d3dx8d.dll`）；③Web 移植（独立仓库 `th08-web`，不在本子模块内）。选择直接决定后续"调试与状态提取"的技术基座。
- 建议方案：**A. 以 VC7 原生重建 bugfix 构建作为正式运行载体**（normal 构建仅作精确性证据、不用于运行）。理由：与逆向工程目标同构（同 ABI、同地址、同 `.map`/PDB 符号可对齐），无需 WSL/Wine，本机已实测启动成功。
- 备选方案：B. VC7 为主 + 追加现代 Windows 移植（需先补齐 D3DX8 替换与上游已知启动缺陷，工作量与不确定性大）；C. VC7 为主 + 追加 Linux 移植（需安装 WSL 发行版，`wsl --install` 需重启/多次授权）；D. 只做 Web 移植（不含本逆向工程链路，与"在逆向工程中调试"目标冲突）。
- 风险预警：选 A 意味着运行体**依赖私有零售数据与本地私有工具链**，不可分发、不可在无零售数据的机器上复现；若未来要对外分发或上云训练，必须另立移植路线（建议列为 v1.1+ 议题）。选 B/C 会把 v1.0.0 从"跑通"膨胀为跨平台移植工程，且上游 Windows 移植本身未完成，存在无法收敛的风险。
- 置信度：A 方案 93%（剩余 7% 来自"是否需要可分发性"这一未确认目标）。

## 2. 自决区（本人决策，写明方案与理由）

### D-01 运行体选择：bugfix 构建用于运行，normal 构建仅用于精确性对照
- 方案：两者都构建，但只有 bugfix 产物进入运行目录。
- 理由：F-12 证明 normal 构建无法通过零售版本表校验，运行必失败；bugfix 的 3 处改动均不改变游戏逻辑（版本放行、空指针防护、结算页精灵堆积）。
- 风险：bugfix 产物不能用于"精确性"声明。缓解：验收文档明确禁止以 bugfix 产物作 reccmp/objdiff 匹配声明。

### D-02 游戏数据源：只用日语 1.00d 正版数据，不用汉化版
- 方案：数据一律取 `D:\Games\[th08] 东方永夜抄 (日文版)\[th08] 东方永夜抄 (日文版)\`。
- 理由：`third_party/th08/AGENTS.md` 规定不得分析本地化/补丁版；汉化版（`D:\Games\东方Project\官方游戏\整数作\【不推荐】红妖永花汉化版\...`）会改变 ECL 文本与可能的文件偏移，破坏逆向工程证据链。
- 风险：界面为日文，后续 RL 文本相关特性需注意编码（CP932）。

### D-03 私有资源落地位置：子模块内被 gitignore 覆盖的路径
- 方案：`third_party/th08/resources/th08.exe`（从正版目录复制 840,704 B）、`third_party/th08/scripts/prefix/`（从旧副本整体复制 0.42 GB，绕过 `create_devenv.py` 需要的 VS.NET 2002 介质下载）、`third_party/th08/build/`（构建产物与运行目录）。
- 理由：F-13 证明三条路径均被忽略，子模块 `git status` 可保持干净；`docs/WINDOWS_I386_RUNTIME.md:36-38` 要求在原生 Windows 主机上把目标放在 `resources/th08.exe`。
- 风险：私有/受限材料进入工作区（不提交、不复制进 `Document`）；若误提交会违反上游规则。缓解：提交前执行 `git status --short` 检查，并在总结报告记录"未提交私有材料"。

### D-04 流水线与文档的归属目录
- 方案：新增脚本放根仓库 `tools/th08/`（PowerShell + 复用上游 Python 脚本）；文档放 `Document/Update/Alpha/v1.0.0/`；构建产物、运行目录、证据原图留在子模块 `build/` 内（gitignored），仅把关键截图副本放入文档目录。
- 理由：`third_party/th08` 是上游子模块，AGENTS.md 要求保持单写者、干净工作区，不追加框架自研代码；根仓库是框架本体，应拥有工具与文档。
- 风险：根仓库需自己维护脚本，与子模块脚本存在少量调用耦合（仅调用上游命令，不复制其逻辑）。

### D-05 运行模式：窗口化 640x480
- 方案：staged 运行目录的 `th08.cfg` 偏移 `0x22`（`GameConfiguration.windowed`，`Supervisor.hpp:74`，校验见 `Supervisor.cpp:1432-1443`）置 1，其余字段沿用零售配置（`version=0x00080001`、`lifeCount=2`、`bombCount=3`）。
- 理由：窗口化便于定点截图、避免切换显示模式影响双屏桌面；实测游戏会原样回写该配置，状态稳定。
- 风险：窗口化下渲染路径与全屏略有差异（D3D8 windowed 呈现），如需全屏证据另行一次性验证。

### D-06 关闭方式：优先 `WM_CLOSE`，超时才强杀
- 方案：先 `PostMessage(hwnd, WM_CLOSE)`，等待 ≤8 s；仍在运行才 `Stop-Process -Force`。
- 理由：实测 `WM_CLOSE` 后 exit code 0 并正确回写配置与存档（F-07），强杀会跳过写盘并可能留下损坏的 `score.dat`。
- 风险：若窗口句柄尚未创建（启动 8.2 s 内）需要先等窗口，再关闭，逻辑已在探针脚本中实现。

### D-07 脚本调用方式：统一 `powershell -NoProfile -ExecutionPolicy Bypass -File`
- 方案：所有交付脚本均以此方式调用，并在文档中写明。
- 理由：F-10 实测本机执行策略禁止脚本。
- 风险：若用户机器策略更严（如 AppLocker），需改为手工执行命令。

### D-08 版本目录沿用既有结构
- 方案：沿用 `Document/Update/Alpha/v1.0.0/`，不另建 `v1.0.0 - 名称` 目录；阶段产物平铺该目录，Stage 明细放 `Stage1/`~`Stage4/`。
- 理由：目录已由用户创建（含 `需求文档.md`），避免与用户既有约定冲突。
- 风险：无。

### D-09 空需求文档 `v1.0.1`
- 方案：暂不处理 0 行的 `Document/Update/Alpha/v1.0.1/需求文档.md`。
- 理由：F-14，无内容可解析；本版仅按 v1.0.0 执行。
- 风险：若用户本意是 v1.0.1 覆盖 v1.0.0，需在 Q 阶段答复中纠正。
