# v3.5.0 S0 状态、事件与采集契约

- 日期：2026-10-24
- 依据：[v3.5.0 执行计划](<../执行计划.md>) §3、[研究方案](<../研究方案.md>) §4
- 性质：**预注册契约**。本文件写定后，S0-1…S0-5 的分母、字段集合、未知值语义与判定规则不得根据采集结果修改；若要修改，必须新开版本并说明原因。
- 对象：TH08 1.00d（重建 bugfix 镜像，`third_party/th08/build/play/th08.exe`，模块基址 0x00400000）
- 边界：只读内存；不写进程、不注入、不跳过菜单、不修改 `entity_obs` / `options` / `chunk_safety` 的既有口径。

> 一句话：S0 不是“再多读几个字段”，而是先把“这个字段读到了没有、读的是哪一帧、它能不能和别的字段区分开”写成可复核的合同。S0 不通过，S1–S4 不启动。

## 0. 本轮 S0 只回答什么

> 在不训练任何策略、不改动作空间的前提下，现有只读特权状态是否足以支撑“提前离开大范围攻击、主动清怪、条件性收 P”的因果战术教师所需的状态、事件与采集质量？

具体到五个门：

| 编号 | 判据 | 阈值 | 分母 |
|---|---|---:|---|
| S0-1 | 逐决策时间戳单调 | 100% | 全部采集记录（含终止记录） |
| S0-2 | enemy/item/power 字段可追溯 | 100% | 稳态决策（定义见 §7.3） |
| S0-3 | clear / game-over / left-game 可区分 | 100%（每条终止都有唯一归类与证据） | 全部终止记录 |
| S0-4 | 新采集 `complete` 有效率 | ≥ 95% | 稳态决策 |
| S0-5 | 整局切分 | 100%（同一 `episode` 不跨 split） | 全部局 |

任一 S0 门失败，S1–S4 停止；先修状态/事件/采集，不调门禁。

| stage / stage_frames | `GameManager` + `0x3DDC4` / `0x3DE14` | i32/u32 | 当前面 / 面内帧 | 读失败 → `null` |
| gameplay_frame | `GameManager` + `0x3DDC0` | u32 | 全局游戏帧 | 读失败 → `null` |
| flags | `GameManager` + `0x3DBAC` | u32 | `GameManagerFlags` 位域 | 读失败 → `null` |

**未知值的硬规则**：

1. 读失败只能写 `null` + `schema.*=error`，不能写 0、空列表或 `False` 冒充“不存在”；
2. 空列表只表示“这次读取成功且确实为空”（无 Boss、无敌人、无道具）；
3. `sub_id` 为 `null` 表示“这个敌人此刻的 ECL 上下文不可读”，不是“类型 0”；
4. `gui_*` 读失败时整个 GUI 组为 `null`，不能把 `False` 当作“没有对话”。

## 2. 普通敌人契约

### 2.1 布局与字段

`EnemyManager` 内 `enemies` 为 481 个连续 `Enemy`（每个 0x53D0），`SpawnEnemy1/2` 只使用 0..479，481 是数组末尾的边界。字段：

| 字段 | 偏移 | 类型 | 说明 |
|---|---:|---|---|
| position | 0x2D34 | Float3 | 绝对场地坐标；y<0 表示尚未入场 |
| life | 0x2DFC | i32 | 当前生命；≤0 是死亡中 |
| maxLife | 0x2E00 | i32 | 最大生命（用于击杀进度） |
| activeEclContext | 0x2CA0 | u32 | 当前 ECL 上下文指针 |
| itemDropType | 0x3304 | i8 | 死亡掉落类型；-1/-2 有特殊语义 |
| bossSlot | 0x3313 | u8 | 属于哪个 Boss 槽 |
| flags1 | 0x3324 | u32 | bit0 active，bit1 boss，bit2 collision，bit3 damageable |
| sub_id | 指针 +0x224 | i16 | `EnemyEclContext::subId`，本阶段作为“敌人类型” |

### 2.2 “类型”的口径

本阶段**不把 `enemyIndex` 当类型**（它只是对象池下标，见 `EnemyTimeline.cpp` 的赋值），而是：

```text
enemy_type = activeEclContext->subId   （可读时）
           = null                      （不可读时，且必须标 unknown）
```

`sub_id` 是同一面 ECL 内的出怪子程序号，对“这个敌人会发什么弹”是可复核的稳定代理；它不跨面可比，因此 S1/S3 的分析必须按 `stage` 分组，不能把不同 stage 的 `sub_id` 混为一谈。

### 2.3 读取策略与成本

- 一次 `ReadProcessMemory` 读整个 481×0x53D0 数组（约 9.8 MB），再用 NumPy 步长视图解析，避免 481 次小读；
- 每个 live 敌人再读 2 字节 `sub_id`（可选），读失败记 `null`；
- 实测（2026-10-24 smoke，非门禁）：`read_enemies` 中位 **1.155 ms**、p95 2.44 ms（含 ≤20 个 live 敌人的 sub_id 读）；
- 每决策都读（30 Hz 决策频率下约 3.5% CPU），不做降采样；S1 的离线重放同样按决策序列。

### 2.4 空集合、Boss 与重复

- 无 live 敌人时返回 `[]`（已知空），`activeEnemyCount` 可作交叉核对但不作为唯一依据；
- Boss 同时出现在 `bosses[]` 与 `enemies[]`：trace 里两边都记录，`EnemyInfo.boss=True` 且 `boss_slot>=0`；
- 同一 `slot` 在两个连续决策里可能是不同敌人（对象池复用）：`sub_id` 或 `max_life` 变化即视为新个体，S1 不得只按 slot 跟踪轨迹。

## 3. 道具契约

### 3.1 布局与字段

`ItemManager` 内 `items[2097]` 从偏移 0 开始，每个 0x2E4：

| 字段 | 偏移 | 类型 | 说明 |
|---|---:|---|---|
| currentPosition | 0x2A4 | Float3 | 绝对场地坐标 |
| startPositionOrVelocity | 0x2B0 | Float3 | 初速/插值起点 |
| targetPosition | 0x2BC | Float3 | 死亡散落目标 |
| itemType | 0x2D4 | i8 | 0 小 P / 1 点 / 2 大 P / 3 bomb / 4 full power / 5 extend / 6 星 / 7 time / 8 小点 |
| isInUse | 0x2D5 | i8 | 槽位是否占用 |
| isOnscreen | 0x2D6 | i8 | 是否在屏幕上（不等于可收集） |
| state | 0x2D7 | i8 | 0 default / 1 auto-collect / 2 death-drop / 3 time-rising / 5 apex |
| isMaxValue | 0x2D8 | i8 | 点道具是否已按最大值计分 |

### 3.2 读取策略与成本

- 一次读整个 `items` 数组（约 1.5 MB），实测中位 **0.197 ms**、p95 0.38 ms；
- 只输出 `isInUse != 0` 的道具；`itemCount`（`ItemManager` + 0x17ADA8）可交叉核对数量，但 trace 以实际槽位为准；
- 道具消失 ≠ 被收集：可能是掉出屏幕（`state=default` 且 `y > 场地底 + 16` 时 `Delete()`）。S0 的收集事件必须同时看 **power 增量** 和 **玩家/道具位置**，不能只看槽位消失。

### 3.3 本阶段不做的

- 不把 `isOnscreen` 当“可收集”；
- 不把 `itemDropType` 当“已掉落道具”；
- 不在 item 数组读取失败时用空列表继续，必须 `schema.items=error` 并让该记录不计入 complete。

## 5. P 点契约实验（受控，预注册）

### 5.1 场景

- 难度 Lunatic，Border Team（team 0），练习面 Stage 1（`practice_stage=0`）；
- 不使用 replay、不注入、不读 `score` 作为判据；
- 决策 `frameskip=2`，每决策读一次状态/敌人/道具/shot 参数；
- 控制策略：`AvoidPilot`（局部躲避） + 受控“上移收 P”覆盖：
  - 当 `power < 128` 且存在 in-use P（type∈{0,2,4}）且当前决策的安全间隙 ≥ 2 px 时，覆盖为“上移（move=1）+ focus=1”；
  - 当 `y <= 110` 或不存在 P 时恢复教师动作；
  - 覆盖只用于本实验，不写入 `pilot.py` 的默认行为。

### 5.2 观测

每决策记录：`frame / player.x,y / focus_mode / power / line / auto_speed / box / items[]（含 state）/ schema_status / complete`；每次掉电/收集记录 `power_delta` 与消失槽位。

### 5.3 判定

| 编号 | 通过标准 | 失败处理 |
|---|---|---|
| H-P1/P2 | 两次独立 crossing 中至少一次达到 128.0；无 >128.0；满后无 power 增长 | 契约 fail，停止 S1–S4 |
| H-P3 | 首次 `state 0→1` 的决策 `player.y` 与 `line` 差 ≤ 2 px，且 `line` 在 120–136 | fail → 检查 `primaryShtFile` 偏移，不调动作 |
| H-P4 | 按住 Shift 至少 10 个连续决策 `focus_mode=1`；松开后 2 决策内 `=0` | fail → 重做输入契约 |
| H-P5 | crossing 决策中，所有 in-use P（排除 time orb）在同一/下一决策进入 `AUTOCOLLECT`；漏检 ≤1 颗且能由碰撞盒解释 | fail → 记录例外，P 收集进入条件暂缓 |
| H-P6 | 每次 power 增量 ≤ 该窗口内消失 P 的理论增量，且方向一致；不出现“power 增加但无道具消失” | fail → 契约无效 |

### 5.4 样本量

- **2 次独立 crossing**（两个 episode，各至少一次从 y>128 到 y<128）；
- 若 2 次都因死亡未 crossing，允许最多 3 个 episode 重试；仍不能 crossing → H-P3 判 `not_tested`，S0 总判定 fail（不是 pass）。

## 6. 事件契约

### 6.1 事件种类

| 事件 | 触发 | 证据字段 |
|---|---|---|
| `death` | `deaths` 比上一决策增加 | `deaths_before/after`、`player_state` |
| `stage_clear` | `stage_clear_sequence_active` 0→1，或 `gui_stage_clear_screen_state` 0→非 0，或 `stage` 增加 | `flags`、`gui_stage_clear_screen_state`、`stage_before/after` |
| `game_clear` | `game_cleared` 0→1，或 supervisor 进入 ENDING | `flags`、`supervisor_state`、post-terminal 轮询 |
| `game_over` | `lives` 从 ≥0 变为 <0，或终止后轮询到 retry/game-over 屏 | `lives`、post-terminal 轮询 |
| `left_game` | supervisor 离开 `STATE_GAME_MANAGER` 且不属于上面三类 | `supervisor_state` |
| `stage_transition` | `stage_transition_state` 变化 | `flags` |
| `dialogue` | `gui_dialogue_present` 0→1 / 1→0 | `gui_dialogue_msg_idx` |
| `power_max` | `power` 首次 ≥128.0 | `power` |
| `bomb_used` | `bombs_used` 增加 | `bombs_used` |

### 6.2 终止归类优先级

```text
game_clear > stage_clear > game_over > left_game > max_steps > frame_stalled(unknown)
```

- 每条 episode 只能有 **一个** `termination_reason`；
- `frame_stalled` 是“harness 停止”而不是一种游戏事件；若它是唯一证据，S0-3 记 fail；
- 终止后必须做 **post-terminal 轮询**（最多 5 s）：区分“清关屏冻结了帧计数”与“真的结束/死亡”；
- `max_steps` 只表示采集截断，不得写成 clear。

### 6.3 与 `env.py` 的关系

`env.py` 现有终止判据（supervisor、demo、lives<0、advanced==0）保留不动；S0 探针在 `env` 之外加一层 `classify_terminal()`，只用只读状态与 post-terminal 轮询做归类。这样不会为了 S0 改坏既有训练/评估路径。

## 7. trace schema `v350-trace/1`

### 7.1 逐决策记录（JSONL，一行一条）

```json
{
  "schema": "v350-trace/1",
  "episode": "s0-teacher-ep01",
  "decision": 128,
  "frameskip": 2,
  "frame_pre": 1024,
  "frame_post": 1026,
  "wall_ms": 54321,
  "complete": true,
  "incomplete_reasons": [],
  "schema_status": {
    "player": "ok", "bullets": "ok", "enemies": "ok",
    "items": "ok", "boss": "ok", "power": "ok", "shot": "ok", "gui": "ok"
  },
  "clock": {"stage": 0, "stage_frames": 980, "gameplay_frame": 1026,
            "run_frames": 1026, "flags": 32, "current_spell": -1},
  "player": {"x": 192.0, "y": 300.5, "vx": 0.0, "vy": 0.0,
             "state": 0, "focus_mode": 0, "hurtbox": [0.825, 0.825]},
  "resources": {"power": 64.0, "power_max": 128.0, "lives": 2.0,
                "bombs": 3.0, "score": 1234, "graze": 56, "deaths": 0},
  "bosses": [{"slot": 0, "x": 192.0, "y": 80.0, "life": 7300}],
  "enemies": [{"slot": 7, "x": 320.0, "y": 100.0, "life": 150,
               "max_life": 150, "boss": false, "sub_id": 12,
               "item_drop": 0, "boss_slot": 0}],
  "items": [{"slot": 3, "x": 200.0, "y": 300.0, "type": 0,
             "state": 0, "onscreen": true, "is_max_value": false}],
  "frame_events": {"bits": 64, "item_collected": true},
  "events": ["power_max"],
  "action": [1, 1, 1, 0],
  "teacher": {"clearance": 12.5, "bullets_used": 48},
  "bullets": {"count": 48, "counter": 48, "sidecar_index": 128}
}
```

字段规则：

- `frame_pre/frame_post` 必填；`frame_post = frame_pre + frameskip` 是 complete 的必要条件；
- `schema_status` 的取值只有 `ok | empty | error`：
  - `ok` = 读成功且有内容；`empty` = 读成功且集合为空；`error` = 读失败/未知；
  - `enemies/items/bosses` 允许 `empty`；`player/power/bullets` 不允许 `empty`；
- `events` 是相对上一决策的上升沿/增量，终止记录额外带 `terminal` 对象；
- `bullets` 只写计数与 sidecar 下标，子弹明细在 `bullets/*.npz`：

```text
positions   (N,2) float32   绝对坐标
velocities  (N,2) float32
half        (N,)  float32   max(half_x, half_y)
offsets     (D+1,) int32    第 d 条决策的起止
counter     (D,)  int32     BulletManager.activeBullets（诊断；见 §7.4 修正）
```

`frame_events` 来自 `ReplayManager.frameEventFlags`（`g_ReplayManager` + 0xDA，u16）：
`item_collected` 是 bit 0x40（`REPLAY_FRAME_EVENT_ITEM_COLLECTED`）。它是判断
“这一决策内确实有道具被收集”的直接信号，用于解释 frameskip 盲窗内
“看不见生成、只看见 power 增加”的收集。读不到时写 `null`，不得写 0。

### 7.3 稳态决策（S0-2/S0-4 的分母）

一个决策是 **稳态**，当且仅当：

1. 决策前 `supervisor_state == STATE_GAME_MANAGER` 且 `gameplay_frame > 0`；
2. 决策前不处于 `gui_dialogue_present` / `stage_clear_sequence_active` / `stage_transition_state != 0`；
3. 决策后仍满足 1（终止决策不计入分母；终止证据单独计入 S0-3）。

稳态决策之外的记录写 `excluded_reason`，不计入分母，但仍保留在 trace 中，禁止删除。

### 7.4 `complete` 的定义（预注册）

一个稳态决策 `complete=true`，当且仅当以下全部成立：

1. `frame_post - frame_pre == frameskip`（无符号帧差，允许 32 位回绕）；
2. `bullets.count` 在 `0..0x601` 内，且 sidecar 数组可用（`positions` 行数 = `count`）；
3. `schema_status.player == ok`，且 `player.x/y` 有限、落在移动区内（`MOVE_AREA_X..X+W`, `MOVE_AREA_Y..Y+H`）；
4. `schema_status.enemies/items/boss/power/shot` ∈ {`ok`,`empty`}；
5. `wall_ms` 非递减（允许相等）；
6. `decision == 上一条 decision + 1`，`frame_pre == 上一条 frame_post`。

> **2026-10-24 预注册修正（在正式 S0 采集之前，smoke 发现）**：原第 2 条是
> `|activeBullets - sidecar.count| <= 2`。smoke 实测 1,140 个稳态决策里 406 个
> 不满足，且差值可达 ±100：`BulletManager.activeBulletCount` 是在游戏帧更新中
> **原地清零再累加**的（`BulletManager.cpp:814-822`），读取可能落在更新中途，
> 因此它不是“读取正确性”的度量，而是“游戏更新相位”的度量。若保留该条，
> S0-4 会被一个与采集质量无关的相位竞态判 fail。修正为只检查计数范围与
> sidecar 一致性，并把 `counter` / `counter_delta` 保留为诊断字段（报告必须
> 给出其分布）。修正发生在任何正式 S0 数据之前；阈值与分母不变。

不满足任一条 → `complete=false`，并把所有不满足的原因写入 `incomplete_reasons`（不是只写第一条）。S0-4 的分子是 `complete=true` 的稳态决策数。

## 9. 离线门计算（S0-1…S0-5）

### 9.1 输入

- `trace/*.jsonl`、`episodes.jsonl`、`bullets/*.npz`；
- `manifest.json`（文件 SHA256、行数、episode 列表、代码 git head、环境）；
- 不接受“目录里多出来的 trace 文件”：`verify` 必须扫描目录并与 manifest 核对，多/少文件都 fail（沿用 v3.4.0 Stage 0 的教训）。

### 9.2 公式

```text
S0-1 = 单调记录数 / 全部记录数
S0-2 = (schema_status.enemy/item/power 全部 ok|empty 的稳态决策数) / 稳态决策数
S0-3 = 有唯一终止归类且有证据的 episode 数 / 有游戏终止的 episode 数
S0-4 = complete 稳态决策数 / 稳态决策数
S0-5 = 1 - (跨 split 的 episode 数 / episode 总数)
```

- S0-1：`frame_post >= frame_pre`（非递减；对话/清关屏会刻意停帧，不能用严格 `>`），`wall_ms >= prev.wall_ms`，`decision` 连续；稳态决策的“精确推进 `frameskip`”由 S0-4 的 complete 负责，而不是 S0-1；
- S0-2：`enemy`/`item`/`power` 三项都不得为 `error`；`null` 子字段不直接判 fail（未知类型是允许的，见 §1），但整组 `error` 判 fail；
- S0-3：分母是“有游戏终止的 episode”（`max_steps`/`frame_stalled`/`probe_error` 不计入分母）；`termination.reason` 必须 ∈ {`stage_clear`,`game_clear`,`game_over`,`left_game`}，且 `post_terminal` 有 ≥1 条与 reason 一致的状态证据；若没有任何游戏终止局 → S0-3 判 `not_tested`，S0 总判定 fail；
- S0-4：分子/分母严格按 §7.4/§7.3；
- S0-5：按 `episode` 的稳定哈希分 train/validation（seed 固定为字符串 `v350-s0`），同一 episode 的全部记录只能落在一个 split。

### 9.3 失败即停止

- 任一 S0 门失败：S1–S4 不启动；不修改阈值、不重挑 episode、不删除“坏”记录后重算；
- 允许修复 **实现 bug**（例如事件分类写错）后重跑，但必须在报告里写清“修了什么、重跑了几局、原判据是否变化”；
- `frame_stalled` 若占终止的多数，先修 post-terminal 归类，不得把 `frames_mean` 当 S0 结论。
