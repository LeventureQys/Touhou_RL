## 0. 一句话结论

v3.7.0 在合成几何场景中证明了部分“提前撤离/路线搜索”能力，但真机确认集没有达到改善目标：baseline 为 **1.033 死/局**，新方案为 **1.333 死/局**（30 对确认集）；另一个 **10 对三臂消融** 的 bomb 为 **0.1 vs 2.1 颗/局**，这两组数字不是同一批实验。不过，这个差异**不能直接当作纯算法劣化**，因为确认实验按固定 900 次决策停止，而不是严格按双方相同的 1800 个游戏逻辑帧停止；subject 规划期间游戏继续运行，旧动作保持，实际 frame span 还超过 1800，baseline 又没有记录等价 frame span。

v3.7.1 的第一目标不是继续调视界，而是：

1. 修复并证明真实逻辑帧曝光、输入生效和终止条件；
2. 让 baseline/subject 只差一个明确的实验因素；
3. 在此基础上再判断动作评分、bomb 仲裁、focus/速度模型、预测尾部和路线规划哪个是真因。

**在时钟和对照修复前，禁止宣称“出口规划导致死亡增加”，也禁止用新的真机结果事后选择配置。**

## 1. v3.7.0 已知事实：哪些成立，哪些没有成立

### 1.1 成立的事实

- 全仓最新日志为 **1211 passed + 1 xfailed**；v3.7.0 结算文档中的旧数字 `1207 passed + 1 xfailed` 需要以后续日志校正。
- 真机新方案臂的数据完整率为 1.0，`same_frame=True`，B-05 新方案臂通过。
- subject 控制回路 P95 约 17.4–18.9 ms，超时率约 0.11–0.22%，但这不是完整端到端输入生效延迟。
- 真机主指标没有达到预注册改善目标。
- 真机消融中 subject 的局部版本和出口版本都比 baseline 差，说明问题不只在出口排名。
- 学生模型的移动准确率接近随机，视觉接管不可用。

### 1.2 必须收窄的结论

不能直接写成：

- “新方案已经统计证明比 baseline 差 29%”；
- “线性预测已被完全排除”；
- “同一 session 就是同一初始弹幕/RNG”；
- “subject 与 baseline 都严格跑了相同 1800 帧”；
- “局部安全率 92% 说明控制器更安全”；
- “出口规划是唯一根因”。

更严谨的结论是：

> 30 对确认集的点估计不支持改善，且 subject 点估计更差；95% 配对差区间为 `[-0.24,+0.84]`，因此尚不能精确估计真实劣化幅度。实验时钟、曝光窗口、执行延迟、顺序效应和未控制的 baseline 能力必须先修复。

## 2. 最高优先级问题：v3.7.0 的真机实验没有严格等曝光

### 2.1 现有执行方式

确认脚本用 `frames // 2 = 900` 次决策终止，而不是检查 `gameplay_frame >= 1800`。证据：[live_pairs.py](<../../../../.tmp/live_pairs.py#L26-L60>)。

subject 每次决策大致是：

```text
读状态 → 读弹幕 → 构建 field → 规划 → 写输入
```

证据：[live.py](<../../../../touhou_rl/escape/live.py#L258-L285>)。

真实游戏在规划期间仍继续推进，上一输入继续保持。旧动作的有效时间和新动作写入时间没有被记录为同一逻辑帧边界。已有环境读帧逻辑也不能证明每次写输入后恰好只推进两帧：[env.py](<../../../../touhou_rl/env.py#L236-L252>)。

### 2.2 已观察到的异常

原始 `d8-live-pairs.json` 中：

- pair 1 的 frame span 为 `[2,1845]`；
- pair 2 的 frame span 为 `[2,1854]`；
- 其他 pair 最大终帧约 1949；
- baseline 记录没有等价的 frame span。

证据：[原始配对数据](<../v3.7.0/data/d8-live-pairs.json#L26-L48>)。

因此 subject 可能比名义窗口经历更多游戏帧、更多弹幕生成和更多危险机会；同时规划耗时还会改变旧动作保持时长。v3.7.0 报告把整局慢 2–8% 主要解释成“游戏降速”，这个解释不足够，甚至可能混淆了：

- 游戏帧曝光增加；
- 读取、规划、写键延迟；
- 旧动作持续时间不规则；
- 终止点不一致。

### 2.3 v3.7.1 必须修复

两臂都必须：

1. 以真实 `gameplay_frame` 为唯一终止依据；
2. 记录 `start_frame`、`end_frame`、实际曝光帧数；
3. 记录每次：观测帧、规划开始/结束、输入发送时间、输入生效帧；
4. 记录上一动作实际保持了多少逻辑帧；
5. 记录读状态、读弹幕、构建 field、规划、发送输入、等待的分项延迟；
6. 若无法保证固定游戏帧，就把实际曝光帧数作为分层/协变量，不能只报告 wall-clock；
7. subject 与 baseline 都必须经过同一套观测/输入管线，至少先做“同管线 no-op/回放”校验。

**完成标准：** 每个 pair 的两臂都有可审计 frame span；默认比较相同逻辑帧窗口，而不是相同决策次数。

## 3. 第二优先级：先建立公平的单因素对照

v3.7.0 的 baseline 和 subject 同时改变了很多因素，不能把差异归因于“出口规划”。至少存在以下混杂：

| 因素 | baseline | subject |
|---|---|---|
| 规划器 | 旧 pilot | escape controller |
| 视界 | 旧 pilot 约 20 帧 | 确认集 h6/1，约 14 帧计划 |
| beam/continuation | 每首动作保留多条 continuation | 真机 `beam_width=1` 配置 |
| 排名 | 有 `bottom_bias`、切换惩罚、局部未来 clearance | closure/目标/clearance/switch 等新排序 |
| bomb | 旧 pilot 自己的未来余量规则 | 新 controller `clearance <= 0` 才可能触发 |
| 执行 | 旧策略动作管线 | 新规划耗时和 fallback 管线 |
| 记录 | baseline 没有完整 frame span | subject 有部分 frame span |

baseline 证据：[pilot.py](<../../../../touhou_rl/pilot.py#L94-L121>)、[pilot.py 排名](<../../../../touhou_rl/pilot.py#L311-L349>)。

subject 真机配置证据：[live_pairs.py](<../../../../.tmp/live_pairs.py#L90-L95>)。

v3.7.1 必须分阶段做：

### 阶段 A：管线/时钟对照

- 同一观测和输入管线；
- 一个只改变策略，另一个使用固定 replay action；
- 验证同样的输入序列是否产生同样的逻辑帧跨度和位置轨迹。

### 阶段 B：控制器单因素对照

固定相同：

- frameskip；
- 实际帧窗口；
- beam；
- 视界；
- focus 动作编码；
- bomb 可用量和 bomb 仲裁协议；
- 终止/重生处理。

只逐项改变：

1. baseline 局部评分 vs subject 局部评分；
2. 加/不加 `bottom_bias`；
3. beam/continuation 数；
4. 加/不加出口排名；
5. bomb 仲裁规则；
6. 未来预测/路线层。

**禁止把多项改动打包成一个“新方案”后继续解释因果。**

## 4. 当前最可能的算法问题：动作与资源策略退化

v3.7.0 消融是目前最强的算法方向证据：

| 配置 | 死亡/局 | bomb/局 |
|---|---:|---:|
| baseline | 1.0 | 0.1 |
| subject + 出口排名 | 1.7 | 2.1 |
| subject，仅局部 clearance | 1.5 | 2.0 |

证据：[D8/D9 消融](<../v3.7.0/reports/D8-D9-影子与配对.md#L273-L291>)。

因此，不能只修出口选择。要重点审查：

### 4.1 fallback

subject 无路线时可能保持上一动作、保持 focus 或进入 emergency；确认在无路、unknown、budget exhausted、死亡/重生、无敌期间分别发生什么。证据：[controller.py](<../../../../touhou_rl/escape/controller.py#L265-L285>)。

### 4.2 bomb 仲裁

当前 subject bomb 条件主要是“有 bomb、无冷却、当前 clearance <= 0”，见 [controller.py](<../../../../touhou_rl/escape/controller.py#L423-L429>)。这不是完整资源决策。

v3.7.1 必须记录每次 bomb：

- 触发前 60–120 帧轨迹；
- 当前 clearance 和预测碰撞时间；
- 是否存在可行替代动作；
- bomb 后是否真正改变死亡结果；
- 当时是否处于 deathbomb/无敌/重生相关状态；
- 剩余 bomb 数；
- bomb 是否空耗。

推荐先实现一个严格的对照仲裁：只有在“短时间内多动作都证实不可行，且 bomb 能改变结果”时触发。不要把这个推荐直接写成已验证事实，先做单因素实验。

### 4.3 位置先验和 focus

TH08 不是静态几何迷宫。focus 会改变移动速度，真实生存还依赖屏幕位置、可反向空间和后继路线。baseline 的低位偏好可能是有效生存先验，不能未经对照就删除。

保留两个版本：

- `baseline_policy`：原始策略不改；
- `hybrid_policy`：只在高置信未来封死时调用宏观路线层，平时交给 baseline 局部控制。

先比较 hybrid 是否能在不损伤 baseline 生存率的情况下解决明确的预判场景。

## 5. 合成测试的边界：不能把 A 门通过当作真机能力

合成评估代码明确说明：synthetic world 没有 bomb，baseline/subject 以 `bombs=0` 运行；碰撞后 episode 结束。证据：[evaluate.py](<../../../../touhou_rl/escape/evaluate.py#L10-L16>)、[evaluate.py](<../../../../touhou_rl/escape/evaluate.py#L60-L79>)、[synth.py](<../../../../touhou_rl/escape/synth.py#L274-L303>)。

这类试验适合验证：

- AABB 和逐帧碰撞；
- 规划器是否能找到路线；
- unknown、budget、no-solution 的语义；
- 特定合成场景中的提前撤离。

它不适合直接验证：

- bomb 资源经济；
- 多次死亡/重生；
- deathbomb/无敌窗口；
- 实时规划期间游戏继续推进；
- focus 的真实输入动力学；
- 30 秒持续弹幕中的位置先验；
- 整局死亡数。

v3.7.1 至少新增一个“真机闭环 replay/evaluator”层，使用实际 trace 回放并保留：

- 逻辑帧推进；
- 读/写延迟；
- 输入沉降；
- action hold；
- bomb 和死亡状态；
- 同一段 trace 上的 counterfactual 仅在满足物理/生成假设时使用。

不能把原始人类/策略未来弹幕坐标无条件当作所有反事实动作的真值；这一点遵循 v3.7.0 需求中的数据约束。

## 6. 指标必须分时间尺度

v3.7.0 的 24 帧局部安全率为 subject 92%、baseline 75%，但 subject 整局死亡更多。这不是矛盾，而是指标尺度不一致。

v3.7.1 同时报告三层指标：

### L0：执行层

- 实际逻辑帧曝光；
- 输入生效延迟；
- action hold 帧数；
- planner P50/P95；
- deadline miss；
- stale/read reject。

### L1：局部危险层

- 未来 8/16/24/60 帧碰撞率；
- 最近致死风险；
- 安全方向数；
- bomb 前后可行动作数；
- 预测尾部误差，按碰撞相关弹加权。

### L2：整局生存层

- 固定逻辑帧窗口内死亡数；
- 首次死亡帧；
- 后续死亡帧；
- bomb/局；
- 清弹后存活增益；
- 生存到窗口末的比例；
- 若报告分数，必须同时报告死亡、bomb、擦弹和收点，不能挑单项。

**主指标仍然是固定逻辑帧窗口内的死亡数/首次死亡时间；L1 不能替代 L2。**

B-02 的“可判事件”不能直接作为两臂效果主证据，因为 baseline 854 个事件、subject 338 个事件来自不同轨迹，分母由策略自己改变。若保留，必须做状态匹配或明确只作诊断。

## 7. 配对实验协议 v3.7.1

在以下条件未满足前，不得跑正式确认集：

1. baseline/subject 顺序随机化，至少有 AB 和 BA；
2. 记录并尽可能固定游戏 RNG、reset 状态和弹幕 phase；
3. 两臂都按实际 `gameplay_frame` 终止；
4. 两臂都记录相同 frame span、输入生效和每步延迟；
5. 两臂使用同一输入后端、同一 frameskip、同一窗口焦点条件；
6. technical failure、死亡、重生、无敌、bomb 清弹分别编码，不静默剔除；
7. 确认集配置在运行前冻结，探索集与确认集分离；
8. 任何新增排除规则都必须在正式运行前写入预注册；
9. 先跑小规模时钟/管线验证，再跑正式统计确认集；
10. 报告点估计、配对区间、样本量和所有剔除，不把跨零区间写成确定劣化。

推荐单局协议：

```text
reset
→ 等待固定 gameplay_frame 起点
→ 运行到严格终止帧 F0 + 1800
→ 记录全部输入/观测/状态事件
→ reset
```

若真机无法固定 RNG，则采用 AB/BA 随机顺序、多 session、分层 bootstrap，并明确限制“同 session 不等于同初始弹幕”。

## 8. 真机诊断：每次死亡必须能回答“为什么死”

每次死亡前至少保留 120 游戏帧，字段包括：

- gameplay frame；
- 自机 x/y、focus、速度、判定半径；
- 弹池实体、track identity、出生/消失标记；
- 预测位置与不确定性；
- 规划视界、候选动作数、每个首动作状态；
- 选中路线、出口 ETA、closure ETA；
- 最小 clearance；
- 当前 intent、fallback、unknown/budget/no-solution 原因；
- action sent frame、action effective frame、hold duration；
- bomb available、触发原因、bomb 后结果；
- death/rebirth/invulnerable 状态。

死亡归因必须分类：

1. 观测错误/陈旧/不同步；
2. 预测错误；
3. 路线选择错误；
4. 局部动作执行错误；
5. 输入延迟/动作保持过长；
6. bomb 仲裁错误；
7. 无解或确实不可避免；
8. 实验窗口/重生协议问题。

每一类都要有证据，不允许只看死亡后的最终位置猜原因。

## 9. 视觉学生暂缓扩大

v3.7.0 学生闭环失败集合稳定包括 E-05、SC-15、SC-16；增加双帧、未来标量、未来占用图、分辨率和路线标签都没有稳定改变结果，见 [D10–D12](<../v3.7.0/reports/D10-D12-学生与视觉.md#L172-L209>)。

真机学生还表现为：

- 移动准确率 9.75%，随机约 11.11%；
- 闭环 3.67 死/局；
- 自机视觉锚点可用率约 40.5%。

因此 v3.7.1 不应先扩大视觉网络或训练轮数。必须先让特权 teacher/hybrid controller 在**公平时钟和公平资源协议**下稳定，再重新定义学生目标：路线/代价/不确定性/状态，而不是只预测瞬时动作标签。

## 12. 可执行门禁与交付物

以下是新门禁，不沿用 v3.7.0 的 pass。全部初始为 `not_started`。

| 门禁 | 必须验证 | 通过/停止规则 |
|---|---|---|
| C-01 时钟 | 假时钟在规划期间推进 0/1/3/10 帧、计数回退、读失败、帧跳跃 | 终止逻辑以真实帧为准；回退必须识别为新局/异常，不能产生负曝光或无限运行 |
| C-02 曝光 | 两臂实际起止帧、过冲、所有死亡事件时间戳 | 在预注册窗口 `[F0,F0+1800)` 计数；若读数跨越边界而无法确定死亡归属，显式标 `boundary_unknown`，不得默默算入或删除；预先冻结允许过冲及技术失败规则 |
| C-03 生效时序 | 观测到发送、发送到可观察位移、动作保持帧数 | `send_frame` 不等于 `effective_frame`；测不到时标未知/区间，不能伪造精确生效帧。急转、focus切换、贴边、重生分别标定 |
| C-04 延迟鲁棒性 | 同一策略注入额外 0/5/15/30ms 或等效逻辑帧延迟 | 分离“算法不同”和“计算慢”两个因素；报告额外延迟与死亡/轨迹变化，不能用放慢游戏来通过 |
| C-05 对照冻结 | 共同输入管线、AB/BA顺序、双方配置及代码哈希 | 启动正式确认前全部归档；探索集与确认集不重用 |
| C-06 回归 | 全仓测试、几何/镜像已知xfail、合成专项 | 不删失败测试求绿；新增时钟/边界/延迟测试，不以测试数作为效果门 |
| C-07 真机效果 | 固定逻辑帧死亡、首次死亡、bomb，及配对区间 | 原主张保留：死亡相对下降≥20%，配对差95%上界<0；bomb均值不高于baseline。未达标如实fail/underpowered，不调阈值 |
| C-08 可复现 | 原始记录、冻结配置、运行命令、环境/游戏版本、结果生成脚本 | 另一agent可不依赖历史聊天重算表格。无配对RNG时明确统计限制，不宣称逐帧同世界 |

补充说明：假环境可以要求同初始状态、同输入得到完全相同轨迹；真机若无法固定 RNG，则不能将逐帧一致性设成不可能的硬条件，而应使用重复运行和分层统计。通过 `same_frame` 只能证明快照内一致，不能证明输入及时，也不能证明两臂同初始世界。

### 12.1 必须交付的产物

在本版本目录下新增以下产物；目前尚未生成，不要伪装已经存在：

- `configs/`：探索与正式配置，注明真实帧视界、beam、focus、bomb、位置先验和执行管线；
- `preregistration/`：正式协议、样本量/功效理由、配对方法、AB/BA计划、技术失败/边界事件规则；
- `data/`：两臂同schema逐决策原始trace、逐局摘要、随机顺序、事件、时序与曝光统计；
- `reports/`：P0时钟审计、单因素消融、死亡归因、最终结算；
- `evidence/`：代码/配置/数据SHA-256、测试日志、环境和命令记录；
- 正式工具及测试：不继续只写临时脚本；重算脚本输出表格，避免人工抄写漂移。

若只能完成P0，交付“实验有效性修复”即可，不得标记路线能力通过。若最终仍然没有改善，完整交付负结果也算完成本版调查，但**不算能力验收通过**。

### 12.2 推荐 agent 分工和串行依赖

- Agent A：时钟/输入/曝光管线及测试，拥有 P0；
- Agent B：独立审计原始数据和统计协议；可与A并行，但在C-01…C-05通过前不跑正式效果结论；
- Agent C：控制器与资源单因素消融，在A、B共同批准冻结协议后开始；
- Agent D：只读复核/重算，核验数据、代码、配置和结论边界。

避免多agent同时修改同一个执行循环；先约定文件所有权。遇到游戏可启动但未启动时先检查现有入口，不重复沿用“没有游戏进程所以无法实测”的旧判断。前台 SendInput 会影响用户输入，正式开跑前确认会话允许，结束/异常时释放按键。

## 13. 完成声明边界

v3.7.1 完成后，最多可以根据证据声明：

- “真机比较具备相同逻辑帧曝光和可审计输入时序”；
- “在指定 TH08、指定 frameskip、指定时间窗口和资源协议下，某个单因素改变的效果”；
- “某类死亡归因得到逐帧证据”。

只有在重新跑完公平真机确认集并满足冻结门槛后，才可以声明：

- 新方案改善指定真机主指标；
- 资源约束不退化；
- 局部路线能力迁移到整局生存。

在此之前，不能把 v3.7.0 的合成 A 门通过扩大为真机通过，也不能把 v3.7.0 的 +29% 点估计扩大为已证明的算法本体劣化。
