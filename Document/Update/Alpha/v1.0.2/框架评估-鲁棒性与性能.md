# 框架评估 · 鲁棒性与性能

- 评估对象：`touhou_rl/`（v1.0.2 交付 + 本轮新增的教师/蒸馏），共 21 个模块
- 评估时间：2026-10-18（在本轮「方向澄清：终极目标是纯视觉」之后重做）
- 评估口径：**不以"能不能跑通"为标准**，以「离终极目标（视觉、跨作品）有多远」和
  「在本机吞吐下能不能学出东西」为标准
- 一句话结论：**环境的工程层是稳的（B），但学习层是薄的（D），对视觉目标的适配是零（F）。
  当前框架不是"不够好"，而是"装错了目标"——它是一个很扎实的特权教师工厂，
  还不是一个视觉强化学习系统。**

---

## 1. 结构快照（先看清楚现在有什么）

```
 th08.exe (60 Hz, 单实例, 前台)
     │ 只读内存 + SendInput
     ├─ spec.py      地址/偏移/枚举（全部硬编码，来自 1.00d 逆向）
     ├─ memory.py    进程句柄（PROCESS_VM_READ）
     ├─ state.py     GameState + BulletField + read_boss_positions()
     ├─ winapi.py    SendInput / PostMessage / 抓帧 / 前台
     ├─ menu.py      菜单宏（标题→难度→机体→开打；回放菜单可按面）
     └─ session.py   进程生命周期（启动/重开/互斥体检测）
            │
            ├─ obs.py       self_feat[24] + bullets[64,6] + danger[16,8]
            ├─ reward.py    6 分量奖励
            └─ env.py       Th08Env（MultiDiscrete[9,2,2,2]，frameskip=2）

 学 习 端
     ├─ models.py        DanmakuPolicy（集合编码器 + 4 头 + value）
     │                   ScorePolicy（候选条件价值，本轮新增）
     ├─ dataset.py       分片格式 + 内存缓存
     ├─ bc.py            人类录像模仿
     ├─ collect_pilot.py 教师标注 / DAgger 采集（本轮新增）
     ├─ distill.py       特权价值蒸馏（本轮新增）
     ├─ ppo.py           KL 锚定 PPO（只冒烟过）
     └─ pilot.py         脚本化避险教师（本轮新增）

 部 署 端
     └─ play.py          一条命令：启动 → 菜单 → 开打 → 死亡重开
```

**关键事实：整条链路没有一处消费像素。** 全仓 `Conv2d` 数量为 0；`winapi.grab()` 只在截图里用。

## 2. 鲁棒性逐项评估

评级含义：A 稳、B 可用但有坑、C 有明确风险、D 需要修、F 结构性缺失。

### 2.1 运行稳定性：**B-**

| 事实 | 证据 | 风险 |
| --- | --- | --- |
| 长跑能顶住：单局 6,502 帧、单次采集 22 分钟、40 份回放逐份播放 | `eval/pilot-default-v2`、`datasets/dagger-v2`、`replay-check-all.json` | — |
| 冷启动与菜单宏有 flakiness | 首次 9 份回放检查里 3 份超时失败，单独重跑又通过；40 份里 17 份 Extra 被探针自身的 `stage=0` 缺陷判失败 | 会污染实验结论，且**误判方向正确性** |
| 外部残留进程会让下一轮启动失败 | 实测 `#32770` 对话框与 `another th08.exe`；本轮 3 次失败即此 | 批量实验需要外部看护 |
| `_wait_frames` 0.5 s 超时后不重试 | `env.py:_wait_frames` | 超时会让"动作实际保持帧数 ≠ frameskip"，**动作与状态错位**，噪声直接进标签与奖励 |

**最该修的是最后一条**：它不报错，只让数据悄悄变脏。修法很便宜——记录每步
`frames_advanced`，偏离 frameskip 时打标记或丢弃该步（`env.step` 已经算了这个数，只是没用于校验）。

### 2.2 可复现性：**C**

- 同一策略、同一局的重复评估**接近确定性**：`student-scorer` 两局都是 1,421 帧、79 擦弹
  （步数 704/711 略有差异）——说明"动作序列 → 结果"是确定的；
- 但**跨局不可复现**：`reset_mode` 走菜单/重启进程，进场时机、首帧对齐都在抖；
- 评估只跑 2–3 局。用现有方差（BC 1,286–1,392、随机 2,111–2,695）反推，
  **小于约 20% 的差异在 2 局下不可分辨**。本轮的对比都是 5 倍量级，所以结论不受影响；
  但下一阶段做"微调后涨了 5%"这种判断时，这个评估协议会撒谎；
- 修法：把评估改成**回放对齐**（同一初始帧、逐帧给定动作序列），或者把局数提到 ≥10 并报置信区间。

### 2.3 可移植性（换游戏 / 换版本）：**D**

| 项 | 现状 | 后果 |
| --- | --- | --- |
| 地址与偏移 | `spec.py` 全硬编码（`g_GameManager=0x0161C7A0` 等） | 换作品要重做全部逆向 |
| 版本校验 | **运行时没有任何校验** | 跑错版本时不会报错，只会读到荒谬数据 |
| 基址重定位 | 用 `module_base - IMAGE_BASE` 处理 | 只解决 ASLR，不解决版本 |

**这是最便宜、收益最高的一处修复**：启动时把 `g_Supervisor.exeSize/exeChecksum` 与期望值比对
（重建版的 `CalcExecutableChecksum` 就在 `main.cpp` 里），不匹配直接拒绝启动。
现在的状态是"读错了也不告诉你"，这在换版本/误启动时是最危险的失败模式。

### 2.4 特权观测的完整性：**C**

| 缺什么 | 证据 | 影响 |
| --- | --- | --- |
| **激光** | `spec.py` 有全部 laser 偏移、`state.read_lasers()` 已实现，但**全仓无一处调用** | 激光是中后期头号死因，教师与学生同时"瞎一半" |
| **敌人/Boss** | `state.read_boss_positions()` 已有，但只进 `env.info`，**没进观测契约** | 策略不知道往哪打 → 关卡永不推进 |
| 子弹行为 | 只存位置/速度，无加速度/曲线类型 | 20 帧线性外推对曲线的 `Ecl` 弹幕会失准 |
| 地图尺度 | `danger[16,8]`、最近 64 发 | 已实测"64 发够用"，但那是**教师**的上限，不是视觉学生的上限 |

### 2.5 学习信号的鲁棒性：**D**

1. **奖励函数写好了但几乎没用**：6 分量 + `progress` 的存在感只停留在代码里，
   PPO 至今只跑过 64 步冒烟。**整个系统目前没有组件在优化"活得更久/推进关卡"。**
2. **奖励尺度被事件支配**：`survive` 权重 0.01/步、死亡 −10、过关 +100。
   实测一局 BC 的 `episode_reward ≈ −19.4`（636 步）：其中存活项约 +6.4、三次死亡约 −30，
   其余四项（score/graze/resource/progress）加起来不到 1。
   也就是**奖励 ≈ 死亡计数 + 长度**，稠密项目前几乎没有实际引力。
   这不一定是错的，但必须知道：想让策略"会权衡得失"，现有权重是听不见的。
3. **KL 锚定的对象是坏先验**：`ppo.py` 默认从 BC 初始化并锚定到 BC（`kl_coef=0.5`）。
   而 BC 只有随机策略的 55%。**把自己钉死在一个比随机还差的先验上**，是当前配置的硬伤——
   应当锚定到「教师蒸馏版」或缩小 `kl_coef`，并让 KL 随训练衰减。
4. **标签并列未解决**：已量化（教师对已录标签的平均后悔值仅 0.16 px，但 argmax 只有 21.5% 一致）。
   价值蒸馏修掉了一半（安全区命中率 4.7%→93%），但**危险区后悔值仍然 2.34 px**。

### 2.6 面向视觉目标的适配度：**F**

这一项是结构性缺失，不是打分能概括的：

- 无图像编码器、无帧堆叠、无光流、无域随机化；
- 观测契约是数值向量，与画面无关，加视觉通道等于**重做一整套 observation contract**；
- `obs.py` 文档声称有 `profile.state_source` 开关——**代码里没有**，只有那行注释；
- 有利的一面：抓帧链路已实测可用（`winapi.grab()` 0.678 ms/帧，640×480），
  录像回放也能稳定 60 fps 供离线生成视觉数据。

## 3. 性能与吞吐评估

### 3.1 实测预算

| 量 | 实测 | 出处 |
| --- | --- | --- |
| 游戏逻辑帧率 | 60.0 fps（前台）/ 14.3 fps（失焦） | `probe-v102.json` |
| 决策速率 | 29.0–30.0 决策/s（frameskip=2） | 本轮全部 eval 报告 |
| 读状态 | 0.019 ms（标量）/ 0.537 ms（子弹池）/ 0.678 ms（抓帧） | `probe-v102.json` |
| 策略推理 | 6 ms/帧（425k 参数，GPU） | `runs/bc/bc-summary.json` |
| 教师规划 | 典型 ~1 ms/帧，最坏 14 ms（密弹） | 本轮离线标注 961 帧/s |
| BC 训练 | 0.4–0.9 s/epoch（4.6 万帧） | `runs/bc-dagger` |
| 集采吞吐 | 58–60 帧/s（实时回放） | `capture-report.json` |

决策预算：1/30 s = **33 ms/步**。现状占用约 0.5（读）+ 6（推理）= 6.5 ms，**余量很大**。

### 3.2 这台机器一天能产多少样本

```
1 小时墙钟 = 216,000 游戏帧 = 108,000 决策（frameskip=2）
1 天（按 10 小时有效）      ≈ 1,080,000 决策
```

对照常见量级：

| 路线 | 需要样本 | 本机耗时 | 结论 |
| --- | --- | --- | --- |
| 像素端到端 RL（弹幕类常见 1e7–1e8 帧） | 1e7–1e8 | **2–19 天**不间断 | **不可行**（这就是 v1.0.2 否决 R1 的依据，现在依然成立） |
| 特权状态从零 RL（1e7 决策量级） | 1e7 | **约 4 天不间断** | 勉强，但没有探索先验，不推荐 |
| PPO 微调（1e5–1e6 决策） | 1e6 | **9.3 小时** | 可行，是当前唯一现实的在线 RL 预算 |
| 监督蒸馏（每帧 1 样本，GPU） | 10 万帧 | **GPU 分钟级** | 极其便宜 → 应当把算力压在这里 |

**结论：本机的吞吐只够"监督学习 + 小幅在线微调"，不够"从零学"。**
这不是实现问题，是 60 fps 单实例的物理上限。任何需要 1e7 帧以上的方案在本机都不成立。

### 3.3 结构性浪费

- **GPU 几乎闲置**：BC 每 epoch 0.4–0.9 s，一次训练 24 epoch 不到 20 秒。样本量才是瓶颈，算力不是；
- **环境空闲率高**：每步 33 ms 里游戏占满，Python 在执行前后只有几毫秒活干；
- **重置开销**：单局 133 s 时重启约 10 s（7%）；短局（BC 的 23 s）时约 30%。

## 4. 面向"视觉 + 跨作品"目标，这套框架缺什么

| 缺口 | 现状 | 成本量级 |
| --- | --- | --- |
| 图像编码器 | 无 | 1 天（轻量 CNN/ViT，640×480 → 特征） |
| 帧历史/速度感知 | 无（单帧、无堆叠） | 半天（4 帧堆叠或两帧差分） |
| 视觉标签来源 | 只有特权状态 | 已有（`obs.encode` 就是标签生成器），**这是本框架最大的复用价值** |
| 跨作品输入层 | 无 | 1–2 天（框选 → 等比归一化到固定分辨率） |
| 视觉评估口径 | 无 | 半天（同状态下的分支预测误差 / 存活帧数） |

**最重要的一条判断**：因为从零视觉 RL 在本机不可行（§3.2），
唯一可行的视觉路线是 **"特权表征 → 视觉学生"的监督式蒸馏**：

```
画面 ──CNN──▶ 预测 self_feat / bullets / danger / (激光/敌人)
                     │
                     └─▶ 与特权真值比对（离线，GPU 分钟级，不需要游戏时间）
```

这条路把"学不会"变成"看得准不准"，可用**回归误差**直接度量，且完全离线。
它是本框架现有资产（逆向内存 + 录像 + 教师标注）**唯一能变现成视觉能力**的接口。

## 5. 修复优先级（按杠杆排序）

| 优先级 | 修什么 | 为什么排这里 | 预算 |
| --- | --- | --- | --- |
| 1 | **视觉表征学生**（画面 → 特权观测） | 唯一能把现有资产变成"视觉能力"的路径；可离线评估 | 3–5 天 |
| 2 | **运行时版本校验**（exeSize/exeChecksum） | 最便宜的防"静默读错"；换作品时更是必需 | 1 小时 |
| 3 | **激光 + 敌人/Boss 进特权观测** | 教师上限直接提高；学生标签也更完整 | 1–2 天 |
| 4 | **动作-状态对齐校验**（`frames_advanced != frameskip` 时标记/丢弃） | 消除一个不报错的噪声源 | 半天 |
| 5 | **接上奖励函数**（PPO 真跑 1e5–1e6）+ KL 锚定改到教师蒸馏版、随训练衰减 | 让"练"这条线真正开始 | 1–2 天 + 9 小时机时 |
| 6 | 评估协议升级（回放对齐或 ≥10 局 + 置信区间） | 否则后续"涨了 5%"的判断不可信 | 1 天 |

**不推荐做的事**：把观测从 64 发扩到 256 发、把网络加大、把 PPO 锚定在 BC 上跑更久。
三条都已被本轮的实验否定（见 `推进报告-教师与蒸馏.md` §10.4）。

## 6. 结论

**鲁棒性**：环境与数据层是这台机器上能做到的相当扎实的工程（长跑、断点、单测 39 条、证据齐全）；
风险集中在三处：**菜单/启动的时序 flakiness**、**版本无校验**、**动作-状态可能错位**。
前两处是"会误导结论"，第三处是"会污染数据"。

**性能**：作特权状态学习系统，**够用**（离线蒸馏便宜、在线微调有 9 小时预算）；
作视觉端到端学习系统，**差两到三个数量级**，永远不够。

**因此对"纯视觉"这个终极目标的判断是**：
本框架目前**不构成视觉系统**，但它是**恰好对的教师工厂**——
它提供了视觉路线最缺的东西：明确的、逐帧的、可量化的监督目标。
把框架改造成视觉系统不是"加一个 CNN"，而是**把当前的特权输出当作标签重新组织训练目标**。
