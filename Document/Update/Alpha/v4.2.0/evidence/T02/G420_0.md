## 1 在线腿实现（`touhou_rl/v420/replay_audit.py`，T02 新增）

T01 的 `audit_live_episode()` 占位已被真实实现替换；`audit-time --execute` 不再拒绝。

### 1.1 进程结构

```
audit-time --execute（父进程，无引擎）
  └─ 每个 seed × repeat / 每个 seed：
       1) prepare_private_data_dir()   cp -a score.dat/th08.cfg + 符号链接 th08.dat/thbgm.dat
       2) xvfb-run -a -s "-screen 0 1024x768x24" python -m touhou_rl.v420.replay_audit live-run …
          （子进程 1：真实引擎，role="env"，decision_frames=2，逐帧 readback）
       3) python -m touhou_rl.v420.replay_audit offline-forward …
          （子进程 2：只读落盘 obs，重算前向）
       4) 父进程只做 argv 构造、读回产物、比较
```

理由：引擎崩溃、子进程超时、缺产物都在父进程里是**可命名的失败**，不会被读成测量值；在线/离线前向的比较天然跨进程。

### 1.2 槽的构造（每 2 帧一个决策）

| 概念 | 实测口径 |
|---|---|
| 绝对逻辑帧 | 引擎 reply 的 `frame`（= 共享块 header 帧 = STATE 帧，见 §3） |
| 决策帧 `d` | 该槽第一次 `advance` 之前引擎处在的帧号（= `first.frame - 1`） |
| 提交区间 | `[d, d+2)`；`duration_frames = 2`（由 `second.frame - d` 实测，非常量） |
| 最近可见渲染帧 | `d-1` |
| 4 帧栈 | `d-4..d-1`（渲染帧号 + 每帧 play/hud 的 sha256） |
| 历史 | 最近 8 个**已执行**的 2 帧候选，帧号 `d-16, d-14, …, d-2` |
| 按键发送帧 / 生效帧 | `d` / `d+1`（生效偏移由 §3 的实测延迟决定，不硬编码） |
| 预卷 | 16 帧（= 8 决策历史 + 4 帧栈的最小值），第 0..15 帧不审计，只执行 |
| 策略 | `policy.mode="cycle"`：第 k 槽候选 = `k % 18`（确定性） |

## 3 引擎帧语义实测（在线腿的依据，不是假设）

脚本 `.tmp_v420_t02b/probe_frame_semantics.py`（原始 JSON `.tmp_v420_data/T02/probe/frame_semantics.json`）。做法：reset 后 8 帧 idle（候选 0 = 只开火不移动），再 6 帧「向东」（候选 3），逐帧记录 `reply.frame`、共享块 header 帧、STATE 帧、player_x 与 play 平面 sha。

| 实测 | 值 | 含义 |
|---|---|---|
| `reply.frame` vs header vs STATE | 三者恒等（1,2,3,…） | 逻辑帧号只有一个来源 |
| reset 后 header 帧 | 0 | 第 0 帧是起始态，像素是起始画面（被预卷丢弃） |
| 输入延迟（idle→东） | 发送于帧号 **8**，第一个位置变化的 reply 帧号 **10** | 首次受影响的**逻辑帧 = 9**（reply 帧 f 发布的是逻辑帧 f-1 的模拟）⇒ **引擎自带 +1 帧输入延迟** |
| 位置变化 | 192→196→200→204→208→212（6 帧脉冲恰好 5 次可见位移 + 第 6 次在下一 reply） | 与 +1 延迟一致 |
| 逐帧 play sha | 19 个（含 reset）互不相同 | 逐帧抓像确实在动，不是重复帧 |

因此：`key_send_frame = d`、`key_effective_frame = d + 1`——这不是约定，是**每次运行都重测一遍**的结论：`run.json.key_timing.measured.measured_latency_frames` 在 6 个 run 中全为 **1**，`effective_offset` 全为 **1**。若某次测得 0 或 2，`check_key_timing` 会当场违反（并进入 `unexplained_diffs`），不会静默沿用 1。

## 5 冻结模型的在线/离线前向一致性

- 加载方式：`tools/rl/v410_student_eval.py::load_v410_checkpoint()`（importlib 载入，**原文件未改**），设备 **cpu**，`checkpoint_sha256` 与配置里钉的 `3bc0ec44…` 逐字节校验。
- 在线：每个**被接受**的槽用该槽的 obs（play `(4,112,96)`、hud `(56,160)`、act_hist `(8,18)`，全 `uint8`，用 frozen obs-v3 的 `normalize_play/hud/action_history` 归一）做一次前向，记 18 维 logits + `logits_sha256`，并落盘三平面 `obs_*.npy`。
- 离线：**另一个进程**只读落盘 obs，重算前向，写 `logits_offline.npy` + `forward_offline.json`；父进程按 **float32 字节**逐槽比较。

| 项 | 值 |
|---|---|
| 在线前向槽数 | 6,000 |
| 离线前向槽数 | 6,000 |
| 逐比特相等 | **6,000 / 6,000**（`max_abs_diff = 0.0`，6 个 run 全 `bitwise_equal=true`） |
| 设备 | 两侧均 **cpu**；跨设备（cpu vs cuda）本次**未产生**，单列在 `aggregate.forward_cross_device`（`available=false`），**不计入一致数** |
| obs 形状/ dtype 校验 | play `(4,112,96)`、hud `(56,160)`、act_hist `(8,18)`，全 `uint8`（6 个 run 的 `run.json.obs_contract` 与 `forward_offline.json.inputs` 一致） |

### 5.1 一个必须记录的量化发现：批形状改变结果

第一次实现离线第二遍时用了「1,000 槽一个 batch」，结果是 **逐槽全部不等**（`bitwise_equal=false`）。实测原因不是权重或输入，而是 CPU 卷积的归约顺序：

| 第二遍批形状 | 与在线 logits 逐比特相等 | max abs diff |
|---|---|---|
| batch = 1（每槽一次） | **是** | **0.0** |
| batch = 1,000 | 否 | 3.43e-5 |

因此「同设备必须一致」这句话只有在**同一批形状**下才有意义；部署侧前向就是每决策一次（batch 1），所以离线第二遍固定为 batch = 1（`forward_offline.json.batch_size=1` 与 `batch_note` 记录了原因）。若把 batch=1000 的差异当成「一致」会掩盖真实差异，本任务没有那样做。

## 6 G420-0 判定

判定规则来自 [T01 契约规格](../../experiments/T01-contract-spec.md) §0/§2.2 与 [首轮执行任务单](../../首轮执行任务单.md) §3（T02）：门拆成三条腿，**逐条按实测数字判定，不放宽容忍度、不改分母**。机器可读镜像见 `time.json.g420_0`（`tools/rl/v420.py audit-time` 每次现算）。

### 6.1 L1 时间/动作索引一致 —— **fail**

要求：所有**已消费**样本每 2 帧一槽、每槽有自己观测与标签。

| 语料 | 槽 | 有自己 4 帧 play | 有自己 HUD | 有自己标签（verified） | 判定 | 证据 |
|---|---:|---|---|---|---|---|
| 旧 4 帧语料（v4.1.0 实际消费的 S1c） | 6,600 | **3,300** | **0**（槽 1 无 d+1 的 HUD 行） | **3,300**（槽 1 无 scores） | **fail** | §6.1.1 |
| T02c 重建 2 帧语料（seed 10/11/12） | 19,772 | **19,772** | **19,772** | 9,886 verified / 9,886 仅行为目标（`label_verified=false`） | **时间/动作索引 pass；verified 标签覆盖 49.94%** | §6.1.2 |
| 本在线腿 | 6,000 | 6,000 | 6,000（帧 d-1） | **0**（策略是 cycle，不是教师） | 观测 pass / 标签**不适用** | §4.3、§5 |

#### 6.1.1 旧语料（离线腿，T01 实现 + 本次复跑）

`rows 3,300 / slots_expected 6,600 / slots_with_own_obs 3,300 / slots_with_own_label 3,300 /
slots_action_only 3,300 / slots_hud_missing 3,300 / decision_frame_stride {4: 3299} /
history_stride_frames 4（跨度 32 帧 vs 部署 16 帧）/ history_contains_slot1_action 0（fail）/
mask_decode_mismatches {slot0: 0, slot1_lead: 0, slot1_tail: 137（全部 shoot_release、只清 SHOOT 位、全部落在块内第 4 帧）} /
hash_chain_breaks 0 / bomb_nonzero 0 / status=fail / unexplained_diffs=0`。

⇒ 槽位覆盖 50%、标签覆盖 50%、HUD 对槽 1 完全缺失、历史语义 32 帧 vs 16 帧。**旧语料在 L1 上 fail 是结构性的**：4 帧块写盘格式里就不存在槽 1 的观测与教师评分。

#### 6.1.2 重建语料（T02c，独立代理产出，本文件只引用）

[`REBUILD_2F.md`](../T02c/REBUILD_2F.md) §2/§3 实测：3 个旧 shard 的原样重放 → 逐帧抓像 → 每 4 帧块切成 2 个 2 帧槽，共写出 **19,772** 槽（期望 19,796，冷启动排除 24）；每槽有自己的 4 帧连续 `play`（`d-4..d-1`）、自己的 HUD（帧 `d-1`）、自己的已执行动作、8 条**真实交错**历史（帧 `d-16..d-2`）；逐槽 span/history/4 帧连续/key timing **0 违反**、`unexplained_diffs=0`；`hash_post` **9,898/9,898** 相等、逐帧 HASH 39,592 条；重建槽 0 观测与旧语料**逐字节相同**（`play` 9,886/9,886、`hud` 9,886/9,886）。

⇒ L1 的「时间/动作索引」四问（每槽自己的观测 / 自己的 HUD / 自己的已执行动作 / 8 条不含当前与未来）**在重建语料上全部成立**。
⇒ 但**标签**这一半仍只有 49.94% verified：槽 1 的 `label_source="executed_slot1"`、`label_verified=false`、**不带任何 scores 字段**——它是「教师执行过但未评分」的行为目标，不是 G420-0/G420-1 意义上的逐槽教师标签。

#### 6.1.3 判 fail 的理由（据实）

1. 「所有**已消费**样本」目前指的还是旧 4 帧语料（v4.1.0 的 S1c 训练源）；重建语料是 **T02c 新产物**，尚未成为训练输入，也仍缺 24 个冷启动槽与 50% 的 verified 标签。
2. 本在线腿证明「在线可以做到每槽自有观测 + 逐帧 HASH + 前向一致」，但它的策略是确定性轮换，**不产生标签**（0/6,000）——L1 的标签那一半只能由**逐槽教师查询**补齐。
3. 因此 L1 = **fail**：不是「数据脏」，而是「训练样本的 2 帧覆盖与逐槽标签还没落到被消费的那份语料上」。

### 6.2 L2 HASH 重建零未解释差异 —— **pass**

要求：重放同前缀 HASH 全等。

| 来源 | 规模 | 不一致 | 独立进程 |
|---|---:|---:|---|
| 本在线腿（两次重复互比） | 3 seed × 2,016 帧 = **6,048** | **0** | 是（每 run 一个引擎进程 + 私有 data 目录） |
| [PREFLIGHT_REPLAY](../PREFLIGHT/PREFLIGHT_REPLAY.md)（旧语料前缀重放，交叉验证） | 3 seed × 2 次 × 2,000 帧 = **12,000** | **0** | 是（6 次独立重放，`reset_hash` 6/6 与首行 `hash_pre` 相同） |
| [T02c](../T02c/REBUILD_2F.md)（重建语料逐边界复核） | `hash_post` **9,898/9,898** + 逐帧 39,592 | **0** | 是（写入进程与复核进程分离） |

三份独立测量都指向同一结论：**同一前缀在另一进程里重建出同一 HASH 链，没有任何未解释差异**。本腿不含「CPU/GPU 差异」之类的容忍度调整。

### 6.3 L3 部署输入边界 —— **pass**

要求：4 帧连续、历史 8×2 帧、无未来、形状/dtype 正确。

| 判据 | 实测 |
|---|---|
| 4 帧严格连续且 = `d-4..d-1` | `check_contiguous_render_frames` **6,000/6,000**，违反 0；每帧记 play/hud 两个 sha256 |
| 历史 8 条 × 2 帧 = 16 帧窗口 | `check_history_frames`（窗口 `d-16..d-2`）**6,000/6,000**，`check_history_length` 6,000/6,000 |
| 无未来 / 不含当前 | `check_no_future` 6,000/6,000；`check_history_excludes_current`（带帧号证明）6,000/6,000 |
| 决策跨度与真实持续帧数 | `check_decision_span(d, 2)` 6,000/6,000；`duration_frames` 由引擎帧号实测 = 2 |
| 按键发送/生效可区分且可解释 | `check_key_timing(d, d+1, d)` 6,000/6,000；延迟每 run 重测 = 1 帧（§3） |
| 形状/dtype | play `(4,112,96)`、hud `(56,160)`、act_hist `(8,18)`，全 `uint8`；`_assert_obs_shapes` 逐槽执行 |
| 冻结模型在该输入上前向一致 | 6,000/6,000 逐比特相等（cpu→cpu，§5） |
| 截断/无法归因 | 0 / 0；帧预算终止记为 `cap` 且 `still_running_when_cut=true`，**不当作通关** |

### 6.4 整门判定

> **G420-0 = not passed。**
>
> - L2（HASH 重建零未解释差异）：**pass**
> - L3（部署输入边界）：**pass**
> - L1（时间/动作索引一致）：**fail** —— 旧语料 50% 槽无观测/无 HUD/无标签，且历史 32 帧 vs 16 帧；重建语料在**时间/动作索引**上已 pass，但 verified 标签覆盖仍 **49.94%**，且重建语料尚未成为被消费的训练源。

一句话：**「2 帧节拍 + 每槽观测 + HASH 可重建 + 前向一致」已经被实测证明可做到（L2/L3 与 T02c 的 L1 索引半），但「所有已消费样本每槽都有自己的 verified 标签」还没做到，所以整门不通过。**

## 9 边界（必须与上面的「通过」一起读）

### 9.1 墙钟是争用条件下的观测值

运行期间 v4.1.0 采集进程仍在线（PID 1884178 一带，另有 T03/T02d 的引擎实例），WSL `load average ≈ 17–22`（20 vCPU）。表里的 39.7–45.2 s/2,000 帧、284.5 s 合计都**不是**吞吐承诺。

### 9.2 本在线腿不评价棋力

`policy.mode="cycle"` 是**审计策略**，不是棋手；6 个 run 都在 2,000 帧帧预算处被切断（`cap`），没有任何一局通关。这与 G420-4 无关，也不构成任何能力证据。

### 9.3 只有 3 个 train seed

在线腿覆盖 seed 1/2/3（train split 内、且在 S1c 语料的 train 划分里）。这不是「任意 seed 都成立」的归纳，只是「3 个 seed × 2 次重复上成立」。

### 9.4 跨设备前向差异未生成

两侧都是 cpu，所以「cpu vs cuda 是否一致」**没有测量**，`aggregate.forward_cross_device.available=false`。要回答它必须另跑一次 GPU 前向并按单列口径报告，不能并入 6,000 的一致数。

### 9.5 在线腿没有教师标签

`labels.slots_with_own_label = 0 / 6,000`，原因是策略不是教师。任何把这条读成「在线数据可直接训练」的结论都是错的。

### 9.6 段（episode）与死亡

6 个 run 都只有 1 段、都以 `cap` 结束，**没有**观测到 `first_death` / `game_over` / `stage_clear`；这三类终止目前仍只有代码级单测与 T02c 的 `stage_changed`（seed 12）证据，不在本在线腿的覆盖内。
