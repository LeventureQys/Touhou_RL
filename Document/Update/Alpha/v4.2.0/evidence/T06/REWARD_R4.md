# T06 / WP420-05 第四档：奖励版本 `v420-reward-r4/1`（只加一个威力项，检验"奖励看不见威力"）

对象：v4.2.0 `T06`（WP420-05）第四档。**本档是一次自立实验（self-standing new reward
version），不是 P4 授权的实验**（P4 的 `branch_taken` 仍是
`not_authorized_premise_false`，见 [`REWARD_R3.md`](REWARD_R3.md) §4）。

**这是"奖励看不见威力"这一机制的第一次直接检验。** r3 已经证明奖励能看见首死存活
（`corr(return, 首死帧)` 0.9485，[`REWARD_R3.md`](REWARD_R3.md) §2.2），但 r3 的七个
系数没有一项包含引擎的 `playerPower`：击杀敌人掉落的 P 点、满威力 128、威力被打掉
——**奖励表里完全没有这一维**。本档在 r3 之上**只加一个** `power_gain` 项（只计正的
增量，永不罚），其余七个系数逐字节不变，超参、预算、PPO、折扣、KL 锚、观测分辨率
一个不动。

> R4 uses engine-truth reward and termination, so it is a training-time privileged
> diagnostic: it is **NOT** strict pixel self-improvement (R1) and no result here may
> be reported as R1.

## 0 一句话结论

**奖励确实"看不见威力"，但这一条无法在本档被单独检验，因为观测也看不见威力。**
r4 在 r3 之上只加一个 `power_gain`（正的增量 × 3.906e-04，每局上限 0.0499968 =
`progress_total` 的 10%），50k/22 局跑完：训练内 `Δpower/局` 从对照臂的 **14.5909**
升到 **17.5455（+20.2%）**，但单侧 Welch t = 1.2056、置换检验 p = **0.1196** ⇒
**P1 fail**（方向对、不显著）；`diag_first_death` 20 dev 均值 **1650.05** 帧 >
门槛 1589.2 ⇒ **P2 hold**（+60.85 帧，+3.83%）；40 局 `stage_clear` = **0** ⇒
**P3 fail**。按跑前写死的四条分支，成立的是 **③：存活改善但（显著地）没学会捡 P，
另有路径**。

而**决定性限定**在 §2：引擎把威力画在屏幕 rows 136–151 / cols 488–616，而两处裁剪
（`play` x 32–416、`hud` rows 48–112）**一像素都不覆盖它**；正对照
（`power_band` 探针 R² = 0.99999999、MAE 0.0023）证明"有读数就能读到"，
平移零分布（hud 0.6638 vs 0.7246、play 0.8373 vs 0.8793）证明策略平面上的 R²
是时间/背景伪信号。**所以 r4 的威力项在原理上不可能被像素策略学到**——P1 的不显著
因此有两个不可分离的解释（项仍不够大 / 观测里根本没有这一维），本档**不做归因**。

## 1 r4 奖励表

### 1.1 逐项：单位、事件、计次规则

| 项 | r4 值 | 单位 | 触发事件 | 计次规则 | 版本 |
|---|---:|---|---|---|---|
| `stage_clear_bonus` | 1.0 | reward / 首面完成 | 引擎 stage index 前进 | 每局一次 | r2=r3=r4 |
| `death_penalty` | 0.25 | reward / 每次引擎死亡事件 | `globals.deaths` 增加 | 每次死亡一次 | r2=r3=r4 |
| `bomb_penalty` | 0.1 | reward / 每颗 bomb | `globals.bombsRemaining` 减少 | 每颗一次 | r2=r3=r4 |
| `progress_total` | 0.5 | reward / 走完首面的分数进度 | 分数增加，按 `progress_score_full` 归一 | 累积、硬上限 0.5 | r2=r3=r4 |
| `progress_score_full` | 2631430.0 | 分数点 | 真实首面过关的终局分数 | 归一化分母 | r2=r3=r4 |
| `survive_per_decision` | 1.2e-05 | reward / 决策（2 帧节拍） | 每一个决策（引擎活着） | 每决策一次，被断言约束 | r2:0 → r3/r4:ε |
| `first_life_per_decision` | 3.7890269778720825e-05 | reward / 决策（**第一条命**） | `globals.deaths == 0` 时的每个决策 | 每决策一次，每局硬上限 `first_life_cap` | r3=r4 |
| `first_life_cap` | 0.25 | reward（该集的封顶值） | 不直接发放，只封 `first_life` | 每局最多一次 | r3=r4 |
| **`power_gain`** | **3.906e-04** | **reward / 单位威力** | **`globals.playerPower` 在相邻两决策间增加** | **只在增量 > 0 时计；下降记入诊断、不罚** | **r4 新增** |
| **`power_max`** | **128.0** | **威力单位（TH08 满威力）** | 不直接发放；它是断言的标尺 | 载入时重算一次、fail-closed | **r4 新增** |

两个新项的计次规则，写进代码注释与 `REWARD_UNITS`：

1. **只计正的增量**：`Δpower > 0` 时付 `w_power × Δpower`；`Δpower < 0`（死亡掉威力）时
   付 0，并把 `-Δ` 记进 `power_lost`。因此该项对"掉威力"**没有任何梯度**，不会为了
   拿奖励去死；同时"死掉再捡回来"确实会再付一次（重新收集是真实收益），但一局满威力
   只值 **0.0499968**，而一次死亡是 **−0.25**——捡满一局威力才抵 1/5 次死亡，
   所以这不可能成为刷分路径，这是算术，不是承诺。
2. **开局威力是基线不是收益**：`prev_power` 由 `reset()` 时引擎的真实值初始化
   （`power_first` 只作诊断），第一决策的增量从它算起，不会把"开局 128"算成一次满威力。

  覆盖已审计的 `r3_seed0_50000f.pt`）、`dev_eval.checkpoint/tag/runs_dir`、说明文字，
  外加两个**判据块**（`power_criteria` / `power_readability`，跑前冻结，不参与训练）；
- **七个 r3 系数一个没动**：`stage_clear_bonus 1.0`、`death_penalty 0.25`、
  `bomb_penalty 0.1`、`progress_total 0.5`、`progress_score_full 2631430.0`、

### 1.3 有界断言（逐条复算）

配置里冻结、`resolve_reward()` 每次载入时**重算**并 fail-closed 的断言：

```
power_max = 128.0                      # TH08 满威力，见 §1.4
w_power × power_max ≤ 0.25 × progress_total
  = 3.906e-04 × 128 = 0.0499968  ≤  0.125        PASS（margin 0.0750032）
可采纳上限 0.125 / 128 = 9.765625e-04
本档取值   3.906e-04 = 0.05 / 128
```

**为什么界里没有 `T_max`（这是本档最重要的一处修正）**：`survive_per_decision` 是
**时间型**量——每一个决策都可能再赚一次，所以它的界乘 `T_max`（9943.5 决策）；
`power_gain` 是**库存型**量——一局最多把 128 点威力**收集一次**，不可能每个决策都涨满
128。把库存量乘以视界，等于把系数压小四个数量级：

```
（被作废的第一版）w_power × power_max × T_max ≤ 0.125
  ⇒ w_power ≤ 0.125 / (128 × 9943.5) = 9.821114295771107e-08
  ⇒ 一局上限 = 9e-08 × 128 = 1.152e-05  reward
     vs death_penalty 0.25      （小 21,701 倍）
     vs ε·T_max 0.119322        （小 10,358 倍）
     vs progress_total 0.5      （小 43,403 倍）
     vs stage_clear 1.0         （小 86,806 倍）
```

**这个量级不可能影响策略**，所以那一版的 P1 失败是无法解释的（"捡 P 没用"与"项太小"
不可区分）。**旧系数的 50k 运行（`pilot-r4-VOID-w9e-08.json`，sha 见
`reward_r4.json#voided_first_attempt`）作废，不作为任何判据的证据**，只在 §4.0 单列。

修正后的量级（本档实际使用）：

| 量 | 值 | 相对参照 |
|---|---:|---|
| 一项上限 `w_power × power_max` | **0.0499968** | — |
| 占 `progress_total` | **9.999%** | 十分之一 |
| 相对一次 `death_penalty` | **0.1999872** | 约 1/5 次死亡 |
| 相对一次过关（`stage_clear_bonus + progress_total` = 1.5） | 3.33% | 远低于任务目标 |
| 相对被作废的 1.152e-05 | **4,340 倍** | — |

非过关上界（`max_non_clear_return`，模块重算）：

```
0.5（progress_total） + 0.072006（ε/(1−γ) = 1.2e-05 × 6000.5）
+ 0.25（first_life_cap） + 0.0499968（power cap） = 0.8720028  < 1.5    PASS
```

若把 ε 按更保守的 `ε·T_max = 0.119322` 计（任务书的算式）：
`0.5 + 0.119322 + 0.25 + 0.0499968 = 0.9193188 < 1.5` **也 PASS**（两个口径都写出来）。

新增项没有推翻 r3 的三条既有约束（逐条不变）：

```
断言 ①  ε·T_max = 1.2e-05 × 9943.5 = 0.119322 ≤ 0.125          PASS
断言 ②  ε·T_max + first_life_cap = 0.369322 ≤ progress_total 0.5 PASS
断言 ③  δ × 6598 = 0.25 = first_life_cap（residual 0.0）        PASS
```

`power_max` 只能**上调**（更大的标尺 = 更紧的界），**永远不能下调**：
`resolve_reward()` 里 `power_max < POWER_MAX_TH08` 直接 fail-closed 拒绝。

### 1.4 `power_max = 128` 的来源（实测值，不是猜的）

引擎源码（`/root/Touhou_RL/third_party/th08-rl/src/`，与 `rl_v3` 二进制同源）：

| 证据 | 内容 |
|---|---|
| `Gui.cpp:1381-1387` | `if (g_GameManager.GetPower() < 128) AddFormatText(...,"%d", GetPower()); else AddFormatText(..., "MAX");` —— **HUD 从 128 起显示 "MAX"**，即 128 是游戏自己展示的量程上限 |
| `Gui.cpp:1348-1354` | 威力**条**的顶点是 `Float3(488 + GetPower(), 136/152)`，即条宽 = 威力值（像素），满威力 128 px |
| `ItemManager.cpp:53, 408, 423` | `if (GetPower() >= 0x80) ...`：威力 **≥128** 时 P 点不再加威力、改为加分 |
| `ItemManager.cpp:17` | `g_PowerUpThresholds = {8, 24, 48, 80, 128, 999}`：射击强化阈值的最后一个真实台阶是 128 |
| `GameManager.hpp:279-282` | `GetPower()` 返回 `globals->playerPower`，与线缆上的 `player_power`（`labels/state.py` f9 = `FloatBits(globals.playerPower)`）和 `PlayerSnapshot.power`（`touhou_rl/v400/gym/protocol.py:336`）是同一个值 |

配置可以**上调** `power_max`（更大的标尺 = 更紧的界，代码接受，但同时 `w_power` 必须
相应变小才过断言），**永远不能下调**：`resolve_reward()` 里
`power_max < POWER_MAX_TH08` 直接 fail-closed 拒绝（下调会放松界）。

### 1.5 引擎已经暴露威力（加项不缺数据）

`readings_of()` 现在从同一条 `STATE` 里读 `player_power`（f9），与 `lives_remaining`
（f7）、`bombs_remaining`（f8）同级；`PlayerSnapshot.power: float`
（`touhou_rl/v400/gym/protocol.py:336`）是同一个 `globals->playerPower`。r4 表遇到
`power=None` 时**拒绝**（fail-closed），不会把"没接上"当成 0。

## 2 观测可读性诊断（本实验的另一半）

**问题**：策略的输入是 `hud (1,56,160)` + `play (4,112,96)`。威力在这些像素里吗？
如果读不出来，那么无论 `w_power` 取多少，`power_gain` 都学不到——奖励改不了观测。

**样本**（真实引擎，不是构造数据）：`GameEnv2F` 在冻结的两帧节拍上跑 stage 0 / normal，
一个固定脚本控制器（先飞到道具回收线、再左右扫），**每 2 个决策采 1 帧**：
**900 个探针样本 / 12 个不同威力档 / 威力范围 0–23**，其中第 0 局的 **450 帧**保留整幅
640×480 的绿通道用于区域分析；并做 9 次**裁剪一致性**校验
（`encode_planes_v3(整幅)` 与策略真正拿到的 `play/hud` 逐字节相等，9/9 相等）——
即"我们分析的整幅帧"与"策略看到的平面"是同一帧。

**探针**（`rl.power_probe`）：带截距的线性最小二乘 + 最佳单像素，**样本外**评分
（奇偶对半、双向各一次、取两次测试分的均值），另报 40 次"打乱测试标签"的零分布。
`d > n` 时线性探针可以拟合任意标签，所以**样本内 R² 不作主张**，只报出来作对照。

| 平面 | 样本外 R²（均值 / 最好） | 样本外 MAE | 样本内 R² | 零分布 R² max |
|---|---:|---:|---:|---:|
| `hud (1,56,160)` | **0.6481 / 0.6638** | **2.283** | 0.9042 | −0.6658 |
| `play (4,112,96)` | **0.8303 / 0.8373** | **1.714** | 1.0000 | −0.6679 |
| `power_band`（**正对照**：屏幕 rows 128–150、cols 480–640 的绿通道） | **0.99999999** | **0.0023** | 1.0000 | −0.8734 |

正对照 `power_band` 就是 `labels/spec.py` `HUD_LAYOUT['power']['band'] = (480,128,640,150)`
——引擎**真的**在这个位置画威力（`Gui.cpp:1348-1387`），探针能把它读到 R²≈1、MAE 0.0023。
**所以探针不是坏的**；如果策略平面读不出，那是平面的问题。

**但是 0.6481 / 0.8303 都不是"读出了威力"**。两个混淆对照：

| 对照 | 内容 | 结果 |
|---|---|---|
| 时间基线 | `power ~ 1 + 局 + 决策序号`，同一奇偶切分 | R² **0.5944**（`corr(power, 决策序号) = 0.7545`） |
| 平移零分布 | 保留像素、把标签换成**同一局里平移 37/89/151/211/307 个决策后**的威力（同分布、同光滑度，但不是该帧的威力） | hud 真 0.6638 vs 平移最大 **0.7246**；play 真 0.8373 vs 平移最大 **0.8793** |

**两个策略平面的探针都打不过"被平移过的威力"**（`beats_shift_null = false`）：
它们学到的是"这一段游戏进行到哪了"（背景滚动 + 分数计数 + 机体固定位置），
不是这一帧的威力。这也是为什么时间基线只有 0.594 而平面能到 0.84：像素能构造出
**非线性的时间指示器**，而线性时间模型不能。

**区域几何**（任务要求的"威力变化 1 单位时 HUD 像素变化的区域位置"）：
右侧面板（x 480–640）没有滚动背景，所以目标对（`0 < Δpower ≤ 8`，15 对）在该面板里
**变亮的行列就是 HUD 本身**：逐对的变动行是 **56–72（分数行）** 与 **136–151（威力行）**，
变动列 **488–605**。这与引擎源码逐位吻合：威力条从 `(488,136)` 画到
`(488+GetPower, 152)`，数字文本也在 `(488,136)`（`Gui.cpp:1348-1387`）。

两处裁剪：

| 平面 | 屏幕区域 | 是否包含威力读数 |
|---|---|---|
| `play (4,112,96)` | x **32–416**, y 16–464（`PLAYFIELD_ORIGIN/SHAPE`，4×4 块均值） | **不包含**（威力在 x 488–616） |
| `hud (1,56,160)` | rows **48–72 / 80–96 / 96–112**，cols 480–640（`HUD_BANDS`） | **不包含**（威力在 rows 136–151） |

**结论（决定性限定）**：**观测里没有威力**。引擎把威力画在 rows 136–151 / cols 488–616，
两处裁剪一像素都不覆盖它；`power_band` 正对照证明"有读数就能读到 R²≈1"；
平移零分布证明策略平面上的 0.65/0.83 是时间/背景伪信号。
因此 r4 的 `power_gain` **在原理上无法被像素策略学到**——它可以改变回报的数值，
但策略无法把自己的动作与"威力涨了"关联起来。**这一条足够单独解释 P1 的任何失败**，
并且它不依赖于奖励表的任何数值。

**关于跑前写死的 R² < 0.5 门槛，必须如实说清**：门槛**没有触发**（0.6481 / 0.8303 都
≥ 0.5）。也就是说，按"R² < 0.5 ⇒ 读不出"这条**预先注册**的路线，本档**不能**宣布
"观测读不出威力"。本档宣布它靠的是另外三条：引擎源码的几何（§2 表格，与数据无关）、
`power_band` 正对照（R²≈1）、以及**在看到 R² 之后补做**的两个混淆对照（时间基线与
平移零分布）。后两条是**事后**加的，这一点在 `reward_r4.json` 里标为 `post_hoc`：
预先注册的 R² 门槛本身太弱——任何随时间单调变化的量，都能从任何随时间变化的平面上
被线性探针"读"出来。


## 3 三条判据（跑前写死）

写在 `configs/v420/rl-engine-r4-pilot.json#power_criteria`（**训练启动之前**写入，

四条分支（跑前写死）：

| 分支 | 条件 | 含义 |
|---|---|---|
| ① | P1 + P2 | 威力是存活瓶颈，继续加 |
| ② | 只 P1 | 威力涨了但存活未改善 ⇒ **威力不是瓶颈** |

## 6 判定与四条分支

### 6.1 P1 行为：`Δpower/局` r4 vs r3 同轮对照 → **fail**（方向对，不显著）

| 臂 | n | `Δpower/局` 均值 | sd | min–max |
|---|---:|---:|---:|---|
| **r4**（`power_gain = 3.906e-04`） | 22 | **17.5455** | 8.5118 | 4–35 |
| **r3 同轮对照**（同一张 r3 表，无威力项） | 22 | **14.5909** | 7.7254 | 3–28 |
| 差值 | — | **+2.9545（+20.2%）** | — | — |
| 被作废的第一版（`w_power = 9e-08`） | 23 | 13.8261 | 7.3833 | 4–30 |

- 单侧 Welch t = **1.2056**，正态近似 **p = 0.114**；
- 单侧置换检验（10,000 次重标号，seed 0）**p = 0.1196**；
- α = 0.05 ⇒ **两条检验都不拒绝 H0 ⇒ P1 fail**。

**方向是对的**（+20.2%，且被作废的那一版 13.83 与对照 14.59 几乎一样，说明"项太小 ⇒ 无差别"
确实成立，而修正后的 +2.95 不是噪声之外的量级）。但 n=22 的局间 sd 是 7.7–8.5，
**+2.95 只有 0.36 个 sd**，在 α=0.05 下不可区分于 0。这就是"单 seed、50k、22 局"的**统计
分辨率上限**，不是"效应不存在"的证明。

### 6.2 P1 的另一面：回报差几乎全是新项本身

| 量 | r4 | r3 对照 | 差 |
|---|---:|---:|---:|
| 每局回报均值 | −0.704563 | −0.711745 | **+0.007182** |
| 其中 `power` 项本身的贡献 | **+0.006853**（0.150772 / 22） | 0 | +0.006853 |
| 剩余（行为变化 + 其他项的再分配） | — | — | **+0.000329（占 4.6%）** |

即：r4 与 r3 对照之间 +0.007182 的回报差里，**96.4% 是新加的威力项付给自己的钱**，
只有 0.000329 来自行为差异。这与 P1 的 +2.95 威力/局（p≈0.11）一致：
**项确实在付钱，但策略几乎没动。**

### 6.3 P2 存活：**hold**（但只比门槛高 0.85 个标准误）

| 口径 | n | 均值 | 门槛（跑前写死） | 偏离 | 判定 |
|---|---:|---:|---:|---:|---|
| `diag_first_death` | 20 | **1650.05** | **1589.2** | **+60.85 帧（+3.83%）** | **hold** |

同一支仪器上的参照：R3 重测 **1597.9**（+52.15）、R0 **1650.4**（−0.35）、
D3 1707.5（−57.45）、D2 1757.5（−107.45）。

**必须一起读的三件事**（否则这 +60.85 会被过度解释）：

1. **20 局均值的标准误是 320.40/√20 = 71.64 帧**，+60.85 只有 **0.85 SE**。
   也就是说"比 1589.2 高"这件事，在 n=20 上没有把它与"和 r3 一样"区分开。
2. **门槛 1589.2 来自另一支仪器、另一次运行**（见 §3）；同一支仪器上 r3 是 1597.9，
   所以同仪器口径的增量是 +52.15（0.73 SE）。两个口径都写出来。
3. **r3 的原始 payload 本身不可逐局复现**（§4.2：同一份 r3 表在同机重跑，22 局的帧数
   从 1867 变成 2523 这种量级的差异），所以"r3 = 1589.2"这个参照数自带运行间方差，
   而本档**没有**给 r3 对照臂跑 dev（预算与时间都没允许再跑 40 局）。

### 6.4 P3 能力：**fail**

40 局（2 口径 × 20 seed）`stage_clear` = **0**；最深一局 **3863 帧**（s1n, seed 1009），
是过关所需 13,195 帧的 **29.3%**；40 局里没有一局超过 4,000 帧。
Wilson 95%（0/20）= [0, 0.1611]。与 T08 的 160 局 0 过关一起看：**本仪器上还没有任何
一臂过过关**，所以 P3 的失败不是 r4 特有的，而是整条路线的现状。

### 6.5 四条分支：成立的是 **③**

| 判据 | 判定 |
|---|---|
| P1 行为（`Δpower/局` 显著 > r3） | **fail**（+2.9545，p 0.114 / 0.1196） |
| P2 存活（diag > 1589.2） | **hold**（1650.05） |
| P3 能力（≥1 过关） | **fail**（0/40） |

⇒ 按跑前写死的规则：**分支 ③ —— 存活改善但没学会捡 P，另有路径**。

**这条分支要带三个限定，否则会被误读**：

1. **P1 是"方向对但不显著"**，不是"完全没变化"：+20.2% 的点估计与
   "修正后的项确实在付钱"（回报差 +0.007182 里 96.4% 是新项自己付的）一致，
   只是 22 局分辨不出 2.95 点威力。
2. **P2 的 +60.85 帧只有 0.85 SE**，且参照来自另一支仪器/另一次运行（§6.3）。
   把它当成"r4 真的把存活推高了 3.83%"是过度解释；把它当成"没有证据表明 r4 把存活
   压低了"是安全的。
3. **分支 ③ 的"另有路径"不能被解释成"策略用别的方式学会了存活"**：§2 已经证明
   观测里没有威力这一维，所以 r4 的威力项**不可能**通过"学会捡 P"起作用；能起作用的
   路径只能是"新项改变了回报的数值分布 ⇒ 影响了 critic/advantage ⇒ 间接影响了别的动作"，
   而这条路本档**没有**测量（要做需要一条 `power_gain` 同量级但**打乱符号/随机化**的
   对照臂）。

**一句话**：本档得到的是"**加了威力项之后，首死存活这条线没有变差，也没有显著变好**"，
以及"**观测里根本没有威力**"。它**没有**回答"奖励看不见威力是否是 RL 早死的机制"——
要回答那个问题，必须先让观测能看见威力（或把威力喂成特权输入），再加这一项。


## 7 这不是 R1

1. 奖励用**引擎真值**（死亡、分数、炸弹、stage、**威力**），训练时可见、部署时不可见：
   `reward.source = engine_truth`，`privilege = training_engine_truth_not_in_observation`。
   §2 正是这句话的量化版本——**引擎知道威力，观测不知道**。
2. 策略输入只有像素（`obs-v3`）+ 自身动作历史；`STATE` 只进奖励与裁判，不进网络。
3. 没有教师动作、没有 BC 蒸馏、没有用特权信息做输入；本档不改观测、不改协议。
4. 因此本档的任何结果**不得**说成 R1 自提升，也不得说成"像素策略学会了捡 P"。

## 8 边界（不能主张什么）

1. **不能说"威力是/不是早死瓶颈"**：P1 不显著、P2 只高 0.85 SE，而 §2 证明观测里
   没有威力这一维 ⇒ 两个解释不可分离。本档只报"没有变差、也没有显著变好"。
2. **不能说 r4 优于 r3 / 优于 R0**：diag 1650.05 对 R3 1597.9 是 +3.26%，对 R0
   1650.4 是 −0.02%；两者都在 n=20 的噪声带里，且都不是同轮同仪器对照。
3. **不能说"观测读不出威力"是靠预先注册的 R² 门槛成立的**：门槛（R²<0.5）**没有触发**。
   结论靠的是引擎源码几何 + `power_band` 正对照 + **事后**补做的平移零分布，三者都写在
   §2，`reward_r4.json` 里标 `post_hoc`。
4. **不能把作废的第一版混进任何统计**：`pilot-r4-VOID-w9e-08.json` 的 13.826 与修正后
   17.545 不是同一个实验，前者只作为"界写错会怎样"的记录（§4.0）。
5. **不能外推到 1M / 3 seed**：单 seed（0）、50k、49 更新、22 局。
6. **不能给 20 局均值置信区间**：报告里出现 sd 与 SE 只是用来说明"这个差有多小"，
   不是区间估计；0/20 的 Wilson 区间 [0, 0.1611] 是描述性的。
7. **不能把 FPS / 墙钟当吞吐能力**：r4 50k 的 52.36 fps 与对照臂的 50.81 fps 是在
   load 3.8–5.8 下测的，同机另有语料扩容任务在跑（本档没干扰它、没杀任何进程）。
8. **不能说本档的 dev 数字已经有同轮 r3 对照**：本档没给 r3 对照臂跑 dev，
   P2 的参照是别人的运行（§6.3 第 3 条）。
