### 1.1 接线缺陷已修：episode 真的跑完并进了 PPO

上一轮 `episode 数 = 0`：`collect_rollout` 每次 rollout 都 `env.reset()`，50k 帧被切成
49 段 1,024 帧，没有任何一局跑完、没有任何终局奖励进入 PPO。本轮
`run_pilot` 把上一段的现场（当前观测、episode 编号、本局累计回报）通过 `resume=` 传回去，
于是连续 rollout 接着跑同一局：

| 量 | 上一轮（错误接线） | 本轮（`resume=`） |
|---|---:|---:|
| episode 数 | 0 | **24** |
| `terminated_transitions` | 0 | **24** |
| `truncated_transitions` | 0 | 0 |
| episode 帧数 | n/a | 1415 – 2950 |
| episode 回报 | n/a | -0.7443 … -0.7492 |
| 终局奖励合计 | `{}` | `death -18.0`（72 次死亡）、`progress 0.0614`、`stage_clear 0.0` |
| 引擎重启次数 | 50（每 rollout 一次） | 24（每 episode 一次） |

24 局全部以 `game_over` 结束（每局 3 次死亡 = 72 次，与 `death -18.0`
一致），**没有任何一局过关**——50k 帧、49 次更新不足以学会过面。
终局奖励现在真的在回路里：24 个 terminated transition 各带一次终局罚分。

> **一个记录字段的已知缺陷（不影响训练数学）**：`rl_pilot2.json` 的
> `episode_records[].seed` 全为 0。原因是 `collect_rollout` 从"重建后的
> `StepResult.info`"取 seed，而重建的 StepResult 只带 `env.info()`（其中没有 seed 字段）；
> 真正传给 `env.reset()` 的 seed 由纯函数 `_episode_seed(train_seeds, episode_index)`
> 决定，24 局按序循环 3000→3004（`train_seeds = [3000,3001,3002,3003,3004]`，
> 全部落在 train 池内）。该记录缺陷已修（episode 记录与 `carry` 现在都带真实 seed，
> 单测 `test_resume_keeps_one_episode_running_so_resets_are_fewer_than_rollouts`
> 断言 `episodes[0]["seed"] == 3000`），但本档的 50k 已跑完，不改写已测得的
> payload，只在此如实登记。

另外修掉一个只在边界出现的隐患：若某个终止决策刚好落在 rollout 的最后一步，
旧实现会把"已结束的 episode"的现场交给下一段 rollout（下一步会在死掉的引擎上 step）。
现在 `collect_rollout` 先 `reset` 再 `break`，carry 永远是活的 episode。

**怎么读这个负结果（重要）**：

1. 接线修好之后，R2 的 diag 均值从上一轮的 758.2 变成 **889.35**、s1n 从 1857.1 变成
   **1906.4**：**略有回升，但仍然明显短于 R0**，20/20 配对为负。
2. 所以**不能**再把它读成"上一轮接线错误造成的假象"。真实结论是：**50,000 帧 / 49 次更新
   不足以改进，而这个预算下的更新方向把 BC 先验带偏了**（权重离 A0 的最大偏移约 1.2e-2，
   而 A0 的 logits range 是 55.9，argmax 在大量状态上会翻转）。
3. 这**不是**"RL 让策略变差"的证据：两臂在两口径下都是 0/20 过关，存活长度差异只反映
   "在 0 过关的前提下谁死得更早"，而 50k 帧连"学会活得更久"的门槛都没到。
4. 它**是**一个明确的可执行信息：1M 档之前必须先提高每帧的有效学习信号
   （更长的 rollout / 更小的温度差 / 更大的预算），而不是期待 50k 帧出能力。

## 5 这一档能主张什么

1. **折扣修订后审计 17/17 全 pass**（[`RL_AUDIT.md`](RL_AUDIT.md)），终局过关奖励在
   220 s 任务长度上的可见性从 6.5e-04 提高到 0.333。
2. **接线修复在真实引擎上闭环**：24 局跑完、24 次终局奖励进入 PPO、49 次 PPO 更新、
   新 checkpoint 能被**冻结 evaluator** 读回并**逐比特复现**（logits 最大差 0）。
3. **统计健康**：KL、熵、clip、value loss、梯度范数都有实测值且无 nan/inf，账目自洽。
4. **不能**主张能力：50k 帧、1 seed、0 次过关；R0 = 0/20、R2 = 0/20（两种口径相同），
   且配对存活长度仍然为负。
5. **也不能**把这条真跑当作"R2 有效/无效"的判据：它证明的是**回路、折扣与统计**，
   不是 RL 能不能改善。能力问题属于 1M 档（3 seed）。

2. 每 seed 完成后跑 20 dev 局两种口径，与 R0 冻结记录配对；
3. 至少 2/3 run 的配对差为正，且至少 1 个 run 出现过面（否则 G420-R 仍 not_passed）；
4. 在此之前先确认 50k→1M 的曲线形状：本档 50k 的 KL/熵/actor 偏移都没有发散迹象，
   但**没有**任何"越训越好"的证据，所以第 1 步应带一个中间检查点（如 200k）以免 1M 全废。

## 7 边界

- 50k 帧的结论**不能**写成 1M 档结论；1 个 seed **不能**当 3 个 seed。
- R2 的成功/失败都不是"RL 不可行/可行"的结论，也不是 R1 的证据。
- 训练前后都是 0/20 过关：这是**有效负结果**，不是测量失败。
- 评估侧的 `--data-dir` 是那份私有副本（引擎会重写其中的 `score.dat`），
  只读的 `/root/v400-data` 与本仓库证据树都在 fail-closed 拒绝名单里
  （[`RL_AUDIT.md`](RL_AUDIT.md) §5.2）。
