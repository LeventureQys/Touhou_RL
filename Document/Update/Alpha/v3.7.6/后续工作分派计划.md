## 2. WP-A：合同与动作对齐审查（最高优先级，只读）

### 目的

确认「画面观测 ↔ 回放按键 ↔ 动作生效 ↔ 实际位移」这条链在语义上成立，而不是只看测试是否通过。这是整个 BC 路线的承重假设：一旦对齐错误，标签会把「人类下一步按了什么」错配到「本帧看到的画面」。

### 输入

- [F2 标签契约](<../../../../touhou_rl/f2_labels.py>)
- [F2 数据构建与审计](<../../../../touhou_rl/f2_dataset.py>)
- [回放解码与对齐](<../../../../touhou_rl/v380/replay.py>)
- [序列训练器](<../../../../touhou_rl/tactical_sequence_train.py>)
- [训练修订](<训练修订.md>)
- 实采字段样例：`third_party/th08/build/rl/exact/v376-f2-train-20261104-r1/`（`frame-proof.json`、`proofs.jsonl`、`audit-state.jsonl`）

### 必须回答的问题

1. 当前观测帧对应的是回放输入的**前**一帧还是**后**一帧？证据在哪一行代码、哪一个字段？
2. `stageFrames → replay record index → candidate` 的偏移是否正确？与 `logicFrame`、`hold` 的关系是什么？
3. `previous_actual_candidate` / `effective_frame` / `hold` 三者的语义是否一致？是否存在「记录了按键但动作尚未生效」却当作已执行历史的情况？
4. 回放历史是否给了模型部署时拿不到的信息（例如提前一帧的未来输入）？
5. 人工像素标注是否被内存坐标反向污染（即用特权状态生成「独立」像素标注）？
6. 弹体池槽（`slot`）复用时，是否可能把不同弹体拼成同一条轨迹？两次「瞄准发射」的判据是否成立（发射点、首个可见位置、瞄准时刻三者的区分）？
7. test split 是否真的只在审计阶段被读取，未进入缓存、训练或选模？
8. 当前 BC 路线是否被任何文档或报告写成原 G4 通过？

### 交付

- 按严重性排序的审查报告（P0/P1/P2），每项带**精确文件行号**与**最小复现**；
- 一张明确的「观测—按键—生效—位移」时间线；
- 结论三选一：`允许继续` / `必须先修（列清单）` / `路线需重设计`。

### 验收与停止

- **不得**以「现有测试通过」作为对齐正确的证据；必须给出源码语义或可验证的轨迹对应。
- 发现 P0（标签错配、未来信息泄漏、test 泄漏）时立即停止后续工作包，先修再走。

## 3. WP-B：真实 F2 事件视觉复核

### 目的

从已有候选中确认哪些片段**真的包含可见的瞄准弹流**。F2 是瞄准弹流，没有固有缺口；不能用「自机移动频繁」「内存里有弹」「采集成功」代替可见性证据。

### 输入（已生成，直接打开）

- [训练来源 43 个未审候选](<evidence/f2-review-20261104-r3/train/index.html>)
- [验证来源 45 个未审候选](<evidence/f2-review-20261104-r3/validation/index.html>)
- [测试来源 45 个未审候选](<evidence/f2-review-20261104-r3/test/index.html>)
- 操作细则：[真实 F2 复核交接](<真实F2复核交接.md>)
- 候选清单与排除记录：同目录 `candidates.json`、`audit.json`、`review-template.json`、`asset-index.json`

> 已知数据事实：train 的 `stageFrame 5451` 重复 55 行、validation 的 `5706` 重复 94 行（logicFrame 仍前进），**整组歧义帧已被排除**，部分候选因此被拒（train 拒 7、validation 拒 5、test 拒 5）。此排除不得回退，也不得用 first/last 猜对齐。

### 建议分两轮，不要一次标完 133 个候选

**第一轮：事件筛选（只判取舍，不做逐帧标注）**

每个候选给出：接受 / 拒绝 / 无法判断；可见线索；发射体与弹流时间范围；是否含**两次可确认的瞄准发射**；遮挡、混合弹幕、池槽重用等风险；拒绝理由。

**第二轮：少量可靠事件精标**

只标足以支撑真实短测的一批事件：

- 独立像素标注的自机位置与弹体轨迹（`image_px`，640×480 原图，游戏区原点 (32,16)）；
- 每个样本绑定具体 `frame` 与 image SHA；
- 同一发射体的 ≥2 次瞄准证据；
- 显式容差与 reviewer 身份；
- `context_only`、unknown、bomb、非 18 路按键一律不给动作监督。

### 交付

- 候选筛选表（覆盖全部联系表候选，不得跳号）；
- 合格事件的 review JSON（可直接进入正式 plan）；
- 拒绝与不确定事件清单及理由；
- 每来源有效事件数、有效动作行数、动作分布、`context_only` 比例；
- 若不满足合同，明确写出缺什么。

### 停止条件

现有片段没有足够可确认 F2 事件时，**报告覆盖不足并申请定向补采**，不得放宽 F2 定义凑数。

## 4. WP-C：正式数据计划与最小训练协议冻结

### 目的

把「候选」变成一份真正能交给 builder 的冻结 plan，并预先定义训练与评估判据，避免看到结果后再挑指标。

### 必须冻结的内容

1. 每个事件的来源、起止帧、选取理由、review SHA。
2. train/validation/test 分配（**先分 replay/template/episode/derived 组，再切窗口**）。
3. 关联关系：同 replay、同模板、镜像/派生来源必须同组；「同一弹幕模板的不同回放」不能未经讨论就称为模板泛化。
4. unknown / bomb / 不支持的 18 路动作 / 缺帧 / 歧义 stage 帧的处理规则。
5. 坐标目标不适用：`gap_center`、`relative_dx`、`deadline`、`route` 必须 `null` 且 mask `false`；只有示范动作监督。
6. 最小数据量的统计单位：**独立来源组、独立事件、有效监督行、动作变化行**，不是累计截图数。
7. 长训练前的诊断协议：固定小样本拟合、validation 选模、test 封存、失败分类与停止条件。

### 必须补的判据（BC 特有陷阱）

BC 很容易靠「保持上一动作」拿到漂亮总体准确率，因此必须在看结果前冻结：

- 总体准确率；
- 类别平衡准确率；
- **动作变化行**准确率（留出集里真正改变动作的帧）；
- 逐事件宏平均（避免一个长事件掩盖失败）；
- 「保持上一动作」基线；
- 多数类基线；
- 像素消融诊断（置零像素后是否仍然准确，用于识别捷径）。

### 交付

- 正式 `v376-f2-bc-plan/1` 计划（来源引用相对仓库根，禁止路径逃逸）；
- 版本化训练配置；
- 事件与 split 清单；
- 数据覆盖报告（各来源、各事件、各动作分布）；
- 训练/选模/评估冻结协议，注明「新增方案」而非原预注册。

### 验收

计划结构检查通过；三个 split 独立且无泄漏；判据在看结果前已冻结；数据量满足协议或明确写出不足。

## 5. WP-D：真实数据集构建与对抗审计

### 目的

在**真实**数据上完成构建与内容审计。工程夹具跑通不算。

### 命令链（占位路径在复核后替换）


### 必须检查

- 上游 exact proof、采集配置、replay 身份三者一致；
- 原始 PNG 与标签证据逐帧绑定；
- 回放动作重新解码，不读 `inputReadback`；
- stage 帧歧义组整组排除；
- 当前与过去图像在因果范围内；
- 输入 / 标签 / 审计资产物理隔离（含硬链接别名）；
- 逐帧像素内容跨 split 去重；
- replay / template / episode / derived 分组无泄漏；
- unknown 零监督；
- train/validation 每个事件都有可评分窗口（burn-in 16 + window 32）。

### 交付

- 正式 manifest 与 SHA；
- 审计 JSON；
- 完整命令、退出码、日志；
- 排除样本与 unknown 统计；
- 失败与修复记录（失败的构建目录保留，不覆盖）；
- 明确结论：`real BC dataset admitted` / `rejected`。

### 停止条件

任何身份、像素、分组、因果检查失败即停，保留失败资产。**不得**通过放宽审计、改 schema 或静默丢弃事件来让审计通过。

## 6. WP-E：真实数据缓存与一次更新短测

### 目的

证明真实数据确实能驱动优化，而不是只在夹具上能跑。

### 顺序

1. 核对 baseline checkpoint 身份（当前训练骨干 `third_party/th08/build/rl/runs/v104-v3-E5-s7/policy.pt`，SHA 记录在 [baseline-20261104-r3](<reports/baseline-20261104-r3/baseline.json>)）与预处理版本。
2. 构建 train/validation 特征缓存，**不加载 test tensor**。
3. 骨干参数与 buffers 前后摘要一致。
4. CPU 最小 batch 完成 forward/backward。
5. GPU 一次更新或严格有界短测。
6. 检查：参数确实更新；unknown 不产生更新；无 NaN；维度/标签正确；checkpoint 可读回；报告写明 BC、研究专用、非部署。

### 命令（占位）

```powershell
python -B -m touhou_rl.tactical_feature_cache `
  --manifest <new-dataset-dir>/manifest.json `
  --baseline third_party/th08/build/rl/runs/v104-v3-E5-s7/policy.pt `
  --out <new-cache-dir> --device cuda --batch-size 16

python -B -m touhou_rl.tactical_sequence_train `
  --manifest <new-dataset-dir>/manifest.json `
  --cache-index <new-cache-dir>/index.json `
  --baseline third_party/th08/build/rl/runs/v104-v3-E5-s7/policy.pt `
  --out <new-train-dir> --arm N1 --epochs 1 --max-updates 1 --seed 7 --device cuda
```

> 注意：缓存会绑定源码哈希。**先锁定源码再构建缓存**；若期间有代码改动，缓存会以 `cache compute protocol/source mismatch` 拒绝，这是保护而非 bug（本轮已实际发生过一次，记录在 README）。

### 交付

- cache manifest/index 与 SHA；
- resolved 训练配置；
- 一次更新日志；
- 参数更新与骨干不变证据；
- checkpoint 读回结果；
- 明确结论：`可以按冻结配置安排正式训练` / `仍需修复（列清单）`。

### 停止条件

`updates=0`、参数未变、出现 NaN、加载了 test、或骨干被改动 → 判定失败，不得用「loss 下降了」代替。

## 7. WP-F：正式训练前独立放行审查

### 目的

由**未参与实现与调参**的执行者只读检查整条证据链，防止「自己实现、自己验收」。

### 必须回答

1. 训练目标是什么？是否被误写成原关系目标 G4？
2. 数据为什么可以称为 F2？依据是逐帧证据还是文本声明？
3. 标签证明的是「人类做了什么」还是「应该做什么」？
4. 观测与动作是否因果对齐？
5. 三组独立性能支持哪种泛化结论（同关卡？跨关卡？跨作品？）
6. 是否有人看过 test 后改过阈值、样本量或排除规则？
7. 是否存在「保持上一动作」捷径？
8. 正式训练的预算、选模与停止条件是否已冻结？
9. 是否有会改变结果解释的未解决问题？

### 交付

一张放行表：

| 检查项 | 结论 | 证据路径/SHA | 未解决风险 |
|---|---|---|---|

最终结论只能三选一：**允许按指定配置训练** / **允许有限诊断，不允许正式训练** / **拒绝，先修指定问题**。
