## 0. 三十秒版本

这是一个「**用像素玩东方 Project（当前 TH08）**」的视觉策略项目。

- **训练期**可以读游戏内存，但它只作为**特权教师**（算出 18 个候选动作的安全值）；
- **部署期**只吃三块裁图像素，不看内存、不看真值；
- 当前学生是**蒸馏**出来的（不是强化学习）：学的是「教师会怎么给 18 个候选打分」；
- 感知已经很强（自机位置误差 **2.4 px**，危险图逐帧相关 **0.82**），
  但**闭环还打不过随机**（真机 3 局均值 **1627.7 帧**，随机约 2419.7）；
- 已定位原因：**动作分布与人类严重不符 + 逐帧 argmax 有 50.7% 的翻转**（详见 §7.1）。

下一个人的核心任务不是继续加大蒸馏，而是让策略**在闭环里像个会玩的东西**（时序一致性 / 人类动作监督 / 更强的目标），
细节见 §7.3。

## 1. 原因与目标

### 1.1 为什么"只用视觉"

东方系列的信息全部在屏幕上：自机、子弹、道具都在场地内，资源在 HUD 上。
用内存可以做到近乎完美，但那条路**不可迁移**——换一作、换个版本、换个平台就废了。
所以本项目的定位是：

```
内存特权状态 ──(教师 / 标注 / 参照系)──▶ 视觉学生 ──(部署)──▶ 只接收屏慕像素
```

读内存的代码（`state.py` / `memory.py` / `obs.py`）**只是标注器**，它的输出永远不许进入部署策略的输入。

### 1.2 本轮（v1.0.4）的两个具体目标

| 目标 | 判据 | 为什么挑这两个 |
| --- | --- | --- |
| **A-01 位置精度** | 全验证集 7241 帧，位置误差 `< 10 px`，且 danger 逐帧相关中位 `> 0.8` | 位置是"能不能看清"的地基；v1.0.3 卡在 12.8 px，且 danger 只有 0.64 |
| **A-02 策略排序** | 0–15 px 危险桶里，教师后悔值 `< 1.5 px`（并列报告 top3） | 学生把 18 个候选的**排序**学对，而不是把值回归对 |

配套还有 A-03（跨回放不退化 ≤1.25×）、A-04（真机 ≥3 局、`frames_mean > 4000`、`hit_step_cap=0`）、
A-05（单测 ≥178 且 0 failed）、A-06（三个工程缺陷有证据）。

### 1.3 本轮实测结果（结论）

| 项 | 结果 | 数字 |
| --- | --- | --- |
| A-01 | **pass** | 位置 **2.4066 px**、danger 逐帧中位 **0.8166**（同一轮，全量 7241） |
| A-02 | **pass** | 0–15 桶 **1.271 px**（1076 帧）、top3 **0.6403** |
| A-03 | **fail** | 跨回放比 **1.2675 > 1.25**（超 1.40%） |
| A-04 | **fail** | 真机 3 局 1446/1800/1637 帧，**均值 1627.7 < 4000** |
| A-05 | pass | 702 passed / 0 failed |
| A-06 | pass | D9/D10/D11 各有实测证据 |

**整版未通过**，且 A-04 是"离线达标但闭环不行"——这正是本项目现在最要命的地方。

### 1.4 明确不做的事（别浪费时间）

- 不再新增回放、不做全量采集（跨回放实验已证明多一份回放只值 +17% 误差）。
- 不提高场地输入分辨率（224×192 → 336×288 实测更差：21.95 vs 15.59 px）。
- 不动教师定义、动作空间、候选顺序、标签口径（改了就没有可比性）。
- 本轮没有接 PPO / 放雷学习 / 历史动作输入。

## 2. 数据集与结构

### 2.1 两份数据，角色不同（这点必须先搞清）

| 代号 | 目录 | 帧数 | 分片 | 角色 |
| --- | --- | ---: | ---: | --- |
| **A** | `third_party/th08/build/rl/datasets/pilot-ud0059-v2` | 72,413 | 566 | **唯一训练源**。train 65,172 / val 7,241 |
| **B** | `third_party/th08/build/rl/datasets/pilot-ud0063` | 69,336 | 542 | **只做跨回放守卫**，永不训练、不选模、不调参 |

- 划分是固定帧级划分：`seed=7`、`val_fraction=0.1`、`val_frames=7241`，
  验证索引 SHA-256 = `e5d4ebbe6d8de05793520a393fc1fdbea2b1e2c4db9ff7c1632908340c76655f`。
  这个 sha 是**硬门槛**：任何一次验证覆盖算出来的 `visited_index_sha256` 必须与它逐字相等。
- B 现场**没有 manifest**（这是事实，不是 bug）。它的评估清单由工具生成：
  `Document/Update/Alpha/v1.0.4/Stage3/S3-1/evidence/ud0063-evaluation-manifest.json`
  （`stats.evaluation_only=true`、`provenance.purpose=external-evaluation-only`）。
- B 只有一次守卫机会。**用掉就要如实记 `external_guard_uses`，不能重跑挑结果**（本轮已用掉一次，=1）。

### 2.2 一个分片文件里有什么

每个 `collect-XXXXX.npz` 是「**原生分辨率的 PNG 字节流 + 特权标签**」：

| key | dtype | shape | 含义 |
| --- | --- | --- | --- |
| `region_name` | `<U24` | (3,) | `playfield` / `hud_score` / `hud_status` |
| `region_hw` | int32 | (3,2) | 各区域原生 (H,W) = (448,384) / (34,216) / (126,216) |
| `playfield_blob` | uint8 | (n_bytes,) | 该区域这一片的 PNG **串接**字节 |
| `playfield_offset` | int64 | (n+1,) | 第 i 帧是 `blob[off[i]:off[i+1]]` |
| `hud_score_blob` / `_offset` | 同上 | 同上 | |
| `hud_status_blob` / `_offset` | 同上 | 同上 | |
| `self_feat` | float32 | (n,24) | 特权自机特征（见 §2.3） |
| `bullets` | float16 | (n,64,6) | 最近 64 颗子弹：`dx,dy,dvx,dvy,half_size,valid`（相对自机、按距离排序） |
| `danger` | uint8 | (n,16,8) | 16×8 粗粒度弹幕计数（全场地） |
| `action` | uint8 | (n,4) | **人类回放的真实操作** `[move, shoot, focus, bomb]` |
| `meta` | float32 | (n,8) | `frame, stage, score, graze, lives, bombs, power, deaths` |

注意两个**反直觉**的点：

1. **分片里没有 `value`**（教师评分）。`manifest.has_teacher_values` 写的是 `true`，但那是"该数据集应配有教师值"，
   实际教师值在**独立 npz** 里（见 §2.4）。读分片的 `value` 会 KeyError。
2. **人类动作 `action` 一直都在，但本轮训练没用它**。这是下一轮最值得捡的东西（§7.3）。

### 2.3 `self_feat` 的 24 维（`obs.py` 的契约，不要改顺序）

```
0  自机场地相对 x         1  自机场地相对 y
2,3 恒为 0（保留槽：原始速度会泄漏"当前输入"，v1.0.2 因此塌成"保持当前速度"）
4  focus 模式(0/1)        5  lives/8        6  bombs/8       7  power/128
8  graze/20000          9  score/2e8     10  clock_time/20 11  time_orbs/20
12 stage/6              13  stage_clear_flag(0/1)
14 活跃子弹数/700        15 半径 192 px 内子弹数/120
16..23  八向"危险射线"最近距离（1.0 = 安全，0 = 贴脸）—— 0°/45°/90°…共 8 个方向
```

### 2.4 三种"缓存"，各自身份校验方式不同

| 缓存 | 位置 | 内容 | 身份校验 |
| --- | --- | --- | --- |
| **解码缓存** | 与分片同目录 `collect-XXXXX.decoded-<region>-<H>x<W>.npy` | `uint8[n,H,W,3]`，按模型输入尺寸解好 | 旁边有 `<npy>.json`，`schema=v104-decode-cache/1`，记录源 npz 的 `name/frames/bytes/sha256`、region、shape、dtype、`cache_sha256` |
| **教师值缓存** | `<dataset>-teacher-values-v104-<fingerprint>.npz` | `values` float16 `[72413,18]` | 同名 `.json`，`schema=v104-teacher/1`，绑定 566 个分片的 busen_hash、manifest sha、val sha、候选版本、完整 `PilotConfig`、`pilot.py` 源 sha |
| **B 评估清单** | `Stage3/S3-1/evidence/ud0063-evaluation-manifest.json` | manifest v1 结构 | `evaluation_only=true`、`purpose=external-evaluation-only` |

**为什么要身份**：v1.0.3 曾因为"按行数 n 复用缓存"而踩过数据错配的坑。
现在**没有 sidecar 的旧缓存一律不信任**：读帧会回退到 PNG 解码并计数（`decode_cache_stats` 能看到 `no-identity`/`invalid` 计数）。

本轮的落盘量（实测）：

- A 的 224×192 三 ROI 解码缓存：**1698 个文件 / 16,851,012,096 B**
- B 的三 ROI 解码缓存：**1626 个文件 / 16,134,972,672 B**（= payload 16,134,764,544 + 1626×128 头，差 0 B）
- A 的 336×288 playfield 缓存：566 个，**至今没有 sidecar**，属于"历史遗留、不信任、不扩建"

### 2.5 时序历史：`causal-segment-v1`

模型吃 3 帧（`depth=3`）。离线怎么取历史有两条契约：

- `legacy`：只按分片夹断（旧行为，保留兼容）。
- **`causal-segment-v1`（本版默认用于 v104 实验）**：同一分片内，只有
  「`stage` 相同、`deaths` 相同、`frame` 有限且严格递增、**相邻差值恰为 2**」才认为是连续；
  一旦不满足就**切段**。段内 oldest→newest；段首缺历史就重复段首帧；meta 不可信的样本把全部槽位设成当前帧。
- **禁止跨分片**：没有逐行 episode id，跨片连续性无法证明。

实测（A，depth3）：5865 段、最长 128 帧、`gap` 重置 5298 次（即 delta≠2 的地方很多）、
重复历史样本 **6714/72413 = 9.27%**。B 是 4.97%。

⚠️ 在线部署**不读 stage/frame/deaths**，而是「episode reset 后重复首帧填满 3 帧」。
所以离线切段规则与在线填充规则**本来就不等价**，这是已知的训练/部署时序差异，必须如实披露。

## 3. 算法核心结构

### 3.1 输入：三块原生 ROI（像素预算的取舍）

游戏客户区 640×480，切成三块**原生分辨率**采集（不缩放在采集端做，缩放在读的时候做）：

| 区域 | 客户区矩形 (x,y,w,h) | 模型输入 H×W | 为什么 |
| --- | --- | ---: | --- |
| `playfield` | (32, 16, 384, 448) | 224×192 | 子弹/自机/敌机。缩到 224×192（1/2）实测最优；336×288 更差 |
| `hud_score` | (424, 36, 216, 34) | 34×216 | 分数数字要能读，不能缩 |
| `hud_status` | (424, 88, 216, 126) | 126×216 | 残机/雷/Power/Graze |

- 唯一的预处理入口是 `vision.regions_to_batch()`：`uint8[B,D,H,W,3] → float32/255`（在 device 上做除法）。
  **不要再写第二份归一化**——v1.0.2 出过"两份预处理漂移"的事故。
- 模型内部把 `[B,D,H,W,3]` 拼成 `[B,3D,H,W]`（D=3 → 9 通道）。

### 3.2 动作空间：18 个候选

```
index = focus*9 + move            # focus ∈ {0,1}, move ∈ 0..8
move: 0静止 1上 2右上 3右 4右下 5下 6左下 7左 8左上
部署执行时: action = [index%9, 1, index//9, 0] = [move, shoot=1, focus, bomb=0]
```

- 完整环境动作是 `(9,2,2,2)`（move, shoot, focus, bomb），但**视觉策略只决定前三维中的 move/focus**，
  shoot 恒为 1、bomb 恒为 0（本版不放雷）。
- `act()` 返回四元组 `(actions int64[B,4], logp zeros[B], max_preference[B], extra zeros[B])`。
  **第三项是"最大偏好"，不是 RL 价值**，不能拿去喂 PPO。

### 3.3 教师：`AvoidPilot`（`pilot.py`）

这是整个项目的"老师"，也是蒸馏目标的来源。它的本质是一个**滚动时域的 beam 规划器**：

1. 候选 = 9 个方向 × 2 种 focus = **18** 个首步动作；
2. 每个候选按物理位移表外推（实测标定：未 focus 轴向 4.0 px/帧、斜向 2.828；focus 2.0 / 1.414；
   自机半宽 0.825，focus **不缩小**判定点，只降速度）；
3. 对弹幕做解析式碰撞预测（子弹当匀速直线圆，半宽 + `bullet_pad=0.5`），
   `horizon_steps=10` 步、每步 `frameskip=2` 帧 → **前瞻 0.33 s**；每个首步动作保留 `quota_per_action=2` 条后续路径；
4. 每个首步动作的**值** = 「整条路径上的**最小间隙**」+ 有界的偏好项：

   ```
   pref = bottom_bias * (y - MOVE_AREA_Y) / MOVE_AREA_H        # bottom_bias=0.30，偏好靠下=更多反应时间
        - aim_weight * |x - boss_x| / MOVE_AREA_W               # aim_weight=0.0，本版关闭
   value = min_clearance + pref - switch_penalty * 方向是否改变
   ```
   偏好项被刻意设计成**有界**（合计最多能影响 `bottom_bias + aim_weight` 像素的净空），
   所以它不会把"用 1 px 净空换射击位置"这种自杀行为排上来；
5. `candidate_scores()` 返回这 18 个值（float32 `[18]`），单位是**净空像素**；
6. `act()` 取 argmax，并在「最佳净空 < `bomb_min_clearance=-1.5`」且还有雷时放雷（部署策略不放雷，这条只用于教师真机跑分）。

**本轮生成标签时的固定配置**：`AvoidPilot(PilotConfig(switch_penalty=0.0))`
——把方向切换惩罚**关掉**，因为标签是"每一帧都重新规划"的值，不希望把迟滞写进标签。
⚠️ 副作用：学生从标签里学不到迟滞，而部署又是逐帧 argmax —— 这正是 §7.1 那个 50.7% 翻转的直接来源之一。

**关键设计选择**：蒸馏的是**值**而不是**动作**。因为教师的价值经常并列（实测：最优−次优差值 p50 只有 0.609 px，
24.9% 的帧完全并列），如果学"标签动作"，并列会变成"模型随机挑一个"；学值则并列对不产生梯度。

### 3.4 学生 v2（`vmodels2.py`，554,873 参数）

```
playfield [B,9,224,192]
  ├─ Conv5 s2 9→32 → Conv3 s2 32→64 → Conv3 s2 64→96 → Conv3 s1 96→96
  │     → 特征图 [B,96,28,24]（stride 8，一格 16 原生 px）
  ├─ heatmap 头: 1×1 conv → [B,28,24] logits → soft-argmax → position[B,2]
  ├─ danger 头: AdaptiveAvgPool(16,8) → 1×1 conv → [B,128]（16×8 行优先）
  └─ vector: AdaptiveAvgPool(2,2) → Linear → [B,64]
hud_score [B,9,34,216] → CNN → 64 维
hud_status[B,9,126,216] → CNN → 64 维
fusion → trunk(256) → policy head Linear(256,18) / self head Linear(256,22)
```

v2 的**致命上限**：heatmap 是 28×24，一格 16 原生 px。soft-argmax 再好，位置精度也就卡在格子这个量级——
实测 72 轮训练后停在 **13.06 px**，怎么调都不动。

### 3.5 学生 v3-st（`vmodels3.py`，1,507,162 参数）——本版的关键改动

```
playfield [B,9,224,192]
  ├─ Conv5 s2 9→32 → Conv3 s2 32→64 → 2×(3×3 残差 64) → F4 [B,64,56,48]
  ├─ Conv3 s2 64→96 → 2×(3×3 残差 96) → F8 [B,96,28,24]
  ├─ 定位: F8 上采样到 56×48，与 F4 拼 160 通道 → Conv3 64 → Conv1 1 → heatmap [B,56,48]
  │        soft-argmax → position[B,2]；熵/log(HW) 与 max prob 一起进 location_stats[B,2]
  ├─ 局部路: 以**预测位置.detach()**为中心，在 F4 上采一个原生 128×128 窗口，
  │        16×16 bin 中心双线性采样（grid_sample, padding=zeros, align_corners=False）
  │        + 同网格采全 1 得到的有效性 mask → 65 通道 → 2 层 conv → [B,128]
  ├─ 全局: F8 1×1 → 32 → AdaptiveAvgPool(7,6) + 2 个坐标通道 → [B,128]
  ├─ HUD: 两块各自小 CNN，但**只吃最新一帧 t**，各 64 维
  └─ fusion 400 → 256 → 256 → features[B,256]
       policy Linear(256,18) / self Linear(256,22)+position=[B,24] / danger [B,128]
```

**为什么它一下就赢了**：56×48 的 heatmap 一格是 **8 原生 px**（v2 是 16），
位置精度上限直接翻倍；再把 F4（细节）与 F8（全局）融合成单一分布，抑制局部歧义。
参数量只涨 2.7 倍，**不是容量问题，是输出网格分辨率问题**。

消融（正式预算 72 感知 + 12 策略，各一次）：

| 配置 | 位置 px | danger | 0–15 桶 | top3 |
| --- | ---: | ---: | ---: | ---: |
| E4 局部关 | 2.3314 | 0.8006 | 1.899 | 0.5959 |
| **E5 局部开（冻结款）** | 2.4066 | 0.8166 | **1.271** | **0.6601** |
| E6 策略辅助关 | 2.1873 | 0.8037 | 1.519 | 0.6354 |

→ 局部 ROI 分支值 0.63 px 的桶后悔（−33%），策略期辅助项值 0.25 px（−16%），**两者都必要**。

### 3.6 损失（`vision_losses.py` + `vision_train.py`）

感知期（state stage）：

```
loss = 1.0*heatmap_CE(σ=2 高斯目标) + 1.0*coord_loss + 1.0*danger_smooth_l1 + 1.0*self_smooth_l1
coord_loss = mean((|Δx|*384 + |Δy|*448)/2) / 100
danger 目标 = log1p(count/8)，16×8 网格
```

策略期（policy stage）——**目标是排序**，三种可选：

| objective | 公式 | 权重 |
| --- | --- | --- |
| `legacy-reg` | `SmoothL1(s, clip(v,-8,40)/10)` | `(rank_weight=0, regression_weight=1)` |
| `centered-reg` | `SmoothL1(s - mean(s), (v - mean(v))/10)`，不 clip | 同上 |
| `rank` | 全部 153 个 i<j 对里只取 `|v_i-v_j| > 0.5` 的对，`softplus(-sign(Δv)·Δs)`，逐帧有效对平均→再对批平均 | `(1, 0)` / `(1,0.1)` / `(1,1)` |

外加策略期辅助（保留感知能力）：`hm=0.1, xy=1.0, danger=0.2, self=0.1`，
其中 self 辅助只对原始索引 `4..12` 与 `14..23`（19 维）计损失，排除保留槽 2/3 与恒定的 13。

**实测哪一刀有用**：`legacy-reg → centered-reg` 把 0–15 桶从 3.728 压到 3.050（−18%）、top3 翻倍；
纯 `rank` 并没有更好（3.110）。所以"教师价值并列导致回归塌成常数"这个假设**部分成立**，
但 **v2 的整体天花板是网格，不是损失**。

### 3.7 训练/选模规则（`vision_train.py`）

- 两阶段：先感知（默认 72 轮），再策略（默认 12 轮）。
- 策略期前 2 轮**冻结**编码器/感知，只训候选头；后 10 轮联合，
  **切换时重建 optimizer**：head lr=3e-4、encoder/perception lr=1e-4。
- 验证**必须全量**：`drop_last=False`，7241 帧 = 76 批（75×96 + 41），
  记录 `actual_frames` 与 `visited_index_sha256`。**丢尾批是旧版真实缺陷（D9），别再引入**。
- 选模（`selection_contract=v104`）：
  - `state.best` = **第一个**位置<10 且 danger 中位>0.8 的**同一轮**（写 `state-pass.pt`）；
    没有这样的轮次才回落到位置最优的 `state.pt`。**绝不拼接两轮的指标**。
  - `policy.best` = 按 `(0–15 桶后悔, 全局后悔, 较早 epoch)` 字典序最小；**空桶不得参与**。
- run 目录 `runs/v104-<experiment>-s<seed>`，已存在有效 summary/权重就拒绝覆盖。

### 3.8 指标口径（`vision_metrics.py`，不可改）

| 指标 | 定义 |
| --- | --- |
| 位置误差 | `(|Δx|·384 + |Δy|·448)/2`，**全验证集 7241 帧**的均值 |
| danger 相关 | 逐帧 16×8 网格在 `log1p(count/8)` 域的 Pearson，过滤恒定/非有限帧后取**中位数** |
| 后悔（regret） | `max(v) − v[argmax(s)]`，**用未 clip 的原始教师 px** |
| 危险桶 | `[0,15) [15,30) [30,60) [60,120) [120,∞)`；最近有效子弹距离 `sqrt((dx·192)²+(dy·224)²)`；无有效子弹归 120+ |
| top3 | 按 `(−教师值, 候选索引)` 稳定排序取前 3；`top3_tie` 是"值 ≥ 第三名原值"的扩展集合 |
| near_optimal_05 | `max(v) − v[chosen] ≤ 0.5` |

### 5.3 游戏本体到底怎么被控制（这是最容易踩坑的部分）

`env.step(action)` 一次做四件事：

**① 保持前台 + 注入按键**

```python
self._focus_guard()                       # 每 15 步检查一次
keys = spec.action_to_buttons((move, shoot, focus, bomb))  # 位掩码
keyboard.set_keys({"up","down","left","right","z","shift","x"} & ...)
```

- **输入是合成按键（scan code `SendInput`）**。TH08 的 DirectInput 键盘用 `DISCL_FOREGROUND`，
  所以**窗口必须在前台**，否则游戏收不到任何键。这是本轮 A-04 第一次拿到 0 局的原因
  （用户的任务管理器是 High 完整性且占着前台，Medium 完整性的进程 `SetForegroundWindow` 被 UIPI 拒绝）。
- 备选后端 `PostMessageKeyboard` 只在 `dontUseDirectInput` 配置下有效，**不需要前台**——理论上支持多实例并行，
  但本项目当前走 SendInput。

**② 等固定帧数**

```python
state = self._wait_frames(self.config.frameskip)   # 默认 2 帧
```

即"一个决策 = 一次按键 + 2 个逻辑帧"。`frameskip=2` 时 60fps 下就是 30 Hz 决策。
实测一轮决策的端到端时延 **p50 10–12 ms、p95 ≈15 ms**，相对 33 ms 的预算是够的。

**③ 判终止（这是 `frame stalled` 的来源）**

```python
if state.supervisor_state != STATE_GAME_MANAGER: terminated, reason="left game (...)"
elif state.is_demo:                              terminated, reason="attract demo"
elif state.lives < 0:                            terminated, reason="game over"
elif advanced == 0:                              terminated, reason="frame stalled"
```

`advanced` 是 `gameplay_frame` 的增量。**掉光所有残机后游戏停在 continue/game-over 界面，
`supervisor_state` 仍然是 2，但 `gameplay_frame` 不再前进** → 记为 `frame stalled`。
（本轮 A-04 的三局全是这个原因，不是被截断。）

**④ 采下一帧观测 + 算奖励**

`_capture_observation()` 会读内存拿 `GameState` 与子弹池（特权信息，只用于 reward 与终止判定，**不进策略**）。

### 5.4 reset 的两种模式

| `menu` | 关掉进程再重开？——不会，只走菜单回到标题再进游戏，进程复用 | 快速迭代 |
| **`relaunch`（evaluate 默认）** | 每局 `session.close()` 后重新启动进程，保证"干净进关" | 正式评估、验收 |

## 7. 已知陷阱、失败原因与下一步

### 7.1 A-04 为什么是 "离线 1.27 px、真机 1627.7 帧"

本轮做了两条诊断，**一条排除、一条命中**：

**排除**：不是部署跟不上。三局决策时延 p50 = 10.4 / 12.2 / 11.0 ms、p95 ≈15.4 ms；
`frame_delta` 三局 711/714、898/900、816/819 为 2，仅各 1 次为 1、各 1 次非正（终止帧）。

**命中**（512 个验证帧上的策略行为剖析）：

| 项 | 策略 | 人类回放 |
| --- | ---: | ---: |
| 静止占比 | **1.6%** | **58.6%** |
| focus 占比 | **5.7%** | 24.8% |
| 相邻帧 argmax 翻转率 | **50.7%** | — |

也就是说：**它每两帧就换个动作、几乎从不静止、几乎不用低速**。
离线 regret 对这种"每帧乱跳"几乎不敏感（跳来跳去后悔都差不多），闭环却会被它直接打死。

结构性原因：学生学的是「教师 18 个候选的值」，而**部署时是逐帧独立 argmax**。
教师的 beam 规划是有时序一致性的（它还带 `_prev_move` 做迟滞，只是本版把 `switch_penalty` 设成了 0），
学生这边把这层时序一致性**丢掉了**。

### 7.2 本轮踩过并已修掉的坑（别再踩）

| 坑 | 现象 | 现在怎么防 |
| --- | --- | --- |
| **`--seed` / `--w-coord` 是伪参数** | argparse 收下但不传给 config，`cfg.seed` 恒为 7 | 已修两行 + 加了 **AST 通用网测试**（49 个 flag 必须都被 `args.<dest>` 读取）+ 变异验证 |
| **训练不可位级复现** | 同配置同 seed 的两个 run 从 **ep1** 就分叉（31.10 vs 22.50 px） | 只能靠多 seed；**0.1 px 级差异不能当信号**（比如 3.049 vs 3.050 是噪声） |
| **A-01 的 danger 余量极薄** | seed 7 = 0.8166、seed 17 = 0.8082，线是 0.8 | 只能说"观察上通过"，**不能说稳过**；要再 1–2 个 seed |
| **验证丢尾批（D9）** | 7241 帧只验 7200 | `drop_last=False` + `visited_index_sha256` 硬校验 |
| **缓存按行数复用** | v1.0.3 数据错配 | 解码缓存/教师值都必须有 sidecar 身份；无身份一律不信任并回退 |
| **`%TEMP%\pytest-of-a5935` ACL 坏** | 所有 `tmp_path` 用例 `PermissionError` | 用 `.pytest-tmp\<role>` 重定向 `TEMP/TMP` + `-o cache_dir=`（**环境问题，不是代码问题**） |
| **游戏抢不到前台** | A-04 第一次 0 局，`TimeoutError: screen 4 did not become ready` | 先确认前台不是高完整性窗口（任务管理器）；`_focus_guard` 每 15 步会尝试恢复前台 |
| **单实例互斥** | 第二个 `th08.exe` 起不来 | `"Touhou 08 App"` 互斥量；多实例只能走 PostMessage 后端 |
| **125% 缩放** | ROI 全偏、尺寸虚拟化 | `__COMPAT_LAYER=HIGHDPIAWARE` + 进程自身 `dpi_aware()` |

### 7.3 下一步建议（按性价比排序）

1. **人类动作监督（最便宜的增量）**：数据集里 `action[n,4]` 一直存在，本轮完全没用。
   加一个 18 类（或 move/focus 双头）的动作分类辅助头，与现有排序损失共训。
   人类 58.6% 静止 / 24.8% focus 的分布本身就是很强的先验。
2. **时序一致性**：部署时不要裸 argmax。最小改动是给候选分数做**迟滞/平滑**
   （如对相邻帧 logits 做 EMA，或加 `switch_penalty` 的推理期版本）；
   更彻底是把"连续 K 帧动作序列"作为训练目标。**这一步不需要重训也能先验证**。
3. **把 A-04 当成主指标**：现在离线指标已经够看，闭环才是瓶颈。
   建议每次改动都跑 3 局真机（约 2 分钟/局），并把 `frames_mean` 作为一等指标。
4. **再补 1–2 个 seed**：判断 A-01 的 danger 余量（0.8082–0.8166）会不会翻转。
5. **A-03 若要翻案**，只能由用户授权**新回放做新守卫**或书面改判据——不能重跑同一份 B。
