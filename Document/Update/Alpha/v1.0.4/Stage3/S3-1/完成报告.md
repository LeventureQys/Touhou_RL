## 2. 接口契约（输入 / 输出 / shape / dtype / 异常码）

### 2.1 `VisionDataset`

```python
VisionDataset(
    dataset_dir,
    max_cached_shards=None,          # 完整分片数量上限；None = 只受字节预算约束
    cache_budget_bytes=536_870_912,  # 512 MiB，v1.0.3 是 2_000_000_000 + per_frame=1200 假估算
    decode_threads=8,
    use_decode_cache=True,
    *, history_contract="legacy", verify_source_digest=True,
)
```

- 位置参数顺序不变（`vision_train.py:394`、`tools/rl/compare_state_models.py:24`、`pipeline/process` 的调用无需改动）。
- 输出/行为：
  - `frames(indices, region="playfield", out_h=None, out_w=None) -> uint8[B,H,W,3]`（shape/dtype 与原实现一致；缺 ROI 抛 `KeyError`）。
  - `region_frames(indices, sizes) -> dict[str, uint8[B,H,W,3]]`、`labels(indices) -> dict`（`self_feat f32[n,24]`、`bullets f16[n,64,6]`、`danger u8[n,16,8]`、`action u8[n,4]`、`meta f32[n,8]`，列序 frame/stage/score/graze/lives/bombs/power/deaths）原返回不变。
  - `stack_indices(indices: list[int], depth: int) -> int64[B,D]`，签名不变。
  - `cache_stats() -> dict`：`budget_bytes / resident_bytes / hits / misses / evictions / full{entries,bytes} / label{entries,bytes}`（契约 8 键，精确集合有单测）。
  - `decode_cache_stats() -> dict`（新增诊断）：`enabled/hits/missing/invalid/disabled/reasons/verified_source_digests/contract`。
  - `history_audit(depth=3) -> dict`；`close()` 幂等释放缓存与线程池；`__enter__/__exit__`。
- 预算语义（D10 逐字实现）：
  - 只计 `ndarray.nbytes`；full 与 label 记录共享同一 array 对象时只计一次（`_Residency` 按 `id()` 去重），`full.bytes` / `label.bytes` 是分项逻辑和、可能重叠。
  - 每次命中刷新统一 LRU；插入**前**先按 `resident + incoming <= budget` 预淘汰，使 `cache_stats()["resident_bytes"]` 在任何时刻都不超预算；`max_cached_shards` 只约束完整分片记录数（label-only 记录由字节预算约束，见 §6.5 说明）。
  - `cache_budget_bytes=0`：不驻留任何对象，但调用仍返回正确数据（单测 `test_zero_budget_retains_nothing_but_still_returns_values`）。
  - 单片超预算：临时返回、不驻留（`test_single_entry_over_budget_is_returned_but_not_resident`）。
  - **不计入**：mmap 页、临时 batch、OS 页缓存、线程池；**不承诺 RSS**。
- 生命周期：`close()` 后再调用 `frames/labels/stack_indices/history_audit` 抛 `RuntimeError("v104:CACHE: VisionDataset is closed; create a new instance")`。

### 2.2 历史契约

| 契约 | 规则 |
| --- | --- |
| `legacy`（默认） | 夹到样本所属分片首帧（v1.0.3 原样）。 |
| `causal-segment-v1` | 连续段 = 同分片内：前后样本 meta 均有限、stage 相同、deaths 相同、`frame[i]-frame[i-1]==2`（蕴含严格递增）。槽位 oldest→newest；段首不足 D 的槽重复段首；不可信/缺 meta 样本所有槽 = 自身并隔断其后样本；**不跨片、不看未来**。 |

`stack_indices` 返回全局索引，`out[row, -1]` 即中心帧。D 必须为正整数（`v104:CONFIG`），索引必须落在 `[0, total)`（`v104:DATA`）。无 episode id，故不能宣称识别所有同 stage 重开（残余风险见 §9）。

### 2.3 `history_audit(depth=3)` 输出

`contract_version / history_contract / dataset / frames / shards / depth / delta_histogram / delta_pairs / history_delta_histogram / resets{shard,stage,death,gap,untrusted,total} / segments / longest_segment_frames / untrusted_frames / cross_shard{stage,death,delta_histogram} / repeated_history_samples / repeated_history_ratio / resets_rule / repeated_history_rule / repeated_history_denominator`。

- 只读 `meta`（`decode_cache_stats().hits == 0` 有单测），不改 split。
- 重复率 = 含重复槽的中心样本数 / 总帧数；D1 结构上恒为 0（无可重复槽）。
- `resets` 是**断点事件**计数：一次断点可同时满足多个类别（如 stage 变化同时跳帧），因此 `sum(类别) >= total`；数据集首个样本视为流起点，不计 reset。这两条写进 JSON 的 `resets_rule` 字段。

### 2.4 解码缓存文件与 sidecar

- 文件名不变：`collect-00000.decoded-playfield-224x192.npy`，`uint8[n,H,W,3]`，`mmap_mode="r"` 读取。
- sidecar 名 `<cache>.json`（即 `…224x192.npy.json`；读取时兼容 `…224x192.json`）。
- sidecar schema（实例取自 A，B 同构）：

```json
{"schema": "v104-decode-cache/1",
 "source": {"name": "collect-00000.npz", "frames": 128, "bytes": 19915772,
            "sha256": "925ae048bd5e2338b536cb1614596fc90f585a29558b3cb0bf7e024d0040ee88"},
 "region": "playfield", "shape": [128, 224, 192, 3], "dtype": "uint8",
 "cache_sha256": "a737c6ca976a809cfb922fc265b61e05009960a5940aa3a17751692b88dbe6cb",
 "payload_verified": true}
```

- 读取校验顺序：存在性 → `ndim==4` → `dtype==uint8` → `C==3` → `H/W` → `n==分片帧数` → sidecar schema/region/shape/dtype → `source.name/frames/bytes` → `source.sha256`（**每分片只算一次**，`_source_digests` 记忆化，不每 batch 重 hash）。任一不符 → 回 PNG 解码并在 `decode_cache_stats().reasons` 记录原因（`no-identity`、`source-digest`、`shape`、`frames`、`dtype`、`unreadable`、`missing`…）。
- 无身份旧缓存**只回退不背书**：显式 `build_decode_cache` 才重写。

### 2.5 `build_decode_cache` / `verify_decode_cache`

```python
build_decode_cache(dataset_dir, sizes, *, verbose=True, verify_payload=True,
                   decode_threads=8, limit_shards=None) -> dict
verify_decode_cache(dataset_dir, sizes, *, verify_payload=True, verbose=False,
                    limit_shards=None) -> dict
```

- 原签名（`dataset_dir, sizes, *, verbose=True`）与旧键保留：`dataset / sizes / files_written / files_skipped / bytes_written / elapsed_seconds`。
- 新增键：`files_invalid`（存在但校验失败，含无 sidecar 的 v1.0.3 文件）、`files_repaired`（其中被重写的）、`files_missing`、`files_expected`、`files_present`、`bytes_total`（目标文件 `stat` 之和，Run 末重新 stat 统计）、`cache_contract`（`v104-decode-cache/1`）、`shards_visited`、`payload_verified`。
- `bytes_written` = 本次新写字节；`bytes_total` = 目标 stat。
- 写路径：解码 PNG → 临时文件（`np.save` 到文件句柄，避免 `.npy` 后缀被改写）→ 重新 mmap 读回逐值比对 → 计算 `cache_sha256` → 写临时 sidecar → `os.replace(npy)` → `os.replace(sidecar)`；异常时删除临时文件、**不破坏既有有效文件**、**绝不改 npz**。
- `verify_decode_cache` 对每个目标重新校验（可选校验 `cache_sha256` 全文件摘要），返回 `files/files_ok/files_invalid/bytes_total/invalid_reasons/invalid[]`。

### 2.6 CLI `tools/rl/prepare_v104_data.py`

```
--dataset PATH  --mode {cache,audit,eval-manifest}  --out PATH
--depth {1|3}（默认 3）  --history-contract（默认 causal-segment-v1）
--decode-threads 8  --limit-shards N（仅冒烟用）
```

| 模式 | 行为 |
| --- | --- |
| `audit` | 只读 meta，写 `history_audit` JSON（含 `mode/dataset/manifest/decode_cache/cache_stats/generated`）。depth 只接受 1/3。 |
| `cache` | 固定三 ROI（224×192 / 34×216 / 126×216）；先算 free 预检（缺失+需替换 payload + 最大单文件 + 32 MiB sidecar 余量 + 1 GiB 余量），不足则 `v104:BUDGET` **不写任何文件**；再 build → 全量 verify；报告含 `precheck/build/verification/free_bytes_before/free_bytes_after/manifest`。 |
| `eval-manifest` | 仅对**无** `manifest.json` 的外部数据集有效（A 有 manifest → `v104:CONFIG` 拒绝）；拒绝把结果写到数据集默认 manifest 路径；同内容复用（忽略 `created` 的内容摘要），内容不一致 → `v104:EVIDENCE` 拒绝；不写 B 默认 manifest、不调用 process。 |

- `cache`/`audit` 拒绝把报告写到「看起来是 DatasetManifest」的文件上（保护 A manifest）。
- 退出码：0 成功；2 已知契约/manifest/IO 异常（stderr 前缀 `v104:<CODE>: `）；其它异常保留 traceback 且退出 1；argparse 用法错误退出 2。

### 2.7 异常码（`ValueError("v104:<CODE>: <detail>")`）

| CODE | 触发 |
| --- | --- |
| `CONFIG` | 未知 `history_contract`；`depth` 非正整数；CLI `--depth` 非 1/3；`eval-manifest` 用在已带 manifest 的数据集；数据集目录不存在 |
| `BUDGET` | `cache_budget_bytes < 0`（原文 `v104:BUDGET: cache_budget_bytes must be >= 0`）；free space 预检不足 |
| `DATA` | 非法索引（越界/非整数/NaN）；meta 行数与帧数不一致；`history_rows` 输入长度不符 |
| `CACHE` | 关闭后的数据集被再次使用；写入校验发现 shape/dtype/回读不一致 |
| `EVIDENCE` | 覆盖 DatasetManifest；`eval-manifest` 既有输出内容不一致；写入数据集默认 manifest 路径 |

## 6. 预算与历史审计分析

### 6.1 delta 直方图（分片内相邻样本的 frame 差）

**A（71,847 对）**：`2: 66549`、`3: 5008`、`4: 87`、`5: 44`、`6: 154`、`-30942: 1`、`-26908: 1`、`-22393: 1`、`-19008: 1`、`-16731: 1`。

**B（68,794 对）**：`2: 66562`、`3: 2001`、`4: 65`、`5: 42`、`6: 117`、`7: 2`、`-27932: 1`、`-24178: 1`、`-19538: 1`、`-18619: 1`、`-16543: 1`。

- `every=2` 只覆盖 92.6%(A)/96.8%(B) 的相邻对；`delta=3..7` 是采集跳帧（约 7.3% / 3.2%），`delta<0` 是**分片内帧号回退**（A 5 处、B 5 处，回退 1.6×10⁴~3.1×10⁴ 帧，形如重开/回放跳转）。三类都被 `causal-segment-v1` 判为断点；`legacy` 会把断点前的帧当成"历史"喂给断点后的中心帧，这正是 D11/C2 指出的实质缺陷。
- 分片内所有 delta 均有限（无 `nonfinite`），meta 无缺失。

### 6.2 跨分片诊断（仅诊断，契约不跨片）

A：跨片 stage 变化 0、deaths 变化 0；跨片 frame 差分布 `2:34, 3:227, 4:239, 5:16, 9:20, 10:2, 12:21, 14:1, 15:5`。
B：跨片 stage/deaths 变化均 0；`2:22, 3:153, 4:263, 5:74, 6:5, 7:2, 9:2, 10:3, 11:1, 12:7, 13:1, 14:1, 15:3, 18:4`。

跨片 stage 连续、deaths 也连续（两个数据集都是单回放连续采集），**但从数据本身无法证明跨片就是同一 episode**，所以契约依旧不跨片；这也说明「按分片夹断」损失的历史只是分片边界的 1~2 个槽，而分片内的跳帧/回退才是主要污染源（A 5,864 个断点里 5,298 来自 gap）。

### 6.3 reset 计数与重叠

- A：`shard 565`（566 片，首片起点不计）+ `stage 5` + `death 1` + `gap 5298` + `untrusted 0`，`total = 5864`。`sum(类别)=5869 >= 5864`，重叠 5 次：5 处帧号回退同时伴随 stage 变化（同一个重开事件被 stage 与 gap 各记一次）。
- B：`shard 541` + `stage 5` + `death 0` + `gap 2232` + `untrusted 0`，`total = 2773`，`sum=2778`，同样 5 次重叠。
- 单测 `test_audit_reports_expected_resets_and_overlap` 与暴力复算用例共同锁定「类别可重叠、total 是事件数」的语义。

### 6.4 重复历史样本比例

判定口径：`depth` 个槽中出现任意两个槽指向同一帧，该中心样本计一次；分母是总帧数。

| | A | B |
| --- | --- | --- |
| causal d3 | 6714 / 72413 = **9.2718%** | 3446 / 69336 = **4.9700%** |
| legacy d3 | 1132 / 1.5633% | 1084 / 1.5634% |
| causal d1 | 0 | 0 |

legacy 的 1.56% 恰好是每片起始 2 个样本（566×2 / 542×2），因为它只在分片首夹断；`causal-segment-v1` 把这部分扩到 9.27% / 4.97%，多出来的正是**分片内跳帧与帧号回退**造成的段首（A 有 11 个分片整片每个样本都重复历史，因为该片内 delta 恒为 3）。这部分样本的 3 帧输入完全相同，模型无法从它们学到运动；报告出来是为了让 S3-3 在 depth3 训练时明确这一比例，而不是把重复当成有效时序信号。

### 6.5 预算实现要点与实测

- 修正点：v1.0.3 用 `per_frame=1200` 估算「总帧数×1200 是否超预算」，真实成本约 253 KB/帧，导致「预算内」实际可驻留约 20 GB；且 `_load_labels` 完全无界、`_load` 是无序 FIFO。现在：真实 `nbytes` + 统一 LRU（命中刷新）+ 分片数量上限 + 插入前预淘汰。
- 实测峰值见 §4.6：最坏路径刚好压在 512 MiB（536.67/536.72 MB，预算 536,870,912 B），真实训练路径只有 ~73-76 MB（因为像素走 mmap，驻留的只有 label 记录）。
- `max_cached_shards` 只约束**完整分片**记录数（任务书「完整片数量上限」），label-only 记录由字节预算约束；因此在 `cached` 探针里 566/542 个 label 记录全部驻留（A 76,368,652 B、B 73,123,584 B，恰好等于该模式峰值）而没有驱逐。这是有意为之：若把 label 也计入数量上限，按 batch 取样会持续抖动，且 v1.0.3 的老上限本来就只针对完整片。
- 明确**不承诺 RSS**：mmap 页、临时 batch、OS 页缓存、线程池都不在预算内。

## 9. 未关闭问题与风险

1. **同 stage 重开无法完全识别**（契约已知限制）：没有逐行 episode id；`causal-segment-v1` 只在 frame 序列/deaths/stage 变化处切段。A 有 5 处帧号回退（各带 stage 变化），B 有 5 处；若存在「同 stage、deaths 不变、帧号仍连续」的重开（例如暂停后继续），契约无法识别。审计已把 delta 直方图与 reset 计数落盘，供后续评估残余影响。
2. **336×288 的 A 缓存无身份 → 现在会回落到 PNG**：这是「不得未经像素核验补写 sidecar」的直接后果。若 S3-3/S3-6 要复用 336×288 缓存，需要一次显式 `build_decode_cache(dir, {"playfield": (336,288)})`（会重写 566 个文件，约 21 GB 写入）；本任务按任务书「336 不扩建」未执行。
3. **训练/验证中心样本共享历史像素**：帧级 split 未改（A val 仍 7241 / sha 未变），但 depth3 下 val 中心帧的历史槽可能落在 train 帧上，仅共享像素、不读对侧标签；S3-3 报告必须披露这一相关性。
4. **在线/离线时序不完全一致**：部署沿用「首帧重复 + episode reset」，名义 `every=2` 不是同步保证（实测 A 7.3%、B 3.2% 的相邻对不是 2 帧）。本轮不宣称离线契约与在线行为严格一致。
5. **驻留预算不等于 RSS**：mmap 页与 OS 页缓存不在预算内；`budget_probe` 报的是 `cache_stats().resident_bytes` 峰值，不是进程 RSS。
6. **B 评估清单的 split 只是通用算法产物**：6933 个 val 索引仅用于跨回放评估；`stats.evaluation_only=true` 与 `provenance.purpose=external-evaluation-only` 已写入清单，但**工具无法在技术上阻止**他人拿它训练，需要流程约束（S3-8/验收方核对）。
7. **并行在途不一致（非本任务）**：`vision_metrics.py`（S3-2）新增 `by_danger` 键后，`test_vision_train.py`（S3-3 所有）旧断言失败（§3.3）。本任务无权修改，提请 MainAgent 在 S3-2/S3-3 交接时处理。
