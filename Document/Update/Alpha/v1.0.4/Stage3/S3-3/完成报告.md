8. 选模：`state.best` 优先首个同轮 joints pass（`state-pass.pt`），否则位置最优（`state.pt`）；`policy.pt` 取 `(0–15 桶后悔, 全局后悔, epoch)` 字典序最小，空桶不参与；`best` 行带 `selection_rule/checkpoint/checkpoint_sha256`（写入前从文件现算）。

### 3.3 吞吐：`_gather` 语义等价去重

```python
requested = dataset.stack_indices(indices, depth).reshape(-1)      # [B*D]
if depth == 1:                    # 不可能重复：保持 v1.0.3 直取，零开销
    frames = dataset.region_frames(requested.tolist(), region_sizes)
    stacked = {name: frames[name].reshape(B, 1, H, W, 3) for name in frames}
else:
    unique, inverse = np.unique(requested, return_inverse=True)
    frames = dataset.region_frames(unique.tolist(), region_sizes)      # [U,H,W,3]
    stacked = {name: frames[name][inverse].reshape(B, depth, H, W, 3) for name in frames}
```

- 只改“怎么取帧”，不改样本集合/顺序/标签/`stack_indices` 语义：`inverse[i]` 保证第 i 个槽位取到与原来完全相同的帧。
- 真实训练批实测（indices 70000..70095、depth 3）：288 槽 → **98 唯一帧**（去重 190 槽，66%），`torch.equal` 与朴素路径逐值相同，labels 也相同（`evidence/throughput.json` 的 `spot_check`）。

- 单测：段首重复、跨分片、D=1 三种情形都断言 `np.array_equal` + dtype/shape 一致 + 标签一致，并断言“确实发生了去重”（`test_vision_train.py` 三条 `_gather` 用例）。
- **实测结论**：depth3 去重后 71.3/71.0 s，仍 > 60 s 硬门；已按指令停止并上报（§6.7）。

**结论（按上级指令停下并上报，未降门限、未改小 batch）**

1. **depth1 去重无收益**：depth 1 的历史栈不可能重复，第一版却仍做 `np.unique`+gather，实测 +9.6% 纯开销。已加 `depth == 1` 直取分支，最终 **39.0 / 39.2 s**，与去重前 **40.7 / 40.3 s** 持平（差异在运行间噪声内）。
2. **depth3 去重后仍是 71.3 / 71.0 s/epoch，仍 > 60 s 硬门**；对照去重前 73.1 / 70.9 s 仅 −1.2%，属噪声。**60 s/epoch 门槛未达，本任务停止继续优化并上报 MainAgent。**
3. **根因不是“重复读帧”，而是“必须物化完整栈”**：`_gather` 的原签名/返回要求它交出完整 `[B,D,H,W,3]` 张量。去重省下 190 行 mmap 读（≈44 MB/批），但 `frames[inverse]` 必须再做一次 288 槽 gather 拷贝（≈67 MB/批），净内存流量反而增加（估算 +17%）。`evidence/gather-probe.json` 的热态每批耗时（同一索引顺序、同一配置跑两趟取第二趟）：

   | depth | 顺序 | naive | fast（去重） | 差值 |
   | --- | --- | --- | --- | --- |
   | 1 | train（shard-chunked，679 批） | 25.20 ms | 26.00 ms | +3%（噪声） |
   | 1 | val（随机跨片，76 批） | 38.03 ms | 39.34 ms | +3%（噪声） |
   | 3 | train | 53.33 ms | 52.15 ms | −2.2% |
   | 3 | val | 71.50 ms | 80.99 ms | **+13.3%** |

   即 d3 训练省 2.2%、验证亏 13.3%，两相抵消（每 epoch 数据耗时都是 ≈41.6 s）。
4. **时间构成**（热态推算）：d3 epoch 71.15 s ≈ 数据 41.6 s（train 679×53.3 ms + val 76×71.5 ms）+ 计算/指标/同步 29.5 s；d1 epoch 39.1 s ≈ 数据 20.0 s（679×25.2 ms + 76×38.0 ms）+ 计算 19.1 s。数据路径约占 59%，但只要 `_gather` 必须返回完整栈，去重就无法降低物化成本。
5. **可选的下一步（需上级裁决，超出本任务允许范围）**：把 unique 帧与索引分别送到 GPU 后在图内展开（会改变 `_gather` 的返回契约）；或降低每批像素物化字节（输入尺寸 / D10 驻留策略 / 更小的 HUD 分辨率）；或按 100 批微基准确认是否可用更大 batch 摊薄。本任务未实施任何一项，也未调整 `batch`、门限或 `depth`。

## 10. 未关闭项（不写 pass）

1. **depth3 吞吐未达 60 s/epoch（blocked + 已上报）**：去重实现正确且逐值恒等，但实测 71.3/71.0 s（去重前 73.1/70.9 s），根因是 `_gather` 必须物化完整栈（§6.7）。按上级指令「若去重后 depth3 仍 >60s，立即停下上报」，本任务**停止优化并上报**；未降低门限、未改跑更小 batch、未调整 depth/batch。可行方向已列在 §6.7 第 5 条，需上级裁决。**本任务不声称吞吐达标。**
2. **全仓 pytest 快照依赖并行工作树**：本任务期间有并行 SubAgent 修改 `evaluate.py`/`vmodels.py`/测试（`test_evaluate_vision.py` mtime 03:52:36、`vmodels.py` 04:05:46）。本任务收工快照为 **482 passed / 0 failed**，但 A-05/S3-8 应以最终全树复跑为准（§5.3）。
3. **短训 run 无 `policy.pt`**：`--max-val-batches 1` 的 96 帧验证切片 0–15 桶 frames=0，按「空桶不得参与选模」不写 policy.pt。这是契约后果，不是缺陷；S3-4 的正式 run 必须 `--max-val-batches 0`（全 7241 验证）才有 policy 选模。**本次独立加载证据因此使用 `state.pt`（`stages.state.best`），不冒充 policy 加载。**
4. **策略选择只在 1 个 epoch/1 个 val 批上跑过真实数据**：`policy.pt` 的桶次级排序只在合成脚本化指标上验证过（单测），未在真实 7241 帧验证集上产生 policy 选模；这是 S3-4 的首轮实验内容，本任务不宣称 A-02。
5. **未跑正式长训**（S3-4）、未启动游戏（S3-8）、未实现 v3（S3-5）。轮速吞吐只在 `--stage state`（感知期）上实测；策略期（含辅助头 + rank 损失）未做 100 批微基准，只记录了短训 1 epoch 的 0.8 s（96 帧、2 批，screening 规模，不能外推为正式吞吐）。
