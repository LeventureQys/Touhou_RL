## 2. 自决区（本人决策，含方案 / 理由 / 风险）

### D-01 v1.0.1 交付范围 = 研究 + 设计 + 可运行的 I/O 垂直切片
- 方案：交付「玩法与先行研究评估 → 网络设计 → 框架 I/O 契约 → 路线图」四份文档，另加 `touhou_rl/` 包（规格、配置、抓帧、注入、只读状态、观测装配、奖励、环境、网络定义、ROI 框选工具、探针脚本），并配单元测试 + 对真实 TH08 的启动测试。**不训练策略**。
- 理由：需求三个动词都是设计类；但接口只有跑起来才能证明其可行（F-08~F-12 的实测就是把设计建立在数字上）。切片限制在「观察/操作/记账」，不含算法收敛目标。
- 风险：切片代码在 v1.1 训练时可能被重构。缓解：契约文档先行（`框架接口契约.md`），代码按契约实现，测试锁行为。

### D-02 视觉为主、特权状态可选（做成开关，不做取舍）
- 方案：观测分 `vision`（必选）、`hud`（屏幕量表）、`state`（内存特权特征，可缺省 + 掩码）。`profile.state_source = "memory" | "none"`；`none` 时 `state_mask` 全 0，网络侧以掩码输入兼容。奖励同理支持「内存优先 / HUD 回退」。
- 理由：`readme.md` 的终极目标是「框选 + 自学 + 跨作品基模」，视觉通道必须是一等公民；而 v1.0.0 明确要「从逆向工程中获得信息回馈 RL」，特权状态是最便宜的高质量监督与奖励来源（F-05/F-10 已实测可读、0.123 ms）。开关化让两条路线共用一套代码，未来做「特权→视觉蒸馏」也不需要改架构。
- 风险：若未来要求「严格纯视觉」做论文级对比，需关闭内存通道并补 HUD OCR（本版只留接口，不实现 OCR）。缓解：`hud` 字段与 `state` 字段在契约中已分离（`框架接口契约.md` §3）。

### D-03 对游戏进程只读，绝不写入
- 方案：`memory.py` 只调用 `OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION)` + `ReadProcessMemory`；不 `WriteProcessMemory`、不 `CreateRemoteThread`、不 patch 字节、不修改 `third_party/th08/src` 与上游构建脚本。
- 理由：F-14 证明写入生命/符卡/火力会被反篡改校验发现并 `CRASH_GAME()`；上游 `AGENTS.md` 也禁止改目标二进制。只读即可满足观测/奖励需求。
- 风险：只读无法做「重置到关卡开头」的作弊式复位，需要靠菜单重开或重启进程。缓解：D-09。

### D-04 本版单实例、前台注入；并行实例方案推迟
- 方案：v1.0.1 一次只控制一个游戏窗口；每次注入前强制前台并校验。并行环境（多实例同时训练）推迟到 v1.2，方案为 `dinput8.dll` 代理（进程内伪造 `GetDeviceState` 返回值），届时可脱离前台限制并支持 N 实例。
- 理由：F-11 证明前台 `SendInput` 可用（9.3 ms）；DirectInput `DISCL_FOREGROUND`（`Supervisor.cpp:937`）决定后台窗口收不到键盘，`SendInput` 无法绕开。先用最简路径打通链路，避免本版膨胀为「输入代理 DLL 工程」。
- 风险：单实例训练吞吐低（30 决策/秒）。缓解：路线图把「样本效率优先（DQN 家族 + 录像模仿）」列为 v1.1 主线，并明确 v1.2 代理 DLL 为吞吐扩展点。

### D-05 技术栈：Python 3.12 + numpy + Gymnasium API + PyTorch（v1.1 换 CUDA 轮子）+ TOML 配置 + pytest
- 方案：运行时零第三方重依赖（仅 numpy/Pillow，抓帧用 ctypes 直连 Win32）；接口遵循 Gymnasium `Env` 语义；网络用 PyTorch（本版装 CPU 版仅做形状/参数量验证）；配置用 TOML（`tomllib` 读 / `tomli-w` 写）；测试 pytest。
- 理由：Python 是教学与生态的最短路径；Gymnasium 语义让未来能直接接 Stable-Baselines3 / CleanRL 等；TOML 是 Python 3.11+ 标准库可读格式，避免额外解析依赖；Win32 直连避免 `pyautogui`/`mss` 这类会擅自改变 DPI/输入的库。
- 风险：CPU 版 torch 无法验证显存与真实吞吐。缓解：v1.1 Stage 3 第一步安装 CUDA 轮子并记录 `nvidia-smi` 证据；本版只声明参数量与 FLOPs 级估算。

### D-06 动作空间：`MultiDiscrete([9, 2, 2, 2])` + 扁平索引 72 双表示
- 方案：`[移动, 射击, 低速, 炸弹]`；移动 0=静止、1=N、2=NE、3=E、4=SE、5=S、6=SW、7=W、8=NW（屏幕坐标，y 向下）；扁平索引 `flat = move*8 + shoot*4 + focus*2 + bomb`，两者一一对应（双射测试）。
- 理由：东方系列操作是「8 向 + 3 个功能键」；分解式表示便于多头策略与动作掩码（某些作品无 Bomb/低速），扁平表示便于 DQN 类算法直接复用；炸弹做成**边沿触发**（按下即松开），避免按住连发。
- 风险：72 个组合里有无效组合（如静止+射击=仍可射击），不算问题；真正的风险是「低速+移动」需要同时按下，已由多键同帧注入覆盖（F-11 实测 `0x44`）。
- 风险：帧跳过 2（30 决策/秒）对高密度弹幕可能太粗。缓解：`frameskip` 可配，v1.1 用「自适应帧跳过」实验对比 1/2/3。

### D-07 观测契约：全局视野 + 局部跟随 + 量表 + 特权 + 元信息
- 方案：`frame`（场地 384x448 → 96x112，RGB，叠 4 帧）、`local`（自机中心 160x160 裁剪 → 96x96，RGB，叠 4 帧）、`hud`（8 维归一化量表 + 掩码）、`state`（24 维归一化特权特征 + 掩码）、`meta`（8 维整数元信息）。
- 理由：弹幕游戏需要两种尺度——全局看弹幕形状/Boss 位置，局部看清自机周围 2–4 px 的判定；只降采样全局会让细弹模糊（`PIFE` 论文与弹幕游戏通行做法都指向「对象级/局部细节更重要」）。两路叠帧提供速度信息（弹幕有惯性，`Bullet::velocity` 存在）。
- 风险：96x112 对 384x448 是 1/4 降采样，最小的 2x2 判定弹可能糊成一团。缓解：`local` 用 1/2.4 降采样（160→96 约为 1.67x），并保留原始 `frame` 供图像类方法（如模板匹配）使用；网络输入尺寸可配。

### D-08 奖励：多目标向量 + 标量加权，权重在 profile 里
- 方案：奖励拆成 6 个分量 `[survive, progress, score, graze, resource, event]`，同时输出标量 `r = w·v`；权重、上限、事件惩罚全部写在 `profile.reward`。默认权重见契约 §5。
- 理由：`thrl` 的多目标 PPO 论文说明弹幕游戏的「分数/生存/资源」是相互冲突的目标，单标量会掩盖权衡；而 `readme.md` 的目标是「让基模自己学规则」，多目标向量正好是未来做偏好/权重自适应的接口。
- 风险：权重是超参，本版无法给出「训练有效」的证据。缓解：文档明确「默认权重仅为起点，v1.1 用消融实验校准」，并在验收文档中把权重合法性（归一化、非负、总和）作为可测项而非效果项。

### D-09 回合控制：v1.0.1 用「重开进程」复位，菜单级复位放 v1.1
- 方案：`reset_mode = "relaunch"`（`WM_CLOSE` → 重启 → 导航到 Stage 1）为本版默认；`reset_mode = "retry_menu"`（Esc → Retry → Restart）只留接口与任务书，不在本版实现。
- 理由：F-12 证明「启动 + 3 次 Z 进关」稳定且总耗时 ~12 s；菜单级重开要做菜单状态机（`TitleScreen` 的 `currentScreen` 偏移未在源码中给出 `C_ASSERT`，需额外逆向，F-05 只验证了 `cursor/currentScreenState`）。本版先把确定性拿到手。
- 风险：重开进程的 12 s 空转会让「短回合采样」效率低。缓解：v1.1 实现 retry 宏，路线图里已列。

### D-10 产物与证据的落盘位置
- 方案：框架代码放根仓库 `touhou_rl/`；一次性探针放 `tools/probes/`；运行产物、截图、JSON 证据放子模块被 gitignore 的 `third_party/th08/build/play/evidence/`；需要审阅的关键 3–5 张图复制到 `Document/Update/Alpha/v1.0.1/evidence/`；大文件（截图/模型/录像）不入库。
- 理由：延续 v1.0.0 的 D-03/D-11（子模块保持干净、私有材料不入库），同时让文档自带可审阅证据。
- 风险：证据分散两处。缓解：验收文档逐项写明证据绝对路径。

### D-11 窗口识别与 DPI 策略
- 方案：`find_game_window(pid)` 以「同 PID + 类名 `BASE` + 可见 + 面积最大」为准，标题只作日志；启动子进程时注入 `__COMPAT_LAYER=HIGHDPIAWARE`；抓到尺寸与 profile 声明不符时报错并提示 DPI 兼容层。
- 理由：F-08 实测标题乱码与 125% 虚拟化；不注入兼容层会得到 800x600 的插值图，直接污染观测。
- 风险：`__COMPAT_LAYER` 是兼容性 shim，微软未承诺长期保留。缓解：若失效，退路是「按实际尺寸抓帧 + 缩放到 profile 尺寸」，并在启动日志里打印实际尺寸。

### D-12 本版不做 HUD OCR，量表走内存；OCR 只留接口
- 方案：`hud.source = "memory" | "roi_decode"`，本版实现 `memory`，`roi_decode` 抛 `NotImplementedError` 并在契约中标注 v1.1 交付。
- 理由：F-10 证明内存读数与 HUD 显示一致且 0.123 ms；OCR（日文/数字字体）是独立工程量，且会引入误识别噪声，不适合与接口设计同时做。
- 风险：`state_source="none"` 的纯视觉模式在本版拿不到量表奖励，只能靠像素差分等弱信号。缓解：契约允许外部注入 `hud_override`，v1.1 补 OCR。

### D-13 网络：共享视觉主干 + 门控循环 + 多头 + 游戏条件化
- 方案：双尺度 CNN 主干（全局 96x112、局部 96x96）→ 特征拼接 → GRU(256) → 策略/价值/奖励分量辅助头；跨作品用 `game_embedding`（16 维）经 FiLM 调制主干，并预留 LoRA 式适配器（v1.4）。参数量目标 2–4 M。
- 理由：弹幕是「局部危险 + 全局形状 + 时序惯性」三者叠加，循环结构对躲弹必要；多目标辅助头让奖励向量与价值共享表示；FiLM + 适配器是跨作品基模的低成本可行路径（不改主干、按作品调少量参数）。
- 风险：GRU 让并行采样（多环境）实现复杂，单实例下 BPTT 需要序列缓存。缓解：v1.1 先用帧栈（无循环）的 DQN 拿到基线，再升级循环；本版网络只做前向形状/参数量验证。

### D-14 版本路线（详见 `路线图.md`）
- 方案：v1.0.1 接口与切片 → v1.1 单关 RL 基线（DQN 家族 + 课程 + 录像模仿）→ v1.2 吞吐与多实例（dinput8 代理）+ 多关卡 → v1.3 多作品统一动作/观测 → v1.4 基模 + 适配器 + 少样本微调 → v2.0 「自学规则」（内在动机 + 世界模型 + 自动 ROI 发现）。
- 理由：每版都以「可验收的环境/指标」为门禁，避免一次性铺开无法收敛。

### D-15 测试与门禁
- 方案：单元测试覆盖 8 个模块（spec/profile/capture 几何/observation/memory 解码/reward/env/models）；启动测试为「真实 TH08 跑 `touhou_rl.tools.rollout` 200 步 + 截图 + JSON」；门禁要求两者都有证据，缺一即「未完成」。
- 理由：系统规则要求新功能单元测试 + 启动测试；且本版新增文件 ≥3、影响面大，属于强制门禁情形。
