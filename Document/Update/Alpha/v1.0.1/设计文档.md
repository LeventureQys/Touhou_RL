## 1. 背景与目标

### 1.1 项目终极目标（来自根 `readme.md`）

> 用「框选游戏区」的方式，让强化学习学会玩东方系列 STG；最好训练出一个**基模**，能在不同作品上自己游玩、自己学规则、自己微调。

拆成三条可验收的能力链：

1. **观察**：用户框选屏幕区域 → 系统把区域变成张量（含 HUD 量表语义）；
2. **操作**：策略把张量变成键盘动作 → 真正作用到游戏窗口；
3. **学习**：用游戏内事件（生存/得分/擦弹/资源/关卡进度）构造奖励 → 训练 → 跨作品迁移。

### 1.2 本版目标（v1.0.1）

| 目标 | 交付物 | 不做什么 |
| --- | --- | --- |
| 玩法与先行研究评估 | 本文 §3、§4 | 不做文献综述级篇幅 |
| 网络设计 | 本文 §9 + `touhou_rl/models.py` 可前向验证 | 不训练、不调参 |
| 框架输入输出设计 | `框架接口契约.md` + `touhou_rl/` 包 | 不做 HUD OCR、不做并行实例 |
| 路线规划 | `路线图.md` | 不承诺时间点 |
| 可行性证明 | 单元测试 + 真实 TH08 启动测试（`验收报告.md`） | 不追求策略表现 |

### 1.3 本版硬约束（来自实测，编号见 `问题清单.md` §0）

- 游戏是 **60 fps 帧同步**的 32 位 Windows 程序（F-12）；
- 只能**读**内存，写会被反篡改机制判死（F-14）；
- 抓帧最快的路径是**窗口 DC BitBlt 1.98 ms**，且窗口被遮挡也能拿到画面（F-09）；
- 键盘必须**前台**才能被 DirectInput 读到，注入延迟 9.3 ms（F-11）；
- 窗口标题是乱码，必须用 **PID + 类名 `BASE`** 识别；DPI 需兼容层才能 1:1（F-08）；
- 冷启动到标题 2.42 s，进 Stage 1 约 +3 次按键，首屏子弹约 9 s（F-12）。

## 2. 东方系列 STG 玩法研究

### 2.1 通用结构（TH06–TH19 共享）

| 要素 | 说明 | 对 RL 的含义 |
| --- | --- | --- |
| 场地 | 竖屏弹幕场（本作 384x448，见 F-07），外层是 HUD 栏 | 观测可裁出场地；ROI 可配置 |
| 自机与判定 | 自机是 2–4 px 的**极小判定点**，弹幕是上百个 2–8 px 的圆形判定 | 需要**局部高分辨率**，全局降采样会糊掉致死细节 |
| 操作 | 8 向移动 + 射击（Z）+ 低速/聚焦（Shift，显示判定点、移速减半）+ 炸弹（X） | 离散、低维、组合式动作空间（见 §7） |
| 帧同步 | 逻辑固定 60 fps，输入每帧采样一次 | 决策频率天然是 60 Hz；帧跳过是算力/精度的交换 |
| 弹幕 | 数百发子弹，带速度、加速度、变换（裂变/变色/激光） | 状态有强时序惯性 → 需要帧栈或循环 |
| 资源 | 残机（lives）、符卡/炸弹（bombs）、火力（power）、擦弹（graze）、点数道具 | 多目标权衡：活得久 vs 分数高 vs 留资源 |
| 事件 | 中弹、Bomb、符卡取得、Boss 击破、关卡通过 | 稀疏奖励锚点 |
| 计分 | 擦弹、道具、符卡加成、Boss 击破、关卡通过 | 可分项奖励，也可只作辅助信号 |

### 2.2 本作 TH08（东方永夜抄）特化

- **人妖槽（youkai gauge）**：自机在人/妖形态之间切换，影响弹幕与得分；`ZunGlobals::youkaiGauge` 可读（F-05）。
- **时间球（time orbs）**：收集可延长时间/改变关卡进度，`currentTimeOrbs/totalTimeOrbs` 可读。
- **符卡（Spell Card）**：Boss 的符卡战有独立的取得判定，`spellcardsCaptured` 可读。
- **队伍/机体**：4 组队伍 + 单机体，影响射击形态（`shotType`）。
- **录像系统**：按帧记录输入字（F-19），是模仿学习与确定性评测的现成数据源。

### 2.3 从玩法推出的设计结论

1. **观测必须双尺度**：全局（弹幕形状、Boss 位置、道具分布）+ 局部（自机周围致死细节）。
2. **动作应是「方向 + 3 个功能键」的组合**，而不是 72 个自由动作；炸弹要边沿触发。
3. **奖励必须多目标**：生存、得分、擦弹、资源、进度互相冲突；单标量会把「苟活」和「刷分」混为一谈。
4. **回合天然很长**（Stage 1 约 60–100 s ≈ 1800–3000 决策），折扣因子/回报分解必须按「长时程」设置。
5. **可用的特权信号极丰富**（自机坐标、子弹位置、Boss HP、量表全部可读）→ 适合做「特权教师 + 视觉学生」，但推理侧应保持可纯视觉。

## 3. 先行实现评估

| 实现 | 做法 | 优点 | 局限（对本项目） | 我们借鉴什么 |
| --- | --- | --- | --- | --- |
| **thrl**（https://codeberg.org/thrl/thrl，论文 DOI `10.5281/zenodo.21788472`） | Rust 环境 + Python 训练；MOPPO（多目标 PPO）+ 课程学习 + 帧跳过；环境用 Taisei headless 模拟器、PC-98 作品用打过补丁的 DOSBox-X；仅 Linux/WSL2 | 有论文、有环境保真度论证、多目标奖励、课程设计、明确算力预算 | 不支持 Windows 版 TH06–TH19；依赖模拟器/移植体，不是原版可执行文件；无本项目式「只读特权状态」通道 | 多目标奖励结构、课程学习、帧跳过与吞吐预算、环境与训练解耦的进程边界 |
| **opfromthestart/touhou-ai**（https://github.com/opfromthestart/touhou-ai） | Rust；`dfdx` 神经网络、`enigo` 注入、`screenshots` 定位分数、`device_query` 取输入；纯视觉；NekoProject 640x400 测试 | 纯视觉链路（截图→动作）可复现；依赖少 | 只有「截屏 + 注入」的裸链路，无状态通道、无跨作品抽象；README 未给出训练规模与结果 | 纯视觉链路的可行性；「截图定位分数」提示 HUD 可做 ROI 解码 |
| **PIFE**（IEEE CoG 2022，https://esslab.jp/publications/ItoiCOG2022.pdf） | 排列不变特征提取器：把弹幕对象集合（子弹/自机）编码成定长向量 | 对象级编码样本效率远高于像素；对弹幕数量与顺序不敏感 | 需要对象级真值（内存或检测器） | 特权通道的特征形状；v1.2 的「特权→视觉蒸馏」教师 |
| **ACM 2024 弹幕 DQN**（https://doi.org/10.1145/3650215.3650381） | 像素 DQN 基线 | 证明像素端到端 DQN 在弹幕上可学到东西；基线实现简单 | 样本效率低、无跨作品设计 | v1.1 的像素 DQN 基线（作为「能学」的最快证据） |

**结论**：本项目的差异化优势是「**原版可执行文件 + 精确逆向工程**」——同一份 `th08.map` 同时给出渲染布局和内存布局（F-04/F-05），
因此可以同时拥有「视觉通道（面向迁移）」与「特权通道（面向效率与教师信号）」。这一点上述实现都不具备。

## 4. 总体架构

```
┌─────────────────────────── 训练侧（Python / PyTorch） ───────────────────────────┐
│ 算法：DQN 家族（v1.1） → PPO/MOPPO + 课程（v1.2） → 多作品联合 + 适配器（v1.4）    │
│ 组件：回放缓冲 / 序列缓存 / 课程调度 / 评估器 / 日志与检查点                       │
└──────────▲──────────────────────────────────────────────┬───────────────────────┘
           │ (obs, reward, terminated, truncated, info)    │ action
┌──────────┴──────────────────────────────────────────────▼───────────────────────┐
│                       touhou_rl.env（Gymnasium 语义）                            │
│  ObservationAssembler   RewardEngine   EpisodeController   ActionEncoder          │
└──────────▲──────────────────▲──────────────────▲──────────────────▲─────────────┘
           │ 帧 (uint8)        │ GameState        │ 状态机/宏         │ 键盘状态
┌──────────┴──────────────────┴──────────────────┴──────────────────┴─────────────┐
│                       游戏适配层（按作品实现 GameBackend）                        │
│  WindowCapture(GDI BitBlt)  StateReader(只读 RPM)  KeyInjector(SendInput)         │
│  WindowLocator(PID+class)   StageLauncher(菜单宏)  ProfileLoader(TOML)            │
└──────────┬──────────────────┬──────────────────┬──────────────────┬─────────────┘
           │ BitBlt           │ ReadProcessMemory│ SendInput        │ 启停进程
     ┌─────▼─────┐      ┌─────▼─────┐      ┌─────▼─────┐      ┌─────▼─────┐
     │ th08.exe  │      │ th08 内存 │      │  键盘     │      │ 游戏目录  │
     └───────────┘      └───────────┘      └───────────┘      └───────────┘
```

分层原则：

1. **游戏适配层可替换**：换作品只实现 `GameBackend`（或只改 profile 的偏移/ROI），env 与算法不动。
2. **观察与现实解耦**：`GameState` 是结构化数据（本版由内存解码），不是「某种语言的 dict」；视觉与特权是两条独立通道。
3. **训练侧只见 Gymnasium**：算法不需要知道 TH08 存在。

## 5. 观测设计

### 5.1 三通道 + 掩码

| 通道 | 形状 | 语义 | 缺失时 |
| --- | --- | --- | --- |
| `frame` | `[K,112,96,3]` uint8 | 场地全貌（384x448 → 96x112，RGB，叠 K=4 帧） | 必有 |
| `local` | `[K,96,96,3]` uint8 | 以自机为中心的 160x160 裁剪 → 96x96（约 1.67x 降采样） | 必有（自机位置未知时退化为中心底部） |
| `hud` | `[8]` float32 + mask | 残机/符卡/火力/擦弹/分数/点数/时间/时钟，归一化到 [0,1] | mask=0，值填 -1 |
| `state` | `[24]` float32 + mask | 特权特征：自机坐标、焦点、子弹数、最近 2 发子弹相对位置/距离、Boss HP、关卡帧数、死亡标记等 | mask=0，值填 NaN |
| `meta` | `[8]` int32 | `game_id, stage, difficulty, episode_step, total_frames, last_action_flat, done_reason, flags` | 必有 |

### 5.2 为什么是 96x112 + 96x96

- 场地 384x448 → 96x112 恰好 1/4 降采样，保持 6:7 宽高比；
- 1/4 下最小的 2x2 px 判定弹约 0.5 px，单靠全局必然丢失 → 局部通道把自机 160x160 区域以 1.67x 降采样呈现，
  使 2 px 子弹仍占约 1.2 px；
- 4 帧叠帧给出速度信息（`Bullet::velocity` 存在，弹幕有惯性）；K=4 在 30 决策/秒下覆盖 133 ms。

### 5.3 归一化（契约 §3 定义精确公式）

- 颜色：`u8 / 255`；
- HUD：按 profile 中每项的 `scale` 除以（如 `lives/8`、`score/1e8`），并 `clip(0,1)`；
- 特权：位置除以场地宽高，距离除以对角线，数量除以容量；
- 缺失一律用 mask 表达，**不用 0 冒充**（0 在归一化后是合法值，会误导网络）。

## 6. 动作设计

`MultiDiscrete([9,2,2,2])`：

| 维度 | 取值 | 语义 |
| --- | --- | --- |
| move | 0 静止；1 N；2 NE；3 E；4 SE；5 S；6 SW；7 W；8 NW | 屏幕坐标，y 向下；同时按对应方向键 |
| shoot | 0/1 | Z 键按住 |
| focus | 0/1 | Shift 按住（低速 + 显示判定点） |
| bomb | 0/1 | X 键**边沿触发**（本帧按下 → 注入后立即释放） |

扁平等价索引：`flat = move*8 + shoot*4 + focus*2 + bomb ∈ [0,71]`（双射，单元测试锁定）。

设计要点：

- 组合式表示让网络可以共享「方向」与「功能键」的表示，也让动作掩码（某些作品无炸弹）天然可行；
- 帧跳过 `frameskip=2`（30 决策/秒）默认；跳帧期间**保持**动作（按住语义），炸弹只在第一帧触发；
- 不做「斜向 = 两个方向键同帧」之外的加速技巧；低速移动速度由游戏决定。

## 7. 奖励设计（多目标）

标量奖励 = 6 维向量按权重内积：

| 分量 | 公式（默认） | 设计理由 |
| --- | --- | --- |
| `survive` | `+0.01` / 决策步（终局步为 0） | 提供持续的正向梯度，避免「早死早超生」 |
| `progress` | `+0.001 * ΔBossHP + 0.0001 * Δstage_frames` | 逼近 Boss/推进关卡是主要学习信号 |
| `score` | `+1e-6 * Δscore` | 100 万分 = 1.0，量级与生存项可比 |
| `graze` | `+0.001 * Δgraze` | 鼓励贴弹（东方核心技巧），但权重低于生存 |
| `resource` | `+0.002*Δpower + 0.001*Δpoint_items + 0.01*Δtime_orbs − 0.02*bomb_used` | 资源是长期收益；Bomb 有成本 |
| `event` | `−1.0*death + 0.5*spell_captured + 5.0*stage_clear` | 稀疏事件锚点 |

约束：

- 每个分量先 `clip(−10, +10)` 再加权，防止「分数爆涨」把其它信号淹没；
- 权重、每项 `scale`、事件惩罚全部写进 `profile.reward`（契约 §5），训练日志必须快照权重；
- 本版**不评价权重好坏**——只校验：非负、归一化、键完整、缺失字段报错（验收文档 A-05）。

## 8. 回合与课程

### 8.1 回合定义

- **开始**：`reset()` → 保证「人控 Stage 1 起始状态」（`supervisor_state==2`、`is_demo==False`、`is_replay==False`、`gameplay_frame` 归零后开始计数）。
- **终止**：残机耗尽（`lives<0`）、关卡通过（Boss 击破/状态迁移）、窗口丢失/进程退出。
- **截断**：达到 `max_frames`（默认 5400 帧 = 90 s）或外部中断。
- **复位模式**：本版 `relaunch`（WM_CLOSE → 重启 → 3 次 Z 导航，实测约 12 s，F-12）；v1.1 增加 `retry_menu`。

### 8.2 课程（v1.2 起）

| 阶段 | 内容 | 门禁 |
| --- | --- | --- |
| C0 | Stage 1 前 15 s（第一波敌机） | 存活率 ≥ 50% |
| C1 | Stage 1 全程 | 通关率 ≥ 20% |
| C2 | Stage 1–3（中途续关/练习模式） | 平均存活帧数提升 |
| C3 | 全作 6 面 + Extra | 不设硬指标，按进度曲线 |

课程切换由 `curriculum.json`（v1.2 交付）控制，本版只定义语义。

## 9. 网络架构

### 9.1 结构（`touhou_rl/models.py` 已实现前向）

```
frame (12,112,96) ──► CNN_global ─┐
                                  ├─► concat(256+256+8+24=544) ─► FC 512 ─► FiLM(game_emb) ─► GRU(256)
local (12,96,96)  ──► CNN_local  ─┤                                                          │
hud (8) / state (24, mask) ───────┘                                                          ├─► policy: 9 / 2 / 2 / 2
                                                                                             ├─► value: 1
                                                                                             └─► reward_head: 6（辅助）
```

| 模块 | 细节 | 参数量 |
| --- | --- | --- |
| `CNN_global` | Conv(12→32,3,s2)+GN+ReLU → Conv(32→64,3,s2)+GN+ReLU → Conv(64→96,3,s2)+GN+ReLU → Conv(96→128,3,s1)+GN+ReLU → AdaptiveAvgPool(4x4) → FC(2048→256) | ≈ 0.70 M |
| `CNN_local` | 同构（输入 96x96），最后一层 FC(2048→256) | ≈ 0.70 M |
| 融合 | `concat(256,256,8,24) → Linear(544→512)+ReLU` | ≈ 0.28 M |
| 条件化 | `Embedding(game_id,16) → Linear(16→1024) → (γ,β)` 作用于 512 维（FiLM） | ≈ 0.02 M |
| 循环 | `GRU(512→256)` | ≈ 0.59 M |
| 头 | policy 9 + 2 + 2 + 2；value 1；reward 6 | ≈ 0.02 M |
| **合计** | | **≈ 2.3 M** |

### 9.2 为什么这样设计

- **双尺度**：见 §5.2，弹幕游戏的「局部致死细节 + 全局形状」必须分开编码；
- **GN 而非 BN**：单实例在线采样 batch 小、分布漂移快，GroupNorm 更稳；
- **GRU 而非 Transformer**：单实例、低延迟推理，GRU 的常数开销最小；注意力版本留到 v1.3 做「对象级编码」时再引入；
- **辅助奖励头**：让 6 维奖励向量与价值共享表示，同时给「多目标」提供显式学习信号（v1.2 的 MOPPO 可直接复用）；
- **FiLM 条件化**：跨作品基模的最小侵入方式（不改主干、按作品调制），v1.4 再加低秩适配器。

### 9.3 算法路线（与网络解耦）

| 版本 | 算法 | 理由 |
| --- | --- | --- |
| v1.1 | Double DQN + Dueling + n-step(3) + 经验回放（可选 PER） | 单实例、离策略、样本效率优先；72 个扁平动作在 Q 头上很便宜 |
| v1.2 | PPO / MOPPO + GAE + 并行实例 | 多目标向量奖励与稳定性；并行靠 `dinput8` 代理（D-04） |
| v1.3+ | 联合训练 + 适配器 + 元学习 | 跨作品基模 |
| v1.1 补充 | 录像模仿（BC）→ RL 微调；特权→视觉蒸馏 | 用现成录像（F-19）绕过冷启动；用特权教师加速视觉学生 |

### 9.4 算力预算（本机 RTX 4070 SUPER 12 GB，F-13）

- 决策频率 30 Hz → **108,000 决策/小时**；
- 一次 Stage 1 完整回合 ≈ 2700 决策 ≈ 90 s 游戏时间 + 12 s 复位开销；
- v1.1 门禁定为 **100 万决策**（≈ 9–10 小时挂机），指标是「平均存活帧数显著高于随机策略」；
- 单次前向（2.3 M 参数、96x112x12 输入）在 4070 上预计 2–4 ms（批 32 时 GPU 利用率低，瓶颈在环境侧），因此**环境吞吐是主要瓶颈**，这也是 v1.2 做并行实例的直接原因。

## 10. 跨作品基模设计

### 10.1 统一接口

| 维度 | 统一方式 |
| --- | --- |
| 观测 | 场地按 profile 的 `playfield` 归一化到固定 384x448 → 96x112；HUD 按 `scale` 归一化；动作/键位由 profile 映射 |
| 动作 | 统一 9+3 动作语义；每作品给 `action_mask`（无 Bomb/无低速时屏蔽） |
| 奖励 | 统一 6 分量；每作品给权重与事件定义 |
| 元信息 | `game_id` 进 embedding；`difficulty/stage` 进 meta 与 embedding |

### 10.2 迁移策略

1. **共享主干 + 条件化**：多作品联合训练，`game_id` 经 FiLM 调制（§9.1）；
2. **低秩适配器**（v1.4）：每作品一组 `rank=8` 的瓶颈层，冻结主干热启动新作品；
3. **元学习**（v1.4）：RL² 式「把最近 N 步轨迹作为上下文」；MAML 作为对照；
4. **特权蒸馏**（v1.2）：用内存对象特征当教师在训练期监督视觉主干（学生），推理只用视觉；
5. **自学规则**（v2.0）：内在奖励（RND/ICM）+ 世界模型预测误差 + 自动 ROI 发现（把「人框选」升级为「模型提议 + 人确认」）。

### 10.3 「框选」工具的定位

`readme.md` 的核心交互是「用户框选 → 定义语义」。本版交付 `touhou_rl/tools/annotate_rois.py`：
截图 → 拖拽矩形 → 选择角色（`playfield` / `hud.lives` / `hud.score` / …）→ 写回 profile TOML。
它既是 v1.0.1 的可用工具，也是 v2.0「自动框选」的人工标注来源。

## 11. 工程约束与风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 反篡改：写内存必崩 | 无法作弊式复位/改数值 | 只读（D-03）；复位靠重启/菜单 |
| DirectInput 前台限制 | 无法并行多实例 | v1.2 `dinput8.dll` 代理（D-04） |
| DPI 缩放 | 抓帧被插值放大 | `__COMPAT_LAYER=HIGHDPIAWARE` + 尺寸校验（D-11） |
| 窗口重建（启动早期） | 缓存 HWND 失效 | 每次抓帧前校验并重找（F-08 踩坑 2） |
| 标题乱码 | 无法按标题找窗口 | PID + 类名 `BASE`（D-11） |
| attract demo 假阳性 | 误判「在游戏内」 | 查 `flags.isDemoMode/isReplay`（F-05/D-09） |
| 抓帧帧率抖动 | 同一帧被采两次 | 记录 `gameplay_frame` 作为真实时间戳，训练侧按它对齐 |
| 单实例吞吐低 | 训练慢 | 路线图 v1.2 并行；v1.1 用离策略 + 录像模仿提样本效率 |
| 私有数据不可分发 | 无法开源复现 | 论文级复现需另备「Taisei/移植体」路线（不属本版） |

## 12. 本版不做什么（防止范围膨胀）

- 不训练策略、不产出模型权重、不声称任何分数；
- 不实现 HUD OCR、不实现并行实例、不实现 `retry` 菜单级复位；
- 不修改 `third_party/th08/src` 与上游构建脚本；
- 不做跨作品（TH06/TH07…）实际接入，只保证接口可扩展（profile + backend）。
