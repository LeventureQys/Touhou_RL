## 2 阻断级缺陷：`session_action_for_state` 对 4 个会话状态全部崩溃

发现者：主代理（11:12:17 落盘版本复核），执行代理在同一轮冒烟里也撞到同一处。

### 2.1 现象

```python
S.session_action_for_state("menu")
# TypeError: SessionAction.__init__() got multiple values for argument 'state'
```

`playing / hit_pending / respawn / unknown` 正常返回 `None`，而 `menu / transition /
ending / game_over` **全部 TypeError**。触发链：
`advance()` → `_sync_key_control()` → `compile_session_action()` →
`session_action_for_state()`。后果是会话层**在任何需要发键的状态都不可用**——
菜单、过面、结局、game over 重开四条路全部不可用。

### 2.2 根因与修法

```python
request = SESSION_ACTIONS.get(state)
return SessionAction(state=state, *request)   # state 既关键字又是首个位置参数
```

改为位置展开，并加注释说明为什么不能回退：

```python
# Positional expansion: ``state`` must not be passed by keyword *and* be the
# first positional argument of ``*request`` (that raised TypeError for every
# session-driven state, i.e. the session could not press a key at all).
return SessionAction(state, *request)
```

### 2.3 回归测试（本次新增，专为此 bug）

| 测试 | 断言 |
| --- | --- |
| `test_every_state_maps_to_a_session_action_or_none` | 对 `SESSION_STATES` **每一个**状态调用一次；4 个 actor 驱动状态返回 `None`，4 个会话状态返回合法 `SessionAction`，且 `as_dict()["controller_source"]=='session'`、`actor_loss_mask==0` |
| `test_session_action_fields_keep_their_documented_order` | `dataclasses.fields(SessionAction)` 仍是 `[state, move, focus, shoot, bomb]`；`as_dict()["requested"]` 顺序仍是 `[move, focus, shoot, bomb]` |
| `test_session_driven_states_compile_with_actor_loss_mask_zero`（4 参数） | 端到端：分别喂 `menu_overlay / stage_banner / game_over_prompt / ending_credits`，断言不抛异常、状态正确、`session_owns_keys` 为真、`action.actor_loss_mask == 0`、`controller_source == 'session'`、`executed_masks` 长度为 2 且属于 72 个合法掩码 |
| `test_playing_does_not_hold_the_keyboard_and_cannot_compile` | 反向：`play_field_live` 时 `compile_session_action()` 抛 `SessionStateError`（"does not hold the keyboard"） |

## 3 任务 A：`touhou_rl/v430/session.py`

### 3.1 状态集与判定

`SESSION_STATES = playing / hit_pending / respawn / transition / game_over / menu /
ending / unknown`（与 `DEVELOPMENT_GUIDE` §9 同集合）。

输入是 `PixelEvidence`：`frame_index`、`frame_digest`(+`digest_scope`)、
`captured_at_s`、`elapsed_capture_s`、`scene`、`play_field_dark_ratio`、
`player_sprite_visible`、`hit_flash_visible`、`visible_life_pips`。
`scene` 是像素检测器的**闭词表**标签（`play_field_live / stage_banner /
menu_overlay / ending_credits / game_over_prompt / unrecognised`）；
分不清就**必须**说 `unrecognised`。

判定顺序（`_infer`）：ending → game_over_prompt → menu → stage_banner →
（上一帧 playing 时的）hit flash / 生命灯减少 → 活场且暗像素 > 0.9 → `unknown` →
活场且定位到自机 → `playing` → 活场但无自机 → `respawn`/`unknown` → `unrecognised`。

### 3.2 「不读真值」的两条独立证明

1. **行为哨兵**：`PixelEvidence.from_mapping()` 先跑 `assert_pixel_only()`，
   再解析。`SESSION_TRUTH_FIELDS` 覆盖 `stage_id / stage / stage_clear /
   stage_truth / game_over / lives / bomb_count / resource_truth / engine_frame /
   seed / teacher_action …`，并且叠加 `contracts.PRIVILEGED_FIELD_NAMES`。
   `SessionMachine(context=...)` 同样跑这条哨兵。
2. **静态依赖审计**：`session_source_audit()` 用 `ast` 读本文件源码，拒绝任何
   `touhou_rl.v400.gym.env / v400.gym.protocol / v400.teacher / v430.rl /
   v430.teacher / torch / numpy …`，并要求 import 全部落在允许清单内。

覆盖测试：`test_truth_fields_are_refused_in_evidence`（13 个字段参数化）、
`test_truth_fields_are_refused_in_the_machine_context`（6 种嵌套形状）、
`test_contract_privileged_names_are_also_refused`（8 个契约禁名）、
`test_session_source_imports_no_engine_module`。
关键断言：注入真值后 `machine.state` **保持不变**、`len(ledger.samples)` 不增加
（fail-closed，不是「忽略后继续」）。

### 3.3 owner 独占

会话与 actor 共用同一个 `actions.KeyOwnership`。会话**只在** `SESSION_ACTION_STATES`
（menu/transition/ending/game_over）里 `take_control()`，一回到活场立即
`release_control()`。`take_control()` 不吞 `OwnerConflictError`，直接向调用方抛出。
`compile_session_action()` 在发键后**重新校验** `controller_source=='session'` 与
`actor_loss_mask == SESSION_ACTOR_LOSS_MASK(0)`，不信任编译器的返回值。

覆盖测试：`test_two_owners_cannot_hold_the_keyboard`（actor 持有时会话 `advance`
抛 `OwnerConflictError`，且 `bus.holder` 仍是 actor）、
`test_switching_owner_must_be_explicit`（会话持有时再建 actor 编译器抛错；回活场后
`bus.holder is None`）、
`test_session_compiler_reports_session_and_actor_compiler_reports_actor`
（session=0、actor=`ACTOR_LOSS_MASK_ON`=1）。

### 3.4 `unknown` 不补零

- `unknown` 映射到 `None` 动作（`session_action_for_state(UNKNOWN) is None`），
  因此它在结构上**不可能**发键，也不可能被当成 playing 交给 actor。
- `unknown` 不会因为「看起来像游戏结束」而变成 `game_over`；只有 `game_over_prompt`
  像素场景才行。
- 两个像素特征互相矛盾（`scene=play_field_live` 但暗像素 > 0.9）时判 `unknown`，
  不做「取方便的那个」的仲裁。
- `visible_life_pips is None`（读不出）绝不当 0 用：`None` 既不制造也不掩盖 hit。

覆盖测试：`test_unknown_is_not_filled_with_playing_or_game_over`（5 帧序列，
逐帧断言状态不在 {playing, game_over}、`action is None`、`session_owns_keys is False`、
对应 span 的 `key_owner is None` 且 `session_decisions == 0`）、
`test_unknown_is_sticky_until_a_positive_pixel_signal`、
`test_unrecognised_keeps_a_pending_death_beat`、`test_none_life_pips_is_never_read_as_zero`。

### 3.5 菜单/过面/结局/重开计数

等待态本身即 `menu / transition / ending / game_over`；`ledger.totals()` 直接给出
`menu_waits / transition_waits / ending_waits / game_over_waits / unknown_waits`。

重开：离开 `game_over` 或 `ending` 进入 `menu`/`playing` 时自动记一条
`RestartRecord{restart_index, reason, source, from_state, to_state, frame_index,
frame_digest, frame_digest_scope, captured_at_s, session_elapsed_s}`。
`reason` 取自闭词表 `RESTART_REASONS = game_over_restart / ending_restart /
manual_reset / scene_reload / harness_reconnect`；后三个只能由
`record_manual_restart(reason=...)` 以 `source="operator"` 写入——**像素推断不许冒用
人工原因，人工重置也不许藏在像素推断里**。

覆盖测试：`test_restart_count_and_reasons_are_auditable`（2 次重开、reason/source/
from-to/帧号/摘要/时刻/会话时长逐字段断言 + `assert_complete()` 的
`restart_reasons`/`restart_sources`）、
`test_a_manual_restart_requires_an_operator_reason`、`test_a_plain_menu_visit_is_not_a_restart`。

### 3.6 「过面/结算期间不丢奖励」

这是本片最关键的一条，实现方式是**区间归属 + 可证完备性**：

1. 每个 `PixelEvidence.elapsed_capture_s`（会话自有时钟的间隔）归属到**该间隔发生时
   正在生效的那个状态**的 span。换状态时先归账再关 span，新 span 从当前时刻起算。
2. `attach_reward(name, value)` 把奖励分量钉在**当前打开**的 span 上；
   `note_event(event)` 追加闭词表事件。二者都不解释语义，只保证信息不丢。
3. `SessionSpan.duration` 是 `contracts.check_duration(external_controller_clock)`
   的产物——与会话外 actor 步长同一单位、同一来源（`DEVELOPMENT_GUIDE` §5.3 的
   共享外部时钟），`effective_frames = hz * elapsed`。
4. `SessionLedger.assert_complete()` 六项独立校验，任何一项失败即
   `SessionLedgerError`（不是警告）：样本序号恰好划分 `0..n-1`；每个 span 的
   `elapsed` 等于其样本间隔之和；全部 span 之和等于全部样本之和；帧号严格递增且
   相邻 span 在同一帧、同一时刻衔接；`elapsed == end_captured_at_s -
   start_captured_at_s`。**丢一个 span、丢一个样本、丢一段时钟都会被抓到。**
5. 尾随零长度 span（最后一帧刚好换状态）不四舍五入成正常步长，而是记
   `duration_source="invalid"` + `effective_frames=None`，并在 `assert_complete`
   里只允许它出现在**最后**；带奖励/事件的零长 span 不会被静默丢弃。

覆盖测试：`test_transition_span_keeps_duration_events_and_reward`（过面期间
`attach_reward("stage_clear", 1.0)`；断言 transition span 的 `sample_count==2`、
`elapsed==2×interval`、`duration_source==external_controller_clock`、
`effective_frames≈60×elapsed`、事件含 `stage_banner_seen`、
`reward_components=={"stage_clear":1.0}`、`key_owner=="session"`、
`actor_loss_mask==0`、`session_decisions==2`；`reward_rollup` 的 `states==['transition']`
且 `elapsed_capture_s` 等于该 span；`totals.total_elapsed==5×interval`）；
`test_the_ledger_detects_a_dropped_span`、`test_the_ledger_detects_a_zero_length_span_in_the_middle`
（人为破坏 span 后 `assert_complete` 必抛）、
`test_a_fractional_transition_does_not_lose_the_zero_length_final_span`、
`test_reward_attached_before_any_evidence_is_refused`、
`test_a_duplicate_reward_component_on_one_span_is_refused`。

### 4.6 换行符 digest 口径（主代理硬性要求）

**实现位置**

| 位置 | 内容 |
| --- | --- |
| `evaluate.py` `DIGEST_SCOPE_TEXT = "text/lf-normalized"` / `DIGEST_SCOPE_BINARY = "binary/raw"` / `DIGEST_SCOPES` | 口径定义（唯一权威定义处） |
| `normalize_lf()` | 唯一的规范化函数：`bytes.replace(b"\r\n", b"\n")` |
| `digest_bytes(payload, scope=...)` | 文本先规范化再哈希；二进制直接哈希；未知 scope 直接抛 |
| `describe_bytes()` | 同时给两种口径的摘要 + `line_endings{crlf,lf_only,has_crlf,mixed}` 普查 |
| `identify_bytes()/identify_file()` | 产出的身份**必带** `digest_scope`（无分支可以漏写） |
| `check_identity()` | 有 `sha256` 无 `digest_scope` → `MissingDigestScopeError`；非法 scope 同样拒绝 |
| `verify_identity()` | 不一致时**先判口径**：只有另一口径能复现 → `DigestScopeMismatch`（"the bytes are identical but the digest was taken under a different scope … This is a 口径 (line-ending) difference, not a content change"）；两种口径都对不上 → `DigestMismatch`（"the content differs … A line-ending change alone would have matched under …; it did not."） |
| `assert_identity_scopes()` | 递归扫描任意结果/字典，逐个身份断言口径存在；`evaluate._finish()` 与 `write_result()` 都对整份结果跑一遍 |

**二进制口径**：`session.py` 的 `DIGEST_SCOPE_PIXELS = "binary/raw"` 用于每一帧
`frame_digest`（`PixelEvidence` 强制它，写别的值直接抛「captured pixels are binary
and are never line-ending-normalised」）。两个常量的等价性由
`test_the_pixel_digest_scope_matches_the_binary_scope` 守住，不会各写各的。

**测试覆盖**

- `test_text_digests_ignore_line_endings_and_binary_digests_do_not`：同一内容 CRLF/LF
  两版，文本口径摘要相等、二进制口径不等，并断言 `line_endings` 普查值。
- `test_scope_mismatch_and_content_mismatch_are_different_failures`：两种失败的
  **异常类型与消息**都不同，消息里分别出现 "not a content change" / "content differs"。
- `test_a_pixel_digest_must_be_hashed_as_binary`。
- `test_the_plan_spec_itself_is_a_crlf_file_so_the_scope_matters`：本检出
  `PLAN_SPEC.json` 确实是 CRLF（`line_endings.crlf == 948`），文本口径与二进制口径
  摘要不同，用错口径的 pin 会得到 `DigestScopeMismatch`。若某次检出是纯 LF 则该测试
  `skip`（不会假通过）。
- `contract-001.json` 的 7 个身份字段全部带 `digest_scope: text/lf-normalized`，
  并附 `line_endings`；`identity_count: 7`。

### 5.2 写盘前强制 `assert_result_schema`（主代理硬要求 #1/#3）

- `ContractValidation.execute()` 在返回前**先**调
  `contracts.assert_result_schema(result)`。
- 真正的写盘入口是
  `write_checked_result(out, payload)`：**先** `assert_result_schema`，通过后才
  `emit_result()`（`x` 模式，仍拒绝覆盖）。返回 `(ok, message)`，失败时
  `cmd_validate_contract` 打印原因并返回 **exit 2**，**不创建任何文件/目录**。
- 因此 `contract-001.json` 是「过了 `assert_result_schema` 才写」的，且
  `command_class="contract"`。
- **为什么它不能报 `capability_gate='pass'`**：`validate-contract` 是协议/一致性
  校验，不是能力测量。`contracts.assert_result_schema` 规定
  `capability_gate ∈ {pass,fail}` 必须附独立裁判的 `capability_judgement`（judge +
  被封存证据的 sha256），且 `command_class='training'` 一律不许报 pass/fail；
  本命令两者都没有，于是只能 `not_run`。`capability_gate_detail` 里写明了这一点。

### 5.3 没破坏 `audit`

只做了三处**加法**：`RESERVED` 里移除 `validate-contract` 键、`build_parser()`
新增一个 `validate-contract` 子解析器、新增上述代码块。`audit` 的函数体、参数形状、
`emit_result` 语义均未改动。`touhou_rl.v430.*` 的 import 全部延迟到
`cmd_validate_contract` / `write_checked_result` 内部，`audit` 的 import 图保持原样。
