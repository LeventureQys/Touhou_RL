## 2. 分段规则

纯位置切分，是 `len(transitions)` 的确定性函数：

```text
loss_start    = k * unroll                      k = 0, 1, 2, ...
loss_end      = min(loss_start + unroll, n)     尾部可以短
context_start = max(0, loss_start - burn_in)    永不为负
context_steps = loss_start - context_start <= burn_in
loss_steps    = loss_end - loss_start = min(unroll, n - loss_start)
```

每个段返回 11 个字段：`episode_id`、`segment_index`、`episode_steps`（即 `n`）、
`context_start`、`loss_start`、`loss_end`、`context_steps`、`loss_steps`、
`steps`（整窗 `loss_end - context_start`）、`context_mask`、`loss_mask`。

两个 mask 都是**整 episode 长度**（`n` 个 bool），与输入列表、与 `gae` 的输出数组
逐位对齐，因此消费端可以直接按位置切片（`transitions[context_start:loss_end]`），
不会索引错步。`context_mask` 恰在 `[context_start, loss_start)` 为 `True`，
`loss_mask` 恰在 `[loss_start, loss_end)` 为 `True`，两者不相交。

### 200 步 / `burn_in=64` / `unroll=64` 的实际段表

| `segment_index` | context 区间 | context 长 | loss 区间 | loss 长 | 整窗 `steps` |
| --- | --- | --- | --- | --- | --- |
| 0 | `[0, 0)` | **0** | `[0, 64)` | 64 | 64 |
| 1 | `[0, 64)` | 64 | `[64, 128)` | 64 | 128 |
| 2 | `[64, 128)` | 64 | `[128, 192)` | 64 | 128 |
| 3 | `[128, 192)` | 64 | `[192, 200)` | **8** | 72 |

共 4 段，loss 长度 `64 + 64 + 64 + 8 = 200`（整条 episode，无重叠、无遗漏）。
第 0 段 `context` 长度是 **0** 而不是 64：episode 开头没有任何真实步，`context_mask`
全为 `False`，没有为凑 64 补假步。第 3 段的 loss 长度是 **8** 而不是 64：尾部按真实
剩余步数切，没有被 padding 补到 64。

### 不变量、顺序与重叠

- `segment_index` 从 0 单调递增；`loss_start` 非降，**段内顺序等于输入顺序**（函数
  从不排序、从不打散）。测试用 `reward=float(index)` 的唯一 id 验证每一段的
  `loss_mask` 选出的 reward 序列等于输入切片且严格递增，且各段拼接后恰好是
  `0..199` 各一次。
- **loss 区之间绝不相交**：`segment[k].loss_end <= segment[k+1].loss_start`
  （此处相邻），各段 loss 长度之和 == 200。
- **burn-in 区可以与上一段 loss 区重叠**，这是设计意图：第 2 段 context
  `[64,128)` 与第 1 段 loss `[64,128)` 完全重叠。重叠只发生在 context 上，
  任意两段的 `loss_mask` 交集为空。
- **跨 episode 绝不合并**：`segment_episode` 只接受单一 episode，输入出现第二个
  `episode_id` 立即 `SequenceError`；`segment_batch` 还额外校验「记录里的
  `episode_id` 必须等于该 episode 的键」，标记错位同样抛错（否则会把两个 episode
  悄悄串进一个序列）。

## 3. padding 不进统计：具体断言方式与两个分母

`padding_statistics` 对一批段返回（关键字段）：

| 字段 | 含义 |
| --- | --- |
| `effective_steps` | `Σ loss_steps` —— **唯一允许**做优势/熵统计分母的数 |
| `loss_mask_true` | 从 `loss_mask` 重新数出的 True 数，必须 `== effective_steps`（交叉校验） |
| `context_steps` / `context_mask_true` | burn-in 步数：更新 hidden，但**永远不是** loss 步 |
| `window_steps` | `Σ steps`：带真实数据的格子（context + loss） |
| `pad_width` | 矩形 batch 的行宽（默认 `max(steps)`；`pad_to` 可显式给） |
| `naive_denominator` | `sequences * pad_width` —— 把 padding 当有效步时的分母 |
| `masked_steps` | `naive_denominator - effective_steps`：必须被 mask 掉的格子数 |
| `padding_slots` | `naive_denominator - window_steps`：完全无数据的 padding 格 |

### 两个分母的实测数值

**（a）10 步短 episode**（`burn_in=64, unroll=64`，唯一一段 `loss=[0,10)`、`context=[0,0)`）：

| 口径 | 分母 | 说明 |
| --- | --- | --- |
| `effective_steps` | **10** | 真实 loss 步：断言 `== 10`，且 `loss_mask_true == 10` |
| `context_steps` | **0** | 开头不足 64 步时不补假步；断言 `context_mask_true == 0` |
| `naive_denominator`（`pad_to=64`） | **64** | 若把 padding 当有效步 |
| `masked_steps` | **54** | `64 - 10`；`padding_slots == 54` |

对照：不传 `pad_to`（行宽 = 最宽真实窗 = 10）时 `naive_denominator == 10 ==
effective_steps`、`masked_steps == 0`。**这正说明 padding 宽度必须显式声明**，
否则“两个分母相等”只是因为根本没声明 padding。

**（b）契约 rollout：512 步 episode**（8 段，行宽 `64+64=128`）：

| 口径 | 数值 |
| --- | --- |
| `sequences` | `8 == sequences_per_minibatch` |
| `effective_steps` | **`512 == effective_minibatch_steps`** |
| `context_steps` | `448`（`7 * 64`；第 0 段没有 context） |
| `window_steps` | `960`（`64 + 7 * 128`） |
| `pad_width` | `128` |
| `naive_denominator` | **`1024`**（`8 * 128`） |
| `masked_steps` | `512`（`= 448` burn-in `+ 64` padding） |

断言写成算式而不是字面量对照：`effective_steps == EFFECTIVE_MINIBATCH_STEPS`、
`naive_denominator == 8 * 128`、`masked_steps == context_steps + padding_slots`。

**fail-closed**：`padding_statistics` 会从 mask 反算 True 位置并与声明的区间逐位比对，
人为把一个 padding 格子标成 loss（把 `loss_mask` 加长一格 `True`）、或把 mask 写成
`0/1` 而非 `bool`、或 `pad_to` 比最宽真实窗还窄，都会抛 `SequenceError` 而**不是**
返回一个更大的分母。

## 4. `segment_end` 的最终语义决策（W03A TODO #2 / #1）

**决策：分段边界不改变 `terminated` / `truncated` 语义，只在数据层切分。**

W03A 把 `segment_end=True` 暂按 `truncated` 处理（`bootstrap_mask=1` +
`continuation_mask=0` + 强制要求 `terminal_value`）。本切片**推翻**该临时口径：

- `segment_end` 现在**只被校验**必须是真正的 `bool`，对
  `bootstrap_mask` / `continuation_mask` **没有任何影响**；
- 想在一个切点 bootstrap 的调用方必须**显式**表达：
  `truncated=True` + `terminal_value`，或用 `terminal_value` 结束序列；
- 这样 §7.2 的 `A_t` 不受“数据怎么摆”影响，只受“任务怎么结束”影响。

理由是数据块结束不是任务中断：把切点当 truncation 会零掉 continuation，从而**改变
切点之前所有** `advantages`；而 rollout 写出端为了分块而打标记是布局事实，不该改写
return 语义。

### 「分段不改变 advantages」的断言方式（精确 `==`，无容差）

`test_segmentation_does_not_change_advantages`：

1. 200 步 episode，`values = [0.01 * t]`，先整体跑 `gae`（`full`）；
2. 复制一份，在每个段边界（`loss_end - 1`，即索引 `63 / 127 / 191`）置
   `segment_end=True`，再跑 `gae`（`again`）；
3. 对 `advantages` / `value_targets` / `deltas` 三个键断言
   `again[key] == full[key]` —— **精确浮点相等**；
4. 再逐段断言 `again[key][loss_start:loss_end] == full[key][loss_start:loss_end]`；
5. 另做一次**真正独立**的运行：最后一段的窗口结束于真实数据末尾，因此
   `gae(transitions[128:], values[128:])` 的 `advantages` / `value_targets` 必须
   与 `full[...][128:]` **逐位相等**。

实测：**全部相等**（`True`，无容差、无需 approx）。

反向对照 `test_a_segment_boundary_is_not_a_truncation`：同一边界若写
`truncated=True`，则（i）缺 `terminal_value` 时 `SequenceError`；（ii）给了
`terminal_value=0.0` 后 `advantages` 与整体运行**不相等**。同一位置写
`segment_end=True` 则与整体运行**完全相等**。三者一起才证明“语义没变、边界没漏”。

### 序列末尾（保留 W03A 行为，并显式覆盖）

末尾元素既非 `terminated` 也非 `truncated` 时仍是 `bootstrap_mask=0`（`d = r - V`）。
`test_tail_without_end_flag_keeps_bootstrap_mask_zero` 显式断言：
`deltas[-1] == 0.25 - 0.2`、`value_targets[-1] == (0.25-0.2) + 0.2`；在末尾加
`segment_end=True` 结果不变；显式给 `terminal_value=2.0` 时才
`deltas[-1] == 0.25 + gamma * 2.0 - 0.2` 并使 `advantages[-1]` 改变。

### 与 W03A TODO #1（中段边界必须抛错）的关系

**保留、未放宽。** 中段 `episode_id` 变化且上一步既非 `terminated` 也非
`truncated` 仍然 `SequenceError`。本切片**不**替调用方合成 truncation：

- `segment_episode` 只接受单 episode，从不改写任何 end flag，因此它既不会制造、
  也不会掩盖这个边界；
- `segment_end=True` **不能**顶替 end flag：`test_segment_end_does_not_rescue_a_mid_sample_episode_boundary`
  断言 `ep1(segment_end=True) → ep2` 仍然抛错。

理由：是否该在 rollout 写出端自动合成 truncation，属于写入端契约（`contracts.check_bootstrap`
与 `TRUNCATION_REASONS` 的职责），在分段这种纯函数里猜测会让记录错误变成静默数值错误。
若将来判定要合成，应在写入端合成 `truncated=True` + `terminal_value`，而不是放宽 `gae`。
