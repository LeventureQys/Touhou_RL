## 2 CLI 接线（`tools/rl/v430.py validate-splits`）

```powershell
python tools/rl/v430.py validate-splits --config configs/v430/splits.json --out <new result.json>
```

- **参数**：`--config` 缺省 `configs/v430/splits.json`；`--out` 必填。
- **不覆盖**：`--out` 已存在时**在读取配置之前**就拒绝，exit **2**，文件一个字节都不动
  （与 `audit` / `validate-contract` 同一约定，复用同一 `emit_result` 的独占创建）。
- **调用方式**：`lineage.validate_splits(str(cfg_path), strict=True)`——**不带任何放宽参数**，
  CLI 也不提供放宽开关。
- **写盘顺序**：`SplitsValidation.execute()` 末尾先 `contracts.assert_result_schema(result)`，
  失败就抛错不返回结果；`cmd_validate_splits` 再用 `write_checked_result(out, result)`
  做第二次 schema 校验，通过后才 `emit_result` 独占创建文件。**不存在"先写后校验"的路径**：
  schema 不过 → 不写文件 → 退出码 2。
- **`command_class = "data"`**：取自 `contracts.COMMAND_CLASSES` 已注册枚举
  （`audit / contract / training / evaluation / confirmation / adaptation / settlement / planning / data / teacher`）。
  W09 校验的是**数据谱系注册表**，既不是 W01 的 `contract`（配置↔模块协议一致性），
  也不是 `evaluation`（不跑 episode）。**没有自造新枚举值**。
- **`capability_gate = "not_run"`**：谱系校验不是能力测量。`capability_gate_detail` 里写明理由，
  并把 `G430-E0` / `G410-6` 都记为 `not_run`。`contracts.assert_result_schema` 保证本命令无法
  把它抬成 `pass`/`fail`（那需要独立的 `capability_judgement` 记录）。
- **`split_registry_sha` + `digest_scope`**：直接取纯函数返回的 `split_registry_sha` 与其
  `split_registry_sha_scope`，同时以 `digest_scope`、`split_registry_sha_scope`、
  `split_registry_sha_canonicalization` 三个字段成对记录，摘要不裸奔
  （顶层、`research_result` 里各一份，两处一致）。

（纯函数把自己的判定归为输入/协议决定，见 `lineage.py` 末段与 `W09.md` §2）。本 CLI **没有**改
`lineage`，而是在结果里保留它的原判 `research_result.lineage_exit_code = 2`（测试里对同一份配置
断言了这一点），同时按 `EXECUTION_PLAN.md` §4 把"有效测量未达门"映射到进程退出码 **3**。
只有两种情况仍走 2 且**不写文件**：配置读不出来/解析不了/schema 不是 `v430-splits/1`
（`load_splits_config` 提前 fail-closed），以及纯函数报告里出现 `P_CONFIG_UNREADABLE` / `P_SCHEMA`
（`SPLITS_INVALID_INPUT_CODES` 兜底）。

## 7 剩余阻塞 / 风险（不隐瞒）

1. **本包不是能力证据**：`capability_gate = not_run`。G430-X 只多了"谱系腿有真实 CLI 证据"这一小块，
   仍未通过；G410-6 仍需 W10 在两个冻结留出家族上跑真实 episode。
2. **`2` vs `3` 是两套口径并存**：`lineage.exit_code_for` 保持 2（纯函数自认输入/协议决定，未改），
   CLI 按计划表给 3。两份口径都写进了结果（`lineage_exit_code` 与 `exit_code`），下游若只看
   `lineage.exit_code_for` 会看到 2——这是**有意保留**的差异，不是漏改。
3. **证据文件不可覆盖**：`splits-001.json` 已经存在，重跑同一 `--out` 会 exit 2。要刷新证据必须换新
   文件名（例如 `splits-002.json`）或人工删除旧文件；本包不删除任何证据。
4. **`.tmp_w09b_audit.json` / `.tmp_w09b_contract.json`** 是本包做回归时的临时产物，被 `.gitignore`
   覆盖，不作为正式证据；正式证据只有本目录下的 `splits-001.json` 与本文件。
5. **既有工作树状态与本次无关**：`git status` 里 `Document/Dialogs/*.md` 的删除、以及整个 v4.3.0
   代码树的未跟踪状态，在本包开始前就存在，本包未动它们，也未 `git add`。
