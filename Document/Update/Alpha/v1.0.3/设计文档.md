## 0. 三十秒上下文

## 3. 架构 v2：三流独立编码器 + heatmap 坐标

### 3.1 设计意图（为什么是这三个改动）

1. **场地流保留空间分辨率**：自机是 ~16×16 原生像素的小目标，弹幕是 2–10 px 的点。把 14×12 的特征图平均成 2×2，等于把「自机在左半还是右半」以外的信息全部丢给后面的一层线性层。v1 的 70.97 px 与「只知道象限时 ~48–56 px 的误差地板」同量级，说明它确实退化到了象限级。
2. **坐标用 heatmap + 加权期望**：直接回归两个标量时，梯度只能通过全局池化后的向量回传，无法表达「位置在空间上是局部的」。heatmap 让每个空间格都参与预测，加权期望再给出亚格精度。
3. **HUD 独立编码器**：HUD 是文字与图标（笔画级高频、位置固定），场地是稀疏点目标。共享卷积核等于要求同一组滤波器同时擅长两件事；而 HUD 三块区域尺寸差异极大（34×216 与 126×216），共享也迫使池化尺寸统一。

### 3.2 输入契约（不变）

| 分区 | 原生尺寸 (H,W) | 模型输入 (H,W) | 说明 |
| --- | --- | --- | --- |
| `playfield` | 448×384 | 224×192 | 精确 1/2 缩放，保持纵横比；`Image.BOX` 区域平均（`vision.resize_area`） |
| `hud_score` | 34×216 | 34×216 | 原生，不缩放 |
| `hud_status` | 126×216 | 126×216 | 原生，不缩放 |

- 帧张量：`uint8`，每分区 `[B, depth, H, W, 3]`；经 `vision.regions_to_batch` 变成 `float32/255`（唯一预处理入口，不得复制第二份）。
- `depth` 默认 1（可 3）。`depth` 只影响卷积输入通道数 `3*depth`。

### 3.3 网络结构（完整定义）

```
playfield 分支（独立权重）
  Conv2d(3*depth → 32, k=5, s=2, p=2) + ReLU     -> (112, 96)
  Conv2d(32 → 64,  k=3, s=2, p=1) + ReLU          -> (56, 48)
  Conv2d(64 → 96,  k=3, s=2, p=1) + ReLU          -> (28, 24)   # 总 stride 8
  Conv2d(96 → 96,  k=3, s=1, p=1) + ReLU          -> (28, 24)   # 空间精修
  ├─ heatmap_head : Conv2d(96 → 1, k=1)                     -> [B, 1, 28, 24] -> squeeze(1) 后对外暴露 [B, 28, 24]
  ├─ danger_head  : AdaptiveAvgPool2d((16, 8)) + Conv2d(96 → 1, k=1) -> logits16 [B, 1, 16, 8]
  └─ global_pool  : AdaptiveAvgPool2d((2, 2)).flatten -> 384
                    Linear(384 → 128) + ReLU                -> pf_vec [B, 128]

hud_score 分支（独立权重，width=16）
  Conv2d(3*depth → 16, k=5, s=2, p=2) + ReLU       -> (17, 108)
  Conv2d(16 → 32, k=3, s=2, p=1) + ReLU            -> (9, 54)
  Conv2d(32 → 48, k=3, s=2, p=1) + ReLU            -> (5, 27)
  AdaptiveAvgPool2d((2, 8)).flatten -> 768
  Linear(768 → 64) + ReLU                          -> score_vec [B, 64]

hud_status 分支（独立权重，width=16，与 hud_score 结构相同但权重独立）
  ... -> (16, 27)
  AdaptiveAvgPool2d((8, 4)).flatten -> 1536
  Linear(1536 → 64) + ReLU                         -> status_vec [B, 64]

fusion
  trunk = ReLU(Linear(256 → 256)(concat[pf_vec, score_vec, status_vec]))   -> [B, 256]

heads
  self_head  : ReLU(Linear(256 → 256)) → Linear(256 → 22)   # self_feat[2:24]
  candidate_embed : Embedding(18, 64)
  score_head : ReLU(Linear(256+64 → 64)) → Linear(64 → 1)   # 每个候选一个值 -> [B, 18]
```

- 允许实现者在**不改变任何外部契约（§3.4/§3.5）**的前提下微调通道数，但参数量必须落在 **450,000–650,000**（单测断言，见 S3-1 任务书）。
- HUD 两分支必须**权重独立**：不得复用同一个 `nn.Module` 实例。
- 三路分支都**不得**把特征图池化到 (2,2) 作为唯一空间信息出口；场地流的空间信息出口是 heatmap 与 danger 头。

### 3.4 输出契约（硬约定）

`VisionScorerV2.decode_state(regions, features=None) -> dict`：

| 键 | 形状 | dtype | 含义 |
| --- | --- | --- | --- |
| `self_feat` | `[B, 24]` | float32 | 特权观测的 24 维回归输出；**0:2 由 heatmap 解码填充**，2:24 来自 `self_head` |
| `danger_log` | `[B, 128]` | float32 | `log1p(danger/8)`，**行主序展平**（16 行 × 8 列） |
| `heatmap_logits` | `[B, 28, 24]` | float32 | heatmap 原始 logits（训练用；部署不需要） |

其它方法（与 v1 同名同签名，`evaluate.py` 依赖）：

| 方法 | 返回 |
| --- | --- |
| `features(regions)` | `[B, 256]` |
| `score(regions, features=None)` | `[B, 18]`，候选 = `focus*9 + move`（与 `pilot.candidate_scores` 的列顺序一致） |
| `act(regions, deterministic=True)` | `(actions[B,4] int64, zero[B], value[B], zero[B])`；`actions[:,1]=1`（始终射击）、`actions[:,3]=0`（不放雷） |
| `num_parameters()` | int |
| `config.region_sizes` | `dict[str, tuple[int,int]]`，键必须是 `playfield`/`hud_score`/`hud_status` |
| `config.depth` | int |

**错误行为**：`regions` 缺少 `config.region_sizes` 里的任一分区时抛 `KeyError`，消息格式 `missing regions [..]; got [..]`（与 v1 一致）。`decode_state` 在 `state_head=False` 时抛 `RuntimeError("this model was built with state_head=False")`。

### 3.5 数值细节（必须逐条实现，不得自行发挥）

**(a) heatmap 目标构造**

```
grid_w, grid_h = 24, 28
rx, ry = truth_self_feat[:,0], truth_self_feat[:,1]        # 已在 [0,1]，playfield 相对坐标
gx = rx * grid_w - 0.5                                     # 连续格坐标，格中心 = 整数
gy = ry * grid_h - 0.5
gx = clip(gx, -1.0, grid_w)                                # 允许落在边界外半格
gy = clip(gy, -1.0, grid_h)
target[i, y, x] = exp(-((x-gx)^2 + (y-gy)^2) / (2*sigma^2)), sigma = 1.5
target /= target.sum()                                     # 归一化为概率分布
```

**(b) heatmap 损失**：`loss_heatmap = -(target * log_softmax(logits.flatten(1), dim=-1)).sum(-1).mean()`，即对归一化高斯目标的交叉熵（等价于 KL 差一个常数）。

**(c) 坐标解码（训练指标与部署共用同一函数）**

```
p = softmax(logits.flatten(1), dim=-1)                     # [B, 672]
col = (p * arange(grid_w ).expand(grid_h, grid_w).flatten()).sum(-1)   # 0..23
row = (p * arange(grid_h).unsqueeze(1).expand(grid_h, grid_w).flatten()).sum(-1)
rx_hat = (col + 0.5) / grid_w
ry_hat = (row + 0.5) / grid_h
self_feat[:,0], self_feat[:,1] = rx_hat, ry_hat
```

该函数必须是**模块级公共函数** `vmodels2.decode_position(logits) -> (rx, ry)`，训练指标与 `decode_state` 都调用它（理由与 `regions_to_batch` 相同：两次实现一定漂移）。

**(d) danger 目标与损失**：目标 `log1p(danger/8)`（`danger` 为 uint8 计数，[16,8]）；损失 `smooth_l1(danger_log.reshape(B,16,8), target)`。池化到 (16,8) 用 `adaptive_avg_pool2d`，它与 28×24 特征图的边界对齐误差 ≤ 0.875 个特征格（≈7 原生 px），相对 28 px 的 danger 格可接受；单测需验证「合成单格弹点在预测中被定位到正确格或相邻格」。

**(e) self 头损失**：`smooth_l1(self_feat[:,2:24], truth[:,2:24])`。**不对 0:2 加回归损失**（位置只由 heatmap 损失驱动），避免两套梯度互相抵消。

**(f) 总损失**：`loss = w_heat*loss_heatmap + w_self*loss_self + w_danger*loss_danger`，默认 `(1.0, 1.0, 1.0)`，可在 `VisionTrainConfig` 中配置。默认不做梯度累积、梯度裁剪 1.0（与 v1 一致）。

**(g) policy 阶段**：损失与 v1 完全一致（`smooth_l1(predicted[18], clip(teacher,-8,40)/10)`），只把主干换成 v2。

### 3.7 位置精度的可行性地板（实测）

目标 `< 10 px`，先确认结构上到不了 10 px 的不是这份设计。三个可量化的下限（验证集 7,247 帧实测）：

| 项 | 数值 | 说明 |
| --- | ---: | --- |
| 网格量化（one-hot argmax 解码） | **4.00 px** | 每格 16 原生 px（448/28 = 384/24 = 16），argmax 落在格中心，单轴误差均匀分布 → 均值 8/2 = 4 px |
| 解码范围限制 | **0.557 px** | `soft-argmax` 输出被限制在 `[0.5/W, 1-0.5/W]`；验证集有 3.99% 帧的 `rel_x` 越界（最远 -0.062），实际贡献仅 0.56 px |
| 合计 | **≈ 4.6 px** | 相对 10 px 目标留约 2 倍余量；soft-argmax 在格间插值还能低于该值 |

同时记录两个会影响读数的事实：

- `rel_y` 在 **0.929** 处饱和（p95 = p99 = 0.929，对应原生 y≈416 px，是自机移动区的下边界），因此 y 方向的难度集中在「是否贴底」而非连续定位；
- 「永远预测验证集中位数」这一平凡基线的位置误差是 **82.65 px**，比 v1 的 70.97 px 还差 —— 说明 v1 确实学到了东西，只是精度停在象限级。

## 4. checkpoint 契约（跨 SubStage C5）

`save_vision_checkpoint(path, model, extra=None)` 产出的 payload：

```python
{
  "kind": "vision_scorer",
  "arch": "v1" | "v2",          # 新增；由 model 类型推断，调用方不需要传
  "state_dict": {...},
  "config": {...},              # v1: VisionNetConfig.__dict__；v2: VisionNetConfigV2.__dict__
  "frame": {"H": 128, "W": 112, "C": 3, "depth": int},   # 兼容字段，保持不变
  "extra": {...},
}
```

`load_vision_checkpoint(path, map_location) -> (model, extra)`：

1. `kind != "vision_scorer"` → `ValueError("not a vision checkpoint")`；
2. `arch` 缺失 → 按 `"v1"` 处理（旧 checkpoint 必须仍能加载，这是回归项 V-09）；
3. `arch == "v1"` → `VisionScorer(VisionNetConfig(**config))`；
4. `arch == "v2"` → `VisionScorerV2(VisionNetConfigV2(**config))`；
5. 其它 → `ValueError(f"unknown vision arch {arch!r}")`；
6. `frame.H/W` 与 `vision.VISION_H/W` 不一致 → 保持 v1 现有行为（抛 `ValueError`）。

`VisionNetConfigV2` 必须是 `@dataclass`，字段全部可 JSON 序列化（tuple 会被 `json` 自动转 list，加载时需转回 tuple）。

## 5. 指标契约（跨 SubStage C2）

新模块 `touhou_rl/vision_metrics.py`，**纯 numpy，不依赖 torch**。所有函数签名固定如下（S3-2 产出，S3-3 调用）：

```python
def player_position_mae_px(pred: np.ndarray, truth: np.ndarray) -> tuple[float, float]
    """pred/truth: [N, 24] 归一化 self_feat。返回 (mean_px, p95_px)。
    单帧误差 = (|dx|*384 + |dy|*448) / 2；mean_px 与 v1 的 val_player_pos_px 同口径（保证 70.97 可比）。"""

def danger_metrics(pred_log: np.ndarray, truth: np.ndarray) -> dict
    """pred_log: [N, 128] 或 [N,16,8]；truth: [N,16,8] uint8。
    返回 {"danger_corr","danger_corr_perframe_mean","danger_corr_perframe_median",
          "danger_corr_perframe_valid","danger_iou","danger_cell_acc","danger_mae_log"}。
    - danger_corr：全部（帧×格）展平后一次 Pearson（v1 口径，保留可比）
    - perframe_*：逐帧 128 格 Pearson；pred 或 truth 为常量时该帧无效（nan），不计入
      mean/median，无效帧数写入 danger_corr_perframe_valid
    - busy 判定：log 目标 > 0.2（与 v1 一致）；iou = |P∩T| / |P∪T|（并集为 0 时该帧不计入）
    """

def bullet_count_mae(pred: np.ndarray, truth: np.ndarray) -> float
    """索引 14（active_count/700）× 700 的平均绝对误差。Q1 的修复点。"""

def ray_mae(pred: np.ndarray, truth: np.ndarray) -> float
    """索引 16:24 的平均绝对误差（v1 口径）。"""

def self_mae(pred: np.ndarray, truth: np.ndarray) -> float
    """全 24 维平均绝对误差（v1 口径）。"""

def policy_metrics(pred: np.ndarray, teacher: np.ndarray, bullets: np.ndarray) -> dict
    """pred: [N,18] 模型输出；teacher: [N,18] px 单位真值；bullets: [N,64,6]。
    返回 {"top1","regret_px","by_danger":[{bucket,frames,top1,regret_px}...]}。
    by_danger 桶边界固定 (0,15),(15,30),(30,60),(60,120),(120,inf)，标签格式 "0-15" / "120+"。

    **最后一桶的判据是 `danger >= 120`（不是 `danger < inf`）**：64 个子弹槽全无效时距离为 inf，

def heatmap_hit_rate(logits: np.ndarray, truth: np.ndarray) -> float
    """logits: [N,28,24]；truth: [N,24]。argmax 格是否落在真值的 3×3 邻域内。诊断用。"""

def all_state_metrics(pred_self, pred_danger_log, truth_self, truth_danger, *,
                      heatmap_logits=None) -> dict
    """聚合 state 阶段指标。pred_self/truth_self: [N,24]；pred_danger_log: [N,128] 或 [N,16,8]；
    truth_danger: [N,16,8]。返回键（不带 val_ 前缀）：
      self_mae, player_pos_px, player_pos_p95_px, ray_mae, bullet_count_mae,

      danger_corr_perframe_valid, danger_iou, danger_cell_acc
      [+ heatmap_hit_rate 当 heatmap_logits is not None]
    这些键加 `val_` 前缀后必须与 §7.2 的 summary 字段一一对应（S3-3 负责加前缀）。
    """
```

口径约束（违反即验收失败）：

- `player_position_mae_px` 的**主口径**是 `(|dx|·384 + |dy|·448)/2` 的均值，与 v1 的 70.97 px 严格可比；不得改成欧氏距离（那会系统性放大 1.0–1.4 倍且不可比）。
- `danger_corr` 与 `danger_corr_perframe_median` **必须同时报告**；A-01 只认 per-frame median。
- `by_danger` 的 **120+ 桶包含「最近弹距离未定义」的帧**（64 槽全无效，画面无子弹）。v1 的旧实现按 `danger < inf` 分桶会把这类帧从所有桶丢掉，导致 `120+` 桶的 `frames` 与 `regret_px` 与 v1 不可直接比较（v1.0.2 报的 `120+ = 1.869` 是丢弃后的值）。0–15 桶不受影响，A-02 判据不受影响。
- 所有指标在验证集上计算时，验证集必须由 manifest 校验（§6.1）。

## 6. 数据切分与 R3 设计（Q3 + D5）

### 6.1 训练启动门禁

```
manifest = DatasetManifest.load(dataset_dir/"manifest.json")   # 缺失 → ManifestError
train_idx, val_idx = manifest.verify(dataset_dir)             # 分片存在性 + 字节数 + 多余文件 + 分割哈希
```

- `verify()` 返回的 `val_idx` 必须与 `index_digest` 记录一致（`manifest.py:174-179` 已实现）；
- 训练**不得**再用 `default_rng(seed).permutation(total)` 现场重算（这是 D1 的修复点）；
- 例外：合成测试数据集通常没有 manifest → CLI 提供 `--allow-missing-manifest`，此时划分回退到现场推导并在 summary 里写 `"manifest_verified": false`。**真实数据集上不得使用该开关**（验收 V-08 会检查）。

### 6.2 子采样规则（R3 的数据来源）

- 验证集永远取 manifest 的 7,247 个索引，**不参与子采样**；
- 训练集（65,225 帧）按 stage 分层：
  1. 用 `VisionDataset.stage_of(indices)` 取每个索引的 stage（来自分片 `meta[:,1]`）。**索引语义**：入参与出参都是**数据集全局索引**（`0..total-1`），返回 `int64` 数组、形状与入参相同；因此要按索引查表必须先取全量 `stage_map = dataset.stage_of(list(range(total)))`，此时 `stage_map[i]` 就是全局索引 `i` 的 stage；
  2. `stratified_prefix(train_indices, stage_of, fraction, seed)` 的第二个参数就是这份 `stage_map`，函数内部用 `stage_of[index]` 查表（**按全局索引取，不是按 `train_indices` 里的位置取**）；
  2. 按 stage 升序遍历；每个 stage 内对索引排序，再用**同一个** `np.random.default_rng(seed)` 实例依次 `permutation`（即单实例顺序消费，不是每个 stage 新建一个同 seed 的 rng；两种读法的可观察契约——可复现、分层、嵌套、fraction=1.0 集合相等——完全相同，此处固定为单实例）；
  3. 取前 `round(fraction * n_stage)` 个；
  4. 拼接后按索引升序返回。
- `fraction=1.0` 必须返回原训练集（顺序可不同，集合必须相同）。
- **嵌套性**：同一 seed 下 `subset(0.25) ⊂ subset(0.5) ⊂ subset(1.0)`，单测断言。

### 6.3 R3 三个数据点与判定

| 数据点 | `--train-fraction` | 训练帧数（实测，逐 stage 取整后求和） | 用途 |
| --- | --- | --- | --- |
| D1/4 | 0.25 | **16,307** | 曲线左端 |
| D2/4 | 0.50 | **32,613** | 曲线中点 |
| D4/4 | 1.00 | **65,225** | 与 R1 主实验同一配置 |

> 注意：逐 stage 取整再求和会与「对总数取一次 round」差 1 帧（16,306 vs 16,307）。以本节实测值为准，验收时允许 ±1%。

判定规则（写死，避免事后解释）：

- **「数据仍有收益」** ⇔ 在 100% 点上，`val_player_pos_px(1.00) ≤ 0.85 × val_player_pos_px(0.50)` **或** `val_regret_px_bucket_0_15(1.00) ≤ 0.90 × (0.50)`；
- 否则判**「已平台化」**，R4 不执行，A-05 记为「条件未触发」；
- 「有收益」也不自动执行 R4：按 Q3 裁决，先补采 3 份回放做跨回放验证（约 2 小时 / 65 GB），再决定全量。

### 6.4 同架构同验证集约束（D8）

R3 的三个训练点必须使用**同一个架构配置、同一份验证集、同一套指标代码**；只允许 `--train-fraction` 不同。不得引用 v1.0.2 的 4,524 帧 vs 72,472 帧跨分布对比作为结论。

### 7.3 选模与 checkpoint 落盘

| 文件 | 何时写 | 选模键 |
| --- | --- | --- |
| `state.pt` | 每次 `val_player_pos_px` 刷新最小值 | `val_player_pos_px`（D2） |
| `state-bestdanger.pt` | 每次 `val_danger_corr_perframe_median` 刷新最大值 | per-frame median（对照用） |
| `state-pass.pt` | **首次**出现「`val_player_pos_px < 10.0` 且 `val_danger_corr_perframe_median > 0.8`」的 epoch | 联合达标（见下） |
| `policy.pt` | 每次 `val_regret_px` 刷新最小值 | `val_regret_px`（沿用 v1 结论） |
| `best.pt` | 与最后执行的阶段一致 | 兼容保留，**不作验收依据** |

**为什么需要 `state-pass.pt`**：A-01 要求两个阈值**同时**满足，而 `state.pt` 只按位置选。若第 3 轮 pos=9.5 / perframe=0.85（联合达标），第 5 轮 pos=8.0 / perframe=0.70（位置更优但联合未达），那么按位置选模会丢掉唯一同时达标的权重，A-01 会被误判为失败 —— 这是假失败。因此：

1. 训练侧：联合达标时立即写 `state-pass.pt`（`extra={"stage":"state-pass","a01":{"pos_px":…,"perframe_median":…,"epoch":…}}`），**只写第一次**，不覆盖；
2. 判定侧：A-01 的正确判定是「**存在**某个 epoch 同时满足两个阈值」，而不是「位置最优的 epoch 满足」。`check_a01.py` 必须扫描 `stages.state.history`（见 S3-5 任务书）；
3. **部署必须用 `policy.pt`，不得用 `state-pass.pt`**：A-01 的证据用 `state-pass.pt`（或 history 里的达标轮次），但 `state-pass.pt` 产自 state 阶段，**评分头从未训练过**，拿去 `act()` 等于随机策略。A-04 只允许用同一个 run 的 `policy.pt`（它的主干已在 state 阶段训练过）。
4. 若 A-01 在 state-only 的筛选跑里达标而主实验未达标，A-01 仍判 fail（主实验才是验收对象），`state-pass.pt` 只作诊断证据。

`extra` 字段至少包含：`{"stage", "epoch", "arch", "train_fraction", "val_index_sha256"}`。

### 7.4 训练集/验证集批次限制必须分离

v1 的 `batches()` 用同一个限制切 train 与 val。筛架构时会用 `--max-train-batches`，若同时切小 val，则 `val_player_pos_px` 只在 10% 的验证帧上算，噪声足以让两个配方排名颠倒。因此：

- `--max-train-batches` 只作用于训练；
- `--max-val-batches` 只作用于验证，实验脚本必须显式设为 0。

### 7.5 实验落盘规则（D4）

- 每次尝试写 `third_party/th08/build/rl/runs/v103-exp-<NN>/`，`<NN>` 为两位序号；
- **禁止覆盖** `runs/pilot-v1/`（v1.0.2 多份报告引用它作证据基线）；
- 实验表 `Document/Update/Alpha/v1.0.3/Stage3/实验表.md`，一行一次尝试，列固定：
  `| 序号 | 配方 | arch | 训练帧数 | max_train_batches | 位置误差 px | perframe corr 中位数 | 0-15 桶后悔值 | 用时 s | summary 路径 |`；
- 一个配方只允许改一个变量；同时改两项必须拆成两行并在「配方」列注明组合原因。

## 8. 部署端契约（R5 / A-04 + 跨 SubStage C6）

### 8.1 隔离性口径的澄清（重要）

需求文档 R5 写「该局全程不调用 `state.py`」。**字面不可实现**：`evaluate.py` 通过 `Th08Env`（`touhou_rl/env.py`）驱动游戏，`env.reset()` / `env.step()` 内部必然读内存来计算奖励、死亡与终止条件——那是评估脚手架，不是策略。

因此本版把该要求落成**可验证的三条**：

1. **I-1 策略输入只有像素**：`vision_model.act(...)` 的唯一入参是 `vision.regions_to_batch(stacks, device)`，`stacks` 仅由 `env.render()` 的截图经 `_regions_from_screen` + `FrameStack` 产生（`evaluate.py:144-169`）；
2. **I-2 策略侧不出现特权字段**：视觉分支的代码路径不得引用 `obs.Observation`、`info["bullets_raw"]`、`info["bosses"]`、`state.*`；
3. **I-3 可自动验证**：注入 stub env（只提供 `render/reset/step/action_space/close`）跑 3 步，`step` 在 `info` 里放入带哨兵/毒丸的 `bullets_raw`/`bosses`，断言策略输出与它们无关（同样像素 → 同样动作），且 `env.state` 访问计数为 0。实现拆成三条测试（`test_vision_act_receives_pixels_only` / `test_policy_never_reads_env_state` / `test_actions_independent_of_privileged_fields`），见 S3-4 任务书 §5。

### 8.2 `eval-report.json` 的视觉节点（跨 SubStage C6）

### 8.3 A-04 判据（D6）

- `--episodes 3`（不少于 3），`frameskip=2`、`difficulty=lunatic`、`team=0`；

- 逐局数字全部入报告；**不得**用 ran-out-of-max_steps 的局冒充存活。

### 8.4 帧堆叠深度必须来自 checkpoint（现存缺陷，本版必修）

**现状**：`evaluate.py:50` 的 `vision_depth` 默认 `3`，`evaluate.py:149-154` 用它构造 `FrameStack`；但模型卷积的输入通道数是 `3 * config.depth`（`vmodels.py:82` 与 v2 同构），由训练时的 `--depth` 决定。试点模型 `runs/pilot-v1` 的 `depth` 是 **1**，而 `--vision-depth` 默认 3 → `regions_to_batch` 产出 `[B,3,H,W,3]`，`_as_batched` reshape 成 `[B,9,H,W]`，`conv2d` 期望 3 通道 → `RuntimeError`。也就是说：按需求文档 R5 的命令（不传 `--vision-depth`）部署一个 depth=1 的模型，**今天就会崩**。

**契约**：

1. `--vision-depth` 默认改为 `0`，语义为「跟随 checkpoint 的 `config.depth`」；
2. 非 0 且与 checkpoint 的 depth 不一致 → `SystemExit(f"--vision-depth {n} != checkpoint depth {d}")`，**不得**静默覆盖；
3. `eval-report.json` 的 `vision.depth` 记录实际使用的深度（即 `config.depth`）；
4. 单测必须覆盖「默认跟随 checkpoint」与「显式冲突时报错」两条。

## 12. 风险与未决项

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| heatmap 在 28×24 下仍达不到 10 px | A-01 失败 | D3 已留退路：下探 stride 4（56×48，8 px/格），代价约 ×1.6 显存与时间 |
| per-frame corr 主判据过严 | A-01 可能在 8 epoch 内不达标 | 允许增加 epoch 数；实验表记录 epoch 与指标曲线，判定用 best epoch |
| v2 每次尝试耗时高于需求文档的「10 分钟」 | Stage 3 预算从 1–2 天变紧 | 用 `--max-train-batches` 先做筛（val 全量），胜出配方再全量确认；筛一次约 6–8 分钟 |
| 帧级子采样高估数据价值（同回放相邻帧相关） | A-03 判定偏乐观 | Q3 已规定：若有斜率先补采 3 份做跨回放验证；A-05 仍不自动触发 |
| 真机启动测试需要独占游戏窗口 | 可能阻塞 S3-6 | 若无法启动，按纪律写入问题清单置顶区，不得用训练指标替代 |
| v2 的 danger 池化对齐有 ≤7 px 近似 | danger 指标上限略降 | 单测限定 ±1 格容差；per-frame corr 判据不含对齐假设 |
