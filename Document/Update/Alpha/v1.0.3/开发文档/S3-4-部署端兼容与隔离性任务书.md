## 1. 背景与目标（无需任何对话历史）

项目的终极目标是**部署端只看像素**：模型只吃用户框选区域的截图，不许读游戏内存。当前评估入口 `touhou_rl/evaluate.py` 已经有一条视觉分支（`--vision-checkpoint`），它只把 `env.render()` 的截图喂给模型。

现在有三件事要补：

1. **v2 架构兼容**：新架构（S3-1）的 checkpoint 要能被同一入口加载与推理；
2. **可自动验证「只看像素」**：需求文档写的是「该局全程不调用 `state.py`」，但 `Th08Env.step()` 内部必然读内存算奖励与终止——那是评估脚手架，不是策略。因此本版把要求落成可测的三条（见 §4.2），需要给 `run_evaluation` 注入 stub env 的能力；
3. **证据完整**：`eval-report.json` 里要能读到「用了哪个架构、每块分区喂多大」，否则 A-04 的结论无法被复核。

**你的目标**：改 `evaluate.py` 让 v1/v2 都能部署、报告带上视觉节点、并给出可自动化的隔离性证明。你**不**需要跑真机（那是 S3-6）。

## 4. 实现契约

### 4.1 让 env 可注入（为可测性，最小改动）

在 `EvalConfig` 增加字段：

```python
env_factory: Callable[[EnvConfig], object] | None = None   # None -> Th08Env
```

`run_evaluation` 里：

```python
env = (cfg.env_factory or Th08Env)(EnvConfig(...))
```

- **参数名、默认值、行为**：默认 `None` 时与现在完全一致（真实游戏）。
- 不得改变 `EnvConfig` 的构造参数或 `Th08Env` 的任何行为。

### 4.2 隔离性的三条可验证约束（这是本 SubStage 的核心）

需求文档 R5 的「全程不调用 `state.py`」在字面上不可实现（`env.step()` 内部要读内存算奖励与终止）。本版把它落成：

| 编号 | 约束 | 验证方式 |
| --- | --- | --- |
| I-1 | 策略的唯一入参是像素张量 | 视觉分支里 `vision_model.act(...)` 的实参必须且只能是 `vision.regions_to_batch(stacks, device)`；`stacks` 只能来自 `env.render()` |
| I-2 | 视觉分支代码路径不引用任何特权字段 | 在该分支内不得出现 `info["bullets_raw"]`、`info["bosses"]`、`obs.Observation`、`state.` 字样（`grep` 可查） |
| I-3 | 策略输出与特权字段无关（自动化） | 单测：stub env 的 `info` 里塞入「毒丸」对象（任何属性访问都抛 `AssertionError`），跑 3 步；断言不抛异常、动作与另一组不含毒丸的 run 完全一致 |

实现要求：

- 视觉分支只允许从 `info` 读 `episode`（用于本局统计）；**不得**读 `bullets_raw` / `bosses` / `bombs` 之外的任何特权键。`bombs` 读取仅出现在视觉分支之外（见 `evaluate.py:162-163`），保持原样。
- 建议在视觉分支加一行注释说明为什么 env 仍会读内存（供复核者理解，不改变行为）。

### 4.3 `eval-report.json` 的视觉节点（跨 SubStage 契约 C6）

仅当 `vision_model is not None` 时，`report` 顶层增加：

```json
"vision": {
  "checkpoint": "third_party/th08/build/rl/runs/v103-exp-01/policy.pt",
  "arch": "v2",
  "depth": 3,
  "region_sizes": {"playfield": [224,192], "hud_score": [34,216], "hud_status": [126,216]},
  "frame_shape": {"playfield": [224,192,3], "hud_score": [34,216,3], "hud_status": [126,216,3]},
  "isolation": "I-1: policy input is regions_to_batch(env.render crops) only; env bookkeeping still reads memory"
}
```

- `arch` 取自 checkpoint 的 `extra` 或 payload（`load_vision_checkpoint` 返回的模型类型也可判定：`VisionScorerV2` → `"v2"`，`VisionScorer` → `"v1"`）。**两处都要能判**，以模型类型为准。
- `region_sizes` 取自 `vision_model.config.region_sizes`（两个 config 都有该 property）。
- `report["policy"]` 必须仍为 `"vision"`（`evaluate.py:113-122` 的逻辑不变）。
- 不得删除或改名任何现有报告字段（`checkpoint_extra`、`frameskip`、`episodes`、`summary` 等）。

### 4.4 帧堆叠深度必须来自 checkpoint（必修缺陷）

**现状（会在 S3-6 直接崩）**：`evaluate.py:50` 的 `vision_depth` 默认 `3`，`evaluate.py:149-154` 用它建 `FrameStack`；但模型卷积要求的输入通道数是 `3 * config.depth`（`vmodels.py:82`，v2 同构）。试点模型 `runs/pilot-v1` 的 `depth` 是 **1**，所以按需求文档 R5 的命令（不传 `--vision-depth`）部署 depth=1 模型时，`regions_to_batch` 产出 `[B,3,H,W,3]`、`_as_batched` reshape 成 `[B,9,H,W]`，`conv2d` 期望 3 通道 → `RuntimeError`。

**契约**：

1. `--vision-depth` 默认值改为 `0`，语义 = 「跟随 checkpoint 的 `config.depth`」；
2. 解析顺序：先 `load_vision_checkpoint`，取 `depth = model.config.depth`；再若 `args.vision_depth != 0 and args.vision_depth != depth` → `SystemExit(f"--vision-depth {args.vision_depth} != checkpoint depth {depth}")`；
3. `EvalConfig.vision_depth` 字段保留，但 `run_evaluation` 内部一律用 `model.config.depth` 建 `FrameStack`；
4. `eval-report.json` 的 `vision.depth` 记录实际使用的深度。

### 4.5 兼容要求

- `--vision-checkpoint` 指向 v1 checkpoint（payload 无 `arch`）→ 正常部署，`report["vision"]["arch"] == "v1"`；
- 指向 v2 checkpoint → 正常部署，`arch == "v2"`；
- 不存在 `--vision-checkpoint` 时**不出现** `vision` 节点（其它 policy 分支的报告结构零变化）。
