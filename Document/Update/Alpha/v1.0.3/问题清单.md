## 2.5 置顶区（Q4，验收阶段新增，未关闭）

### Q4 · 数据集 73% 的样本画面冻结，标签仍在前进 —— 使 A-01/A-02/A-04 的判定与 v1.0.2 的核心结论同时失效

- **问题描述**：`third_party/th08/build/rl/datasets/pilot-ud0059` 中，从分片 `ud0059-00153.npz` 开始到最后一个分片 `ud0059-00565.npz`（共 414 个分片、52,888 个样本、占全量 **73.0%**），每个分片内三块分区（`playfield` / `hud_score` / `hud_status`）的 PNG **只有 1 张唯一内容**；而同一分片内的 `meta.frame` 正常推进（如 4134→4136→…→4388）、`self_feat` 有 73 个不同取值。冻结的那一帧与**最后一帧干净帧**（`ud0059-00152.npz` 的最后一帧，全局索引 19,583）**SHA-256 完全相同**（`2cdd709898ce…`，311,702 字节）。
- **实测证据**：
  - 干净区间：全局帧 `0 … 19,583`（19,584 帧，27.0%），覆盖 stage 0 全部、stage 1 全部、stage 2 的前约 2,000 帧；
  - 冻结区间：`19,584 … 72,471`（52,888 帧，73.0%），覆盖 stage 2 大部与 stage 4/5/7 全部；
  - 冻结图是一张**正常游戏画面**（stage 2 Keine 关），不是菜单/黑屏/转场；
  - 采集循环没有报错：`capture-report.json` 记录 72,472 帧、31.03 样本/s、`ended_reason = "left game"`，看起来完全正常。
- **根因（代码层）**：`touhou_rl/winapi.py:383-396` 的 `GdiCapture.grab()` 用 `GetDC(hwnd)` + `BitBlt`。窗口内容陈旧时 `BitBlt` **仍然返回成功**，取回的是上次绘制的内容；采集循环（`touhou_rl/vision_capture.py:155-186`）**没有任何「画面是否在变化」的校验**，因此一次静默的窗口停止刷新会被当作 28 分钟的正常采集。
- **影响（必须一起看）**：
  1. 模型在冻结帧上只能输出常数：实测 stage 4/5/7 的预测坐标逐位相同（`pred_x=0.3902, pred_y=0.6687`，`corr = nan`），argmax 只落在 2 个格子；
  2. 上报的 `val_player_pos_px = 68.07` 被坏数据灌水：**干净帧上是 38.82 px（corr_x 0.801 / corr_y 0.890），冻结帧上是 79.67 px**；
  3. danger 的 per-frame 相关只有 0.29–0.34，与「图像恒定、标签变化」时的边际预测一致；
  4. A-04 真机 1,352 帧低于随机 2,419.7 帧，是在 73% 不可学样本上训练出来的策略；
  5. **v1.0.2 的核心结论「数据从 4,524 扩到 72,472 帧反而更差，说明架构是瓶颈」被推翻**：4,524 帧那次是 2.7 分钟的短采集（落在干净区间内），而 72k 这次 73% 是坏数据。两者不是「架构对比」，是「干净 vs 损坏」的对比。v1.0.3 因此是在追一个假象。
- **建议方案**：
  1. **立即冻结该数据集**：不得再用于任何训练/评估结论；保留 19,584 帧干净子集作为临时可用数据；
  2. **先修采集器再加校验**：`GdiCapture.grab()` 增加「连续 N 帧完全一致且标签在变化 → 抛异常中止」的自检，并在 `capture-report.json` 里记录 `frozen_frames` 与最长连续相同帧长度；同时增加 `IsIconic`/前台失焦的硬失败；
  3. **然后重新采集**：先用 1 份回放做端到端验证（必须 0 冻结帧），再谈 R4；
  4. R4 在全量采集前必须补一条验收项：「连续相同帧检测 = 0」。
- **备选方案**：若短期内无法修采集器，可只用现有 19,584 帧干净子集做架构迭代（stage 0/1 + 少量 stage 2），但结论不能外推到全流程。
- **风险预警**：重新采集 1 份回放约 39 分钟 / 21.5 GB；若采集器缺陷未修就上 21 小时全量，可能产出 730 GB 的坏数据。**这是当前最大的风险。**
- **置信度**：99%（逐帧 SHA-256 比对 + 冻结图渲染 + 逐 stage 误差分解三方一致）

## 2. 置顶区（已清空）

以下 3 条曾因「涉及技术路线分歧 / 需要授权修改明文约束」升级为置顶。**用户已于 2026-10-18 全部裁决，结论对 Stage 2/3/4 具有约束力。**

### Q1 · `bullet_count_mae` 取错通道 —— 裁决：**授权修复，历史数字加注无效**

- **问题描述**：`touhou_rl/vision_train.py:158` 计算 `bullet_count_mae` 时取 `predicted[:, 13] * 700.0`。按 `touhou_rl/obs.py:136-157` 的 `self_feat` 布局，索引 13 是 `float(state.stage_clear_flag != 0)`（`obs.py:151`），索引 14 才是 `min(1.0, active_count / 700.0)`（`obs.py:152`）。
- **实测证据**：遍历 567 个分片（72,472 帧），`self_feat[13]` 的最小值 = 最大值 = **1.0**，即死通道；`self_feat[14] * 700` 才是真实弹量，最小 1.0、最大 700.0、均值 240.8、中位数 181.0。因此 `v1.0.3/需求文档.md` §2.3 的「S1 子弹数误差 15.1 颗」实际在量 `700 × |预测值 − 1.0|`，是伪指标。
- **裁决结论**：按 bug 修复，改用索引 14；在 v1.0.3 与 v1.0.2 相关报告中标注该历史数字无效。
- **风险预警**：修复后 S1 弹量误差需要重新计算，真实误差可能远大于 15.1 颗；该指标不进入 A-01/A-02 判据，仅作观察项。

### Q2 · A-01 的 danger 判据可被平凡模型刷掉一半 —— 裁决：**并列加 per-frame corr，并以其为主判据**

- **问题描述**：`touhou_rl/vision_train.py:167-180` 的 `danger_corr` 是把 `(帧 × 128 格)` 全部展平后算一次 Pearson。该口径的大部分方差来自「这一帧整体多危险」，不需要任何空间定位能力。
- **实测证据**（验证集 7,247 帧，标签 `danger`，目标 `log1p(danger/8)`）：
  - 只给「每帧真实总弹量」这一个标量（oracle 标量）：corr = **0.557**
  - 该标量 × 一个固定空间先验：corr = **0.669**
  - 同一平凡预测的 per-frame corr：均值 0.351、中位数 0.298，**达标(>0.8)率 0%**
  - 同一平凡预测的 busy-cell 准确率 = 0.822、IoU = 0.538
  - 对照：当前模型 `val_danger_corr` = 0.475、`val_danger_cell_acc` = 0.7006 —— **两项都低于平凡基线**
- **裁决结论**：A-01 增加并列判据 `per-frame corr 中位数 > 0.8`（主判据），全局 corr 与 busy-cell 指标降为参考项、仍须报告。
- **风险预警**：主判据变严后，A-01 可能在 8 epoch 内难以达标，需要更长的迭代预算；这是有意为之（避免「corr 达标但不会定位自机」的假通过）。

### Q3 · R3 的数据来源 —— 裁决：**先帧级子采样（18k/36k/72k），有斜率再补采 3 份**

- **问题描述**：`需求文档 §3 R3` 要求用 1 份 / 4 份 / 10 份数据画曲线，但 `third_party/th08/build/rl/datasets/` 下只有 `pilot-ud0059` 一份视觉数据（其余 `lunatic-bt`、`dagger-*` 是特权数据，无像素）。按每份 39 分钟 / 21.5 GB 计，补到 10 份约需 6 小时采集 + 195 GB，与需求文档 §9「Stage 3：1–2 天、纯 GPU、不占游戏」直接矛盾。
- **裁决结论**：R3 分两步。
  1. **第一步（本版必做，0 成本）**：在 `pilot-ud0059` 上做**帧级子采样**曲线，即训练集取 25% / 50% / 100%，对应 1 / 2 / 4 倍；验证集**固定不变**（见 D5）。
  2. **第二步（仅当第一步仍有斜率）**：再采 3 份回放（约 2 小时 + 65 GB）做跨回放曲线，替代原计划的「4 份 / 10 份」。
- **风险预警**：帧级子采样只回答「同分布数据量是否饱和」，回答不了「跨回放泛化」。若第一步曲线已平台化，可以不采第二步直接否决 R4；若第一步仍有斜率，第二步是必需的，因为同一回放的帧高度相关，饱和点会被高估。

## 3. 自决区（8 条，均已定，Stage 2/3 直接执行）

### D1 · 验证集必须由 manifest 校验，不得现场重算

- **问题描述**：`touhou_rl/vision_train.py:226-230` 用 `np.random.default_rng(seed=7).permutation(total)` 自己推导划分，**完全没有读 manifest**。实测它推出的验证集与 `pilot-ud0059/manifest.json` 记录的 `val_index_sha256 = e7c7b6c0…` **完全同集**（7,247 帧），但这是「碰巧一致」——`manifest.py:39-56` 与 `vision_train.py:226-230` 是两份独立实现，任何一侧改动都会静默漂移，而需求文档 R2 明文要求「不得重新划分」。
- **建议方案**：`vision_train` 启动时读 `<dataset>/manifest.json`，调用 `DatasetManifest.load()` + `verify()`，只在 `index_digest(val) == splits["val_index_sha256"]` 时继续，否则抛 `ManifestError` 退出。划分本身不改。
- **备选方案**：把 `manifest.split_indices` 直接 import 进 `vision_train`，删掉重复实现（更彻底，但会动到已通过测试的代码路径）。
- **风险预警**：`verify()` 会校验分片字节数与目录内多余文件；若有人手工动过数据集目录，训练会直接失败——这是期望行为。
- **置信度**：98%

### D2 · state 阶段选模口径改为 position 指标

- **问题描述**：`touhou_rl/vision_train.py:361` 按 `val_row["loss"]` 选 `state.pt` / `best.pt`。该 loss = `smooth_l1(self_feat) + smooth_l1(danger_log)`，danger 有 128 维、self_feat 24 维，**loss 被 danger 主导**；而 A-01 判的是 position + danger 两个独立指标。按 loss 选模可能选中 position 更差、danger 更好的 epoch。
- **建议方案**：state 阶段按 `val_player_pos_px` 最小选 `state.pt`，同时在 summary 的每个 epoch 行里保留 danger 三项指标；另存一个 `state-bestdanger.pt` 供对照，避免丢掉另一个指标的最优点。
- **备选方案**：按 position 与 danger 的归一化加权和选模（需先定权重，引入新的调参面，不推荐）。
- **风险预警**：多存一个 checkpoint 会让 `runs/` 体积翻倍（每个约 2.8 MB，可忽略）。
- **置信度**：95%

### D3 · heatmap 分辨率定为 stride 8（28×24 网格）

- **问题描述**：`touhou_rl/vmodels.py:81-90` 的主干是 4 次 stride-2，总 stride 16。playfield 模型输入 (H=224, W=192)（`vmodels.py:53-57`）→ 特征图 14×12 → 每格 32 原生 px。若在 /16 特征图上出 heatmap 再做加权期望，误差地板在 15–20 px 量级，A-01 的 < 10 px 有结构性风险。
- **建议方案**：playfield 独立编码器用 3 次 stride-2（总 stride 8）→ 特征图 28×24，每格 16 原生 px，接 1×1 卷积出单通道 heatmap，坐标 = soft-argmax 加权期望。HUD 两路各自独立小编码器，不受此限制。
- **备选方案**：若 8 epoch 内位置误差停在 15–20 px，再下探到 stride 4（特征图 56×48，每格 8 px，显存与耗时约 ×1.6）。
- **风险预警**：/8 的 playfield 特征图比 /16 大 4 倍，显存与每 epoch 耗时上升；当前 158 秒/epoch（depth=1, batch=96）预计涨到 200–260 秒/epoch，仍在「每次尝试约 10 分钟」量级内。
- **置信度**：92%

### D4 · 实验落盘与选模记录规则

- **问题描述**：`touhou_rl/vision_train.py:399-412` 里，`policy.pt` 存的是**最优 regret 的 epoch**（实测第 5 轮，3.717），但 `summary["stages"]["policy"]["final"]` 存的是**最后一轮**的 `by_danger`（第 8 轮，0–15 px 桶 4.03）。需求文档 §2.3 把「3.717 / 4.03」并列，实际是**两个不同 epoch**；A-02 的判据（0–15 px 桶 < 1.5 px）因此没有对应到任何被保存的权重。另外 `best.pt` 在 state 阶段与 policy 阶段被依次覆盖（`vision_train.py:366` 与 `407`），语义会漂移。
- **建议方案**：
  1. 每个 epoch 的 `by_danger` 全量写入 summary，并为 best epoch 单独写 `best` 节点（含 metrics + epoch 号）；
  2. 验收只允许用 `policy.pt` / `state.pt`，`best.pt` 保留兼容但不再作为验收依据；
  3. 每次架构尝试写到独立目录 `runs/v103-exp-<NN>/`，**不覆盖 `runs/pilot-v1/`**（它是 v1.0.2 的证据基线，被多份报告引用）。
- **备选方案**：只追加不改结构（会让 A-02 继续不可追溯，不推荐）。
- **风险预警**：`runs/pilot-v1/vision-summary.json` 的结构被 `Document/Update/Alpha/v1.0.2/` 多份报告引用，改结构后旧报告仍可读（只增字段），但生成器需向后兼容。
- **置信度**：97%

### D5 · R3 的验证集与训练集切分方式

- **问题描述**：做数据量曲线时，若直接用 `(seed=7, 0.1)` 对每个子集重新划分，三次实验的验证集**内容不同**，曲线不可比。需求文档 R2 又要求验证集固定。
- **建议方案**：验证集永远取 `pilot-ud0059` 的**固定 7,247 个索引**（即 manifest 的 `val_index_sha256`）；子采样**只作用于训练集**（65,225 帧），按 stage 分层等比抽取 25% (16,306) / 50% (32,613) / 100% (65,225)。三个数据点的验证集字节级相同。
- **备选方案**：固定同一个随机子集序列（如 `default_rng(7).permutation(train_idx)` 取前缀），保证 25% ⊂ 50% ⊂ 100%（可加性更强，推荐优先采用）。
- **风险预警**：分层子采样在 stage 内是随机抽帧，同一回放相邻帧高度相关，25% 子集的独立信息量可能远低于名义值；结论只能用于「是否还有斜率」，不能外推为「X 帧等于 Y 份回放」。
- **置信度**：94%

### D6 · A-04 的随机基线与通过口径写死

- **问题描述**：需求文档 §2.1/§5 写随机基线 **2,418 帧**，但仓库里唯一的落盘证据 `third_party/th08/build/rl/eval/comparison-v103.json` 记录的是 `frames_mean = 2419.7`（3 局，单局 2,118–2,695，波动 ±12%）。取整差异本身无意义，问题是**通过口径没写死**（几局、取均值还是单局、`max_steps` 多少、是否允许 step cap 截断）。
- **建议方案**：A-04 判据 = `mean(frames_reported) > 2419.7`，**≥ 3 局**，逐局数字入报告；`hit_step_cap` 必须为 0（不能靠跑满步数上限冒充存活）；`--frameskip 2`、`--difficulty lunatic`、同机体，与基线一致。
- **备选方案**：以单局最差值为判据（过严，随机基线单局最低 2,118，会让阈值随机波动）。
- **风险预警**：`max_steps` 若小于基线的单局步数会截断存活；基线未记录 `max_steps` 字段，需在 Stage 3 复跑一次随机基线并落盘完整参数。
- **置信度**：96%

### D7 · 采集速率字段修复（不影响 R4 的 730 GB 估算）

- **问题描述**：
  1. `touhou_rl/vision_capture.py:89` 声明 `first_game_frame` 后**从未赋值**（全文无赋值点），而 `vision_capture.py:220` 用它做写入条件 —— 当前代码**永远不会写** `game_frames_span` / `samples_per_game_second` 两个字段。
  2. 磁盘上 `pilot-ud0059/capture-report.json` 里的 `game_frames_span = 35958` / `samples_per_game_second = 120.93` 是**旧版**（`last − first`）产物。实测按分片 `meta` 逐段求和，六个面的帧跨度分别为 16,732 / 19,009 / 22,393 / 26,908 / 30,943 / 35,958，**真值 151,943**；`gameplay_frame` 每面重置，所以旧公式只取到了最后一面。真实速率约 28.6 样本/游戏秒，与「30 Hz」一致。
  3. `vision_capture.py:140-143` 只在 stage **变化**时追加 `stages_seen`，所以首个面（stage 0）永远不进列表（现有 report 是 `[1,2,4,5,7]`，实际 6 个面）。
- **建议方案**：赋值 `first_game_frame`（或在去掉该字段的同时用 `game_frames_total` 直接判定），修 `stages_seen` 记录首个面，重算后缀字段。
- **风险预警**：R4 的成本估算用的是「回放总帧数 4,581,131 ÷ 2 = 2,290,566 样本」，**与该字段无关**，修复不改变 730 GB / 21.3 小时。
- **置信度**：99%

### D8 · R3 的实验设计必须同架构同验证集，不得复用旧对比
- **问题描述**：需求文档 §2.2 用「4,524 → 72,472 帧，位置误差 48 → 71 px、danger 相关 0.82 → 0.475」支撑「架构是唯一瓶颈、数据无用」。但两个版本跨了数据分布：第一版是 **Stage 1 单面 / 2.7 分钟**，试点是 **6 个面全覆盖**（`v1.0.2/视觉改造报告-第一批.md` §2 vs `v1.0.2/视觉方案-网络与数据结构.md` §10.3）。danger 相关从 0.82 掉到 0.475 里有多少来自池化、多少来自画面变密，现有证据分不开。
- **建议方案**：保留「先改架构」的路线（池化抹平位置这一机制在代码层已确认成立，见需求文档 R1），但**把「数据无用」降级为待验证假设**：R3 用 D5 的同架构同验证集曲线来判定，不再引用跨分布的 16 倍对比作为结论。
- **备选方案**：先补一个「同数据、同架构、只改池化」的单变量消融（约 2×10 分钟）再进 R3 —— 若时间允许，这是最强的证据。
- **风险预警**：若 R3 显示数据仍有斜率，则需求文档「不要采全量」的默认结论会被推翻，R1 的架构投入可能部分白费；这是必须承认的风险。
- **置信度**：90%

### D9 · 验证循环丢弃尾部残批（7200 / 7247），本版不修

- **问题描述**：`touhou_rl/vision_train.py` 的 `batches()` 按整批迭代（`range(0, n - batch + 1, batch)`），验证集 7,247 帧在 batch=96 下只跑 75 批 = **7,200 帧**，尾部 47 帧被丢弃。因此 `stages.*.history[*].val_frames = 7200`，而 summary 顶层 `val_frames = 7247`。设计文档 §7.2 的示例原先写 7247，与实际不一致。
- **建议方案**：**v1.0.3 不修**。理由：修了会让「同一批实验里前后跑的验证子集不同」（已产出的 exp-01…05 用旧逻辑、后续用新逻辑），破坏横向可比性，而这个可比性正是 A-01/A-03 判定的基础。已固定记录：顶层 `val_frames=7247` 是划分大小，`history[*].val_frames=7200` 是实际计分帧数，验收读顶层。
- **备选方案（v1.0.4）**：`batches()` 增加 `drop_last` 参数，验证路径传 `False` 并对末批做补零掩码；或把 batch size 改为能整除 7247 的值——后者会连带改变训练动态，不推荐。
- **风险预警**：若将来有人用不同 batch size 跑对照实验，被丢弃的尾部帧不同（例如 batch=128 时丢 79 帧），指标会产生 <1.1% 的不可比偏差。**任何跨 batch size 的对比都必须先修此缺陷。**
- **置信度**：99%
