## 3. 五件必落地事项：实现位置与证据

### 3.1 manifest 门禁（D1）

| 要求 | 实现 | 证据 |
| --- | --- | --- |
| 有 `manifest.json` 时必须 `DatasetManifest.load()` + `verify()` | `_resolve_split()`：`manifest_path.is_file()` → `DatasetManifest.load()` → `manifest.verify(dataset_dir)`，未捕获异常 | 两次 smoke 跑首行打印 `manifest_verified True`、`val 7247` |
| 校验失败抛 `ManifestError` | `verify()` 原样上抛，未捕获、未重写哈希 | `test_manifest_gate_rejects_wrong_hash`（把 `splits.val_index_sha256` 改成 `deadbeef` → `ManifestError`） |
| 无 manifest 时只有 `--allow-missing-manifest` 才回退旧推导 | `elif cfg.allow_missing_manifest:` → `default_rng(seed).permutation(total)` | `test_manifest_gate_required_without_flag`（不加 flag → `ManifestError`） |
| `--train-fraction < 1.0` 且 manifest 未验证 → `SystemExit` | `_resolve_split()` 内 `raise SystemExit("--train-fraction requires a verified manifest")` | `test_train_fraction_requires_manifest` |
| summary 记录三项 | `train_fraction` / `val_index_sha256` / `manifest_verified` 顶层键 | §6、§7 的 summary 片段 |

额外加固（自决，见 §10）：`manifest.total_frames != len(dataset)` → `ManifestError`，避免"清单说 72,472、目录里多/少了一帧"导致后续 `IndexError`。

### 3.5 批次限制分离（设计 §7.4）

- `batches(indices, shuffle, max_batches)` 单参数化；训练那趟传生效的 `max_train_batches`（= `cfg.max_train_batches or cfg.max_batches_per_epoch`），验证那趟传 `cfg.max_val_batches`，两者互不影响。
- 证据：单测 `test_max_train_batches_does_not_shrink_val`（`--max-train-batches 1 --max-val-batches 0` → `history[0].val_frames == 4 == summary.val_frames`；`--max-val-batches 1` 时才变成 2 帧，说明两个旋钮各自独立）。
- 真实数据上：`--max-val-batches 20` 时 `state.history[0].val_frames = 1920`（=20×96），而顶层 `val_frames = 7247`（=`len(val_idx)`），逐 epoch 可核对"验证集没被切小"。

## 10. 自决项（任务书未规定或存在两种读法，已自行决定）

| 编号 | 事项 | 决定 | 理由与风险 |
| --- | --- | --- | --- |
| E1 | `--device` 是否加 `choices=["cuda","cpu"]` | 不加，按任务书 §4.1 类型列保持 `str` | 设计 §7.1 写 `{cuda,cpu}`，任务书写 `str`，两处不一致；取较宽松者，`cuda:0` 这类写法仍可用。风险：无（非法设备名由 `torch.device` 抛错） |
| E2 | 拒绝覆盖的判定范围 | 除"等于/位于 `…/rl/runs/pilot-v1` 内"，再加上"解析后末段名 == `pilot-v1`" | 验收文档 V-13/§7.1 用相对别名 `runs/pilot-v1` 指代同一目录；只按绝对路径判定会漏掉在别的 cwd 下敲别名的情况。风险：有人故意想建 `pilot-v1` 目录会被拒，这正是要防的 |
| E3 | 旧名 `--max-batches-per-epoch` 与新名同时给出 | 新名非 0 时以新名为准；新名为默认 0 时取旧名；`VisionTrainConfig` 也保留同名字段，`train()` 里归一成"生效的训练上限" | 无法区分"未给"与"给了 0"；文档化于 `--help` 与 §2 表格。`config.max_train_batches` 记生效值，所以经旧名启动的跑也会被 S3-5 识别为筛选跑。风险：`--max-train-batches 0 --max-batches-per-epoch 3` 会被读成 3 |
| E4 | `stages.state` 额外写 `best_danger` 与 `pass_epoch` | 写入 | 让 `state-bestdanger.pt` / `state-pass.pt` 的归属 epoch 在 summary 里可追；纯增量键，不影响 §7.2 必需键 |
| E5 | `--allow-missing-manifest` 遇上有 manifest 的目录 | manifest 分支优先（不看该 flag） | 与任务书 §4.2 伪代码一致；避免"加了 flag 就绕过校验"的误用 |
| E6 | `manifest.total_frames != len(dataset)` | 抛 `ManifestError` | `verify()` 只比较 shard 记录之和，不比较目录实际帧数；不补这一条会退化成后面的 `IndexError`。风险：数据集被手工改动时会直接失败，这是期望行为 |
| E7 | 末尾不足一个 batch 的尾批 | 丢弃（沿用 v1 的 `range(0, len-batch+1, batch)`） | 不改 v1 语义。副作用：验证集帧数 < `batch_size` 时 `val_frames=0`；实验配置 `batch_size=96` 时无影响，但小合成数据集必须把 `batch_size` 调小（单测已如此处理）。写进 §11 |
| E8 | `policy.history[*].val_regret_px_bucket_0_15` 的值来源 | 直接取 `by_danger` 里 `0-15` 桶的 `regret_px`（空桶时为 0.0，桶不存在时为 `null`） | `vision_metrics.policy_metrics` 恒定输出 5 桶，因此实际总是数值；空桶的 0.0 需配合 `bucket["frames"]` 读。验收读 `by_danger`，不读这个扁平键 |
| E9 | `stages.state.final` | 也写（最后一行） | 设计 §7.2 示例只列 `history`/`best`，但 §4.5 提到 `stages` 下有 `history`/`best`/`final`；与 policy 对称，且验收不读它。风险：低 |
| E10 | `teacher_values_for` 的存储 `value` 分支 | `dataset.batch(...)` 改为 `dataset.labels(...)`  | `VisionDataset` 没有 `batch` 方法，原分支一旦触发就是 `AttributeError`；当前 pilot 分片无 `value` 数组（`has_teacher_values: false`），所以该 bug 从未暴露。改为 `labels()`（其内部按需返回 `value`）。风险：该分支仍未被真实数据覆盖，仅由代码阅读保证 |
| E11 | `pipeline train` 的 vision 分支仍传 `max_batches_per_epoch`（`touhou_rl/pipeline/train/__init__.py:140`） | 在 `VisionTrainConfig` 保留同名字段并在 `train()` 归一成生效上限，而不是让它 `TypeError` | 删字段会让三阶段 CLI 的 vision 分支直接崩（旧单测只跑到 modality 检查就 raise，覆盖不到）。实测已修复，见 §11 的 F4。风险：两套名字并存，靠 `--help`/`config` 说明 |
