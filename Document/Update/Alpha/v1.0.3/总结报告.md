## 1. 这一版想干什么，干成了什么

**目标**（需求文档 §3）：把视觉学生从「能跑通」修到「看得准」，并且只有在数据曲线证明还有收益时，
才允许开始 21 小时的全量采集。

| 需求 | 内容 | 结果 |
| --- | --- | --- |
| R1 | 改视觉架构（场地不池化到 2×2、坐标用 heatmap、HUD 独立编码器） | **已实现**（三流独立编码器 + 28×24 heatmap + soft-argmax，554,873 参数） |
| R2 | 用同一份 72k 帧验证 | **已执行**（7 次跑，全部固定验证集 7,247 帧） |
| R2 达标线 | 位置 < 10 px、per-frame corr > 0.8、0–15 桶 < 1.5 px | **全部未达**（68.07 px / 0.342 / 4.081 px） |
| R3 | 数据曲线决定要不要采更多 | **blocked**（前置未成立）；另做了纯诊断的斜率探测，不作闸门证据 |
| R4 | 全量采集（条件触发） | **未执行**，且不建议执行 |
| R5 | 部署端只看像素的真机验证 | **链路通过、表现未达**（1,352.3 帧 vs 随机 2,419.7） |
| R6 | 文档与过程 | **完成**（六份文档 + 六份完成报告 + 过程日志 E-01…E-09） |

一句话：**架构按设计改完了，工程链路全通，但精度目标没达到；而「为什么没达到」这次查清了。**

## 2. 三个真正有价值的结论

### 2.1 架构不是错的，是泛化不够（本版最重要的证据）

两个独立诊断：

| 诊断 | 结果 | 说明 |
| --- | --- | --- |
| 过拟合 100 帧（仅 heatmap 损失，400 步） | 位置误差 **97.30 → 8.06 px** | 同一个网络在同一份数据上能做到 < 10 px：**没有结构性问题、没有标签错位** |
| 主实验 checkpoint 解码对比（128 验证帧） | 期望解码 65.9 px、**argmax 41.0 px**、常数 71.1 px、`corr(x)=0.678` | 热图带真实空间信息，但分布过宽，加权期望被拉向中心 |

因此 A-01 未达的原因是**「从 65k 帧、单一回放学不到可泛化的定位」**，而不是「池化/heatmap 方向错」。
这直接改变了下一步该往哪走：不是换架构，而是**先拉长训练、再考虑数据多样性**。

### 2.2 换超参在 8 epoch 预算内无效

四组筛选（depth 3 / σ 1.0 / w_heatmap 2.0 / 基线）的位置误差是 74.32–76.38 px，跨度 2.8%。
说明这几个旋钮在该预算下**都不是瓶颈**，继续在此处调参是浪费。

### 2.3 全量训练仍在下降，没收敛

exp-05 八轮：74.61 → 72.64 → 73.94 → 72.44 → 70.73 → 69.26 → 69.51 → 68.07，
末轮单轮改善 1.44 px，且 per-frame corr 单调上升（.291 → .342）。
**曲线没平**，这是「先加 epoch」而不是「先加数据」的直接依据。

## 3. 工程产出（可复用资产）

| 产出 | 价值 |
| --- | --- |
| `touhou_rl/vmodels2.py`（307 行） | 三流独立编码器 + heatmap + `decode_position`/`heatmap_target`，参数量比 v1 少 21% |
| `touhou_rl/vision_metrics.py` | 唯一指标实现（弹量索引 14、per-frame corr、五桶后悔值），训练与判定共用 |
| `touhou_rl/vision_split.py` | 分层、可嵌套、可复现的训练集子采样 |
| `touhou_rl/vision_train.py`（改写 761 行） | manifest 门禁、25 个 CLI 参数、`state-pass.pt` 联合达标落盘、`vision-summary/2` schema |
| `touhou_rl/evaluate.py` | v1/v2 双兼容、depth 跟随 checkpoint（修掉一个必然崩溃）、`vision` 报告节点、`env_factory` 可注入 |
| `tools/rl/v103_sweep.py` | 配方批量执行、目录最低空位、跨次调用合并、实验表自动追加 |
| `tools/rl/check_a01.py` | 机器判定 A-01/A-02/A-03，`r4_authorized` 恒 false |
| 单测 159 条 | 旧 59 条零退化 |

期间修掉的真实缺陷（都不是测试能发现的）：

1. **部署必崩**：`evaluate.py` 的 `--vision-depth` 默认 3 而试点模型 depth=1 → 实测 `RuntimeError`，
   改为跟随 checkpoint；
2. **pipeline 报告静默退化**：schema 迁移后 `train-report.json` 两个字段变 null，不报错、测试全绿，
   只有把真实产物喂进旧消费方才能发现；
3. **A-01 会假失败**：state 只按位置选模会丢掉唯一联合达标的轮次 → 新增 `state-pass.pt` 与「扫描全部
   epoch」的判定规则；
4. **主实验会选错**：筛选跑（160 batch、state-only）可能被当成主实验 → `--primary` 显式指定 + 排除规则。

## 4. 没做到的事（不弱化）

1. **A-01 未达，且比 v1 更差**（68.07 vs 70.97 px；per-frame corr 0.342 vs 全局 0.475 是不同口径，
   但 per-frame 口径下游模型 0.342 与平凡基线 0.298 基本持平）；
2. **A-02 未达**（4.081 vs < 1.5），与 v1 的 4.03 持平 —— 位置不准，策略就不可能准；
3. **A-04 未达**：视觉策略真机 1,352.3 帧，**比随机策略低 44%**。它会动，但不会躲；
4. **A-03 未成立**：没有数据曲线，因此「数据是否仍是瓶颈」**本版没有回答**；
5. **R4 未执行**，这是正确决定，但也意味着 2,290,566 样本 / 730 GB 的采集能力仍未验证；
6. **数据斜率探测有致命混淆项**（固定 batch 数导致过池次数不同），**不能当作「数据无用」的证据**；
7. `D7`（采集速率字段）与 `D9`（验证丢残批）两个缺陷按计划留到 v1.0.4。

## 5. 对 v1.0.4 的建议（按信息量/成本排序）

| 优先级 | 动作 | 成本 | 判据 |
| --- | --- | --- | --- |
| 1 | 8 → 24/40 轮（state-only） | 1–1.75 小时 | pos 若降到 < 20 px，说明主因是欠训练 |
| 2 | 并列报告 `val_player_pos_argmax_px`，试温度锐化解码 | 近零 | 期望解码当前比 argmax 差 25 px |
| 3 | 用 24 轮结论判断是否需要第 2/3 份回放 | +2 小时采集 | 若同数据加 epoch 已平台化，再引入跨回放 |
| 4 | 修 D7、D9 | 半天 | 跨 batch size 对照前必须先修 D9 |
| 5 | stride 4 **降级**（原设计 §12 把它当首选退路） | ×1.6 开销 | 68 px 不在 15–20 px 量级，改量化地板无法弥补 58 px |

**不建议在 v1.0.4 之前做任何全量采集**：当前状态下采 21 小时只会得到一个「在更大数据集上仍然不会躲」的模型。

## 6. 一句话给下一个人

把这一版当成**排除法的一次成功**：它证明了「问题不在池化、不在超参、不在解码、不在标签」，
并把范围收窄到「训练预算与数据多样性」两件事上。
过拟合 8.06 px 这个数字是本版最硬的资产——它说明路走得通，只是还没走到。
