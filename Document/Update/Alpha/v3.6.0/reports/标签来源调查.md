# v3.6.0 标签来源调查：bullet→enemy 归属、符卡/无敌相位、逐敌人身份

- 日期：2026-10-25
- 依据：[T1-D2 报告](<T1-D2报告.md>) §6.2（下一批的依赖顺序）、[策略标签契约](<../contract/策略标签契约.md>) §5
- 性质：**可行性调查 + 采集契约变更前置**。不改任何门禁，不产出策略判定。
- 起因：D2 报告把三条策略的失败归因到**标签**而不是特征（ENEMY 两次增量过门、绝对门不过；BOSS 方向为负；EMERGENCY 阳性 30）。这一轮回答"这些标签能不能做出来"。

## 1 bullet→enemy 归属：位置追踪不可辨识，必须落 `slot_id`

### 1.1 源码事实

`third_party/th08/src/BulletManager.hpp` 的 `struct Bullet`（`C_ASSERT(sizeof(Bullet) == 0x10b8)`）字段全集：sprites、position、velocity、speed、angle、stateTimer / activeTimer、transform flags、color、state、offscreenFrames、isGrazed、collisionDisabled、transformIndex、transforms[18]、exStates[7]。

**没有 owner / 发射源字段**（没有 enemy 指针、没有 enemy index、没有 bullet 的 parent id）。唯一的"来源"线索是 `BulletChildPatternPrimary/SecondaryPayload`——那是**子弹生子弹**的子模式，不是敌人归属。

所以"这颗子弹是哪个敌人发的"**不可能直接读**，只能重建。

### 1.2 位置追踪的实测：不可辨识

`touhou_rl/bullet_track.py` 的第一条路是用 `pos + vel * frameskip` 预测上一帧子弹在下一帧的位置，未匹配者视为新生成。在 D2 的 `replay-ep01`（4,999 个决策、约 160 颗弹/决策）上测**匹配容差**敏感性：

| 匹配容差 | 推断的新弹数/决策 | 归属率（32 px 内） |
|---:|---:|---:|
| 1.5 px | **11.32** | 36.6% |
| 3.0 px | **5.19** | 42.4% |
| 4.5 px | **3.48** | 50.8% |
| 6.0 px | **2.74** | 56.3% |
| 10.0 px | **2.15** | 67.7% |

**新弹数随容差单调下降且不收敛**（1.5 → 10 px 掉了 5.3 倍）。这不是"参数没调好"，而是**不可辨识**：一颗运动不严格等于 `pos + vel*frameskip` 的**幸存弹**（减速弹、极坐标加速弹、以及读取落在帧更新中间造成的相位偏差——v3.5.0 已经为 `activeBulletCount` 记录过这个问题）与一颗贴着它生成的**新弹**在 `(position, velocity, half)` 上无法区分。容差调大就把新弹吸收成幸存弹，容差调小就把幸存弹报成新弹。

同时，"归属率随容差上升"也是**循环的**：容差变大 → 新弹变少 → 剩下的是更靠近敌人的那些 → 归属率自然变高。所以 37%–68% 这一串数字不能当"归因覆盖率"读。

### 1.3 根因与修复

根因很具体：**trace 丢掉了 `slot_id`**。`probe35._bullets_raw()` 已经算出 `slot_id`，但 `TraceWriter` 只存了 positions/velocities/half/offsets，没存它。

一颗子弹"是不是新的"在有槽位号时是**精确可判**的：上一快照里未激活、这一快照激活 = 新弹；槽位回收再用也天然算新弹（上一快照里没有它）。不需要运动模型、不需要容差。

已实现：

1. `TraceWriter` 现在把 `slot_id` 写进 `bullets/*.npz` 的 `slots`（不能用时填 −1，并在 `close()` 的返回值里报 `slot_ids`）；
2. `bullet_track.spawns_by_slot(prev_slots, cur_slots)`；
3. `track_episode()` 自动检测 `slots` 是否存在，存在就走精确路径（`match_method="slot_id"`），否则退回位置匹配（`match_method="position"`）并在报告里显式标出；
4. 单测 `test_spawn_rate_is_identifiable_only_with_slot_ids` 直接把这个发现钉住：同一段合成的"一颗线性弹 + 一颗减速弹、零次真实生成"数据，位置匹配在 0.5 px 容差下报出 >0 次生成、在 8 px 下报出更少，而槽位法报 **0**。

### 1.4 真机验证（短跑）

用修好的采集器跑 400 个决策（第 1 面开场，约 800 帧）：

- sidecar 出现 `slots` 数组，13,261 个条目，**没有 −1**（说明 `slot_id` 一路传到了落盘）；
- 同一快照内槽位唯一；跨快照可见槽位回收（首决策槽位 `[1536]`，末决策 `[41..51]`）；
- 槽位法新弹率 **0.54 / 决策**——比任何位置匹配的估计（2.15–11.32）低 **4–20 倍**。

注意这个 0.54 来自**开场 800 帧**（几乎无弹幕），不能当作全段速率。要拿到可信的全段速率，必须用带 `slots` 的语料重采。

### 1.5 结论与代价

- **D1 / D2 的语料没有 `slots`**，所以 ClearEnemy 的"击杀后发弹减少"标签**在现有数据上做不出来**，位置代理不可信；
- 重采代价：D2 的 6 局约 17 分钟真机时间，D1 的 9 局约 18 分钟；两组都能顺带把下面的新字段一起采了（所以不亏）。

## 2 符卡 / 无敌相位：`current_spell` 是死字段，但真正的解在 `Enemy`

### 2.1 `current_spell` 已确认不可用

D2 报告 §5.3 已记录：`GameManager::currentSpellCardNumber`（i16 @ 0x3DBB0）在 D1 读成恒 0、在 D2 读成恒 −1（按 u32 读时是 65535），正常游玩里**不写这个字段**。读取宽度已修（`<h`），但修完仍然是常量。

所以 §2.4 要的"非符 / 符卡 / 无敌 / 对话 / 阶段转换"不能靠它。

### 2.2 `struct Enemy` 里已经有答案

`third_party/th08/src/EnemyManager.hpp` 的 `Enemy` 结构（字段均有 `C_ASSERT(offsetof(...))`）里有四组**当前 trace 没有采**的字段：

| 字段 | 用途 | 对应的策略缺口 |
|---|---|---|
| `EnemyFlag1Bits.damageable`（flags1 bit 3） | 此刻是否可被伤害 | §2.4 输出窗口 / 无敌相位 |
| `EnemyFlag1Bits.acceptsDamage`（bit 6） | 是否接受伤害 | 同上（与 damageable 交叉验证） |
| `EnemyFlag1Bits.noDamageDuringStop`（bit 31） | 停止期间免伤 | 僵直/无敌停顿 |
| `i32 phaseStartingLife` | 当前相位开始时的生命 | **相位边界与进度**（§2.4） |
| `i32 enemyIndex` | 逐敌人稳定 id | 跨帧追踪敌人（ClearEnemy 目标跟踪） |
| `BulletSpawnDescriptor bulletSpawnDescriptor` | **待发射的弹幕描述符** | §2.3 "预测发弹量" |
| `i32 shootIntervalFrames` + `ZunTimer shootIntervalTimer` | 发射间隔与相位 | 同上 |

其中 `phaseStartingLife` + `flags1.damageable` 两个字段就足以把 §2.4 的"输出窗口"变成可测标签：

```text
damage_window(i)  = flags1.damageable AND boss present
phase_k(i)        = 由 phaseStartingLife 的跳变切分
label             = 在该窗口内 Boss HP 下降量（已可读）
```

而 BOSS 块现在的负增量很可能是"用一个死列（`spell`）冒充相位"的直接后果——换成 `damageable` 之后，特征才第一次与标签对齐。

`bulletSpawnDescriptor` 更直接：它是**敌人当前的发射描述符**，也就是"接下来会发什么"。读到它，ClearEnemy 的 `predicted_bullet_generation` 从启发式（距离/生命加权）变成真实字段。

## 3 采集契约的变更清单（下一轮执行）

`state.EnemyInfo` 增加 4 个字段 + `trace35._enemy_dict` 落盘：

| 新字段 | 来源偏移 | 说明 |
|---|---|---|
| `flags1` | `OFF_ENEMY_FLAGS1 = 0x3324`（已有 C_ASSERT） | 只存原始 u32，位含义放契约里解释，避免解码错误被埋进读取层 |
| `phase_starting_life` | `offsetof(Enemy, phaseStartingLife)` | 需在源码确认偏移并写 `C_ASSERT` 对齐 |
| `enemy_index` | `offsetof(Enemy, enemyIndex)` | 同上 |
| `damageable` | `flags1 >> 3 & 1` | 由 `flags1` 派生，便于人读 |

外加 `slot_id`（已实现）。

**注意**：`phaseStartingLife` / `enemyIndex` 的偏移必须从源码 `C_ASSERT` 或布局推算确认，不能猜。若源码里没有现成 `C_ASSERT`，就用 `sizeof` + 前后字段的 `C_ASSERT` 夹逼，并把推算过程写进契约（v3.5.0 的 Item 偏移就是这么来的）。

采集后要跑的门：

| 门 | 判据 |
|---|---|
| `damageable` 有方差 | Boss 在场时两态都至少 10% 的决策 |
| `phase_starting_life` 跳变次数 | 每局 ≥2（第 1 面有非符与符卡） |
| `slots` 覆盖率 | 100% 决策无 −1 |
| 槽位法新弹率 | 与位置匹配估计同量级即视为可疑，需人工抽查一局 |

## 4 对三条策略的影响

| 策略 | 现状 | 采集后 |
|---|---|---|
| ENEMY | 增量 +0.07 / +0.11 过门，但标签是**全局弹数变化**代理，绝对门 0.44 / 0.37 不过 | 可以测"该敌人在未来 60/240 帧生成多少弹"（槽位法 + 就近归属），这才是 §2.3 的原意 |
| BOSS | D1 unstable、D2 方向为负；`BOSS_spell` 是死列 | `damageable` + `phaseStartingLife` 给出真实的输出窗口与相位 |
| EMERGENCY | D2 underpowered（bomb 阳性 30） | **不因这次采集改善**：仍然需要"会死的臂"。这是独立的数据需求，不要指望换字段解决 |

## 6 本轮没有做的事

- 没有把位置法的归属率当成"覆盖率"写进任何结论；
- 没有在没有 `slots` 的 D1/D2 上硬造 ClearEnemy 标签；

- 没有改任何门禁阈值；
- 没有重采（留到下一轮，与新字段一起采，省一次 17 分钟）。
