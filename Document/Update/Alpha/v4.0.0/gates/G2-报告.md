## 0. 判定（唯一）

```
G2 = 未达（按原文口径）
```

三条互不重叠的理由（任一单独成立即不可达）：

1. **death 召回按原文口径不可达**：全语料 530 个 death 事件里只有 342 个（64.53%）伴随 HUD 变化，
   其余 188 个发生在 `lives == 0`。本轮把 test 切片扩到 908 个事件后，仍有

2. **bomb 门样本不足**：test 切片只有 20 个 bomb 事件，取值 100%，

3. **stage_clear 门不可测**：引擎没有 stage_clear 事件位；`lives` 上跳 0 次、`bombs` 上跳 40 次只构成弱代理，
   不足以定义事件（EXP-P2-004 §1）。原文要求 ≥99%，本轮仍记「不可测」。

**限定口径（选项 A）下**：death 门已**全部达标**（可观测召回 100.00%（LB 99.52%，n=804）、

game_over 是**原文判据里没有的门**（12-P2 §6 只列 death / bomb / 过面 / 读数 / 分数符号 / 在线校验）。

### 1.2 `04-阶段计划.md` G2 摘要原文

### 1.3 本报告的统计口径

- **判定用 Wilson 95% 单侧下界**，不用点估计（沿用 EXP-P2-004）。零失败时 Wilson LB = `n/(n+3.8416)`，
  因此 ≥99% 需要 `n ≥ 386`；`1−3/n`（rule-of-three）在 `n=300` 时给 99%，两者都报，判定取更保守的 Wilson。
- **零样本不算 100%**：`n=0` 的行一律「不可测 / 未达标」。
- **death 事件计数口径**：`death` 位的上升沿（含 shard 第 0 帧）。本报告读完整 `labels.jsonl`；
  EXP-P2-004 的 split 由 `index.json` 构建（比磁盘少 872 帧的未入索引尾部 shard），
  因此既有 test 切片在本报告里是 272 事件 / 190 预测（EXP-P2-004 报告 270/189），判定不变。

## 4. game_over 门（原文无此门，本轮新增）

### 4.1 为什么既有语料是 0 样本

既有采集器把 `STEP` 回包的 `game_over=` 词写进 `go` 列。实测该词**从未为 1**：
补采 A 的 18,000 帧里 `game_over_frames = 0`、
补采 C 的 14,400 帧里也是 0；
而同一批帧用 `HUD` 命令读到的 `gameOverFlag` 分别有 **941** 与
**9333** 帧为 1。
结论：不是游戏没进入 game over，而是**采集器读错了信号源**——`gameOverFlag` 只在 EXP-P2-005 新增的 `HUD` 里。
本轮已给采集器加 `--hud`（`hgo` 字段），并用 `tests/test_v400_reward_detector.py` 覆盖。

### 4.2 真正跑到 game over 的局

- 补采 A：20 个 shard 全部在 900 帧内耗尽三条命并继续步进（`advanced=1` 恒成立），
  `gameOverFlag` 上升沿 **20 个**（20 个 shard 各 1 个），落在 843–847（`still` 为 886）。
- 补采 C：6 个 2400 帧的局，同样每局 1 个 onset，**game-over 停留 9,333 帧**（每局约 1,555 帧）。
- 单局探针 `.tmp_v400_g2/gameover_probe.py`（5000 帧）：第三次死亡在 i=841、`gameOverFlag` 在 **i=845（+4 帧）**、
  `STEP game_over` 恒 0、`displayStale` 从 0 一路涨到 4154 —— 与 lives 递减的 +4 延迟完全一致。

### 4.3 可观测信号（像素侧）

`play96` 相邻 60 帧的平均绝对差（LAG=60）：

| 类别 | 帧数 | 均值 | 中位 | p95 | max | min |
|---|---|---|---|---|---|---|
| game over 帧 | 10,274 | 6.1749 | 0.0 | 50.8146 | 53.3203 | 0.0 |
| 游戏内帧 | 20,566 | 24.1457 | 23.9801 | 39.8869 | 48.1719 | 3.4838 |

**这是可以分离的**：重试画面静止后 `play96` 差分**中位数为 0**，而游戏内在 20,566 帧里
**最小也有 3.4838**。阈值取调参语料（补采 B 的 161,000 个游戏内帧）
最小值的 **一半** = 1.736（预注册规则，不看评测集）。

### 4.4 检测器指标（状态门：区间 vs 检出段）

| 项目 | 数值 |
|---|---|
| 真值区间（`gameOverFlag` 连续段） | 26 |
| 检出段（`play96` 差分 < 阈值的连续段） | 6 |
| 命中区间 | 6 |
| **区间召回** | 23.08%（LB 11.03%，n=26） |
| **区间精确** | 100.00%（LB 60.97%，n=6） |
| 检出延迟（区间起点 → 首个检出） | 中位 89.0 帧 / max 89 帧 |
| 帧级混淆（TP/FP/FN） | 8,799 / 0 / 1,475 |

但**区间召回只有 23.08%**——原因不是检测器失效，而是观察窗不够：

因此 game_over 门本轮判「**样本不足 + 观察窗不足**」，不计入达标（§5 第 10、11 行）。

### 13.5 像素检测器

**判据（可解释）**：游戏内画面下亮上暗，过面屏换成「上亮下暗」的结算面板。令


**为什么用「跳变」而不是「电平」**：`vgrad >= 6` 的电平判据在 **stage 2** 上失败——
