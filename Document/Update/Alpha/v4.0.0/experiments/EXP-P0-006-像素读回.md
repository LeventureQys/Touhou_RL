# EXP-P0-006 像素读回（env 角色的观测通道）

- 日期 / 工作包：2026-11-07 / P0-WP3
- 假设：`TH08_RL_HARNESS` 构建的进程能在 `EndScene` 之后把渲染结果读回，且读到的是**含 HUD 的完整 640×480 客户区**（D-03 要求回报检测器必须能看到 HUD）。
- 预注册：主指标 = `PIXELS` 命令返回 640×480 且非零字节数不为 0，导出的帧经目检为真实游戏画面并包含 HUD。通过阈值 = 两条都成立。样本量 = 1 帧（Stage 1 Normal，第 120 帧）。
- 设置：
  - 子模块 `rl-harness` 分支，提交 **`56ee7f1`**
  - 流程：`RESET 0 1 0 1234 1` → 6 × `STEP 1 20`（共 120 帧）→ `PIXELS <path>`
  - 环境：xvfb + `LIBGL_ALWAYS_SOFTWARE=1 LP_NUM_THREADS=1`
- 结果：**两条主指标都成立**。
  - `PIXELS` 回复 `pixels=640x480 nonzero=983868 checksum=7572677e928cabf3`
  - 导出的帧（[frame-stage1-normal.png](<../evidence/EXP-P0-006/frame-stage1-normal.png>)）显示：Stage 1 的秋色背景、自机、带血条的敌机，以及右侧完整 HUD——`Player ★×8`、`Spell ★×3`、`Power 0`、`Graze 0`、`Point 0/100`、`Time 0/2500`、难度 `Normal`，右下角 174.00 fps。
  - 同一进程内重复调用 `PIXELS` 得到相同 checksum，说明读回是稳定且确定的。
- 有效性自检：
  - V1 是：像素直接来自 `glReadPixels`，未经任何裁剪；HUD 可见即证明没有走 playfield 裁剪（v3.9.0 L1/L1b 的失败点之一）
  - V2 不适用
  - V3 是：`nonzero=983868` 占 640×480×4 = 1,228,800 的 80%，不是空白帧
  - V4 不适用
  - V5 是：平凡基线是"读回全黑"；`nonzero` 与目检画面都远超基线
  - V6 不适用
  - V7 否：只跑了 1 次；确定性由 EXP-P0-005 的 5,000 帧哈希覆盖，但像素级跨进程一致性尚未测
  - V8 是：这一帧就是学生将来能看到的全部输入，没有内存读数掺入
  - V9 是：指标在运行前由 `10-P0` §4.5 与 D-03 固定
- 结论：**成立**。env 角色的观测通道打通，且确认包含 HUD。
- 成本：GPU 0 h；墙钟约 0.5 h；磁盘约 0.2 MB。
- 尚未做（P0-WP2 与 WP3 的欠账）：
  - `glReadPixels` 的**读回成本**未测——这是 WP2 决策表最后一项；需要 PBO 双缓冲对照。
  - 像素还没进共享内存，目前走文件 + checksum；`obs_spec` 的分辨率冻结在 G2。
  - 跨进程像素一致性（同种子同帧、两个进程逐字节相等）未测，它属于 G0.2 第 4 项。
- 下一步：把像素放进 POSIX 共享内存（去掉写文件的绕行），同时用 PBO 双缓冲测出读回开销，补齐 WP2。
