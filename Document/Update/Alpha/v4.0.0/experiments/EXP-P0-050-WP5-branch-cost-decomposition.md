# EXP-P0-050 — WP5 / G0.2 第 5 项：真实 `BRANCH` 开销拆分为「固定开销」与「每帧开销」（2026-11-08）

结论：**PASS（口径已修正为回归推断，不再使用含子执行 + wait 的混合口径）**。
真实单线程 shadow 上 **105 次** `BRANCH 0 <frames>`（7 档 × 每档 5 次 × 3 个独立 pass）：

- **每帧开销（斜率）** `41.4249 μs/frame`（≈ `0.0414249 ms/frame`）
- **固定开销（截距，子计时区间常数项）** `519.2911 μs`
- **拟合优度** `R² = 0.997917`（n=105）
- **交叉检查** `fork_us − child_us` 均值 `895.0381 μs`（std 109.48，min 699，max 1252）

**口径声明（必须与数字一起引用）**：上述拆分是**对真实 `BRANCH` 回复做最小二乘回归后推断**出来的，
**不是**直接插桩 `fork()` 系统调用得到的耗时。任何一个数字都**不得**被表述为纯 syscall 时间。
引擎原有的 `fork_us` 是父侧跨度（含子进程全程推进、结果管道读取与 `waitpid`），属**混合口径**，
本卡不再把它当作 fork 开销。

## 1. 为什么口径必须改：两个字段各自包住了什么

来源：`third_party/th08-rl/src/rlharness/fork.cpp`（`HandleBranch`，WSL 侧工作树实际源码）。

| 字段 | 起点 | 终点 | 实际含什么 |
|---|---|---|---|
| `fork_us` | `fork()` 调用前一刻 `Micros()` | `ReadAll(pipefd)` **与** `waitpid()` 都返回之后 | `fork()` + 子进程整段推进 + 子进程写管道 + 父侧读管道 + 回收 → **随 frames 线性增长，是混合量** |
| `child_us` | 子进程内 `fork()` 返回后，`close(pipefd[0])` 与 `SetMask()` 都完成时的 `Micros()` | 子进程 frames 循环结束（写管道之前） | 仅「子进程计时区间内的逐帧推进」→ 干净的每帧信号；`SetMask` 与管道写/读均不计入 |

- 子进程循环体是 `PumpOneFrame()` + `CurrentStateHash()`，因此**每帧斜率含逐帧哈希计算**，
  是「引擎推进 + 哈希」，不是纯模拟耗时。
- 两个计时器都是 `CLOCK_MONOTONIC` 截断到微秒（`Micros()`），单样本截断误差 ≤ 1 μs。
- 因此 `child_us ≈ a + b·frames` 的 `b` 是每帧开销，`a` 是子计时区间内的固定常数项；
  `fork_us` 中扣除 `child_us` 剩下的部分才是「子循环之外」的固定开销。

**旧口径的后果（本卡实测，见第 4 节表）**：`fork_us` 均值从 h=1 的 `1464.67 μs` 涨到 h=300 的
`14149.47 μs`。若把它当「分支固定开销」，同一台机器上会得出相差约 **9.7 倍**的结论。

## 5. 拟合结果

模型：`child_us = intercept + slope · frames`，普通最小二乘，n = 105，x ∈ [1, 300]。

| 量 | 值 |
|---|---|
| **每帧斜率 slope** | **41.424868 μs/frame**（0.041424868 ms/frame） |
| 斜率标准误 | 0.186464 μs/frame |
| **截距 intercept** | **519.291110 μs** |
| 截距标准误 | 26.616130 μs |
| **R²** | **0.9979174** |
| 残差 std | 203.315079 μs |
| SS_res / SS_tot | 4 257 713.2 / 2 044 455 605.7 |

> 标准误只反映**本次运行内**的散点，不含跨进程/跨时段漂移；不要把 `±0.19 μs` 读成绝对精度。

`fork_us` 自身也做同样拟合（对照用）：slope `41.978153 μs/frame`，intercept `1361.688107 μs`，
`R² = 0.9973971`，残差 std `230.395808 μs`。

**分解汇总**：

| 组成 | 估计值 | 含义 |
|---|---|---|
| 每帧推进（含逐帧哈希） | **41.4249 μs/frame** | 斜率 |
| 子计时区间固定项 | **519.2911 μs** | `child_us` 截距 |
| 子循环之外固定项（fork + 管道 + 回收） | **895.0381 μs** | `fork_us − child_us` 实测均值 |
| 每分支固定开销合计（实测口径相加） | **1414.3292 μs** | 519.2911 + 895.0381 |
| 每分支固定开销合计（`fork_us` 直接拟合截距） | **1361.6881 μs** | 两条路径相差 **3.87%** |

## 6. 交叉检查：`fork_us − child_us`

| 量 | 值 |
|---|---|
| 均值 ± std | 895.0381 ± 109.4833 μs |
| 范围 | 699 – 1252 μs（n=105） |
| 对 frames 拟合 | slope **0.553285 μs/frame**，intercept **842.3970 μs**，R² 0.291957 |
| 逐档均值 | 850.87 / 846.07 / 806.47 / 872.87 / 942.80 / 949.80 / 996.40 μs |
| 逐档漂移 | max−min = 189.9333 μs，占均值 **21.22%** |
| 该分量相当于主斜率的 | **1.3356%** |

解读：`fork_us − child_us` **近似**与帧数无关（按 JSON 中显式规则「逐档均值极差 ≤ 50% 均值」
判定 `flat=true`），但**存在小幅正趋势**（≈0.553 μs/frame，约为每帧成本的 1.34%）。这与
「结果管道 payload 随帧数增大（每帧 16 字节哈希）+ 子进程退出时页表回收量随被触碰页面增多」
的方向一致，因此严格说法是：**固定项主导（≈842 μs 常数），叠加一个小的帧数相关分量**，
而不是「绝对常数」。本卡不把 21% 的漂移隐去。

## 7. 重复性（同一进程内 3 个 pass）

| pass | n | slope (μs/frame) | intercept (μs) | R² | `fork_us−child_us` 均值 (μs) |
|---|---|---|---|---|---|
| 0 | 35 | 41.008 | 510.85 | 0.99844 | 864.57 |
| 1 | 35 | 41.425 | 520.49 | 0.99830 | 904.77 |
| 2 | 35 | 41.842 | 526.54 | 0.99746 | 915.77 |
| 汇总 | 105 | 41.4249 ± 0.4167（**1.006%**） | 519.2911 ± 7.9106（**1.523%**） | 0.99746 – 0.99844 | — |

- 每帧斜率在 pass 间相对离散 **1.01%**，截距 **1.52%**：斜率是更稳的那个量，
  **截距是最不稳的系数**（它由冷启动效应支配）。
- `fit(fork_us) = fit(child_us) + fit(fork_us − child_us)` 在数值上**精确成立**，
  但这是 OLS 系数对响应变量的线性性导致的**代数恒等式**，**不是**独立证据；
  真正独立的一致性检查是「`fork_us` 直接拟合截距 1361.69」对「截距 + 实测均值 1414.33」，
  两者相差 3.87%。

## 8. 解释（哪些是测量、哪些是推断）

1. **每帧成本 41.42 μs 是实测回归量**：含 `PumpOneFrame()` 与逐帧 `CurrentStateHash()`，
   不含 fork、不含管道、不含回收。
2. **截距 519.29 μs 的成因是推断**：h=1 时每帧 613.80 μs、h=300 时 43.844 μs，
   说明存在约 520 μs 的一次性成本；该成本只可能发生在子进程计时区间内（`SetMask` 在
   `begin` 之前、不计入），与「新 fork 出来的子进程首帧冷缓存 + 写时复制缺页」一致。
   **本工具不统计缺页次数**，所以这是**数据支持的推断，不是独立测量量**。
   等价说法：截距 ≈ 12.5 帧的稳态开销。
3. **`fork() + 管道 + waitpid` ≈ 842–895 μs 是两次真实计时之差**：它把子循环之外的一切
   合成一个固定项，仍**不是** `fork()` 单次系统调用耗时。
4. **实用推论**（供 WP5 预算使用，基于本机本次回归，非跨机常数）：
   `总耗时(h) ≈ 1414.3 μs + 41.42 μs × h`；固定项占比 < 50% 需 `h > 34.14` 帧（即 ≥ 35 帧）；
   h=300 时固定项约占 **10.22%**，h=1 时约占 **97.15%**——小 horizon 的分支几乎全是固定开销。

## 9. 限制与未覆盖

- **不是 `fork()` syscall 插桩**：全部数字来自对真实回复的回归推断，不得改名为纯 syscall 时间；
  没有任何一次实验单独隔离 `fork()` 前后时刻。
- **单次运行内的重复性**（3 pass）已量化；**跨进程 / 跨时段 / 跨机器**复现未纳入本产物。
  本次会话期间，共享 WSL 克隆里的 `th08-modern` 曾被并发工作**重新链接两次**
  （会话内先后观察到 SHA 前缀 `591c521d` → `25148702` → `a6b146ff`），
  这正是本工具改为用 `/proc/<pid>/exe` 钉住运行镜像身份、并要求
  `running_image_matches_binary=true` 的原因；被替换掉的早期运行**不在此卡引用范围内**。
  因此本卡只对 `a6b146ff…` 这一构建负责。
- **单机单核场景**：20 逻辑核的 WSL VM，未做 CPU 绑核/频率锁定，未排除同机其它负载
  （包括上述并发编译）对绝对值的扰动。
- **掩码固定为 0**：只覆盖一条全零输入的真实 StageStart 轨迹；不同掩码会改变每帧工作量，
  斜率不保证对任意掩码成立。
- **每帧斜率含哈希**：若只想量「模拟推进」，需扣掉 `CurrentStateHash()` 的成本，
  本实验未单独测量该项。
- 父进程全程未 `STEP`（`parent_frame` 恒 0）；「父状态随帧演化后分支成本是否变化」未覆盖。
- 引擎 `BRANCH` 上限 300 帧（`HandleBranch` 校验），>300 的 horizon 需分段推断，本卡不含外推验证。
