# EXP-P0-007 共享内存与读回成本

- 日期 / 工作包：2026-11-07 / P0-WP3（并补齐 P0-WP2 的"读回成本"一行）
- 假设：把状态与像素放进 POSIX 共享内存后，Python 侧能直接映射读取，控制管道只走命令与短回复；同时能量出 `glReadPixels` 的真实开销。
- 预注册：主指标 = ①Python 映射共享段后读到的头部、25 字段与像素与 harness 的回复一致；②在同进程内用 `READBACK 0/1` 对照，得到单帧读回耗时与吞吐差。通过阈值 = 两项都成立且数值自洽。样本量 = 各 1 次（读回各 300 帧）。
- 设置：
  - 子模块 `rl-harness`，提交 **`eb55712`**
  - 布局：`[0,64)` 头部（magic `0x30303456`、协议版本、帧号、状态哈希、尺寸、flags）、`[64,192)` 25 个 u32 字段、`[192,…)` 640×480 RGBA，合计 1,228,992 B
  - 环境：xvfb + `LIBGL_ALWAYS_SOFTWARE=1 LP_NUM_THREADS=1`
- 结果：**两项都成立**。

  共享内存（Python 直接映射 `/dev/shm/v400smoke`）：

  ```text
  segment: 1228992 bytes
  header : magic=0x30303456 version=1 frame=40 hash=e95533f3f54f9646 640x480 stateBytes=100 flags=0x3
  state  : f0=40 f1=0 f14=20048 f24=1
  pixels : first bytes [82, 76, 76, 205, 85, 77, 78, 205]  nonzero=1228800
  ```

  头部哈希 `e95533f3f54f9646` 与 `HASH` 命令的回复完全相同，`flags=0x3` 表示状态与像素都有效。

  读回成本（同一进程、300 帧、`READBACK` 开关前后对照）：

  | | 吞吐 | `glReadPixels` |
  |---|---|---|
  | `READBACK 0` | 145.6 fps | — |
  | `READBACK 1` | 130.4 fps | **5,329.5 µs/帧** |

  吞吐只掉 10.4%，而单帧读回要 5.3 ms——因为 `glReadPixels` 强制的那次同步，本来 `Present` 也要等；两者不是叠加关系。
- 有效性自检：
  - V1 是：Python 读的是 harness 自己 mmap 的同一段内存，不是经过序列化的副本；头部哈希与管道回复交叉验证
  - V2 不适用
  - V3 是：段长 1,228,992 = 192 + 640×480×4，与布局常量自洽；`nonzero=1228800` 说明像素非空
  - V4 否：读回成本只有一次 300 帧窗口，未重复；数值用于量级判断足够
  - V5 是：平凡基线是"共享段全零"；实际头部与像素都有真实数据
  - V6 不适用
  - V7 否：读回成本未换实例数重跑
  - V8 是：像素块就是学生将来的输入
  - V9 是：指标在运行前由 `10-P0` §3 布局与 WP2 决策表固定
- 结论：**成立**。WP2 决策表里"读回成本"这一行关闭；按 16 实例合计约 1,080 fps 估算，仍落在 500–2,000 区间，继续但按实测做预算。
- **一个会影响 G0.2 第 4 项的发现**：两次运行的**状态哈希完全相同**（`e95533f3f54f9646`），但**像素 checksum 不同**。原因是 HUD 上那个 fps 读数是按挂钟算的（画面右下角显示 "174.00 fps"），所以即使游戏状态逐位一致，渲染出的像素也会随实际耗时变化。`10-P0` WP5 第 4 项要求"按轨迹 + harness commit 重新生成的像素与原始缓存逐字节相等"，因此必须二选一：在 harness 模式下把 fps 读数固定，或者约定比较时排除 HUD 的 fps 区域。这属于 WP8 的判据细节，已记入任务清单。
- 成本：GPU 0 h；墙钟约 1.0 h；磁盘约 0.01 GB。
