# EXP-P0-078：T7 引擎——同一进程反复 `RESET` 与统一构建 `rl_v3`

- 日期：2026-11-10。Provider=DeepSeek，模型=DeepSeek v4.1 flash。
- 工作包：T7（任务书 [2026-11-10-P3 重启](../tasks/2026-11-10-P3重启任务书.md) §4 T7）。验收门：T7.1（进程内重开）、T7.2（统一构建）、T7.3（可选：状态区自动刷新）。
- 结论：**T7.1 / T7.2 / T7.3 全部达成**。根因是「开机请求只有一个消费者，而该消费者在第一局开始时就把自己从 chain 上删掉了」。修法不是 fork、也不是强推 `SupervisorState_GameManagerRestartFromBeginning`，而是把 supervisor 自己的状态机送回标题画面（引擎自己的"返回标题"路径），让标题的 Ready 状态**再一次**消费开机请求。修完后同一 shadow 进程连续 10 次 `RESET` 全部 `ready=1`，其中 9 次 `mode=in-process`；**3 个种子 × 每次 5,000 帧，共 50,000 帧逐帧哈希与 3 个全新进程完全一致（`different_frames=0`）**；`RESET` 墙钟中位数 **0.5834 s**（门限 1.5 s，旧路径每局重启进程 6–7 s）。统一构建 `build/rl_v3`（SHA-256 `691bfd77…68ef6`）合并了 `rl_laser` 的激光判定窗、`rl_events` 的 `EVENTS 0x0080`、`rl_score` 的 `HUD` 与 T7.1/T7.3，`HASH` 前 100 帧与 `rl_events` 逐帧一致，G0.2 第 1 项在 `rl_v3` 上复跑 **5000/5000 相等**，12 份覆盖四个难度的差分回放 **12/12 identical**。

## 预注册（写于运行之前）

- 主指标 1：同一进程连续 **10** 次 `RESET`，每次回复 `ready=1`。
- 主指标 2：在种子 **1234 / 1235 / 1236** 上，每次 `RESET` 之后的 **5,000** 帧 `hash=` 序列与**新进程**用同一 `StageStart` 得到的序列**逐帧**完全一致（`different_frames=0`、`frames_compared=5000`）。
- 主指标 3：`RESET` 命令墙钟（写命令到收到回复）**中位数 ≤ 1.5 s**。
- 通过阈值：三条全部满足；且 warm 进程与每个参照进程 `exit_code=0`；每条 `STEP` 恰好推进 1 帧并带 16 位十六进制 `hash=`。
- 样本量：10 次 `RESET` × 5,000 帧 = **50,000** 帧，对照 3 个全新进程 × 5,000 帧 = 15,000 帧。掩码序列沿用 EXP-P0-049（SplitMix64 seed 400、白名单 `0x00F7`、5,000 帧文本 SHA-256 `4173ff413d4bc18e27b771e86de16a441f765ac92b273c68ab7e32f5ee585e1f`），`StageStart` 同为 `RESET 0 1 0 <seed> 1`（practice=1，引擎在该模式下把 `lifeCount` 设为 8，单局才撑满 5,000 帧）。
- 判据冻结位置：`touhou_rl/v400/gym/inprocess_reset.py` 的 `REQUIRED_RESETS=10`、`REQUIRED_FRAMES=5000`、`RESET_WALL_LIMIT_S=1.5` 与 `evaluate()`；该工具在第一次验收运行**之前**写完，运行后未改阈值。非 `10 × 5000` 的运行会被工具标成 `preflight-only`、`pass=false`，不计为验收证据。

## 1. 根因：第二次 `RESET` 为什么一定失败（源码定位）

现象（[EXP-P4-001 §7.1](../experiments/EXP-P4-001-rl-prototype.md)）：第二次 `RESET` 返回 `ready=0 setup_frames=1800`，`frame` 停在 0。

链条如下，全部是既有源码，不是推断（行号为基线 `bef369a`、即 T7 改动之前的行号）：

1. `RESET` 并不自己切状态，它只是**装填一个开机请求**：`ArmStart()`（`src/rlharness/rlharness.cpp:972` 调用，实现 `src/rlharness/rlharness.cpp:1074-1082`）。
2. 这个请求**只有一个消费者**：`ConsumePendingStart()`，而它在全仓只有一个调用点——标题画面 Ready 状态（`src/TitleScreen.cpp:453-456`，`#ifdef TH08_RL_HARNESS` 内的 `if (modern::rlharness::ConsumePendingStart()) return CHAIN_CALLBACK_RESULT_CONTINUE_AND_REMOVE_JOB;`）。对 `src/` 全目录 grep `ConsumePendingStart` 只有这一处（另有定义与声明）。
3. `CHAIN_CALLBACK_RESULT_CONTINUE_AND_REMOVE_JOB` 的枚举值是 **0**（`src/Global.hpp:64`），`Chain::RunCalcChain()` 收到 0 就走 `CutImpl(tmp1)` 把该 calc 任务**从 chain 上摘掉**（`src/Global.cpp:178-184`）。于是第一局开始时，标题画面的 job 就被永久删除。
4. 第一局里 `g_Supervisor.curState` 已经是 `SupervisorState_GameManager`（2），`g_startArmed` 也已被消费。第二次 `RESET` 再 `ArmStart()` 时，**chain 里已经没有能消费它的元素**，`ConsumePendingStart()` 永远不会被调用。
5. 于是 `HandleReset` 的有界循环（`src/rlharness/rlharness.cpp:989-1003`）里 `sawInProgress` 永远为 false：`GameManager::AddedCallback` 从未运行，`gameplaySetupState` 也就不会出现 `GAMEPLAY_SETUP_IN_PROGRESS`。循环跑满 `kMaxSetupFrames = 1800`（`src/rlharness/rlharness.cpp:985`），`ready` 保持 false。
6. `ResetFrameCount()` 在循环之后**无条件**执行（`src/rlharness/rlharness.cpp:1033`），所以帧号被清零；`g_resetReady = ready && …`（`src/rlharness/rlharness.cpp:1051`）为 false。

三个观测值与这条链一一对应：`ready=0`、`setup_frames=1800`、`frames=0`。**不是** RNG、不是 GL、不是 setup 子线程超时。

## 2. 实现（只动 `src/rlharness/**`，没有 fork、没有改游戏逻辑）

第二局必须重新走一遍引擎**自己**开局时走的那条路。三条候选路径的取舍：

| 候选 | 结论 |
|---|---|
| `SupervisorState_GameManagerRestartFromBeginning`（`src/Supervisor.cpp:231-243`） | 可用，但它不经过标题画面：`wantedState2` 不等于 `TitleScreen`，`GameManager::AddedCallback` 会走另一条 loading VM 分支（不 `StartEffect`），与冷启动不是同一条代码路径，逐帧一致没有保障。**未采用。** |
| 在 harness 里手工重建 GameManager chain | 等于复制引擎逻辑，违反"不改游戏逻辑"。**未采用。** |
| **把 supervisor 送回标题画面**（采用） | 引擎自己的"返回标题"转移：`GameManager → TitleScreen` 时执行 `GameManager::CutChain()`、`curState = Init`、`ReplayManager::SaveReplay(NULL,NULL)`，再由 `init_titlescreen` 重新 `TitleScreen::RegisterChain(TITLE_SCREEN_REGISTER_STANDARD)`（`src/Supervisor.cpp:213-223`、`159-167`）。标题走到 Ready，`ConsumePendingStart()` 再消费一次并把自己摘掉，`TitleScreen → GameManager` 注册新 chain。**冷、热两条路径在这里汇合，此后是同一段代码。** |

改动共 4 处，都在 `#ifdef TH08_RL_HARNESS` 内：

1. `GameplayChainActive()`（新函数）：`g_Supervisor.curState == SupervisorState_GameManager && g_GameManager.globals != NULL`，用来判断这次 `RESET` 是冷启动还是进程内重开。
2. 热路径：`g_Supervisor.curState = SupervisorState_TitleScreen`，由 supervisor 自己的 `OnUpdate` 在下一帧完成 CutChain + 重建标题。**未使用 fork**：按 03 §3.2，持有 GL 上下文的进程不得 fork，这条路径也不执行任何进程/线程重建。
3. **实测踩到的第二个坑（必须记录）**：标题重建时 `TitleScreen::ActualAddedCallback()` 会读 `g_GameManager.IsPracticeMode()` 决定打开哪个菜单（`src/TitleScreen.cpp:3782-3790`），而这一步发生在 `ConsumePendingStart()` 应用本次请求**之前**。上一局是 practice 时，重建的标题直接进"练习难度选择"（`src/TitleScreen.cpp:395-420`），**永远走不到** StartMenu 的 Ready 分支，请求再次无人消费。第一次实现因此仍然 `ready=0 setup_frames=1800`（`DEBUG` 显示 `curState=1` 卡在标题），诊断后改成在切换前先清 `flags.isPracticeMode/isSpellPractice`；`ConsumePendingStart()` 两帧后会把本次请求的值重新写回，所以对局本身不受影响。
4. `RESET` 期间把 `g_mask` 置 0：`RESET` 由引擎驱动，调用方上一次决策的按键不能喂给标题画面（否则可能被菜单吃掉）。调用方在 `RESET` 后的第一个 `STEP` 里重新给 mask。
5. T7.3：`HandleReset`/`HandleStep` 结束时调用 `PublishState(fields, hash)`，把同一份 25 字段与同一哈希写进共享内存状态区（`state_published=1` 随 `RESET` 回复一起给出）。`RESET` 回复新增 `mode=cold|in-process` 与 `state_published`，都是**追加字段**，旧解析器按 `key=value` 读不受影响。

`gym` 侧（T7.3 的 fail-closed 半边）：`Th08Env` 记录 `RESET` 是否声明 `state_published=1`；声明了，就在每次 `RESET`/`STEP` 之后核对**共享区 header 的帧号**是否等于该回复自报的帧号，不等就抛 `StaleStateError`，绝不返回上一次的旧状态。没声明的旧构建保持原行为（仍要 `STATE` 先行），不猜。

## 9. 限制（必须与结论同时引用）

1. **shadow 角色**：本卡的 50,000 帧全部来自 `--rl-role shadow`（null device，无 GL）。重开走的是同一段 supervisor 状态机，但"带渲染的 env 角色重开逐帧一致"没有在本卡测；`rl_v3` 的 env 角色可用同一工具加 `--rl-role env` 复测，代价是每帧多了读回。
2. **practice=1 是 `StageStart` 的一部分**：引擎在该模式下把 `lifeCount` 设为 8，5,000 帧才不会中途 game over。这不证明"不死"或完整 6 面流程。
3. 逐帧 `hash=` 是 25 个跟踪字段的 FNV-1a 摘要，**不是全内存哈希**；相等只覆盖这 25 个字段。
4. 只覆盖 Stage 1 / Normal / team 0 / seed 1234–1236；其它面、难度、机体、更长的重开序列没有测。
5. `RESET` 墙钟是在**同机还有 T1 的 12 实例量产**（load average 22.9 / 20 核）时测得的，比空载更保守；反过来，本卡的绝对秒数不能当作空载性能。
6. 差分回放是 **ON vs portable OFF 的退路 C**（`10-P0` WP1 第 4 条授权），不是与零售可执行文件的逐位一致；`rl_v3` 通过的是"与 OFF 构建逐字节一致"。
7. 温度/频率、CPU 亲和性未固定；单线程证据来自 `DEBUG threads=1`。
8. **激光判定窗只做到"编译进二进制"级别的证据**：本卡 6,000 帧 Stage 6A 探针与 EXP-P1-021 自己的 24,000/30,000 帧探针都抓到 0 条活体激光（激光攻击在后期 Boss 战），`LASERS` 在采样帧上都回 `OK … count=0`。因此"18 字段行"的证明来自二进制格式串 A/B（`rl_v3` = `rl_laser` = `rl_score` = `rl_events` = 18 字段，`rl_hazard2` = 12 字段）与未修改的 `FormatLaserRow()`，**不是**一条活的激光行。
9. 本次运行期间同机 WSL 环境被其它任务改动过：`/root/v400-venv/bin/python` 的符号链接与 `build/rl_v3` 的产物在 10:42 被外部清除。`rl_v3` 已用同一 commit 重建并得到**逐字节相同**的 SHA（§7 第 4 条），`/root/v400-t7-bin/th08-modern` 另存了一份副本；本卡所有数字都对应这个 SHA。

## 10. 结论

**成立。** 同一进程可反复 `RESET`（10/10 `ready=1`，9 次走进程内重开），每次重开后的 5,000 帧与新进程逐帧一致（50,000 帧 `different_frames=0`），`RESET` 墙钟中位数 0.5834 s（门限 1.5 s）。统一构建 `rl_v3` 合并了 `rl_laser`/`rl_events`/`rl_score` 与 T7.1/T7.3 的能力，未改变 25 字段 HASH 语义与既有命令前缀；G0.2 第 1 项在 `rl_v3` 上复跑通过，12 份覆盖四个难度的差分回放全部 identical。**未触发止损**（确定性没有回归），`rl_v3` 可以交给后续任务使用。
