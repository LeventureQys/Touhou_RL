# EXP-P0-003 多实例扩展曲线：渲染路径的全机吞吐

- 日期 / 工作包：2026-11-07 / P0-WP2
- 假设：这台机器（20 逻辑核）用多进程并行能把"渲染 640×480 并产生观测"的合计吞吐推到 `10-P0` 要求的 ≥ 2,000 帧/s。
- 预注册：主指标 = N 个实例在稳定窗口内的合计逻辑帧率；通过阈值 = `10-P0` WP2 决策表（≥2,000 按原设计继续；500–2,000 继续但按实测重估预算；<500 停下问负责人）；样本量 = 每个 N 一次 20 s 窗口，另对 N=16 做一次逐实例有效性复核。
- 设置：
  - 二进制 `build/measure/th08-modern`（`-O0`，`main.cpp` 临时插入帧计数器，测完已还原）
  - 回放 `th8_ud2cd4.rpy`（`lunatic-3-b`，149,986 次计算），`TH08_RENDER_AUDIT_FAST=1`
  - GL：`LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe`；**每实例 1 个光栅线程**（`LP_NUM_THREADS=1`），避免超订
  - 单个共享 `Xvfb :77`（16 个独立 X server 会让测试端自身成为瓶颈）
  - **每实例独立 `--data-dir`**（`~/v400-data/inst-N`：`th08.dat`/`thbgm.dat` 只读符号链接，`th08.cfg` 与 `score.dat` 各自一份），对应 `10-P0` §4.7
- 结果：

  | N | 合计 fps | 每实例 fps | 并行效率 |
  |---|---|---|---|
  | 1 | 99.2 | 99.2 | — |
  | 4 | 444.7 | 111.2 | 112% |
  | 8 | 719.3 | 89.9 | 91% |
  | 12 | 1038.4 | 86.5 | 87% |
  | 16 | **1194.3** | 74.6 | 75% |
  | 16（`LP_NUM_THREADS=0`） | 1053.3 | 65.8 | 66% |

  - 复核：N=16 时 **16/16 个实例都在推进帧**（t=30s 逐实例计数分别为 900–1600，全部非零），合计 16,000 → 38,000 帧 / 20 s = **1,100 fps**，与主测 1,194 fps 吻合。
  - 单实例放开光栅线程（`LP_NUM_THREADS=0`）可达 **约 400 fps**，说明单实例的瓶颈是"单核＋单光栅线程"，而多实例的瓶颈是总核数。
- 结论：**成立但未达标**。全机渲染合计落在 **1,000–1,200 fps**，处在决策表的 **500–2,000 区间** → 按 `10-P0` WP2 规则：**继续，但必须按实测重估 P3/P4 预算**，不能按原设计的 2,000 fps 做算力规划。
- 有效性自检：
  - V1 是：计数器插在 `RunCalcChain()` 之后直接数逻辑帧；截图确认运行的是 Lunatic 实战（分数、火力、Graze 都在变），不是标题演示
  - V2 不适用
  - V3 是：主测 1,194 与复核 1,100 相差 8%，同量级
  - V4 否：每个 N 只有一次窗口，未做多次重复；曲线形状可用，但每个点不宜当作精确值
  - V5 是：平凡基线 = 单实例 99 fps；N=16 的 1,194 是它的 12 倍，扩展真实存在
  - V6 不适用
  - V7 部分：N=16 用了两次独立测量（主测与复核），结论一致
  - V8 不适用
  - V9 是：指标与阈值在运行前由 `10-P0` WP2 固定
- 三个会改变后续做法的发现：
  1. **`LP_NUM_THREADS` 是必须显式管理的旋钮**。单实例放开线程是 400 fps，锁到 1 线程只剩 99 fps；多实例时锁 1 线程反而更好（16 实例 1,194 vs 放开 1,053）。布置实例数时要按 `实例数 × 光栅线程 ≈ 核数` 来配。
  2. **必须每实例独立 `--data-dir`**。共用一个数据目录时，N≥8 会大量 `Segmentation fault`——多个进程同时读写同一个 `score.dat`。隔离后 16/16 全部健康。这条与 `10-P0` §4.7 一致，已被实测确认是硬要求。
  3. **WSL 的算力被 `.wslconfig` 卡在 8 核 / 12 GB**（Windows 侧是 20 逻辑核 / 34 GB）。首轮测出的扩展塌陷（N=8 掉到 55 fps/实例、N=12/16 全 0）就是这个原因。把 `processors` 改到 20、`memory` 改到 24 GB 并 `wsl --shutdown` 之后才得到上表。原文件已备份到 `%USERPROFILE%\.wslconfig.bak-v400`。
- 成本：GPU 0 h；墙钟约 1.2 h；磁盘约 0.2 GB。
- 已知缺口：`glReadPixels` 读回成本未测（需要临时加代码，留给 WP3）；"推演"帧/s 未测（`LP_NO_RAST` 已被 EXP-P0-002 证明不可用作代理，必须等空设备模式）；D3D12 硬件 GL 通路在 `wsl --shutdown` 后失效（`dmesg` 报 `dxgkio_query_adapter_info: Ioctl failed: -2`），本轮全部改用 llvmpipe，硬件后端对比待 GPU 通路恢复后补。
- 下一步：把上表换算成 P3/P4 的预算（P4-B 的四臂 × 3 种子 × 5000 万帧需要多少墙钟），写进 EXP-P0-002 的重估一节；然后进入 WP3，用空设备模式补"推演"吞吐。

## 预算重估（`10-P0` WP2 决策表要求）

按实测 **1,100–1,194 fps** 的全机渲染吞吐换算，对照 v3.9.0 实测的 **21.19 决策/s**：

| 项 | 数值 |
|---|---|
| 相对 v3.9.0 的提速 | **约 52 倍**（1,100 ÷ 21.19） |
| 1,000 万帧 | 2.3–2.5 h |
| 5,000 万帧（P4-B 单次 run） | 11.6–12.6 h |
| P4-B 全部 12 个 run（4 臂 × 3 种子） | **140–151 h** |
| P3 单轮 DAgger（按 1,000 万帧估） | 2.3–2.5 h |

对照预算（D-05：GPU ≤ 400 h；`04-阶段计划`：P4 时间盒 15 工作日 ≈ 360 h）：

- 140–151 h 落在 360 h 的时间盒内，约占 GPU 预算 400 h 的 35%（此处只计 CPU 墙钟，训练本身的 GPU 时另计）。
- 结论：**按原设计继续可行，但 P4-B 需要独占机器连续约 6 天**，期间不宜再跑其他重负载。若要把时间压到 3 天，就得把种子数从 3 降到 2 或把每臂帧数减半，那是 P4-WP2 预注册时要显式记录的取舍。
- 加速的主要杠杆（按收益排序）：①提升单实例效率（`-O2` 未验证，若可行可能翻倍）；②降低观测分辨率并在 harness 内缩放（`10-P0` WP2 的备选方案之一）；③等 GPU 通路恢复后比较 D3D12 后端。

## 追加：`-O2 -ffp-contract=off` 对照（否掉了 `10-P0` WP2 的最后一行）

把 UNIX 分支的 `-O0` 临时换成 `-O2 -ffp-contract=off` 重建（`build/o2c`），同一套测量方法对照：

| 配置 | `-O0` | `-O2 -ffp-contract=off` |
|---|---|---|
| N=1，1 光栅线程 | 124.1 fps | 110.0 fps |
| N=1，放开线程 | 110.0 fps | 123.5 fps |
| **N=16，1 光栅线程** | **1204.5 fps** | **1038.5 fps** |

**结论：`-O2` 没有带来任何吞吐收益**，两个单实例数字互为噪声（124 vs 110、110 vs 123），而 N=16 时 `-O2` 反而低 14%。

这个负结果很有价值：它说明**瓶颈不在游戏自身的 CPU 代码**，而在软件 GL 栈（Mesa llvmpipe 光栅化 + X11 调用）。因此：

- 不值得为了 `-O2` 去承担 108 份回放逐位复验的成本（`10-P0` WP2 原本要求"只有 108 份全部一致才允许采用 `-O2`"——现在这个取舍不存在了）。
- 真正的加速杠杆只剩两个：**降低观测分辨率**（在 harness 内缩放到 `obs_spec`，像素量与像素填充率同比例下降），以及**用硬件 GL 后端**（D3D12 通路恢复后重测）。

按 30 §6 这不构成问负责人的条件（只是参数级结论），但它把 `10-P0` WP2 决策表里"`-O0` 与 `-O2`"这一行的答案固定下来了。
