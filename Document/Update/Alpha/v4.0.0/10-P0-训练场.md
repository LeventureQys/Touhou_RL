## 3. harness 总体设计

```text
th08-modern（TH08_RL_HARNESS=ON） --rl-control <fd_in>,<fd_out> --rl-shm <name> --data-dir <dir> [--rl-role env|shadow]
```

- 有 `--rl-control` 参数时，进程**不走正常的主循环节拍**。它进入 `RlLoop`：阻塞读取命令，执行命令，返回结果。
- 每推进一帧，就调用一次 `RenderOneFrameUnpaced()`（§4.1）。这个函数里 calc 和 draw **都要执行**，因为有些 draw 回调会修改状态。
- `role=env`：GL 渲染到 FBO 并读回像素（§4.5）。这个进程**永远不 fork**。
- `role=shadow`：空设备模式（§4.6），不建窗口，不建 GL 上下文，不开音频，只有一个线程（§4.7）。所有 fork 都只在这类进程里发生。
- **关于 `LP_NO_RAST`**：它只用于 WP2 的吞吐测量，因为原样构建不支持空设备。正式的影子进程不用它。
- **共享内存布局**（每个进程一块）：

  ```text
  [0, 64)                      头部：协议版本、当前帧号、状态哈希、像素尺寸
  [64, 64+StateExport)         状态导出（定长，见 §5）
  [.., +W*H*4)                 像素（RGBA 或 RGB，按 obs_spec）
  [.., +B*RolloutResult)       分支结果区
  ```

- **不需要**栅栏、ack、GDI：harness 进程内部就是同步的，命令返回时，数据已经在共享内存里了。

## 4. 引擎挂钩点

文件和行号以 `main` 分支（`08c7f00`）为准。分支 `port/portable-64bit` 上的行号可能有偏移，实施时要重新定位。所有挂钩都要写成 `#ifdef TH08_RL_HARNESS` 加一个函数调用，具体逻辑放在 `src/rlharness/` 里。

### 4.1 一帧到底是什么

- 主循环在 `main.cpp:182-218`（Linux 的入口 `linux_runtime.cpp:293-297` 会调用 `WinMain`）。
- 每次调用 `GameWindow::Render`（`main.cpp:310-395`），在通过 1/60 s 的计时门以后，按以下顺序执行：
  1. `g_Chain.RunCalcChain()`（:348）——**一个逻辑帧**；
  2. `g_SoundPlayer.ProcessQueues()`（:349）；
  3. 当 `cfg.frameskipConfig <= ++framesSinceRedraw` 时，执行 `BeginScene`、`RunDrawChain`、`EndScene`（:362-373）；
  4. `Present()`（:381）。
- `Present()`（:398-438）依次调用 D3D Present、`g_AnmManager->TakeScreencaptures()`、HOME 截图，并递减 `screenTransitionCountdown`。
- calc 链的执行顺序（`Global.hpp:50-96`）：Supervisor(0) → Ascii(1) → GameManager(2) → … → 回放播放(6) → Background(8) → **Player(9)** → Enemy(11) → Spellcard(12) → Effect(13) → **Bullet(14，里面也会更新 Item)** → Gui(15) → … → 回放记录(17)。

**harness 的做法**：新增函数 `GameWindow::RenderOneFrameUnpaced()`。它把 :348-381 的内容原样复制过来，但**去掉计时门**，并强制每帧都画（等价于 `frameskipConfig = 0`）。`RlLoop` 每推进一帧就调用它一次。**calc 和 draw 都必须调用**，原因如下：

- draw 链里有几处会修改状态：`GameManager::OnDraw` 会把 `isInGameMenu` 从 1 推到 2（`GameManager.cpp:589-592`）；`Supervisor::OnDraw2` 会推进加载 VM（`Supervisor.cpp:385-415`）；Background 的 draw 会填 `specialEffectPoints`（`Background.cpp:734-738`）。
- `Present()` 里的 `TakeScreencaptures` 必须执行，否则标题初始化和续关菜单会卡死（`TitleScreen.cpp:3741`、`AsciiManager.cpp:1283-1302`）。

`th08.cfg` 模板中要设置 `disableVsync`，以跳过启动时的 `CheckFps` 校准（`Supervisor.cpp:568, 616-706`）。否则在 xvfb 下测到的帧率大于 65 时，游戏会整套重启。

### 4.2 输入注入

- **注入点：`Controller::GetInput()`**（`Global.cpp:722-806`）。在 harness 模式下，它直接返回 `RlHarness::CurrentMask()`，不再读取设备。调用者在 `Supervisor.cpp:121, 147`。
  - 这样做之后，掩码会经过 `RecordInputAndFps`（calc 优先级 17，`ReplayManager.cpp:238-267`）复制到 `g_GuiMessageInputCurrent`，下一帧才被 Player 使用。**延迟与原生完全一致**（v3.9.0 实测为 +1 帧），并且游戏自己写出的 `.rpy` 也仍然有效。
  - **不要**直接写 `g_GuiMessageInputCurrent`：那样延迟会变成 0，回放保真也会被破坏。
- **智能体掩码的白名单**：`SHOOT|BOMB|FOCUS|UP|DOWN|LEFT|RIGHT`，即 `0x00F7`。MENU(0x8)、SKIP(0x100)、Q(0x200)、S(0x400)、HOME(0x800，Linux 上截图会污染下一帧)、ENTER(0x1000)、D(0x2000)、RESET(0x4000) 一律清掉。
- **系统输入**由 harness 自动注入，不属于智能体的动作，但**要写进轨迹**，确保轨迹可以重放：
  - **换面**：`GameManager.cpp:381-389` 需要 `g_CurFrameInput` 中出现 `SHOOT|ENTER` 的**上升沿**才会进入下一面；按住 SHOOT 不算上升沿。当处于等待换面的状态时，harness 每隔一帧注入一次 ENTER 脉冲。
  - **对话**：当 `dialogue_present` 为真时，注入 SKIP（0x100）以跳过对话。实施时要核实 TH08 确实这样生效；如果不生效，就改用 SHOOT 脉冲。
  - **6A/6B 分歧**：分歧在对话中决定（`Gui.cpp:557-594`）。harness 提供参数 `route ∈ {A, B}`，按源码注入对应的输入，默认是 A。
- 轨迹里记录的是**实际喂给引擎的完整掩码**（智能体部分 | 系统部分），另外用一个位标记出哪些位是系统注入的。

### 4.3 直接进关（`StageStart`）

- **前提**：标题已经初始化完成，也就是 `TitleSetupThread` 已经结束，截图也处理完毕。harness 在启动后先空跑帧，直到出现这个状态，然后用 `PARK` 把这个状态冻结成"标题模板"。此后每次 `RESET` 都从这个模板 `SPAWN`，不必再从头启动进程。
- **进关**：照搬 `TitleScreen.cpp:1755-1791`（正常开局）以及 `:1937-1949` 和 `:1891`（练习关）的赋值，把它们抽成一个函数 `RlHarness::StartStage(spec)`：
  - `g_GameManager.shotType = team`（0–3 为组队，4–11 为单人机体，见 `ScoreDat.hpp:56-71`）；`fullShotType = 0`；
  - `difficulty`（0–3）；`currentStage`（0–8；Extra 时 `difficulty = 4` 且 `currentStage = 8`）；
  - 标志位：`isPracticeMode` 按 `resources` 设置；`isSpellPractice`、`isReplay`、`isDemoMode` 置 0；`cfg.slowMode = 0`；
  - 用 `g_Chain.Cut` 移除标题的 calc 链，然后设 `g_Supervisor.curState = SupervisorState_GameManager`（=2）。
- **种子**：在 `GameManager.cpp:937`（`stageRngSeed = …`）**之前**加挂钩：如果有待设的种子，就执行 `g_Rng.SetSeed(seed)`。这和回放路径固定种子的位置相同（回放在 :932 通过 `ReplayManager::RegisterChain` → `ReplayManager.cpp:601`）。回放能 108/108 逐位复现，就说明这个位置的确定性是成立的。G0.2 的第 1 项负责复核。
  - 注意：`GameManagerSetup.cpp` **不参与编译**（它是用于二进制匹配的探针，见该文件 :24-26），不要在里面加挂钩。
- **资源**：
  - `standard` 资源 = `th08.cfg` 模板中的 `lifeCount`，加上机体默认的 bomb 数；
  - `practice` 资源：游戏会把残机强制设为 8（`GameManager.cpp:751-754`）。
  - 如果需要修改资源，**必须**用 `Set*`/`Add*` 辅助函数，或者改完之后调用 `UpdateAntiTamper()`，否则会触发反篡改，导致禁止射击甚至退出（`GameManager.cpp:497-499`）。另外 `UpdateAntiTamper()` 会消耗 2 个 RNG 值，所以**必须在设种子之前完成**。
- **等待加载完成**：setup 线程会等主线程推进 30 帧以上（`GameManager.cpp:1057-1072`）。harness 在 `RESET` 内部持续推进帧，直到 `gameplaySetupState == COMPLETE`，并且 `runningSubthreadHandle == NULL`，才返回。返回时报告起点帧号。

### 4.4 从回放中途接管（`ReplayStart`）

- **优先方案**：复用游戏自己的回放播放路径进关，并以最快速度快进。分支上的 `TH08_AUTOPLAY_REPLAY`/`TH08_AUTOPLAY_STAGE`（`TitleScreen.cpp:188-240`）演示了如何以编程方式启动回放。这条路径能正确还原第 2 面以后从上一面继承的资源和 rank。
- 到达第 t 帧时**接管**：
  1. 移除回放播放的 calc 元素（优先级 6），加入记录元素（优先级 17）；
  2. 清掉 `isReplay`；
  3. 把输入源切换到 harness 注入。
- **接管不能改变逻辑**。验证方法：
  - 接管之后，继续由 harness 注入"回放剩下的输入"；
  - 与"纯回放播放"相比，状态哈希必须逐帧相等，持续 3,000 帧，在 10 个接管点上都成立。
- 还要检查 `isReplay` 是否影响画面（例如 HUD 上的回放标记）。接管后的画面必须与正常游玩一致。

### 4.5 取帧（主环境进程）

- 渲染目标是一个 640×480 `GL_RGBA` 的 FBO，挂在 `GL_COLOR_ATTACHMENT0` 上（`d3d8_compat.cpp:679-735`）。
- **读回点**：在 `EndScene` 之后（`main.cpp:373`），绑定 FBO，然后 `glReadPixels(0,0,640,480,GL_RGBA,GL_UNSIGNED_BYTE)`。行序是自下而上，需要翻转（参考 `ReadBackbuffer`，`d3d8_compat.cpp:201-212`）。可以用 PBO 双缓冲做异步读回。
- **不要**用 `LockRect`/`UnlockRect` 读：`UnlockRect` 会把表面标记为脏，下一次 Present 就会把旧像素盖到画面上（`d3d8_compat.cpp:190-248`）。这就是 HOME 截图和 `framefence.cpp` 的已知问题。
- harness 模式下，`LinuxDevice::Present` 跳过 blit 和 swap（:470-497），以避开 vsync；但游戏侧的 `Present()` 包装函数照常执行（为了 `TakeScreencaptures` 等）。
- 可选：在 harness 内用盒式滤波把画面缩到 `obs_spec` 规定的尺寸后，再写入共享内存，以降低带宽。

### 4.6 空设备模式（影子进程与分支进程）

- `--rl-role shadow`：不初始化 SDL 视频，不创建 GL 上下文。d3d8 compat 层的设备进入 **null 模式**：
  - 所有绘制和状态调用直接返回 `S_OK`；
  - `LockRect` 返回一块清零的缓冲；
  - 截图请求直接视为完成。
- draw 链**照常执行**游戏侧的代码（原因见 §4.1），只是设备调用变成了空操作。
- **为什么不用 `LP_NO_RAST`**：它仍然会创建 GL 上下文和 X 连接。fork 之后，子进程和父进程共享 X 连接，状态不安全。
- 验证：
  - null 模式跑 108 份回放，结果全部一致；
  - 影子进程与主环境对账 10,000 帧（G0.2 第 3 项）。

### 4.7 fork 安全

`BRANCH`、`PARK`、`SPAWN` 只能在满足以下条件时执行，不满足就拒绝并返回错误：

1. 进程只有一个线程（读 `/proc/self/task` 来检查）。
2. `g_Supervisor.runningSubthreadHandle == NULL`，并且 `gameplaySetupState == COMPLETE`。
3. 音频完全关闭：`th08.cfg` 中 `preloadMusic = 1`、`musicMode = 0`、`playSounds = 0`，环境变量 `SDL_AUDIODRIVER=dummy`。这样就不会创建 `BGMPlayerThread`（`Supervisor.cpp:790-800`、`SoundPlayer.cpp:306-308`）。如果仍然有音频线程，在 harness 模式下把音频初始化整个跳过。

**子进程**：写完结果就调用 `_exit(0)`，不执行 atexit，不写任何文件。

**文件 IO**：

- 每一面开始时，游戏都会写 `score.dat`（`GameManager.cpp:1157`），而 `score.dat` 的内容会影响 HUD 上的 HiScore 显示。harness 模式下要做到两点：
  - 每个进程都用独立的 `--data-dir`（dat 文件用只读符号链接，`th08.cfg` 和 `score.dat` 从**冻结模板**复制）；
  - `score.dat` 的写入改成空操作。
  
  这样，在同一个种子下，画面（包括 HiScore）是确定的。
- `modern-files.txt` 的追加日志在 harness 模式下关闭（`Global.cpp:999-1001`）。

### 4.8 终局与重开

- **game over**：残机耗尽时，游戏设置 `showRetryMenu = 1`（`Player.cpp:1373-1376`），之后 GameManager 返回 `BREAK`，游戏冻结。harness 检测到这个状态，就报告 `game_over` 事件，这一局结束，**不续关**。
- **过面**：
  - `PSN` 类型的套件，在 `stageClearSequenceActive` 出现上升沿时就结束这一局；
  - `RUNN` 套件则继续，由 §4.2 的系统输入完成换面。
- **重开**：从 §4.3 的标题模板 `SPAWN` 一个新进程。这是毫秒级的，替代了 v3.x 每次约 12 s 的进程重启。

## 5. 状态导出 `StateExport`（字段与语义）

**必须遵守的语义修正**（与旧的 `state.py`/`spec.py` 不一致的地方，以源码为准）：

1. 所有实体坐标都以 **playfield 为原点**，换算到屏幕是 (+32, +16)。
2. 子弹的 `collisionSize`（`+0xD34`）是**全宽**。判定半宽 = `collisionSize/2`（`Player.cpp:298-301`）。旧代码 `env.py:154-161`、`obs.py:119-122` 把它当半宽用，**不要复用**。
3. 只有 `state == 1`（FIRED）并且 `collisionDisabled == 0` 的子弹才致死（`BulletManager.cpp:828-953`）。状态 2–4 是生成中，5 是消失中，`bullets[0x600]` 是哨兵（状态 6）。
4. 敌人的判定与绘制位置使用 `worldPosition`（`+0x2D88`），不是 `position`。
5. 机体是 `GameManager.shotType`（`+0x3DBA9`，取值 0–11），不是 `character`。
6. 难度是 `GameManager.difficulty`（`+0x30`）。
7. `globals->score` 是分数的 1/10；HUD 上显示的是 `displayScore`（滚动值）。
8. 自机判定使用 `hurtboxBoundsMin/Max`（复活后会滞后于位置），聚焦不改变判定大小。
9. `g_GameManager.globals` 是一个可能被重新分配的指针，每一帧都要重新解引用。

harness 在进程内直接读 C++ 结构体，**不用偏移**，上面的偏移只是为了和旧代码对照。

| 组 | 字段 | 来源 |
|---|---|---|
| 时钟 | `frame`（逻辑帧）、`stage_frames`、`run_frames`、`gameplay_frame` | `GameManager.stageActiveFrames` / `runActiveFrames` / `gameplayFrameCounter` |
| 设置 | `stage`（0–8）、`difficulty`、`shot_type`、`flags`（practice/replay/stageClearSequenceActive/deathbombFreeze 等位） | `GameManager` |
| 资源 | `lives`、`bombs`、`power`、`score`（×10 还原）、`display_score`、`graze`、`point_items`、`time_orbs`、`deaths`、`bombs_used` | `ZunGlobals` |
| 自机 | `x`、`y`、`hurt_min[2]`、`hurt_max[2]`、`player_state`（0 存活 / 1 复活中 / 2 死亡中 / 3 无敌）、`focus`、`state_timer`、`deathbomb_window`、`bomb_active` | `Player` |
| 子弹 | `n`，以及定长数组 `[0x600]`：`x, y, vx, vy, w, h`（全宽）、`state`、`grazed`、`collision_disabled` | `BulletManager.bullets` |
| 激光 | `n`，以及 `[0x100]`：`x, y, angle, start, end, width, current_width, state, timer, hitbox_start, hitbox_end_delay, in_use` | `BulletManager.lasers` |

| 事件 | `frame_event_flags`（0x2 被弹、0x4 死亡提交、0x200 Die、0x2000 graze 等），以及本帧相对上一帧的资源变化 | `ReplayManager.frameEventFlags`（`+0xDA`） |

**实现要求**：

- 状态导出是**纯读取**，不能修改引擎的任何状态。
- 有一个测试：同一段回放，在开启和关闭导出两种情况下，回放验证都一致。
- 数组只导出活跃的元素，并且按槽位编号排序，以保证确定性。
