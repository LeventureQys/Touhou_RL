## 2. 机器与运行拓扑

**硬件**（2026-11-05/07 实测）：Windows 11，i5-14600KF（20 逻辑核），RTX 4070 SUPER 12 GB，内存 31.8 GB，D: 盘剩余约 1.1 TB。

**训练侧**：放在 WSL2 Ubuntu 24.04 里。

- 代码：在 WSL 的 ext4 分区上 `git clone` 本仓库（不要直接在 `/mnt/c` 或 `/mnt/d` 下工作，那里的文件 IO 很慢）。
- 数据：`th08.dat` 和 `thbgm.dat` 复制一份到 `$V400_DATA/game/`，所有引擎进程只读共享。
- 核心分配（起点，以 P0-WP2 的实测为准）：
  - 12 个引擎进程（6 个主环境 + 6 个影子）；
  - 4 核留给 Python 采集与数据加载；
  - 其余留给系统。

**部署复验侧**：放在 Windows 上，Python 环境沿用现有的（3.12 + torch cu132）。

- 代码通过 git 在两侧同步。
- checkpoint 从 WSL 复制到 Windows（`\\wsl$\...` 路径或 `/mnt/d`）。

## 3. 动作、观测与时间约定

### 3.1 按键位

沿用 `touhou_rl/spec.py:343-351`：

| 位 | 0x01 | 0x02 | 0x04 | 0x08 | 0x10 | 0x20 | 0x40 | 0x80 | 0x100 |
|---|---|---|---|---|---|---|---|---|---|
| 含义 | SHOOT | BOMB | FOCUS | MENU | UP | DOWN | LEFT | RIGHT | SKIP |

### 3.2 动作编码

- **18 个候选动作**：编号为 `cand = focus*9 + move`，开火常开、不放 bomb。这与 v3.8 的约定一致（`touhou_rl/v380/live.py:70-87`）。
- `move` 的顺序沿用 `spec.MOVES`：0=不动，1=N，2=NE，3=E，4=SE，5=S，6=SW，7=W，8=NW（+y 朝下）。
- **学生动作**：`(cand ∈ 18, bomb ∈ 2)`，编码成按键掩码 = 方向位 | FOCUS?(0x04) | SHOOT(0x01) | BOMB?(0x02)。
- 编码函数统一放在 `touhou_rl/v400/gym/actions.py`，内部复用 `spec.action_to_buttons`。

### 3.3 时间

- 决策周期 `P = 2` 逻辑帧，也就是每个决策都把同一个按键掩码保持 2 帧。
- **动作延迟由引擎自然产生**：harness 在游戏原本读取键盘的位置注入掩码（[10 §4](<10-P0-训练场.md>)），所以延迟与真机一致（v3.9.0 实测为掩码 +1 帧、位移 +1 帧）。**不要**在 Python 里额外模拟延迟。
- 真机部署时，抓图和推理还会带来额外延迟。P3-WP4 会在训练中加入"观测延迟 0–1 个决策"的随机化来覆盖这部分。

### 3.4 观测

- `PixelObs`：
  - `pixels: uint8[T, H, W, 3]`：最近 T 帧，每帧是游戏客户区 640×480 经过裁剪或缩放后的结果。缩放方式由 G2 冻结；
  - `prev_actions: int16[K]`：最近 K 个自身动作。
- 主环境进程**每个决策只读回最后一帧**的像素，T 帧堆叠在 Python 一侧完成。
- 坐标约定：引擎里所有实体的坐标都以 playfield 为原点（范围 0–384 × 0–448），绘制时会加上 `arcadeRegionTopLeftPos` (32,16)（`Player.cpp:1514-1517`、`BulletManager.cpp:1577-1580`）。**换算到屏幕像素：`(x+32, y+16)`。** 旧代码 `touhou_rl/obs.py:100-101` 混淆了这两套坐标，**不要复用**。P2-WP2 用叠加目检图复核一次。

## 4. 引擎进程与控制协议

### 4.1 进程角色

| 角色 | 光栅化 | 用途 |
|---|---|---|
| 主环境 `E` | 开 | 产生学生看到的像素 |
| 影子 `S` | 关（空设备模式：没有 GL，也没有窗口，见 [10-P0 §4.6](<10-P0-训练场.md>)） | 与 `E` 保持同一状态，fork 出分支做推演，供教师查询和标签生成 |
| 分支 `B` | 关 | 由 `S` fork 出来，按给定的输入计划推演 H 帧，汇报结果后退出 |
| 模板 `T` | 关 | 停在某个起点状态不动，需要时从它 fork 出新环境（用于快速重开到同一起点） |

**为什么要分出影子进程**：GL 上下文和渲染线程在 `fork` 之后不可用。所以带渲染的进程永远不 fork；fork 只在不渲染的进程里发生。

由于引擎是确定的，`S` 只要和 `E` 喂同样的输入，状态就会一样。两者每 K 帧（默认 60）比对一次状态哈希，不一致就立刻报错，并把那一局标记为无效。

### 4.2 控制协议（抽象层，具体实现见 10-P0）

每个引擎进程通过一对管道接收命令，大块数据（像素、状态）走 POSIX 共享内存。

| 命令 | 参数 | 返回 |
|---|---|---|
| `HELLO` | — | 构建身份（commit、编译开关）、协议版本 |
| `RESET` | `StartSpec` | 起点帧号、状态 |
| `STEP` | `mask: u16`、`frames: u16`、`want_pixels: bool`、`want_state: bool` | 实际推进的帧数、事件、状态（写入共享内存）、像素（写入共享内存） |
| `STATE` | — | 当前状态导出 |
| `HASH` | — | 当前状态哈希（25 字段 + 子弹池摘要） |
| `BRANCH` | `plans: [u16 掩码序列]`、`horizon`、`max_parallel` | 每个计划一份 `RolloutResult`（是否死亡、死亡帧、最小余量序列、事件、分数增量、末状态摘要） |
| `PARK` | — | 把当前状态冻结为模板，返回模板 id |
| `SPAWN` | `template_id` | 从模板 fork 出一个新的环境进程，返回它的控制句柄 |
| `QUIT` | — | — |

`BRANCH` 的实现：`S` 对每个计划 fork 一个子进程 `B`；`B` 推演完毕，把 `RolloutResult` 写进共享内存后 `_exit(0)`；`S` 收集所有结果后返回。不能有任何分支修改 `S` 自身的状态。

### 4.3 状态导出 `StateExport`

字段以 `touhou_rl/state.py` 中已有的命名为基础。完整字段表在 [10-P0 §5](<10-P0-训练场.md>)。大致包括：

- 全局：帧号、面、难度、机体、残机、bomb、power、分数、graze、点数、时间相关量、自机状态；
- 自机：位置、判定半宽、聚焦与否；
- 子弹：位置、速度、判定半宽、状态。只导出活跃的子弹，用定长数组加计数表示；
- 激光、敌人（位置、判定、HP、是否 Boss）、物品；
- Boss、符卡、对话、过面画面等标志位。

## 5. Python API（`touhou_rl/v400/gym`）

```python
@dataclass(frozen=True)
class StageStart:          # 按种子直接进关
    stage: int             # 引擎内部面号（0 = Stage 1；4A/4B/6A/6B 的编号在 P0-WP3 确认）
    difficulty: str        # "easy" | "normal" | "hard" | "lunatic"
    team: int              # 0..3（单人机体在 P0-WP3 确认编号）
    seed: int              # 0..65535
    resources: str = "standard"   # "standard" | "practice"

@dataclass(frozen=True)
class ReplayStart:         # 人类回放快进到第 frame 帧后接管
    replay_id: str         # config/replay-fixtures.json 的 id，或 th08_replay 文件名
    stage: int
    frame: int

@dataclass(frozen=True)
class TrajectoryStart:     # 我们自己的轨迹，快进到第 frame 帧
    traj_id: str
    frame: int

class Th08Env:
    def reset(self, start: StageStart | ReplayStart | TrajectoryStart) -> tuple[PixelObs, Info]: ...
    def step(self, cand: int, bomb: int = 0) -> tuple[PixelObs, float, bool, bool, Info]: ...
    # 第二个返回值是特权回报（只用于日志和 B2 臂）；terminated = game over 或过面（取决于套件）；truncated = 帧数上限
    @property
    def shadow(self) -> ShadowHandle: ...   # 教师查询入口；只能在训练期使用

@dataclass
class Info:
    frame: int
    events: list[Event]          # death、bomb、stage_clear、game_over、life_gain……
    priv: StateExport | None     # 特权状态；bench 的零特权模式下为 None
    traj_id: str

class ShadowHandle:
    def branch(self, plans: list[np.ndarray], horizon: int) -> list[RolloutResult]: ...
    def state(self) -> StateExport: ...

class VecTh08Env:   # N 个 Th08Env 的同步向量化封装；step 时批量下发命令、批量收集结果
    ...
```

**零特权模式**：`Th08Env(privileged=False)` 时 `info.priv` 恒为 `None`，`shadow` 访问会抛出 `PrivilegeError`。bench 评测学生时必须使用这种模式（[20 §7](<20-基准与评测.md>)）。

## 6. 起点库

- **人类回放**：
  - `third_party/th08/tests/fixtures/replays/th08-1.00d/accepted/` 下有 108 份，覆盖 4 个难度、全部路线、Extra。
  - `th08_replay/` 下有 40 份：Lunatic 15、Extra 17、Hard 7、Normal 1。
  - 解码使用子模块里的 `scripts/replay_file.py`（`decode`/`inspect` 可以拿到每一面的 `rngSeed` 和输入流）。
- `ReplayStart` 的实现：走游戏自己的回放播放路径，以最快速度快进到第 `frame` 帧，然后接管控制（详见 [10-P0 §4.4](<10-P0-训练场.md>)）。这条路径会自动还原第 2 面以后从上一面继承的资源和 rank。
- 起点库文件 `$V400_DATA/starts/index.jsonl`，每行一个起点：`{start_id, kind, replay_id/traj_id, stage, frame, difficulty, team, tags}`。tags 例如 `boss`、`spell`、`dense`。

## 7. 数据格式

**原则：回放是数据，像素是缓存。**

| 数据 | 格式 | 位置 | 能否删除 |
|---|---|---|---|
| 轨迹 | `traj-<id>.npz`：`header`（JSON：harness commit、StartSpec、策略 id、周期）、`masks: u16[F]`（逐帧输入）、`events` | `$V400_DATA/traj/` | 不能删（体积很小） |
| 教师标签 | `lab-<id>.npz`：逐决策的 `scores: f32[D,18]`、`bomb: u8[D]`、`margin: f32[D]`、`teacher_id` | `$V400_DATA/labels/` | 不能删 |
| 感知标签 | `perc-<id>.npz`：逐帧的低分辨率目标图（packbits）和标量 | `$V400_DATA/labels/` | 可以从轨迹重新生成 |
| 像素缓存 | `pix-<id>.npz`（zstd）：观测分辨率的 uint8 帧 | `$V400_DATA/pixcache/` | **可以删**，按 LRU 控制总量 |
| checkpoint | `torch.save` 字典：`{"schema":"v400-student/1","config":…,"state":…,"stateSha256":…,"metadata":{harness_commit, train_config_sha, data_ids}}`；哈希算法复用 `touhou_rl/v380/checkpoint.py` | `$V400_DATA/ckpt/` | 不能删；在实验卡片里记录 SHA |

**可复现规则**：任意一份像素或感知标签，都必须能由"轨迹 + harness commit"重新生成。P0-WP5 中有一个测试专门验证这一点。

## 8. 真机部署复验（Windows）

新工具 `tools/rl/v400_real_eval.py`，复用现有的实时栈（`touhou_rl/env.py` 的 `Th08Env` + `touhou_rl/v380/live.py` 的 `LiveAdapter`，即 v3.8.0 `--no-fence` 那一套）：

- 抓图：使用 `LiveAdapter` 抓到的**整帧** 640×480（`session.grab()`，GDI BitBlt），不要走 `pixels.py` 的 playfield 裁剪；然后按 G2 冻结的观测规格处理。
- 推理：学生在 GPU 上推理（v380_eval 是在 CPU 上推理的，这一点要改）。
- 动作：`(cand, bomb)` 编码成按键位掩码，再通过 `spec.action_to_buttons` 转成按键，用 `SendInputKeyboard` 发送（窗口需要在前台）。
- 裁判：死亡、过面等成绩由内存读取器统计，结果只写日志。这与 `DeployStepEnv` 的做法相同。
- 输出格式与 bench 的 `results.jsonl` 相同，套件名记为 `REAL-S1N`。
