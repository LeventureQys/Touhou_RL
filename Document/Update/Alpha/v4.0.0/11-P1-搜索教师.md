# 11 P1 搜索教师

- 依赖：G0（训练场，含 `BRANCH` 与状态导出）。
- 时间盒：8 个工作日。
- 产出：`teacher-v1`（`touhou_rl/v400/teacher/`、`tools/rl/v400_teacher.py`），通过 G1。
- 特权：教师只在训练期使用，只能通过影子进程访问引擎，**永远不进入部署**。

---

## 1. 为什么要这样设计

历史上的教师都输在**近似**上：

- `pilot.py` 用圆形近似加线性外推，只看 20 帧；
- `escape` 用逐帧 AABB 判定，但世界模型是自己预测的，而且排除了激光。v3.7.0 上真机反而比基线更差。
- 另外，`state.py` 读出的子弹 `collisionSize` 是**全宽**，旧代码却当成半宽使用（[10-P0 §5.3](<10-P0-训练场.md>)），所以旧教师眼里的每颗子弹都比实际大了一倍。

v4.0.0 的教师把**引擎本身当作唯一的判决来源**：一个计划会不会死，由 `fork` 出来的真实推演说了算，不由任何近似模型说了算。同时为了控制成本，搜索的"广度"交给廉价的几何搜索，"判决"交给昂贵的引擎推演。

---

## 2. 算法：录制 → 几何搜索 → 引擎验证

每 `R = 2` 个决策（4 帧）重新规划一次，执行计划的前 R 个决策。

```text
plan(S):                                    # S 是影子进程当前的状态
  1. 录制：从 S 分支一条推演，自机按"上一轮计划的剩余部分 + 保持不动(聚焦)"走 H 帧，
     逐帧记录所有致死物的几何（子弹、激光、敌人本体）→ HazardTape[H]
  2. 几何搜索：在 HazardTape 上，用精确的自机运动模型
     （速度、聚焦、边界钳制、1 帧输入延迟）做束搜索，
     对 18 个首动作分别求出"最优续接计划"及其余量 → geo_score[18]
  3. 引擎验证：取 geo_score 最高的 k 个首动作（默认 k=3），
     外加需要标注的动作（DAgger 时是学生的动作），
     对每个动作的最优续接计划，分支做真实推演 H 帧 → 是否死亡、最小余量、事件
  4. 如果验证出的结果与录制不一致（例如自机狙因为自机位置不同而改变了弹道）：
     用验证推演的轨迹重新录制 HazardTape，回到第 2 步。最多迭代 3 次
  5. 选择：在验证存活的计划里，按 §3 的评分取最高者；
     如果没有任何计划存活，并且 bombs > 0 → 放 bomb；否则选择余量最大的那个
  6. 输出 TeacherLabel(scores[18], bomb, chosen_plan, margin, verified_mask)
```

**为什么要录制，而不是直接搜索**：子弹的运动大多与自机无关，只有自机狙和少数脚本例外。先把世界录下来，就可以用几何方法在毫秒级搜索上千条路径。录下来的世界和真实世界之间的差异，由第 3–4 步的引擎验证兜住。

### 2.1 致死物几何（全部来自源码，见 [10-P0 §5](<10-P0-训练场.md>)）

| 致死物 | 何时致死 | 判定几何 |
|---|---|---|
| 子弹 | `state == 1`（FIRED），且 `collisionDisabled == 0` | 以 `position` 为中心、`collisionSize/2` 为半宽的 AABB。注意 `collisionSize` 是**全宽** |
| 激光 | `inUse`，且按 `state` 与 timer 处于有判定的区间（`BulletManager.cpp:1069-1144`） | 在激光坐标系中的矩形：长轴为 `end-start`（`startOffset > 0` 时乘 0.7），半厚为 `width/4`；中心在 `position.x + start + (end-start)/2`，再旋转 `angle` |
| 敌人本体 | `flags1` bit2（collision） | 以 `worldPosition` 为中心、`hitboxDimensions/1.5` 的 AABB，外加拖尾采样点 |
| ECL 旋转光束 | 脚本触发（`EclExIns.cpp:529-597`） | 几何搜索中不建模，**只靠引擎验证兜底**。死亡分析里单独统计这一类死因 |

- 自机判定使用 `hurtboxBoundsMin/Max`（不是 `position ± halfSize`，因为复活后 bounds 会滞后），判定边界含等号。
- 聚焦**不改变**判定大小。team 0 的判定半宽实测为 0.825。

### 2.2 自机运动模型

- 速度：team 0 实测非聚焦为 4.0（轴向）/ 2.8284（斜向），聚焦为 2.0 / 1.4142。其他机体的速度从 `primaryShtFile` / `secondaryShtFile` 读取，**不要写死**。
- 边界：x ∈ [8, 376]，y ∈ [16, 432]（playfield 坐标）。
- 输入延迟：掩码在第 t 帧写入，位移从第 t+1 帧开始。可以复用 `touhou_rl/escape/geometry.py:260-339` 中的执行路径和逐帧 AABB 判定，但**必须修正半宽**（使用 `collisionSize/2`）。
- 自机不在 ALIVE 状态时（DYING、SPAWNING、INVULNERABLE），不做规划，直接输出"不动"。INVULNERABLE 状态下仍然规划位置（为了输出），但不计算死亡。

## 3. 评分

对验证存活的计划 p：

```text
score(p) = 100
         + min(margin(p), 16)                  # 整个地平线上到最近致死物的最小间距（像素），上限 16
         + 4  · align(p)                       # 末端 x 与目标 x 的接近度 ∈ [0,1]；目标 = Boss 或最近敌人的 worldPosition.x
         + 2  · items(p)                       # 推演中收到的点/P 物品数，上限 1
         − 1  · edge(p)                        # 末端离边界小于 24 px 时为 1
         − 3  · high(p)                        # 末端 y < 200 时为 1（太靠上；收点线的设计留到 P4）
死亡的计划：score = 死亡帧 / H × 10           # 越晚死越好，但一定比任何存活计划低
```

- `scores[18]` 中每个首动作的分数，取它所有续接计划里的最高分。经过引擎验证的，用验证后的分数；没验证的，用几何分数减 5（对未验证者打折）。
- 软标签温度 τ 在 P3 里定（[13 §2.4](<13-P3-像素学生.md>)）。
- **权重是初始值**，放在 `teacher/config.py` 中。P1-WP5 可以调参，但每一次修改都要写进实验卡片。

## 4. bomb 规则

1. **主动 bomb**：第 5 步发现所有计划都会死，并且 `bombs > 0`。
2. **决死 bomb**：主环境中出现 `PLAYER_HIT` 事件（`frameEventFlags & 0x2`），并且 `bombs > 0` 时，下一个决策立即按下 bomb。
   - 决死窗口的帧数（`Player.cpp:534-590`）：持有的 bomb 数 × 6；如果时间点数达到阈值再加 7；上限 15。符卡中翻倍，上限 30。机体 0、4、5 再乘以 9/5。没有 bomb 时只有 2 帧。
   - 输入有 1 帧延迟，所以有效窗口还要再减 1 帧。窗口 ≤ 2 帧时决死 bomb 来不及，只能依靠第 1 条规则。
3. 其他情况一律不放 bomb。（何时放 bomb 最划算，这种资源经营问题留给 P4 的专家迭代。）

## 5. 参数与模式

| 参数 | 完整模式（G1 评估、产数据） | 快速模式（DAgger 标注） |
|---|---|---|
| 地平线 H | 48 帧 | 32 帧 |
| 重规划间隔 R | 2 个决策 | 2 个决策 |
| 几何束宽 | 64 | 24 |
| 验证数 k | 3 + 待标注动作 | 1 + 待标注动作 |
| 重录迭代上限 | 3 | 1 |
| 目标速度（单个影子进程） | ≥ 1× 实时 | ≥ 3× 实时 |

- 几何搜索放在 Python + numpy 里实现；如果慢，就用 numba，或者写成 C 扩展。P1-WP1 要先测出单次搜索的耗时。
- 速度达不到目标时，按这个顺序降配：先减 k，再减束宽，再缩短 H。每一次降配都要重新跑一次开发集评测，确认没有降质。

## 7. 门 G1

| 判据 | 阈值 |
|---|---|
| `PSN`（8 面 × 确认种子 100 个） | 平均每面死亡数 ≤ 0.5 |
| `S1N`（确认种子 100 局） | 过关率 ≥ 90% |
| 死因①（执行与验证不一致） | 0 次。只要出现，先修确定性，修好后才能评估 |
| `PSL`、`RUNN` | 只报告，不设门 |
| 速度 | 完整模式下单个影子进程 ≥ 1× 实时；报告产 1 小时游戏数据所需的墙钟 |

### 不过怎么办

- 死因②占多数：说明是真的被困住了。可以加长 H，或者调整 bomb 规则。
- 死因③占多数：在几何中补上 ECL 光束（读取 `EclExIns.cpp` 涉及的敌人变量）。
- 死因①出现：确定性有问题，回到 P0-WP5。
- **止损**：时间盒用完时，如果 `PSN` 平均每面死亡数仍然 > 2，就停下来写分析，并问负责人。这个结论本身很重要：它意味着在当前的动作接口下，就连精确前瞻也做不到，必须先弄清楚为什么。
