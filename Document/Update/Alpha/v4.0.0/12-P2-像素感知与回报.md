# 12 P2 像素感知与像素回报

- 依赖：G0。可以与 P1 并行；P1 的教师可用之后，再把教师轨迹补进数据集。
- 时间盒：8 个工作日。
- 产出：
  1. 冻结的像素回报检测器 `reward-v1`；
  2. 冻结的观测规格 `obs_spec.json`（交给 P3）；
  3. 感知标签生成器（P3 的辅助头会用到）。
  
  通过 G2。

---

## 1. 两个目的

1. **像素回报（能力 C4）**：只看画面，就能知道"死了没有、放了 bomb 没有、过面了没有、还剩几条命和几个 bomb、分数涨了多少"。这是在新作品上"自己练"的前提，也是跨作品协议的前置条件 P3。
2. **感知目标与分辨率（能力 C3）**：把"多大的分辨率才能看清判定附近的子弹"量清楚，P3 按这个结论选输入规格。

v3.9.0 的 L1/L1b 声称"像素奖励不可行"，那个实验是无效的（[01 §2.2](<01-复盘与转向.md>)）。本阶段是第一次正式测试这个问题。

## 2. 数据

### 2.1 来源

训练场的主环境进程在**同一帧**内既渲染画面，又导出状态，所以像素和标签天然对齐。这个优势是栅栏采集没有的。

| 来源 | 作用 | 占比（目标） |
|---|---|---|
| `random`（18 个动作均匀随机，开火常开，偶尔放 bomb） | 制造大量死亡、bomb、game over 事件 | 35% |
| `still` / 偏置随机 | 覆盖各种站位 | 10% |
| 人类回放（`ReplayStart` 快进后继续播放回放输入） | 覆盖后面的关卡、Boss、符卡、过面画面 | 30% |
| 教师（P1 可用之后补充） | 覆盖高水平玩法下的状态 | 25% |

- 设置：team 0；Easy 与 Normal；1–6 面全部（含 4A/4B/6A/6B）。Hard/Lunatic 以及其他机体**只**用于泛化报告（§6），不进入训练。
- 规模：约 150 万帧，按种子划分训练、验证、测试（测试种子来自 bench 的 `dev` 区间之外的独立区间，并记录下来）。
- 存储：轨迹（回放）+ 感知标签分片 + 像素缓存（[03 §7](<03-系统架构.md>)）。

### 2.2 有效性审计（P2-WP2 必须产出的表）

数据生成完毕后，**先出这张表，再训练模型**。这是 [30 §4](<30-执行规范.md>) 的 V1–V3 在本阶段的具体落实：

- 每类事件的正例数量：死亡、bomb、过面、game over、加命。**每类至少 500 个正例**，不够就补采。
- 残机数、bomb 数各取值的分布（0–8），每个取值至少 1,000 帧。
- 分数增量的分布。
- 每个面、每种来源的帧数。
- 随机抽 50 帧，在画面上叠加标签（自机点、子弹框、HUD 数值）后导出成图片，**人工目检**，确认坐标换算正确：屏幕坐标 = playfield 坐标 + (32, 16)。

## 3. 标签（全部由状态导出计算，字段见 [10-P0 §5](<10-P0-训练场.md>)）

### 3.1 事件（逐帧，来自 `frameEventFlags` 和全局量的变化）

| 事件 | 定义 |
|---|---|
| `hit` | `frameEventFlags & 0x2` |
| `death` | `frameEventFlags & 0x4`（死亡在决死窗口结束后正式提交），或者 `deaths` 增加 |
| `bomb` | `bombsUsed` 增加 |
| `stage_clear` | `GameManager.flags` 的 bit9（`stageClearSequenceActive`）出现上升沿 |
| `game_over` | 残机耗尽之后进入续关菜单（`showRetryMenu`）。具体条件在 P0-WP3 核实 |
| `extend` | `livesRemaining` 增加 |

### 3.2 HUD 标量

| 标量 | 来源 | 注意 |
|---|---|---|
| 残机 | `livesRemaining`（f32，取整） | 星形图标位于 (488+16i, 88) |
| bomb | `bombsRemaining` | 星形图标位于 (488+16i, 104) |
| 分数 | **`displayScore`**（HUD 上显示的滚动值），不是 `score` | 位于 (488, 56)，`%.9d` 格式，每个字宽 13 px |
| power | `playerPower`（0–128） | 位于 (488, 136) |

**HUD 滞后**：HUD 的每一行只在对应的 dirty 计数被置位时才重绘（`Gui.cpp:1166-1203`），所以画面上的数值可能晚于内存。处理方法：

- P2-WP1 先测出每一类 HUD 数值从内存变化到画面变化的帧差分布，写进实验卡片；
- 检测器的标签采用"画面应该显示的值"，也就是按实测滞后对齐之后的值。

### 3.3 感知图（逐帧，屏幕坐标）

- 自机位置热图（高斯，σ=2 px）。
- 致死物占用图：按 [11 §2.1](<11-P1-搜索教师.md>) 的几何在原分辨率下光栅化（子弹 AABB、激光旋转矩形、敌人本体），然后下采样到 1/4。
- 未来危险图：t+4、t+8、t+16 帧的占用图（来自已经录好的轨迹的未来帧，按实际执行的动作计算）。
- 标量：自机到最近致死物的距离。

## 4. 模型

### 4.1 像素回报检测器 `reward-v1`

- **输入**：最近 8 帧整帧（640×480 下采样到 320×240，RGB），**包含 HUD**。
- **输出头**：
  - 事件（多标签，含义是"该事件发生在最近 2 个决策内"）；
  - 残机（0–8 分类）；
  - bomb（0–8 分类）；
  - 分数：9 位数字逐位分类，或者 Δ分数分桶。先试逐位分类，因为它可以解释；
  - power（回归）。
- **架构**：小型 CNN（IMPALA 风格），可选加一个空间注意力。
  - 先做**整帧模型**：不硬编码 HUD 坐标，以后迁移时更通用。
  - 如果整帧模型达不到门槛，再做一个**HUD 裁剪模型**（用 §3.2 的坐标裁剪），并在卡片里标注"TH08 专用"。
- **像素回报函数**（放在 `perceive/reward.py`）：

  ```text
  r_pix = 1.0·clip(Δscore_pix/1e5, 0, 1) − 1.0·death_pix − 0.3·bomb_pix + 2.0·stage_clear_pix
  ```

  - 事件采用阈值加去抖：同一类事件 30 帧内只计一次。
  - `Δscore_pix` 取连续 3 次读数的中位数之差，负值截成 0。

### 4.2 感知模型与分辨率研究（P2-WP4）

- 同一个编码器，加上感知头（自机热图、占用图、未来危险图），分别在两种输入上训练：
  - **A**：半分辨率整帧 320×240（playfield 为 192×224）；
  - **B**：原分辨率 playfield 384×448。
- 指标：
  - 自机半径 48 px 以内，占用图的 F1；
  - 自机定位误差；
  - 未来 8 帧危险图的 F1。
- **决策规则**（预注册）：
  - 如果 A 的近身占用 F1 ≥ 0.9，并且不低于 B 的 95%，选 A；
  - 否则选"双输入"：原分辨率 playfield + 半分辨率 HUD。
- 结论写进 `obs_spec.json`，P3 照此执行。

## 6. 门 G2

在测试种子上（team 0，Easy/Normal，全部面）：

| 判据 | 阈值 |
|---|---|
| 死亡事件 | 召回率 ≥ 99%，精确率 ≥ 99%，延迟中位数 ≤ 10 帧（从 `death` 事件帧算起） |
| bomb 事件 | 召回率与精确率均 ≥ 99% |
| 过面事件 | 召回率与精确率均 ≥ 99%（样本少就报告置信区间） |
| 残机数、bomb 数读数 | 逐帧准确率 ≥ 99.5%（按 §3.2 对齐滞后之后） |
| 分数增量的符号 | 一致率 ≥ 99% |
| 在线校验（WP5） | 上面所有指标在实时运行中保持住 |

**泛化报告**（不设门，但必须报告）：

- Hard/Lunatic；
- 其他 11 种机体；
- 关闭 HUD 对齐修正时的表现。

这些数字决定 P5/P6 的预期。

### 不过怎么办

- 某一类事件达不到：先查标签（V1–V3），再查样本量，最后才考虑改模型（加帧数、提高分辨率、换成 HUD 裁剪模型）。
- 分数读数不准：退而求其次，改用"Δ分数分桶"，或者先只用"死亡 + 过面"这两项回报。降级要写进卡片，并通知 P4。
- **止损**：时间盒用完时，死亡检测仍然达不到 95% → 停下来写分析，并问负责人。在这种情况下，P4 的循环 B 不能启动，但 P3 不受影响（P3 只用教师标签，不用像素回报）。
