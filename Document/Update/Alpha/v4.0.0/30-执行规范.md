## 2. 工作区与代码布局

| 内容 | 位置 | 规则 |

**Git 规则**

- 主仓库在分支 `v400` 上工作，子模块在分支 `rl-harness` 上工作。
- 每完成一个工作包提交一次。提交信息用中文或英文都可以，但不得包含 emoji（这是仓库规则）。
- 不 push，除非负责人要求。
- 不提交大件，不提交 `.tmp_*`。

## 3. 工作循环（每个工作包都这样走）

1. 读规格中对应的工作包：目标、产出、验收。
2. 如果规格要求先做 spike，就先做，用实测数字决定是否按原设计继续。
3. 实现代码，同时写单元测试。
4. 跑测试：
   - 新增的测试必须全部通过；
   - 全量回归不能出现新的失败：`python -m pytest touhou_rl/tests tests -q`。在 Windows 侧，由于 TEMP 目录的权限问题，必须加 `--basetemp .tmp_v400_pytest`（见 `ENVIRONMENT.md`）。
   - `harness` 标记要在新建的 `touhou_rl/tests/conftest.py` 中注册。新建之前，确认它不会改变已有测试的行为。
5. 运行实验或产出。**凡是产生数字的运行，都要写一张实验卡片。**
6. 更新 [任务清单](<任务清单.md>)：状态、实验卡片链接、一句话结论。
7. 如果这个工作包是某个门的最后一步，就写门报告（见 §8），然后停下来等负责人确认。

## 4. 有效性自检（任何结论落笔之前，不论正负）

逐条回答。**任何一条答"否"或"不知道"，都不得写结论**，只能写"实验无效，原因是……"。

| # | 检查项 | 反例（v3.9.0 的真实事故） |
|---|---|---|
| V1 | 输入里**是否真的包含**目标信息？ | 用切掉 HUD 的画面去预测残机数 |
| V2 | 标签有没有方差？各类别是否平衡？正例数量够不够？ | 10 个块里 8 个块标签恒定，死亡样本只有 8 个 |
| V3 | 数值是否落在物理上合理的范围内？ | 子弹数 MAE 10,029，而真实范围只有 0–108 |
| V4 | 统计单位是不是独立 episode？样本量是否 ≥ 规格要求？ | 相邻帧被当成独立样本 |
| V5 | 平凡基线（随机策略、恒定动作、预测均值）跑出来是多少？结论是否明显超过它们？ | 合成世界可以被单一恒定动作通过 |
| V6 | 训练场景与评估场景有没有分开（不同种子、不同起点）？ | — |
| V7 | 换一个 seed 重跑，结论是否仍然成立？ | v3.8.0 中 n≤10 的正例补样后消失 |
| V8 | 有没有混入特权信息？学生输入是否只有像素？ | — |
| V9 | 是不是用了预注册的指标？有没有看完结果再换指标？ | — |

自检结果要写进实验卡片的 `有效性自检` 一节，逐条写"是/否 + 证据"。

## 5. 实验卡片模板

每张卡片不超过 1 页。复制下面的模板：

```markdown
# EXP-P1-003 搜索教师 v0 在 Stage 1 Normal 上的通关率

- 日期 / 工作包：2026-11-xx / P1-WP3
- 假设：……（一句话）
- 预注册：主指标 = ……；通过阈值 = ……；样本量 = ……（必须在运行前写好）
- 设置：命令行（可以直接复制运行）、代码 commit、配置文件、种子集、checkpoint SHA
- 结果：主指标点估计 + 95% 区间；关键诊断数字
- 有效性自检：V1–V9 逐条
- 结论：成立 / 不成立 / 实验无效（三选一）+ 一句话
- 成本：GPU 时、墙钟、磁盘
- 证据：evidence/EXP-P1-003/…（JSON 原始数据）
- 下一步：……
```

**规则**

- "预注册"这一行必须在运行之前写好。运行之后不得修改阈值；如果确实需要改，就新开一张卡片，写明理由。
- 失败的实验也要写卡片。不得删除卡片。
- 所有数字必须能从证据 JSON 复算出来。

## 6. 什么时候必须停下来问负责人

遇到下面任何一种情况，停下来，写清楚问题、选项和你的建议，然后等待回复：

1. 需要管理员权限、安装系统级软件、重启机器（例如安装 WSL2）。
2. 需要购买东西，使用付费云服务，或者获取新的游戏资源。
3. 任何可能删除、覆盖已有数据、实验或报告的操作。
4. 要修改 canonical 构建、原始镜像、默认模型，或者要往外部进程写内存。
5. 一个门的止损条件被触发（各阶段规格里写了止损条件）。
6. 预算用到 80%。
7. 规格与实测事实冲突，而且冲突会改变路线（不只是改变参数）。
8. 一个门通过了（G0、G1、G3、G4 需要负责人确认之后才能继续；见 D-09）。

不需要问的情况：规格范围内的参数调整、实现细节、工具选型、bug 修复。这些自己决定，并在实验卡片或提交信息里记录。

**提问格式**：一个问题只问一件事；给出 2–4 个选项，每个选项写明代价和风险；标出你推荐哪个以及理由。

## 7. 文档规范

- 每个阶段只有一份规格（已经写好）。规格需要修订时，直接改规格，并在文件末尾的"修订记录"里追加一行。
- 每个门写一份门报告，不超过 2 页。
- **不要**写多轮验收文档，**不要**写需求、设计、验收三件套，**不要**给每个子任务写单独的计划文件。
- 结论要写成一句可以被证伪的话，并附上证据链接。
- 文档中不使用 emoji。

---

## 8. 门报告格式

文件名：`gates/G<n>-报告.md`。

```markdown
# G1 门报告：搜索教师

- 日期、代码 commit、配置
- 判据（照抄规格）与实测值，逐项列表：判据 / 阈值 / 实测 / 通过与否
- 关联实验卡片列表
- 已知问题与风险（不超过 5 条）
- 成本合计（本阶段，以及 v4.0.0 累计）
- 下一阶段要用到的产出（路径 + SHA）
- 需要负责人确认的事项
```

## 9. 测试规范

- 纯 Python 逻辑必须有单元测试，例如动作编码、回报计算、数据格式、统计工具。
- 涉及训练场的功能必须有集成测试，用 `pytest.mark.harness` 标记，至少包括：
  - 同种子同输入，两次运行轨迹哈希相等；
  - 快照分支与不中断运行在 N 帧内的状态哈希相等；
  - 回放复现：运行回放语料中的若干份，与参考值一致。
- 训练代码至少要有一个"能在 2 分钟内跑完的冒烟配置"，并为它写一个测试。
- 全量回归必须保持绿色。确实无法修复的已知失败，要在任务清单里登记。

## 11. 禁止事项

1. 修改 canonical 构建、原始镜像、默认部署模型，或 v3.x 已有的证据目录。
2. 往**外部**游戏进程写内存、注入代码、做 patch。研究构建在自己进程内的导出不属于此列。
3. 在学生模型的输入里放入任何特权信息（内存状态、引擎导出、教师的内部量）。
4. 打开 v3.7.6 冻结的 sealed test 资产。
5. 看完结果再修改预注册的阈值或指标。
6. 删除失败的实验记录。
7. 在没有通过有效性自检的情况下写结论。
8. 以"提高动作重复次数"作为提速手段，例如把决策周期调到大于 2 帧来刷吞吐数字。
9. 门没有通过就进入依赖它的下一阶段。
