# 2026-11-02 v3.7.3：P0 在帧栅栏上重判（round26）

本节记录一次"把已经冻结的未知重新打开、用新工具重跑、并且在真机上被现实打断三次"的过程。写作目的是让人能复现我的判断顺序，而不是只看到最后的十行通过。

## 1. 起点：用户给的到底是一条什么信息

用户说"继续 v3.7.3 的工作"，并给了 `DATA-ACQUISITION.md`。这篇文档的结论不是"再讨论一下 ±1 帧"，而是：

> 读内存、抓画面、发按键都已经跑通；"两份数据是不是同一帧"也不再是空口……剩下的工作是把这条能力接进正式采集与标签预注册。

而 v3.7.3 的 [P0 出口判定](../Update/Alpha/v3.7.3/reports/P0-exit-round15.md) 在 2026-11-01 写的是：

> 规则 1：显示相位 = unknown……`real_pixel_gate_passed` 恒为 false，直到出现独立呈现栅栏证据。
> 若要解除本冻结：需要能给出呈现栅栏的独立证据……二者都会变更"同一游戏版本/同一输入后端"的前提，**届时 P0 需重跑，不能沿用本轮结论**。

v3.7.4 已经把证据交出来了（240/240 帧 13 项检查、GDI 与后台缓冲逐字节相同），但那一轮**只验证机制**：attract demo、不发按键、不测边界/动力学、不比对 `read_state`。也就是说，`P0-exit` 说的"重跑"其实**从来没做过**。

所以本轮的任务不是"再做一次 fence"，而是：**把 P0 冻结的三条具体欠账，在变体镜像上逐条重测一遍**。三条欠账是：

1. 截图与状态精确同帧（unknown）
2. 每类 20 次独立动力学重复（failed：只有 9–36 个转移）
3. 四边界（partial：每边界只有 1 次饱和）

## 2. 先写预注册，再动真机

`preregistration/p0-fence-round26.md` 在跑之前写死：判据 G1–G11、样本量（240 帧 + 60 张 + 80 次试验 + 4 次推边 + 30 次反向/切轴）、失败语义、以及"看结果后不得放宽阈值"。

两个执行前就发现的协议缺陷，也在看数据之前改掉并留在文档里：

- **单会话 25 秒的 practice 太危险**：stage 1 Lunatic 对一个近乎静止的自机，死亡是常态。改为"demo（时钟/像素/旧读法）+ practice（输入/动力学/边界）"两会话，并说明理由（死亡风险，不是结果驱动）。
- **G9 不能在墙边测**：推到底再反向，位置被 clamp，旧方向多走的 4 px 根本看不见。改为"离开墙 ≥40 px 的反向试验 + 切轴试验"。

这两个修改都不涉及判据数值，属于"测量设计"而不是"降低门槛"。

## 3. 工具：让"打字"发生在 hold 里

`FenceFrameSampler` 原本只做"读"，本轮给它加了一个可选 `on_hold` 钩子：在游戏已经 present 完、正停在栅栏里时执行回调。于是"按键"就锚定在**确定的第 T 帧**上，而不是"某两次 present 之间"。

配套写了两样东西：

- `tools/rl/p0_fence_round26.py`：两会话、六个测量段（M1 时钟 / M5 像素 / M6 旧读法 / M2-M3 试验 / M4 边界 / 反向切轴），带预注册判据的自动判定。
- `tools/rl/p0_fence_round26_derive.py`：只读地把报告要用的数字从原始 JSON/JSONL 里算出来（`derived.json`），避免手抄。

我先用 15 帧 / 3 张样张 / 2 次试验的小样验证管线（不落盘到证据目录），发现两个真问题：

1. **菜单不吃 PostMessage**：practice 会话的标题菜单光标不动（`could not move start menu cursor to item 3`）。历史上的菜单宏都走 SendInput + 前台焦点，所以 practice 会话改用 `SendInput` 并在每步前确认/夺回前台。
2. **`player_state` 语义**：`state.py:98` 写明 alive=0 / spawning=1 / dying=2 / invulnerable=3。demo 里玩家长期是 3（无敌），刚进 practice 是 1（出生），所以"一进游戏就 assert 活着"是错的，要等 0。

## 4. 真机第一次（attempt-1）：被现实打回来

正式跑第一次：demo 段完美（240 帧、59.99 Hz、60/60 样张），practice 段在 C1 20/20、C2 16/16 之后——

```
ProbeAborted: player_state=2 at frame 651
```

第 8 次被打中后生命耗尽，`game left the playing state after a hit`。当时协议是"一次被打中就整场中止"，于是已完成的部分保留、剩下的全部没测。

这一步暴露的不是代码问题，而是**协议问题**：一个与度量无关的打断（子弹打中玩家）把 114 项测量里的 94 项都作废了。科学的做法不是"重跑到没被打中为止"（那会变成挑选数据），而是：**打断只作废当次试验，逐条计数，然后重做**。我把这条写进预注册，判据一字未改。

同时统计出：stage 1 Lunatic 对几乎静止的自机，约 6 秒一次命中；8 条命大约 10 秒游戏时间就用完。

## 5. 第二次（attempt-2）：一个 19 分钟的空转

改成"多局续跑"后第二次跑，20 分钟没有进展。用另一个进程直接读游戏状态：

```
supervisor 6 playing False frame 0 player 1 deaths 9 lives 0
ticket 69732 logic 0 holdPhase 0 holdCount 0 skips 0
```

- `deaths=9`、`lives=0`：这一局早已结束；
- `holdCount=0`：**栅栏 hold 一次都没发生过**；
- `ticket=69732` 而 `logic=0`：游戏在结算/标题画面以 60 Hz 空转。

原因是我重构 `run_practice_session` 时，把 `_arm_holds()`（"先 ack 一帧，再让游戏每帧 hold"）留在了旧函数里，新的 `_start_practice_game` 没有调用。于是每一次 `step()` 都在等一个永远不会出现的 `hold_phase==1`，每次等 3 秒；`_settle` 12 次就是 36 秒一次试验。

修法有两层：

1. 在进入游戏、等自机 alive、确认可控之后 **arm holds**，并把 clock 的 ticket 游标归零；
2. 加两道"空转保险"：连续 3 次试验没有产出就中止该局；单局 240 秒预算。

这条教训值得单独记：**"等待一个条件"的循环，如果条件永不满足，代码不会报错，只会变慢。** 只有"读外部真值"（ticket/logic/holdCount）才看得出它其实什么都没做。

## 8. 最重要的一个"新"结论：1 + 1 = 2

旧报告只能写"发送→生效通常滞后 1 逻辑帧"，因为它把"掩码变化"当成了"生效"。栅栏把两件事分开了：

```
帧 F   （hold 内打字）掩码=旧，位移=旧
帧 F+1            掩码=新（lag_in=1），位移=旧
帧 F+2            掩码=新，位移=新（lag_mv=2）
```

所以"发送 → 位移"是 **2 个整数帧**，不是区间；松开按键同样在第 2 帧停止（80/80）。而反向时"旧方向恰好多走 1 帧 4 px"这件事，也就有了机制解释：掩码→位移本身要 1 帧。

这不是"把 ±1 帧误差膨胀一下"，而是把区间改成了两个可验证的整数。

## 11. 顺手把"每张烧 250 ms"变成 3 µs

正式轮的 M5 有个刺眼的数字：60 张样张，`holdBudgetSkips = 60`，`wait` 中位 235 ms。诊断起来不复杂：

- 采样器 ack 掉第 T 帧后，工具去写 PNG（约 13–23 ms）；
- 这期间游戏已经 present 了 T+1 并进入 hold；
- 采样器回来时读到的 `start_ticket` 是 T+1，而它的逻辑是"**等一张与 start 不同的** ticket"，于是它等 T+2；
- 游戏在 T+1 的 hold 里空转，直到 250 ms 预算到期。

修法是加一个开关：`accept_current=True`，意思是"如果现在正 hold 着、而且这张我还没消费过，就直接用它"。默认关闭，旧行为一字不改（有单测锁住：默认模式在 hold 住但不变化的假 fence 上必须返回 None；`accept_current` 模式必须立刻返回且 ack；已消费过的 ticket 不能被复用）。

然后做 A/B 实测（`tools/rl/fence_sampler_throughput.py`，同一 demo、同一镜像、两种模式各 60 张，**都带真实的逐样张 PNG 落盘**）：

| | 等新 ticket（默认） | accept_current |
|---|---:|---:|
| 吞吐 | 3.8 张/s | **45.2 张/s（11.9×）** |
| `wait` 中位 | 232.9 ms | **3.1 µs** |
| 预算耗尽 | 59 | **0** |
| 13 项检查 | 780/780 | **780/780** |

第一次不带 I/O 的 A/B 两边都是 7.7 ms、0 预算耗尽——**这本身就是个教训**：如果"测量环境"里没有那个真正拖慢的东西（PNG 编码），A/B 会得出"没有差别"的错误结论。所以第二轮把落盘加回去，才复现出正式轮的 235 ms。
