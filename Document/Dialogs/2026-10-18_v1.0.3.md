### 结构性诊断（算出来的，不是猜的）

playfield 模型输入 (224,192)，主干 4 次 stride-2 → 特征图 14×12 → 池化 2×2，每格覆盖 **192×224 原生 px**。
只知道「落在哪个象限」时的误差下限约 48 px(x)/56 px(y)，该指标下约 52 px；实测 70.97 px **比只认象限还差**，
说明主干连象限都没稳定区分开。目标 10 px 在该结构上不可能达到。

## E-02 · 指标与数据口径的三处实测偏差

### 偏差一：弹量指标取错通道（影响一份已发布结论）

`touhou_rl/vision_train.py:158` 写的是 `predicted[:,13] * 700.0`。按 `touhou_rl/obs.py:136-157`：
索引 13 是 `float(state.stage_clear_flag != 0)`，索引 14 才是 `min(1, active_count/700)`。

全量 567 个分片实测：`self_feat[13]` 的最小值 = 最大值 = **1.0**（死通道）；`self_feat[14]*700`
最小 1.0、最大 700.0、均值 240.8、中位数 181.0。

结论：v1.0.2 报告的「S1 子弹数误差 15.1 颗」实际在量 `700 × |预测值 − 1.0|`，是伪指标。

### 偏差二：danger 相关口径可被平凡模型刷掉

验证集 7,247 帧实测（目标 `log1p(danger/8)`，128 格展平后 Pearson）：

| 预测器 | 全局 corr |
| --- | ---: |
| 只给「每帧真实总弹量」一个标量（oracle） | 0.557 |
| 该标量 × 固定空间先验 | 0.669 |
| 当前模型（`val_danger_corr`） | 0.475 |

同一平凡预测器的 per-frame corr：均值 0.351、中位数 0.298，达标(>0.8)率 **0%**；busy-cell 准确率 0.822
（模型是 0.7006，**低于平凡基线**）。结论：`corr>0.8` 不能作为「会不会定位」的唯一判据。

### 偏差三：R3 需要的数据在仓库里不存在

`datasets/` 下只有 `pilot-ud0059` 一份视觉数据（其余 `lunatic-bt`/`dagger-*` 无像素）。补到 10 份 ≈ 6 小时
采集 + 195 GB，与需求文档 §9「Stage 3：1–2 天、纯 GPU、不占游戏」直接矛盾。

### 另附一处采集侧记账错误（与 R4 估算无关）

`touhou_rl/vision_capture.py:89` 的 `first_game_frame` 声明后**从未赋值**，因此当前代码永远不会写
`game_frames_span`；磁盘上 `pilot-ud0059/capture-report.json` 的 `game_frames_span=35958` 是旧版 `last-first`
的产物。按分片 `meta` 逐段求和，六个面跨度 16,732/19,009/22,393/26,908/30,943/35,958，**真值 151,943**。
`gameplay_frame` 每面重置，旧公式只取到最后一面。R4 的 730 GB 用的是「回放总帧数 ÷ 2」，不受影响。

## E-04 · 设计定稿（Stage 2）

### 架构 v2

三流独立编码器：playfield 主干 stride 8（特征图 28×24）+ heatmap 头 + danger 头 + 全局出口；
hud_score / hud_status 各自独立小编码器；融合后 256 维进 self 头（22 维）与候选评分头（18 候选）。

**参数量按契约搭原型实测**（不是估算）：

| 部分 | 参数量 |
| --- | ---: |
| playfield 卷积主干 | 159,360 |
| heatmap 头 + danger 头 | 97 + 97 |
| playfield 全局出口（pool(2,2)+Linear 384→128） | 49,280 |
| hud_score（主干 19,728 + 出口 49,216） | 68,944 |
| hud_status（主干 19,728 + 出口 98,368） | 118,096 |
| fusion trunk | 65,792 |
| self_head（256→256→22） | 71,446 |
| candidate + score_head | 21,761 |
| **合计（depth=1 / depth=3）** | **554,873 / 564,473** |

对照 v1 = 707,129：保留空间分辨率反而更小。原型同时验证了张量形状：
heatmap `[B,28,24]`、danger `[B,128]`、self `[B,22]`、score `[B,18]`。

### 三个可行性地板（实测，用于确认 10 px 目标不是结构性不可达）

| 项 | 数值 |
| --- | ---: |
| 网格量化（one-hot argmax） | 4.00 px（每格 16 原生 px） |
| 解码范围限制（soft-argmax 输出被限制在 `[0.5/W, 1-0.5/W]`） | 0.557 px（3.99% 帧 `rel_x` 越界，最远 -0.062） |
| 合计 | ≈ 4.6 px，相对 10 px 留约 2 倍余量 |

另记录：`rel_y` 在 0.929 处饱和（自机移动区下边界）；「永远预测验证集中位数」的平凡基线是 82.65 px。

### 契约与分工

6 个 SubStage：A 批（S3-1 架构、S3-2 指标与切分、S3-4 部署与隔离性）并行 → B 批（S3-3 训练改造、
S3-5 实验与判定工具）→ C 批（S3-6 实验执行与证据）。跨 SubStage 契约 C1–C6 全部写进相关两份任务书。

| 项目 | 数值 |

## E-12 · 2026-10-18 · 提高 GPU 利用率（数据管线优化）

### 用户提问

「CPU 占用为什么这么高？」以及「提高一下 GPU 利用率，现在明显偏低」。

### 三处根因（全部实测）

**1. torch 线程池空转（最大且纯属浪费）**

| `torch_threads` | 实际耗时 | 进程 CPU | 平均占用 |
| ---: | ---: | ---: | ---: |
| 14（原默认，20 逻辑核） | 35.5 s | 258.7 s | **7.29 核** |
| 4 | 31.3 s | 99.8 s | 3.19 核 |
| 1 | 32.9 s | 57.9 s | **1.76 核** |

模型在 GPU 上跑，torch 的 CPU 并行池没有并行任务可做，只是自旋。**CPU 降 78%，耗时不变。**
修复：`--torch-threads`（默认 0 = 自动，CUDA 时设 1），写入 `summary.config.torch_threads`。

**2. PNG 解码占了一个 batch 的一半时间**

单 batch(96) 剖面：decode **148.5 ms**、`uint8→float32` **37.9 ms**、GPU 步 21 ms。

关键观察：**模型分辨率下的裸 uint8 是 233 KB/帧，而原 PNG 是 253 KB/帧** —— 存解码结果几乎不额外占磁盘。
新增 `build_decode_cache()` / `VisionDataset(use_decode_cache=True)`，把每个分片的每个区域解码后存成
`.decoded-<region>-<HxW>.npy`（mmap 读取，行切片即 memcpy）。真实数据集 1,698 个文件 / **16.85 GB** / 92 秒建完。

**3. `labels()` 因走缓存而退化（副作用，已修）**

走解码缓存后不再打开 npz，标签读取变成现读 30 MB 分片 → `labels` 从 0.2 ms 涨到 **35.4 ms**。
新增 `_load_labels()`：只读 npz 里的标签成员（~140 KB/分片）并单独缓存（566 分片共约 79 MB）。

顺带：`regions_to_batch` 的 `/255` 缩放改为**在设备上做**（uint8 过 PCIe 只要 2 ms，CPU 侧转 float32 要写 4 倍字节）。

### 结果（含 15 步预热）

| 阶段 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 解码 | 148.5 ms | **52.7 ms** |
| `labels` | 0.2 ms | **1.2 ms** |
| `to_batch` | 37.9 ms | **2.6 ms** |
| GPU 步 | 21.0 ms | 22.3 ms |
| **每 epoch（679 batch）** | **≈206 s** | **≈54 s（2.7×）** |
| GPU 占比 | 10–15% | **28%** |

剩余瓶颈是**磁盘带宽**：每样本 233 KB，实测 415 MB/s → 0.56 ms/样本，而 GPU 只需 0.23 ms/样本。
要再往上走只有两条路：减少每帧字节数（降分辨率/裁掉 HUD），或让页缓存热起来（数据集 17 GB < 32 GB 内存，理论上可行）。

新增测试：`tests/test_decode_cache.py`（6 条，含「缓存值与 PNG 解码逐像素一致」「陈旧缓存形状不符时回退」
「CPU 与 CUDA 的 `regions_to_batch` 一致」）。全量 176 passed。
