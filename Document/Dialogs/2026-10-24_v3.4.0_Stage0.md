# 2026-10-24 v3.4.0 Stage 0 执行日志

用户要求「阅读 v3.4.0，继续工作」。v3.4.0 目录下只有 `研究方案.md`，其 §5 明确写着「研究方案，不是执行授权；必须先通过 Stage 0 离线门」。因此本轮范围锁死为 **Stage 0（离线 V/Q 可学习性门）**：不启游戏、不采集、不训练策略、不做 Stage 1 真机对照。

## 先摸清数据，再定标签

读 `研究方案.md`、v3.3.0 验收/总结报告后，先把两套语料的真实形态查清，而不是照抄方案文字：

- `v2.0.0/rollouts`：244 个 trace、约 8 万行；早期 `r1*/r1b/r1c` 目录是旧 schema（没有 `raw_safety_snapshot`），8,326 行；
- `step2-teacher-demos`：16 局、19,229 决策，决策间隔 1–2 帧（密集），但 **23%（4,399 行）`complete=false`**（三次抓帧时间戳不一致）；
- `frame stalled` 不是“卡住”，是 `env.py` 对 game-over/continue 屏的判据（`advanced == 0`），所以 trace 的 terminated 就是“这局死了”；
- 每行弹幕量很小（教师 80 / 学生 54 颗均值），远低于 `entity_obs` 的 320 上限，标签与特征用的是同一批弹，不存在截断泄漏。

由此确定标签契约：18 个候选 × H∈{10,20,40} 帧，自机按候选方向每帧一步（与 `options.STEPS` 同常量）、弹幕直线、**逐帧线段距离**（不点采样，避免高速弹穿模），上限 60 px；若 `remaining < H`（这局在 H 帧内已 game over），强制所有候选 unsafe——“人已经死了，不存在安全候选”。V 用 `remaining = episode_end_frame − frame` 回归，另加 `survive_60/240` 两个分类头。

## 实现（`touhou_rl/stage0_offline.py`）

- `candidate_clearance` / `label_snapshot`：与 `chunk_safety.predict` 同口径，单测在 frameskip=2 时逐元素对齐它的 2/6/10 帧结果；
- `build_cache`：只读复用 `entity_obs.build`（`v313-entity-obs/1`），存 `bullets[320,9]/meta5/grid3×16×16` + `clearance[N,3,18]` + teacher/executed/remaining/split；
- `ValueNet`（剩余帧回归 + 两个生存头）/`CandidateQNet`（18 候选 × 3 视界），MSE 训练，AdamW；
- `evaluate` 按预注册公式算门；`verdict` 里“拿不到指标”一律算失败，不给默认通过。

单测暴露并修掉三个真问题，都是“能跑但错”的类型：

1. **布局不一致会被静默广播**：`candidate_clearance` 返回 `(18,H)`，而 Q 输出 `(H,18)`，MSE 广播后损失仍然是一个数、不会报错。改为缓存里存 `(H,18)`，并在 `train_q` 里加 `predicted.shape != label.shape` 硬检查；
2. `_Batches.batch` 把“行号”又当“位置索引”索引了一次，训练第一个 batch 就 IndexError；
3. CLI 测试漏写 `--root`，被 argparse 拦住（属于测试写错，不是实现错）。

环境侧：`pytest` 的 `tmp_path` 在 `C:\Users\...\Temp\pytest-of-a5935` 上报 `PermissionError`（历史 ACL 问题），与仓库既有 `.pytest-*` 目录的惯例一致，统一改用 `--basetemp .pytest-v340-*` 并把 `cacheprovider` 关掉。

python -m touhou_rl.stage0_offline --train --cache .../cache.npz --out .../stage0 --device cuda --seed 11

构建 246 s：260 局、99,667 解析行、77,668 有效行（77.93%），46.8 MB。训练约 40 s：V 10 epoch（best 9）、Q 12 epoch（best 12，验证损失末轮仍在降）。

## 为什么 fail（事后诊断，不改判据）

- S0-0：77.93% 被三类拉低——旧 schema 8,326 行（语料代际）、玩家处于出生/死亡态 6,925 行（建模口径）、抓帧时间戳不一致 6,748 行（**采集缺陷，教师演示命中 23%**）。第三类是工程 bug，不是“状态不够”。
- S0-3：把“学到标签”和“与教师动作相同”混为一谈。诊断显示 **标签自身的 argmax 与教师一致率只有 48.3%（H=20）/52.1%（H=10）**，教师动作在标签下的平均排名 3.4、安全率 86.6%——教师是 chunked beam + 重规划的规划器，不是“按住一个方向 20 帧”的 argmax。也就是说，即使模型完美复现标签，H=20 也过不了 50%。第二层原因是模型 argmax 精度：H=40 时只复现了 22.9% 的标签 argmax（大量候选顶在 60 px 平台，MSE 不区分 top-1）。

同时必须记住的正结果：Q 的留出 R² 0.915/0.900/0.875，**同状态内**安全排序 AUC 0.852/0.858/0.866；几何标签对真实死亡的 AUC 0.9005。信息在状态里，缺的是正确的监督目标与数据质量。

还有一条自我打折：V 的 0.749 里，**只用“屏幕上有多少弹”这一个信号就有 0.681**（φ 只有 0.448）。所以 V 目前更像“局面推进度”，不能当剩余生存帧预测器用。
